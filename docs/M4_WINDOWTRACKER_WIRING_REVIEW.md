# M4 — ревью сшивки WindowTracker с координатором (overlay_manager.rs)

Статус: **независимое ревью, без изменений кода**. Ветка `feat/m2-edit-mode`, коммит
`88507e8` (координатор: `OverlayMessage::Windows`, `mask_needed`, запуск трекера с
мостом; overlay_manager.rs +68). Прочитаны дифф коммита целиком и актуальные файлы:
`crates/resticker/src/overlay_manager.rs` (3924 строки — включая текущее состояние
цикла с `device_needs_recovery`-ретраем из последующих коммитов),
`crates/rst-win32/src/window_tracker.rs` (модуль cc1c33b, 1200+ строк с тестами),
`docs/M4_WINDOW_TRACKER_DESIGN.md` §5-§6, `crates/rst-core/src/model.rs`
(`VisibilityMode`), `docs/M4_WINDOW_TRACKER_REVIEW.md` (предыдущее ревью модуля).
Проверены все 10 точек `continue` в главном цикле (не пропускают ли они пересчёт
гейта после мутации cfg — не пропускают). Живого запуска с хуками нет (в smoke-тесте
автора конфиг без не-Always стикеров — трекер честно не ставит хуки).

**Общий вердикт:** сшивка корректна и следует дизайну §6; живых багов не найдено.
Единственное осознанное отклонение от дизайн-дока — пересчёт `mask_needed` раз за
итерацию цикла вместо вызовов в точках мутации cfg (рекомендация §6, стр. 205-210) —
проверено и безопасно: пересчёт стоит после `match` и видит любую мутацию cfg той же
итерации, флип доставляется трекеру в ту же итерацию; все `continue`-ветки главного
цикла мутируют cfg **до** `continue` и потому пропуск пересчёта им безвреден (проверено
по всем десяти). Замечания — три низких: гейт сегодня фактически статичен (ни один
живой путь координатора не меняет `VisibilityMode` стикера — настройки приходят через
config.json без live-reload), O(n)-пересчёт на каждое сообщение (включая
высокочастотные MouseMove/Windows) тривиален при n≈25, но стоит пересмотреть при
тысячах стикеров; и debug-лог на каждый снимок ограничен дебаунсом 16 мс, но на
оживлённом десктопе даёт до ~60 строк/с в RUST_LOG=debug. Подробности — ниже.

## 1. Проверено по ключевым вопросам

### 1.1 Fast path (ADR-005) держится: хуки не ставятся до первого `set_mask_needed(true)`

- `WindowTracker::start()` **не** устанавливает хуки (window_tracker.rs:82-83: «Хуки на
  этом этапе НЕ ставятся — трекер «спит» до первого set_mask_needed(true)»); начальное
  состояние `mask_needed: false` (198). Координатор после старта трекера сразу шлёт
  `set_mask_needed(mask_needed(&cfg))` (117-120) — для конфига «всё Always» гейт
  остаётся `false`, хуки не ставятся никогда — заявленный fast path честно жив.
- Идемпотентность переходов (window_tracker.rs:632: повторный вызов с тем же значением
  — no-op) + FIFO-обработка сообщений окна трекера: быстрые флипы false→true→false
  сходятся к последнему значению, хуки не дублируются.

### 1.2 Пересчёт `mask_needed` раз за итерацию — корректно, включая все `continue`

- **Размещение:** пересчёт (1530-1536) стоит **после** `match` и **до**
  `if need_redraw && redraw_all` — любая мутация cfg текущего сообщения видна в той же
  итерации; флип доставляется трекеру до редрав-цикла. Задержка гейта = 0 итераций.
- **`continue`-ветки:** проверены все десять точек `continue` главного цикла
  (727 — внутри `primitives_to_sprites`, не цикл; 1060/1118/1466/1490 — гарды
  `let Some(ms) = ... else { continue }` **до** любой мутации; 1171 — пустой список
  `new_infos` до мутации; 1242/1298/1309/1322 — внутренние `for` ветки
  `MonitorsChanged`, не внешний `match`). Ни одна не мутирует cfg перед пропуском
  пересчёта — пропуск безвреден.
- **Стоимость:** O(n) на каждое сообщение (включая hover-MouseMove и `Windows`-события
  трекера — до ~60/с). При n≈25 — наносекунды; при тысячах стикеров — пересмотреть
  (тогда вернуться к рекомендации дизайн-дока о вызовах в точках мутации).
- **Начальное состояние:** `last_mask_needed = mask_needed(&cfg)` до цикла + стартовый
  `set_mask_needed`; первый пересчёт в цикле — сравнение с тем же значением, повторного
  постинга нет. Симметрия «инициализация + пер-итерация» замкнута.

### 1.3 Мост и канал — тот же паттерн, что у per-monitor форвардеров

- `thread::spawn(move || for ev in tracker_rx { if tx.send(Windows(ev)).is_err() { break; } })`
  (98-105) — копия паттерна форвардеров окон (не мониторно-привязанный вариант).
  FIFO общего канала гарантирует порядок «снимок не обгоняет обработанное событие»
  (дизайн §6, стр. 198-199) — для следующего среза с маской это уже готово.
- Провал `WindowTracker::start()` → `None` (108-111): мост не создаётся, гейт
  пропускает `set_mask_needed` — стикеры без слоёв работают как обычно; не фатально,
  как и заявлено.
- Шатдаун: мост — fire-and-forget (не join'ится), как и форвардеры; при выходе из
  `run()` `tx` дропается, `send` фейлится, поток завершается сам. `window_tracker`
  дропается в обратном порядке объявления локальных переменных: `Drop` шлёт `WM_CLOSE`
  и join'ит pump (выход по `WM_DESTROY` → `PostQuitMessage`) — долгих операций нет
  (дизайн §6, стр. 211-217). Порядок относительно `monitors_map` не критичен — хуки
  трекера не зависят от окон оверлеев.

### 1.4 Ветка `Windows(Changed)` — только лог, `need_redraw` не трогается

- Соответствует дизайну §6 («на этом срезе только принять снимок... и логировать»);
  снимок отбрасывается — хранение появится вместе с первым потребителем (вычисление
  маски, следующий срез), держать его сейчас было бы мёртвым состоянием — удаление
  `window_snapshot` из черновика корректно.
- Снимок содержит только «реальные» окна: собственные оверлеи отфильтрованы по
  `WS_EX_NOACTIVATE` (window_tracker.rs:312-317), message-only окно трекера — тоже вне
  кэша — оклюдерами не станут.

### 1.5 Взаимодействие с блокировкой сессии — самодостаточно

- Заморозка кэша на `WTS_SESSION_LOCK`/разморозка с полным rebuild на `UNLOCK` живёт
  внутри трекера (его собственное WTS-окно, window_tracker.rs:682-698) — координатору
  знать не нужно (дизайн §7: «трекер самодостаточен»). Уже покрыто интеграционным
  тестом `wts_lock_suppresses_emit_unlock_rebuilds`.

## 2. Найденные замечания (все низкой тяжести)

### 2.1 Гейт сегодня фактически статичен — live-пересчёта ждать не от чего

- `mask_needed` зависит только от `VisibilityMode` стикеров (model.rs:301-311:
  Always/Desktop/NeverOverlap/OverlapAllowlist; гелипер = `any(mode != Always)`, пустой
  список — `false`, ровно по дизайну §5, стр. 42). Но **ни один живой путь
  координатора не меняет режим видимости**: кнопка-глаз тулбара тогглит `visible`,
  настройки режимов приходят из окна настроек через config.json, а live-reload конфига
  в `run()` нет (`OverlayCommand` — только AddSticker/Shutdown). Пересчёт-на-каждой-
  итерации начнёт реально флипать гейт, когда появится round-trip настроек/панель
  выбора окон (дизайн §6 перечисляет «round-trip настроек, загрузка конфига» среди
  точек пересчёта).
- **Что это значит:** fast path в этой сборке определяется один раз на старте;
  машинерия пересчёта корректна и future-proof, но «live»-часть сейчас спящая. Не баг
  — стоит зафиксировать в дизайн-доке, чтобы не искать потом.

### 2.2 O(n)-пересчёт на каждое сообщение — приемлемо сейчас, не масштабируется

- Пересчёт выполняется на **каждую** итерацию цикла, включая высокочастотные
  hover-MouseMove и `Windows(Changed)` (до ~60/с на оживлённом десктопе). При n≈25
  стоимость наносекундная; при тысячах стикеров — стоит вернуться к рекомендации
  дизайн-дока (вызовы в точках мутации) или считать гейт инкрементально при
  добавлении/удалении стикера.

### 2.3 Debug-лог на каждый снимок окон

- `tracing::debug!(count = windows.len(), ...)` (1524) — при RUST_LOG=debug на
  оживлённом десктопе до ~60 строк/с (дебаунс 16 мс). Ограничено дебаунсом и debug-
  уровнем — приемлемо; при желании можно логировать только при изменении count.

## 3. Что проверено и корректно (не тратить время на повторную проверку)

- **Fast path** (§1.1): старт без хуков; начальный `set_mask_needed(mask_needed(&cfg))`;
  флипы идемпотентны и FIFO-консистентны.
- **Пересчёт гейта** (§1.2): размещение после `match` до редрав-цикла; все `continue`
  проверены — мутаций cfg перед ними нет; начальное состояние замкнуто.
- **Мост/канал** (§1.3): тот же паттерн форвардеров; провал старта — не фатален;
  шатдаун чистый (WM_CLOSE + join, без долгих операций; мост умирает с `tx`).
- **Семантика `Changed`** (§1.4): лог без side-эффектов, `need_redraw` не трогается —
  по дизайну; снимок отбрасывается осознанно.
- **`mask_needed`-предикат**: `any(mode != Always)`, пустой список — `false` — ровно
  формула дизайн-дока (стр. 42).
- **Самодостаточность заморозки сессии** (§1.5) — внутри трекера, покрыта тестом.

## 4. Приоритеты для координатора

1. **§2.1** — зафиксировать в `M4_WINDOW_TRACKER_DESIGN.md`, что гейт в текущей
   сборке определяется на старте (live-пересчёт проснётся вместе с round-trip
   настроек/панелью окон) — чтобы не искать «почему флип не срабатывает».
2. **§2.2/§2.3** — заметки на будущее (стоимость O(n)-пересчёта при масштабировании;
   спам debug-лога на оживлённом десктопе). Кода не требуют.
3. Отклонение от рекомендации §6 (пер-итерация вместо точек мутации) — задокументировать
   как осознанное (проще и нечего забыть), либо вернуться к точкам мутации при
   появлении live-reload конфига.

# M2 — дизайн-заметка: тулбар при мультивыделении

Статус: **проектировочная заметка, без изменений кода**. Дополняет
`docs/M2_WIRING_PLAN.md` (§4–§6), который описывает тулбар только для одиночного
выделения (`selection.len() == 1`). Здесь — поведение того же тулбара при
`selection.len() > 1`, через уже подключённую марку (`overlay_manager.rs`,
`Gesture::Marquee`, rubber-band). Если решения ниже будут приняты — оформить как
заметку к срезу и учесть в `M2_WIRING_PLAN` (§6, «Дельта» ниже).

Опирается на:
- `SPEC.md` 3.6: «При мультивыделении ползунок прозрачности и числовое поле **не
  отображаются**. Остальные кнопки применяются ко всему выделению.»
- `SelectionSet::bounds` (selection_set.rs:112) — union AABB выделения, уже
  используется для центра диалога удаления (overlay_manager.rs:723).
- Батч-пути, которые уже работают и задают образец undo: `Delete` через
  `begin_delete` (overlay_manager.rs:640) и `Ctrl+D` (overlay_manager.rs:733) —
  оба делают один `commit_undo_snapshot` на всю операцию.

---

## 1. Решение одним абзацем

Тулбар показывается при `active && selection.len() >= 1` (вместо `== 1`).
При `len() == 1` — текущий состав (ползунок + поле + 5 кнопок). При `len() > 1`
— **только 5 кнопок**: ползунок и числовое поле скрыты (SPEC 3.6), остальные
кнопки применяются ко всему выделению, каждая операция = **один шаг undo**.
Якорь позиционирования — `selection.bounds(&cfg.stickers)` (тот же union AABB,
что уже даёт центр модала удаления). Пока марка тянется
(`edit.marquee.is_some()`) тулбар не показывается — после `MouseUp`
пересобирается по финальному выделению.

## 2. Состав тулбара: одиночное против мульти

| Виджет | Одиночное (SPEC 3.6) | Мультивыделение | Решение и обоснование |
|---|---|---|---|
| `TB_SLIDER` + `TB_FIELD` | показаны | **скрыты** | SPEC 3.6 решает жёстко. Ни «применить ко всем», ни «смешанное состояние» не делаем — см. §3.1. |
| `TB_EYE` | тоггл видимости одного | общий тоггл **«показать все / скрыть все»** | детерминированный результат, однозначная иконка; смешанную группу лечит за один клик — §3.2. |
| `TB_ORDER_UP` / `TB_ORDER_DOWN` | `step_up` / `step_down` одного | сдвиг **всего блока выделения** как единого по z-order | по-элементный `step_up` на соседних выбранных вырождается в обмен между собой (артефакт) — §3.3. |
| `TB_DUPLICATE` | дублировать один, выбрать копию | **дублировать всех**, выбрать все копии | переиспользуем батч-путь `Ctrl+D`, извлекаем общий helper — §3.4. |
| `TB_DELETE` | `begin_delete(count=1)` | `begin_delete(count=N)` | **уже работает** через `confirm_dialog` + `selection.len()` — §3.5. |

Порядок кнопок слева направо не меняется (глаз, выше, ниже, дублировать,
удалить — `toolbar.rs` `TB_*` константы); в мульти-режиме просто отсутствует
слайдер/поле слева.

## 3. Разбор по виджетам

### 3.1 Ползунок прозрачности и числовое поле — скрыты

SPEC 3.6 исключает их при мультивыделении. Рассмотрены и **отвергнуты** два
«умных» варианта, чтобы зафиксировать мотив для будущих изменений:

- **«Применять ко всем сразу».** Неоднозначно начальное значение ползунка на
  смешанной группе (у стикеров разные opacity) — пришлось бы вводить эталон,
  что уводит от модели «слайдер показывает значение выделенного». SPEC уже
  выбрал проще.
- **«Смешанное состояние»** (indeterminate-ползунок, пустое поле). Требует
  три-стейт виджетов в `rst-render` (сейчас `Slider`/`NumericField` держат одно
  значение) — отдельная задача на виджеты, а не на тулбар. Откладывается
  осознанно.

Следствие для клавиатуры: числового поля в мульти-режиме нет, поэтому ветка
«поле в фокусе» из `M2_WIRING_PLAN` §10.3 и `Ctrl+V` в поле (§9А) живут только
в одиночном режиме. В мульти тулбар не имеет фокус-виджетов.

### 3.2 Глаз: общий тоггл «показать все / скрыть все»

Дословное «применяется ко всему выделению» для глаза — это «инвертировать
каждого» (`ops::toggle_visibility` в цикле). Отвергаем: на смешанной группе
(часть видима, часть скрыта) результат остаётся смешанным (скрытых показали,
видимых скрыли), и **иконка становится произвольной** — `Icon::Eye`/`EyeOff`
не могут отобразить смесь.

Принятая семантика — сходимость к однородному состоянию:

- `target = !(все выбранные видимы)`.
- Если все выбранные видимы → скрыть всех.
- Если есть хоть один скрытый → показать всех (группа «лечится» за один клик).

Иконка детерминирована: `Eye` когда все видимы (следующий клик скроет всех),
`EyeOff` когда есть скрытый (следующий клик покажет всех). Для одиночного
выделения эта семантика совпадает с существующим тогглом (все видимы → скрыть,
стикер скрыт → показать).

Реализация: новая чистая функция в `rst_core::ops`
(`set_visible_many(config, &ids, visible)` или per-id сеттер в цикле — на
усмотрение реализации), снимок: **один** `commit_undo_snapshot` до применения.
Показ/скрытие рамок выделения и «шахматки» скрытых — существующая логика
`redraw`, не меняется.

Замечание: марка (`rubber_band`, selection_set.rs:104) не фильтрует `visible`,
поэтому скрытые стикеры могут попасть в мультивыделение; «показать всех» —
единственный путь их вернуть одной кнопкой.

### 3.3 Порядок: блок выделения как единое целое

По-элементный прогон `ops::step_up`/`step_down` по id (дословное «применяется к
каждому») **некорректен**: для двух соседних выбранных стикеров `step_up` обоих
обменивает их **между собой** — визуально ничего не меняется; для несоседних
результат зависит от порядка обработки. Артефакт, а не операция.

Принятая семантика — выделение как жёсткий блок:

- «Выше»: весь блок от `min(order выбранных)` до `max(order выбранных)` сдвигается
  на одну позицию вверх по z-order; внутренний порядок и состав блока не
  меняются; элемент, стоявший сразу над блоком, переезжает под него. No-op, если
  верхний выбранный уже на самом верху.
- «Ниже» — зеркально: блок вниз на одну позицию; no-op, если нижний выбранный
  уже внизу.
- Блок может быть и несвязным (между выбранными есть невыбранные) — двигается
  весь диапазон `[min..max]`, что остаётся детерминированным.

Для одиночного выделения эта операция **вырождается ровно в существующие**
`step_up`/`step_down` (обмен с соседом), так что единая семантика не конфликтует
с текущим поведением. Реализация: `ops::step_up_many`/`step_down_many` через
`normalize_orders` + сдвиг границы блока в списке, отсортированном по `order`;
снимок — **один** `commit_undo_snapshot`.

### 3.4 Дублировать: всех + выделить копии

Батч-путь уже существует — `Ctrl+D` (overlay_manager.rs:733): один снимок,
`ops::duplicate` в цикле по выделенным, `resync_sprites`, снять выделение,
выделить **все** новые копии, save. `TB_DUPLICATE` в мульти делает ровно это.

Действие для координатора: извлечь `duplicate_selection(...)` из ветки `Ctrl+D`
и звать его и из `Ctrl+D`, и из `TB_DUPLICATE` (одиночного и мульти) — кнопка
тулбара и хоткей не должны расходиться. Копии кладутся на верх (`max+1`), каждая
следующая выше предыдущей; после операции выделены все копии — тулбар
пересобирается в мульти-режиме.

### 3.5 Удалить: уже работает, менять не нужно

`TB_DELETE` и `VK_DELETE` идут через общий `begin_delete`
(overlay_manager.rs:640): `count = edit.selection.len()` попадает в
`confirm_dialog::message_for(count)` (confirm_dialog.rs:53 — «Delete N
stickers?»), центр модала — центр `selection.bounds()` (overlay_manager.rs:723).
Снимок — один на всю пачку (`ConfirmState.snapshot`). Правок не требуется;
единственное — в мульти подтверждение срабатывает так же, как на батч `Delete`.

## 4. Позиционирование

Якорь — `selection.bounds(&cfg.stickers)` (selection_set.rs:112), union AABB в
DIP. Для одиночного выделения это тот же ось-выровненный прямоугольник, что
сейчас строит `selection_aabb` (toolbar.rs:47) по `SelectionBox` — поэтому
**унифицировать** билдер: он принимает `DipRect` (границы выделения) и режим
(`opacity: Option<f64>`: `Some` — одиночный со слайдером, `None` — мульти без
слайдера/поля), а не `SelectionBox`. Центра отпадает двойная геометрия.

- **Вертикаль**: то же правило, что сейчас (toolbar.rs:64) — под рамкой, при
  нехватке места снизу — над ней; «прижатие к ближайшему свободному краю»
  (SPEC 3.6) остаётся заделом, как и для одиночного.
- **Горизонталь**: центр под центром union-рамки.
- **Ширина**: без слайдера/поля панель уже; `TOOLBAR_WIDTH` становится функцией
  режима (или отдельная константа мульти) — центрирование считается по фактической
  ширине.
- **`bounds()` → `None`** (пустое выделение / все вырожденные стикеры) — тулбар
  не показывать.
- **Скрытие во время марки**: `rubber_band` обновляет выделение на каждом
  `MouseMove` (overlay_manager.rs:1163) — пересборка тулбара на каждый Move
  сбрасывала бы hover и дёргалась. Поэтому: тулбар видим только когда
  `edit.marquee.is_none()`; после `MouseUp` марки — пересобрать по финальному
  выделению. Это соответствует «тулбар едет за выделением», но не за живой
  рамкой.
- **Драг**: в мульти жеста `Drag` пока нет (`resolve_zone` даёт ручки/поворот
  только для одиночного, overlay_manager.rs:841) — тулбар не переводится. На
  будущий мульти-драг — тот же `Panel::translate` по дельте, как в
  `M2_WIRING_PLAN` §4.

Моменты пересборки (расширение таблицы `M2_WIRING_PLAN` §4): смена числа
выделенных — клик (сворачивает к одиночному), `Ctrl+A`, отпускание марки,
`Ctrl+D`/`TB_DUPLICATE`, undo/redo (после `selection.prune`), удаление.
Модал подтверждения рисуется поверх тулбара и блокирует его ввод (приоритет
`pointer_owner`: confirm > тулбар — без изменений).

## 5. Undo / redo

Инвариант: **одна батч-операция = один `commit_undo_snapshot`** — `Ctrl+Z`
снимает её целиком, а не по одному стикеру. Уже соблюдается для `Delete`
(`begin_delete`, overlay_manager.rs:658) и `Ctrl+D` (overlay_manager.rs:737);
распространяется на новые кнопки мульти:

| Операция | Снимков | Примечание |
|---|---|---|
| Марка / `Ctrl+A` (смена выделения) | 0 | меняют только `SelectionSet` — эфемерное состояние редактора, не `Config`; в undo не попадают (текущее поведение, правки не нужны) |
| Глаз (показать/скрыть всех) | 1 | новый; до применения |
| Порядок (блок вверх/вниз) | 1 | новый; до применения |
| Дублировать (всех) | 1 | уже так (общий с `Ctrl+D`) |
| Удалить (всех) | 1 | уже так (`confirm.snapshot`) |

После undo/redo и удаления — существующий `edit.selection.prune` (выделение
не ссылается на мёртвые id) и пересборка тулбара: если из пачки остался один
стикер — тулбар честно возвращается в одиночный режим, если ноль — скрывается.

1. `rst_core::ops`: `set_visible_many`, `step_up_many`/`step_down_many` + тесты.
2. `toolbar.rs`: сигнатура на `DipRect` + режим мульти (без слайдера/поля),

   удаление — существующий `begin_delete`).
4. Извлечь `duplicate_selection` и связать `Ctrl+D` с `TB_DUPLICATE`.
5. Прогон: build/clippy/test + ручная проверка сценария «марка по нескольким →
   тулбар мульти → глаз/порядок/дубликат/удаление → по одному `Ctrl+Z`».

## 8. Открытые вопросы и известные границы (не этой задачи)

- **Клик по выделенному стикеру сворачивает мультивыделение к одному**
  (`selection.click(Some(id))`, overlay_manager.rs:972). Это существующее
  поведение до мульти-драга; тулбар при этом честно переходит в одиночный режим.
  Сознательно не меняем в рамках тулбара.
- **Скрытые стикеры**: `hit_sticker_at` фильтрует `visible` (overlay_manager.rs:825),
  т.е. клик по скрытому в мульти не работает, а марка — работает (рубber_band не
  фильтрует `visible`). Шахматка скрытых и интерактивность (SPEC 3.7) — остаются
  следующими срезами; для тулбара важен только факт, что скрытые могут быть в
  выделении (глаз их возвращает).
- **«Применить opacity ко всем»** — если когда-нибудь понадобится, это отдельная
  задача на три-стейт виджеты слайдера/поля (§3.1), не для M2.

# M2 — ревью среза 6: тулбар + панель у курсора (PointerOwner / rebuild / poll)

Статус: **независимое ревью, без изменений кода**. Коммиты `a32ff4f`
(«feat(bin): M2 integration (slice 6) — toolbar + cursor panel wiring»,
`crates/resticker/src/overlay_manager.rs`, +697/−48) и `0e14c7d`
(«fix(bin): toolbar now follows drag/resize/rotate live», тот же файл, +13/−1).
Прочитаны диффы обоих коммитов и весь актуальный `overlay_manager.rs` (2225 строк);
call-site'ы сверены с `toolbar.rs`/`cursor_panel.rs` (билдеры), `rst-render::widgets`
(`Panel` capture/focus/`key_event`, `Slider`/`NumericField`),
`docs/M2_WIRING_PLAN.md` §2–§6, `rst_core::ops`/`selection_set`. Интерактивного
прогона не было (static review: clippy/fmt/тесты зафиксированы в коммитах;
ручная QA — `docs/M2_MANUAL_QA_CHECKLIST.md`, секции 8/9/14).

**Общий вердикт:** маршрутизация `PointerOwner` (confirm > панель у курсора >
тулбар > сцена), отложенный снимок ползунка и привязка всех кнопок к
`begin_delete`/общим путям сделаны аккуратно; клик по дорожке без движения
действительно не тратит шаг истории. Проблемы — в основном **пограничные
состояния вокруг живого драга ползунка прозрачности** (самый важный класс):
отложенный `ui_pending_snapshot` переживает выход из режима и undo/redo и
коммитится потом, «ни с того ни с сего», на следующем `MouseUp` тулбара;
`CaptureLost` панели оставляет внутри `Panel` застрявший захват; клавиатура до
числового поля не доходит вообще (ветка `take_submitted` — мёртвый код);
глобальные хоткеи (`Ctrl+Z/A/D/V`, `Delete`) не блокируются, пока указатель
принадлежит панели (та же болезнь, что для сцены закрывает guard на жесты).
Плюс две косметические асимметрии панели у курсора и одно латентное место.

## 1. Проверено по явным вопросам задачи

### 1.1 `pointer_owner` / `ui_pending_snapshot` при `Esc` и `Ctrl+Z` во время драга ползунка

Сценарий: пользователь тянет ползунок прозрачности — `pointer_owner =
Toolbar` (overlay_manager.rs:1569), на первом реальном изменении
`ui_pending_snapshot = Some(cfg.clone())` (1505-1506), далее opacity пишется
живо в `cfg`+спрайт через `apply_opacity` (1498).

- **`Esc` (выход).** `handle_key` пропускает Esc (guard на жесты не срабатывает:
  `gesture == None`, overlay_manager.rs:860), зовёт `toggle_edit_mode`
  (overlay_manager.rs:627). Тот сбрасывает **сценный** `pending_snapshot`
  (650), `marquee`, `confirm`, `selection`, но **не** `ui_pending_snapshot` и
  **не** `pointer_owner`. При выходе он **сохраняет `cfg`** (660) — то есть
  полуприменённая opacity уходит на диск, а отложенный снимок «до драга»
  остаётся висеть в `edit`. После повторного входа первый же `MouseUp` по
  тулбару (`handle_toolbar_up`, 1299-1306) сравнит висящий `before` с текущим
  `cfg` и **задним числом закоммитит** его как undo-шаг — вместе с настоящим
  действием этого клика (см. §2.1). Асимметрия с жестами сцены: `Esc` во время
  drag/resize/rotate откатывает жест к старту (639-648), во время драга
  ползунка — «коммитит» (сохраняет), ничего не сбрасывая.
- **`Ctrl+Z` во время драга.** `handle_key` `VK_Z` (894-896) идёт без каких-либо
  проверок на `pointer_owner`: `perform_undo` (748) целиком заменяет `cfg`
  снимком из истории прямо под живым драгом, `rebuild_toolbar` (895) пересоздаёт
  панель (новый ползунок, `dragging=false`), а `ui_pending_snapshot` снова не
  тронут. Итог: следующий `MouseMove`/`MouseUp` продолжает маршрутизироваться
  как `Toolbar` (pointer_owner жив), а на `MouseUp` висящий снимок «до драга»
  коммитится относительно уже откаченного `cfg` — фантомный шаг истории.

Вывод: **`ui_pending_snapshot` и `pointer_owner` не сбрасываются ни на выходе
из режима, ни на undo/redo** — это не закрытые пограничные случаи, а устойчивый
утечка состояния (подробнее §2.1, §2.4).

### 1.2 `TB_FIELD.take_submitted()` параллельно с `TB_SLIDER`-драгом в один `MouseUp`

В `handle_toolbar_up` порядок: `panel.pointer_event(Up)` (1290-1291) → коммит
`ui_pending_snapshot` (1299-1306) → `take_submitted` (1310-1314) → кнопки. Если
бы оба события могли прийти в один `Up`, каждый бы коммитил свой снимок:
сперва «до драга ползунка», затем `cfg.clone()` «после драга + значение поля» —
два undo-шага за один `Up` и две записи на диск. Не паника, но шаги выглядят
«склеенными»: первый `Ctrl+Z` откатит и поле, и ползунок разом.

Однако практически ветка **недостижима**: у `NumericField` `submitted`
выставляется только из `key_event(Key::Enter)` (widgets.rs:864-866), а в
`overlay_manager` клавиши к панели **никогда не маршрутизируются** —
`Panel::key_event` (widgets.rs:1096) в bin-крейте не вызывается нигде
(grep: `key_event`/`Key::` в `crates/resticker/src` — ноль совпадений; `handle_key`
сопоставляет только глобальные комбо и всё прочее глотает `_ => false`). То есть
поле нельзя ни сфокусировать-ввести, ни отправить Enter, и вся ветка
1310-1330 — мёртвый код (см. §2.3). Опасность «двух коммитов в один `Up`»
сегодня не актуальна, но при починке §2.3 порядок (коммит `ui_pending_snapshot`
до обработки поля) станет источником лишнего шага — стоит свести к одному
снимку.

### 1.3 Устаревший `toolbar`/`cursor_panel` после undo/redo

Все три хоткея истории (`Ctrl+Z`/`Ctrl+Shift+Z`/`Ctrl+Y`) вызывают
`perform_undo`/`perform_redo` + `rebuild_toolbar` (890, 895, 900) — тулбар
после undo/redo не бывает устаревшим: панель либо пересобрана под нового
единственного выделенного, либо `None`. Модальное удаление (1775), быстрый
`Delete` (833), `Ctrl+A` (905), `Ctrl+D` (940), клики/Shift+клик (1597, 1604),
отпускание марки (1848), драг сцены (1698) — тоже все проходят через
`rebuild_toolbar`. Тулбар-часть вопроса закрыта.

**Панель у курсора — нет.** `rebuild_cursor_panel` вызывается только из
`toggle_edit_mode` (666), хоткея `ToggleAllStickers` (559), `BTN_LOAD_FILE`
(1445) и `BTN_TOGGLE_ALL` (1457). Undo/redo, удаления, `Ctrl+A`/`Ctrl+D` её не
пересобирают. Иконка «Показать/скрыть все» строится по `all_visible =
cfg.stickers.iter().all(|s| s.visible)` (1222): `Ctrl+Z` после `BTN_TOGGLE_ALL`
(или кнопки «глаз» при одном стикере) возвращает скрытых — панель до следующего
hover-Move показывает **устаревшую** иконку «показать всех», хотя следующий клик
уже скроет всех. Самозалечивается на ближайшем `MouseMove` (пересборка в hover,
1699-1712), но в кадре после `Ctrl+Z` врёт. Фикс: добавить
`rebuild_cursor_panel` рядом с `rebuild_toolbar` в общих точках
(undo/redo/delete/Ctrl+A/Ctrl+D).

### 1.4 Мёртвый id в тулбаре (выделенный удалён «снаружи»)

Панель не хранит id — он выводится из `single_selected_id(&edit.selection)`
на каждый `Up`/`Move` (1293, 1490), поэтому «панель ссылается на несуществующий
id» в смысле хранения невозможна. Мёртвый id мог бы попасть в `selection` только
если где-то меняется `cfg.stickers` без `selection.prune`, но все пути удаления
и undo/redo prunят (761, 785, 1760, 825). Единственный реальный сценарий —
**глобальная операция во время активного удержания кнопки тулбара** (см. §2.4):
`Ctrl+Z`/`Ctrl+A`/`Delete`/`Ctrl+D` выполняются, пока `pointer_owner == Toolbar`,
и могут сменить/очистить выделение между `Down` и `Up` кнопки. Тогда
`handle_toolbar_up`: 1293 вернёт другой/пустой набор, а **висящий
`ui_pending_snapshot` от прерванного жеста всё равно закоммитится** (1299-1306)
относительно уже нового `cfg`. Паники нет, но истории портятся (см. §2.1, §2.4).

## 2. Найденные проблемы

### 2.1 Отложенный `ui_pending_snapshot` не сбрасывается на выходе из режима и undo/redo — утечка с фантомным коммитом

- **Где:** `toggle_edit_mode` (overlay_manager.rs:627-667), `perform_undo`
  (748-766), `perform_redo` (772-790), `handle_toolbar_up` (1293-1295).
- **Что:** `ui_pending_snapshot` выставляется в `poll_toolbar_opacity_live`
  (1505-1506) при первом реальном движении ползунка и забирается ровно в двух
  местах: `handle_toolbar_up` (1299, коммит/отброс) и `CaptureLost` (1878).
  Все остальные пути, которые могут прервать драг ползунка, его не чистят:
  `Esc`→`toggle_edit_mode`, `Ctrl+Z`/`Ctrl+Y`/`Ctrl+Shift+Z` (`perform_undo`/
  `perform_redo`), `Ctrl+A` (селект становится мульти → 1293 делает early-return
  **до** коммита, снимок остаётся висеть бессрочно).
- **Сценарий-минимум:** потянул ползунок (opacity изменилась, снимок положен) →
  `Esc` → режим закрылся, opacity сохранена (660) → вошёл обратно, кликнул
  «глаз» → `handle_toolbar_up` коммитит висящий снимок «до драга ползунка» как
  отдельный undo-шаг **вместе** с снимком глаза (1340). Один клик — два шага
  истории, первый из которых никак не связан с кликом. Либо: `Ctrl+Z` во время
  драга → снимок остаётся и коммитится на следующем `Up` относительно уже
  откаченного `cfg`.
- **Фикс:** сбросить `edit.ui_pending_snapshot = None` (и `pointer_owner =
  None`) в `toggle_edit_mode` рядом со сбросом сценного `pending_snapshot`
  (650), а в `perform_undo`/`perform_redo` — рядом со сбросом `pending_snapshot`
  (758, 779). Плюс не допускать `Ctrl+A`/историю во время драга панели — см.
  §2.4. Тогда снимок живёт ровно от первого `Move` ползунка до его `Up` и
  больше нигде.

### 2.2 `CaptureLost` панели не доставляет терминальное событие в панель — застревает `Panel.capture`/`Slider.dragging`

- **Где:** `handle_input`, `InputEvent::CaptureLost` (overlay_manager.rs:1868-1880).
- **Что:** ветка для `Toolbar`/`CursorPanel` сбрасывает `pointer_owner` и
  `ui_pending_snapshot` (1877-1878) и сразу `return true` — панели не
  отправляется ни `Up`, ни отмена. Внутри `Panel` при этом остаётся
  `capture = Some(slider)` (widgets.rs:1029-1030), а у ползунка
  `dragging = true` (widgets.rs:571). Пока панель не пересобрана (а она
  пересобирается только по смене выделения), `Panel::pointer_event(Move)`
  роутит каждый hover-Move в застрявший capture (widgets.rs:1057-1061) →
  `Slider::set_from_x` двигает ручку и ставит `changed`, ничего не зная о том,
  что жест давно отменён. Видимый эффект: после Alt+Tab во время драга ползунка
  ручка «едет» за курсором при наведениях, и `changed` может остаться взведённым
  до следующего честного `Up`.
- **Сценарий:** драг ползунка → Alt+Tab (`CaptureLost`) → вернулся, водишь мышью
  над тулбаром — ручка ползунка дёргается, хотя кнопка не нажата.
- **Фикс:** в ветке 1873-1879 перед сбросом `pointer_owner` отдать панели
  терминальное событие — например `panel.pointer_event(PointerEvent::Up { pos:
  edit.cursor_pos })` (аналог обычного `Up`, снимет `capture`/`dragging`), либо
  добавить в `Widget` явный `CaptureLost` и пробросить из `Panel`.

### 2.3 Числовое поле не получает клавиатуру: ветка `take_submitted` — мёртвый код

- **Где:** `handle_key` (overlay_manager.rs:839-944), `Panel::key_event`
  (widgets.rs:1096), `NumericField::submit` (widgets.rs:719-735).
- **Что:** `NumericField` получает ввод только через `key_event`
  (widgets.rs:842-872), а `Panel::key_event` в bin-крейте не вызывается вообще —
  `handle_key` обрабатывает лишь глобальные комбо (`Esc`, `Ctrl+Z/Y/A`, `Delete`,
  `Ctrl+D`, `Ctrl+V`) и всё остальное отбрасывает (`_ => false`, 942). Итог:
  цифры/Backspace/Enter в поле не приходят, `take_submitted()` всегда `None`,
  ветка 1310-1330 в `handle_toolbar_up` недостижима. Поле кликабельно (фокус +
  каретка рисуются), но любые клавиши на нём уходят в `_ => false`, а клик мимо
  просто отменяет (`on_blur` → `cancel`, widgets.rs:821-825). В `Ctrl+V` поле
  тоже не участвует: 939-940 уходит в `paste_from_clipboard`, а `Panel::paste`
  (widgets.rs:1112) не используется (это задел плана §9А «вставка в поле»).
- **Это расходится с коммитом** (`a32ff4f`: «numeric field commits its own
  snapshot on Enter») — на самом деле Enter до поля не доходит.
- **Фикс:** в `handle_key` (до `match vk`, после модальной ветки) пробросить
  клавишу в сфокусированный виджет, когда тулбар в фокусе:
  `if let Some(panel) = &mut edit.toolbar { let r = panel.key_event(Key::from_vk(vk));
  if r.consumed { return r.redraw; } }` (аналог `Panel::key_event`); `Ctrl+V` при
  фокусе поля — через `panel.paste(read_text())` (§9А). Отдельно свести двойной
  коммит в `handle_toolbar_up` при совместном `take_submitted` + висящем
  `ui_pending_snapshot` (§1.2).

### 2.4 `handle_key` не блокирует историю/глобальные операции, пока `pointer_owner` — панель

- **Где:** `handle_key`, guard (overlay_manager.rs:860); поля `pointer_owner`
  (233).
- **Что:** guard `if edit.gesture.is_some() && vk != VK_ESCAPE` закрывает только
  **жесты сцены**. Указатель, принадлежащий тулбару/панели (`pointer_owner ==
  Toolbar/CursorPanel`), не проверяется, поэтому пока пользователь держит кнопку
  тулбара или тянет ползунок, работают `Ctrl+Z`/`Ctrl+Shift+Z`/`Ctrl+Y`/`Ctrl+A`/
  `Delete`/`Ctrl+D`/`Ctrl+V` — каждый мутирует `cfg` из-под живого UI-взаимодействия
  (для сцены ровно это запрещено комментарием 851-858). Комбинация с §2.1 даёт
  фантомные undo-шаги; с §1.4 — кнопку тулбара, чей `Up` приходит уже к панели
  другого выделения.
- **Фикс:** расширить guard на UI-владельца указателя — например
  `if (edit.gesture.is_some() || matches!(edit.pointer_owner, PointerOwner::Toolbar
  | PointerOwner::CursorPanel)) && vk != VK_ESCAPE { return false; }` (Esc всё
  равно должен выходить — но тогда §2.1 обязательно с чистить снимок).

### 2.5 Панель у курсора не пересобирается после undo/redo и удалений — устаревшая иконка `all_visible`

- **Где:** `handle_key` undo/redo/`Ctrl+A`/`Ctrl+D` (889-940), `begin_delete`
  (833), модал (1775); `rebuild_cursor_panel` (1217-1223).
- **Что:** см. §1.3: после `Ctrl+Z`/`Ctrl+Y`/удаления, изменивших `visible`,
  иконка «Показать/скрыть все» (строится по `all_visible`, 1222) показывает
  действие для старого состояния до ближайшего hover-Move. Самозалечивание есть,
  но кадр после операции врёт; «глаз» тулбара при одиночном выделении даёт тот
  же класс (иконка `Eye` всегда, toolbar.rs — но для одиночного это осознанное
  упрощение билдера).
- **Фикс:** `rebuild_cursor_panel` в тех же точках, где уже стоит
  `rebuild_toolbar` (undo/redo/delete/Ctrl+A/Ctrl+D).

### 2.6 Панель у курсора замирает во время драга/ресайза/поворота сцены

- **Где:** `handle_input`, `PointerOwner::Scene if dragging`
  (overlay_manager.rs:1677-1698).
- **Что:** коммит `0e14c7d` починил live-следование **тулбара** за стикером
  (1698), но не панели у курсора: в этой ветке после `apply_gesture` +
  `rebuild_toolbar` идёт `return`, а пересборка панели происходит только в
  hover-ветке (1699-1712), куда при `dragging` управление не доходит.
  `edit.cursor_pos` обновляется (1662), но `edit.cursor_panel` остаётся на
  пред-драговой позиции, пока не отпущена кнопка. Видимый эффект: тащишь стикер
  через экран — панель у курсора «отстаёт» и висит на месте до `MouseUp`.
  (План §4 говорит про `translate` по hover-Move; во время драга сцены панель
  не двигалась и по плану — но тулбар теперь едет, а панель нет, асимметрия
  налицо.)
- **Фикс:** в ветке 1677-1698 добавить `rebuild_cursor_panel` (пересборка —
  выбранный срезом способ обновления панели) или `translate` по дельте.

### 2.7 (латентное) фантомный undo-шаг в кнопках тулбара при мёртвом id

- **Где:** `handle_toolbar_up`, `TB_EYE`/`TB_ORDER_UP`/`TB_ORDER_DOWN`/
  `TB_DUPLICATE` (overlay_manager.rs:1339-1375).
- **Что:** `commit_undo_snapshot(edit, cfg.clone())` идёт **до** проверки
  результата операции (`let _ = ops::toggle_visibility(...)`, 1341; `if let
  Ok(...)` у дубликата, 1366). Если `single_selected_id` (1293) вернёт id,
  отсутствующий в `cfg` (по текущим путям предотвращено `prune`, §1.4, но
  ничего в самом UI-пути этого не гарантирует), операция молча no-op, а пустой
  снимок уже в истории — та же болезнь, что в `M2_SLICE_REVIEW.md` п.1, только
  у тулбара. Сейчас недостижимо; фикс на будущее — коммитить после успеха
  (как уже сделано в `paste_from_clipboard`/`add_sticker`, 987-989, 1008-1019).

## 3. Что проверено и корректно (не тратить время на повторную проверку)

- **Маршрутизация `PointerOwner`**: на `MouseDown` приоритет confirm > панель у
  курсора > тулбар > сцена (1532-1563) совпадает с z-order отрисовки
  (redraw: тулбар 2127, панель 2139, модал сверху 2153); решение
  фиксируется на `Down` и живёт до `Up`/`CaptureLost`. `MouseUp` корректно
  сбрасывает `pointer_owner = None` перед опросом (1809, 1823).
- **Отложенный снимок ползунка в честном цикле**: `before` берётся до первого
  `apply_opacity` (1505-1506 → 1498), коммит — на `MouseUp` только если
  `before != *cfg` (1299-1301); клик по дорожке без движения снимка не создаёт
  и шаг истории не тратит. `CaptureLost` отбрасывает снимок (1878) — кроме
  застрявшего `capture` (§2.2).
- **Кнопки тулбара**: каждая — один `commit_undo_snapshot` + op + save;
  `TB_DELETE` идёт через общий `begin_delete` (1376-1388) — диалог не зависит от
  вызова; `TB_DUPLICATE` выбирает копию и пересобирает тулбар (1366-1373).
  Мульти-режим честно не подключён (билдер готов, действия — нет) — как и
  заявлено.
- **Хоткей/кнопка toggle-all**: общий `converge_all_stickers_visibility` (1237),
  пустой/однородный список — `false` без шага истории; панель пересобирается
  после (559, 1457).
- **`apply_opacity`** (1163) идёт через общий `apply_transform` (1133), зеркалит
  поле/ползунок (1323, 1501); opacity в диапазоне 0..100, без NaN.
- **`begin_delete`/модал/cleanup** (833, 1755-1765) — без регрессий относительно
  среза 5: снимок модала синхронизирован по settings, чистка Pasted идёт до
  `ops::delete`, клик мимо модала его не закрывает.

## 4. Приоритеты для координатора

1. **Отложенный снимок ползунка и история под живым UI-драгом (§2.1 + §2.4)** —
   самый заметный класс: `Esc`/`Ctrl+Z`/`Ctrl+A` во время драга ползунка дают
   фантомные undo-шаги и неожиданные коммиты на следующем `Up`. Сброс
   `ui_pending_snapshot`/`pointer_owner` в `toggle_edit_mode` и `perform_undo`/
   `perform_redo` + guard `handle_key` на `pointer_owner`.
2. **Клавиатура числового поля (§2.3)** — поле сейчас полностью инертно, а
   коммит-сообщение обещает работу по Enter; заодно ветка `take_submitted`
   (1310-1330) перестанет быть мёртвой, и стоит свести двойной коммит из §1.2.
3. **`CaptureLost` панели (§2.2)** — терминальное событие в панель, чтобы
   `Panel.capture`/`Slider.dragging` не застревали после Alt+Tab.
4. **Панель у курсора (§2.5, §2.6)** — пересборка после undo/redo/delete
   (устаревшая иконка) и live-следование во время драга сцены (асимметрия с
   тулбаром из `0e14c7d`).
5. **Латентное (§2.7)** — коммит undo в кнопках тулбара после проверки успеха,
   когда доберёмся до мульти-действий.

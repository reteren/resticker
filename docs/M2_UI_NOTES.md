# M2 — дизайн-заметка: тулбар стикера и панель у курсора

Статус: **проектировочная заметка** (не ADR, не спецификация). Фиксирует сравнение
вариантов реализации UI режима редактирования и обоснование выбора. Если решение
будет принято в этом виде — оформить как ADR (дополнение к ADR-002).

Затрагивает пункты ROADMAP M2:
- тулбар под стикером: ползунок прозрачности + числовое поле (SPEC 3.6);
- кнопки тулбара: глаз, порядок выше/ниже, дублировать, удалить (SPEC 3.6);
- панель у курсора: загрузить файл, показать/скрыть всё, настройки, выход (SPEC 3.8).

---

## 1. Контекст

В режиме редактирования (SPEC 3.1) оверлей-окно снимает `WS_EX_TRANSPARENT` и
`WS_EX_NOACTIVATE`, забирает фокус, рисует затемнение 50% **внутри себя** под
стикерами (ARCHITECTURE 5.2). То есть уже в M2 оверлей-окно активно принимает
ввод на всей площади монитора — это тот самый механизм, на котором должны
работать рамка выделения, ручки и тулбар.

Требования к обоим элементам UI:

1. **Точная привязка к выделению.** Тулбар позиционируется под ограничивающим
   прямоугольником выделения, при нехватке места — над ним (SPEC 3.6). При
   перетаскивании стикера тулбар обязан ехать за ним **в том же кадре**, без
   отставания и мерцания.
2. **Только в режиме редактирования.** Вне режима UI не существует вовсе:
   оверлей полностью клик-прозрачен и ничего лишнего не рисует.
3. **Один композиционный слой.** UI должен лежать над стикерами и над
   затемнением, но в той же геометрии, что и они (те же физические пиксели
   монитора, тот же DPI-масштаб).
4. **Событийный рендер (ADR-006).** UI не анимируется сам по себе — перерисовка
   только по событию (движение мыши, изменение выделения, смена значения).

Ниже — три способа реализовать такой UI, с разбором сквозных проблем: вход через
`WS_EX_TRANSPARENT`, DPI, z-order относительно прозрачного оверлей-окна.

---

## 2. Вариант А: нативные дочерние окна Win32

Каждый тулбар/панель — отдельный `HWND` (допустим, дочерний оверлея или popup),
со своим циклом отрисовки поверх контента оверлея.

**Плюсы.**

- Хит-тестинг и ввод отдаются Windows: клики по кнопкам, фокус, клавиатура
  приходят в окно без ручного обратного аффинного преобразования.
- Честный ввод текста: для числового поля можно взять нативный `EDIT`-контрол
  с кареткой, буфером обмена и поддержкой IME.

**Минусы.**

- **Рассинхрон и мерцание при перетаскивании.** Тулбар обязан двигаться
  синхронно с выделением. Отдельное окно значит `SetWindowPos` на каждый кадр
  перетаскивания: движение окна обрабатывается DWM асинхронно и легко отстаёт
  на кадр, а при ресайзе/движении поверх DComp-контента возможны вспышки. Это
  ровно тот аргумент, которым ARCHITECTURE 5.3 уже отверг WebView для тулбара;
  нативное окно легче WebView, но проблема остаётся.
- **z-order в одной полосе.** Если тулбар — отдельное topmost-окно, Windows
  вправе переупорядочить его относительно оверлея и других topmost-окон
  (ARCHITECTURE 3.1 — та же борьба за порядок, которую мы решили не вести).
  Если дочернее — окно выше родителя, но перенос между мониторами (стикер
  перетащили на другой монитор → тулбар обязан стать дочерним другого оверлея)
  превращается в лишний класс задач на M3.
- **`WS_EX_TRANSPARENT` дублируется на каждое окно.** Флаг — бинарный и
  оконно-широкий: нельзя выразить «этот пиксель прозрачен, этот нет». Пока мы
  живём в одном окне, это бесплатно (см. раздел 5); каждое дополнительное окно
  добавляет вторую копию машины состояний «в режиме / вне режима» и риск забыть
  переключить — проглоченный клик.
- **DPI.** Каждое окно — отдельный DPI-контекст. На смешанном DPI (M3) нужно
  транслировать координаты между окном оверлея и дочерними окнами и обрабатывать
  `WM_DPICHANGED` для каждого из них.
- **Свой рендер.** Окно всё равно нужно перерисовывать кастомно (кнопки,
  ползунок) — преимущества стандартных контролов почти не используются, а
  нативный `EDIT` не стилизуется под остальной UI. Гибрид «нативный EDIT в
  окне-контейнере» добавляет IME/фокус-мусор ради одного поля из семи цифр.

**Вывод по варианту:** решает несуществующую проблему (ввод в нативный контрол)
ценой воссоздания всех проблем, от которых ушли в ADR-002. Годится только если
приоритет — «не писать свой текстовый ввод любой ценой».

## 3. Вариант Б: D3D11 immediate-mode UI в том же свапчейне

Тулбар и панель рисуются рендерером как геометрия (квады, скруглённые
прямоугольники, иконки-спрайты, текст) **в конце списка отрисовки** того же
окна оверлея. Хит-тестинг — тот же механизм, что уже нужен для выделения:
обратное аффинное преобразование точки курсора + проверка попадания в
прямоугольники виджетов. Это ровно то, что ARCHITECTURE 5.3 уже зафиксировал
для UI редактора.

**Плюсы.**

- **Идеальная синхронизация.** Тулбар живёт в том же композиционном слое, что и
  стикеры: порядок отрисовки = z-order, движение в том же кадре, ноль
  `SetWindowPos`, ноль мерцания.
- **Ноль лишних HWND.** Нет второй полосы topmost, нет переупорядочивания
  Windows, нет репарент-мусора при переносе стикера между мониторами.
- **Одно координатное пространство.** UI считается в физических пикселях
  монитора с тем же `scale` (DIP→px), что и стикеры. DPI-обработка не
  дублируется: что верно для стикера, верно и для кнопки.
- **Сквозной ввод через флаг окна** работает как надо без дополнительных окон:
  см. раздел 5.
- **Дешёво.** Тулбар + панель — это два маленьких набора квадов, перерисовываются
  строго по событию (ADR-006). Затемнение, рамка, ручки, тулбар, панель — один
  проход, один Present.
- **Будущие вехи бесплатно.** Панель выбора окон (M4, SPEC 4.2) — та же
  immediate-mode отрисовка списка со скроллом; маска перекрытия (M4) применяется
  к спрайтам-стикерам, а UI рисуется поверх неё безусловно — как и должен.

**Минусы.**

- **Текстовый ввод своими руками.** Числовое поле — не `EDIT`, а собственный
  виджет: захват клавиатуры, рисование каретки, фильтр «только цифры»,
  `Ctrl+V`/`Backspace`/`Enter`/`Esc`. Для диапазона 1–100 это приемлемо: IME
  не нужен (только цифры), каретка тривиальна. Сознательно ограничиваем поле
  одним вводом чисел.
- **Шрифты.** Текст кнопок и значений — через DirectWrite (рендер глифов в
  текстурный атлас с кэшем) либо встроенный битовый шрифт. Это самая заметная
  новая работа в `rst-render`.
- **Ручной хит-тест кнопок.** Но инфраструктура (обратная трансформация, bbox)
  уже нужна для выделения стикеров и ручек — тулбар лишь переиспользует её.
- **Нет accessibility** (Screen Reader, UI Automation). Для десктопного оверлея
  это осознанный отказ, как и в ADR-002.

## 4. Вариант В: отдельные окна Tauri

Тулбар и панель — небольшие прозрачные WebView2-окна, управляемые с Tauri-потока.

**Плюсы.**

- HTML-`<input type="number">` даёт настоящий текстовый ввод из коробки.
- Верстка тулбара на CSS быстрее, чем immediate-mode геометрия.

**Минусы.**

- **ADR-002 уже решён против этого.** Каждое окно WebView2 — процесс на 40–80 МБ;
  два окна UI ≈ ещё 80–160 МБ к процессу, который и так держит видео-деколеры.
- **Позиционирование через IPC.** Тулбар обязан ехать за выделением: каждый
  кадр перетаскивания → канал/Tauri-command в основной поток → перемещение окна.
  Задержка от 1 кадра + мерцание — та же болезнь, что у варианта А, но хуже:
  два потока и IPC вместо одного `SetWindowPos`.
- **Борьба за topmost.** Окно тулбара — ещё одно topmost-окно в одной полосе с
  оверлеем; взаимный порядок не гарантирован (ADR-002, ARCHITECTURE 3.1).
- **Прозрачность/клик-сквозь.** WebView-окну нужны `WS_EX_TRANSPARENT` +
  `WS_EX_LAYERED`, а клик-сквозь всё равно оконно-широкий: «просвет» вокруг
  кнопок тулбара (между виджетами) будет либо глотать клики, либо требовать
  ручного `SetWindowRgn`. Попиксельная прозрачность DComp здесь недостижима.
- **DPI.** WebView масштабируется сам, но стыковка его координат с
  DComp-контентом на per-monitor DPI — дополнительный слой трансляции.
- **Скрытие при выходе.** Вне режима редактирования UI должен исчезать: ещё одно
  состояние «показать/скрыть/спозиционировать» через IPC на каждый вход/выход.

**Вывод по варианту:** единственное реальное преимущество — бесплатный ввод
текста — не окупает RAM, IPC-синхронизацию, z-order и DPI. Отвергается тем же
решением, что и ADR-002.

## 5. Сквозная проблема: ввод через `WS_EX_TRANSPARENT`

`WS_EX_TRANSPARENT` — **оконно-широкий бинарный флаг**: окно либо прозрачно для
кликов целиком, либо принимает их целиком. Попиксельного «пусть этот пиксель
уходит дальше» через флаг не выразить (для этого — `SetWindowRgn`, но он тоже
задаёт связные области, а не произвольные пиксели).

Это диктует модель:

- **Вне режима редактирования** флаг стоит — всё окно клик-прозрачно, UI не
  рисуется. Пользователь вообще не должен чувствовать оверлей.
- **В режиме редактирования** флаг снят — окно принимает ввод **на всей площади
  монитора**. Затемнение, клик по стикеру, протяжка рамки выделения, клик по
  кнопке тулбара и перетаскивание панели — **все** эти случаи приходятся в одно
  окно и разрешаются одним хит-тестом по z-order виджетов. Тулбару не нужен
  собственный флаг: он часть того же окна, и его «клик-прозрачность» — это
  просто «промах хит-теста», после которого событие уходит дальше (стикеру,
  пустому месту, рамке).

Именно здесь вариант А и В ломаются: каждое лишнее окно требует своего
переключения флага и не может отдать промах родителю без потери кадра или
проглатывания клика. В варианте Б промах — это `if`, а не переключение режима
окна.

## 6. Сквозная проблема: DPI

Процесс — `PROCESS_PER_MONITOR_DPI_AWARE_V2` (манифест, M0). Оверлей-окно на
каждом мониторе имеет свой масштаб; рендерер хранит `scale` DIP→физические
пиксели на окно (`Renderer::set_dpi_scale`, `placement_to_physical`).

- **Вариант Б:** UI рисуется в тех же физических координатах, что и стикеры, и
  масштабируется тем же `scale`. Виджет, спроектированный в DIP, автоматически
  корректен на 100/125/150/200%. Отдельной обработки DPI для UI нет — её не
  существует как класса задач.
- **Варианты А и В:** каждый дополнительный `HWND` — отдельный DPI-контекст.
  На смешанном DPI (M3) координаты виджета надо транслировать между окном
  оверлея и окном тулбара, обрабатывать `WM_DPICHANGED` для каждого, а панель у
  курсора, пересекающая границу мониторов, — это шторм `WM_DPICHANGED` при
  каждом пересечении. Всё это не нужно нигде, кроме UI, и в варианте Б просто
  отсутствует.

## 7. Сквозная проблема: z-order относительно прозрачного оверлея

Оверлей всегда `WS_EX_TOPMOST` (ADR-004). Внутри него z-order — это порядок
отрисовки: затемнение → стикеры (по порядку слоёв) → рамка выделения/ручки →
тулбар → панель у курсора. UI рисуется последним и безусловно поверх всего.

- **Вариант Б:** тулбар гарантированно выше стикера и затемнения, но ниже ничего
  «чужого» не существует — окно одно, в полосе topmost оно единственное своё.
  Маска перекрытия (M4) режет только спрайты-стикеры; UI ей не маскируется — а
  это и есть желаемое поведение: панель управления не должна «уходить» под окна.
- **Варианты А и В:** тулбар — отдельное окно в той же topmost-полосе. Windows
  переупорядочивает topmost-окна по своим правилам (ARCHITECTURE 3.1), поэтому
  «тулбар выше оверлея» нельзя гарантировать стабильно; либо нужен дочерний
  HWND — но тогда проблема переноса между мониторами.

## 8. Рекомендация

**Вариант Б — immediate-mode UI в свапчейне оверлея.** Он совпадает с уже
принятыми решениями (ADR-002 «весь UI редактора пишется вручную в D3D11»,
ARCHITECTURE 5.3 «тулбар, панель у курсора, панель выбора окон рисуются в
immediate mode») и устраняет все три сквозные проблемы разом: клик-прозрачность
решается хит-тестом внутри одного окна, DPI не размножается по окнам, z-order
становится просто порядком отрисовки.

Что это требует построить в `rst-render`:

1. **Слой виджетов** (небольшой immediate-mode модуль): панель, кнопка, ползунок,
   числовое поле, чекбокс — сущности, умеющие (а) отдавать список примитивов к
   отрисовке и (б) отвечать на точку хит-теста в локальных координатах. Порядок
   проверки — обратный порядку отрисовки (сверху вниз), как для стикеров
   (ARCHITECTURE 5.3).
2. **Шрифты.** DirectWrite → глифы в текстурный атлас с кэшем; либо встроенный
   битовый шрифт. Потребуется для подписей кнопок и значения в числовом поле.
3. **Иконки кнопок** тулбара (глаз, порядок, дубликат, корзина) — загрузка PNG из
   `assets/` как спрайтов-текстур и отрисовка внутри кнопок.
4. **Числовое поле** как собственный виджет: фильтр «только цифры», `Backspace`,
   `Enter` (принять), `Esc` (отменить), `Ctrl+V` (вставить только цифры),
   каретка — рисованная. Клик по полю даёт ему фокус ввода; фокус живёт внутри
   ядра редактирования, а не у Windows.
5. **Хит-тест и фокус** через те же обратные аффинные преобразования, что и для
   выделения — дублирования кода нет.
6. **Позиция панели у курсора** хранится в DIP относительно монитора, рисуется в
   окне того монитора, где находится курсор (на M3 — по мере пересечения границ).

Порядок отрисовки в кадре редактора (снизу вверх): затемнение → стикеры →
рамка/ручки выделения → тулбар → панель у курсора.

## 9. Открытые вопросы

- **Сколько тулбаров рисовать.** По SPEC 3.6 тулбар один (для мультивыделения
  без ползунка), так что дополнительных виджетов на экране максимум два —
  тривиально для immediate-mode. Подтвердить при мультивыделении.
- **Фокус клавиатуры.** Пока у окна фокус, клавиши идут в ядро; надо чётко
  решить, кто получает `Ctrl+D`/`Delete`/`Esc`/`Ctrl+Z`, когда активно числовое
  поле (поле должно забирать цифры себе, а комбинации с `Ctrl` оставлять
  хоткеям). Предлагается: поле перехватывает цифры и `Backspace` всегда,
  `Ctrl+*` и `Esc` — уходят в ядро.
- **Оформить как ADR** при утверждении, дополнив ADR-002.

Если позже понадобится честный многострочный ввод текста (инструменты 2.0 из
ROADMAP «Отложено»), вопрос отдельного окна/WebView вернётся — но не раньше.

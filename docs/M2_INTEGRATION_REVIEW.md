# M2 — интеграционный ревью примитивов и проект ADR-014

Статус: **ревью, без изменений кода**. Читались M2-примитивы (hittest, undo, snap,
ops; selection; hotkey, input, clipboard) с прицелом на их сшивку в
`crates/resticker/src/overlay_manager.rs`.

---

## 1. Ручки и зоны: главное расхождение

Вопрос «совпадает ли enum зон/ручек в `hittest.rs` с ожиданиями `selection.rs` и
`input.rs`» распадается на два факта:

1. **В `hittest.rs` никакого enum ручек/зон нет.** Модуль даёт только геометрию
   (`contains`, `contains_inflated`, `corners`, `aabb`, `to_world`/`to_local`) и
   не знает про «зону под курсором». Зона — это концепция, которой сейчас нет ни
   в одном крейте целиком, и `overlay_manager` будет вынужден изобрести её сам.
2. **Типы ручек раздвоены и по-разному упорядочены:**

| Тип | Где | Порядок вариантов |
|---|---|---|
| `HandleKind` | `rst-render/selection.rs:47` | NW, N, NE, E, SE, S, SW, W |
| `Handle` | `rst-win32/input.rs:180` | N, NE, E, SE, S, SW, W, NW |
| `Corner` | `rst-win32/input.rs:207` | NE, SE, SW, NW |

Одни и те же 8 смыслов под двумя именами и в разных порядках. Пока код
обращается к вариантам по имени — это безопасно, но любой цикл «пройтись по
ручкам и попарно сопоставить» (например, `SelectionBox::handle_rects()` +
`CursorZone::ResizeHandle`) сорвётся на индексах. Углы определены трижды и без
общего типа: `input.rs::Corner`, неявный порядок массива `SelectionBox::corners()`
(`selection.rs:141`, порядок NW, NE, SE, SW) и `hittest::corners`
(`hittest.rs:88`, тот же порядок NW, NE, SE, SW). При попадании в зону поворота
`Corner::NorthEast` overlay_manager должен смапить его на индекс массива — через
хрупкое перечисление, а не через тип.

**Рекомендация (сшивка в M2):** один enum `Handle`/`Corner` в `rst-core`
(геометрия платформенно-независима), оттуда его переиспользуют `selection.rs`
(для `handle_center`/`handle_rects`) и `input.rs` (для `CursorZone`/`cursor_shape`).
Плюс единый enum зоны редактора (`Background`/`StickerBody`/`ResizeHandle(Handle)`/
`RotateZone(Corner)`) — сейчас такой тип есть только в `rst-win32/input.rs:219`
и называется он `CursorZone` (по факту это «результат хит-теста» + «форма
курсора», а имя отражает лишь половину). Его логично положить рядом с хит-тестом.

## 2. Координаты и единицы

- **DIP f64 в core и render, физические i32 на входе.** `hittest`/`snap`/`selection`
  работают в DIP (f64), `input.rs::Point` — физические клиентские пиксели
  (`input.rs:24`). Переход физика→DIP (`dip = phys / scale`) обязан делать
  overlay_manager перед хит-тестом.
- **`Renderer::set_dpi_scale` никогда не вызывается, геттера нет.** Поле `scale`
  приватно (`renderer.rs:245` — только сеттер), и во всём коде нет ни одного
  вызова `set_dpi_scale` (проверено grep'ом). С масштабом 1.0 при манифесте
  PerMonitorV2 стикеры уже сейчас рендерятся в неправильных физических размерах
  на 125/150%. Для M2 это ещё и блокер хит-теста: без знания масштаба точка
  мыши не переводится в DIP. Нужен `Renderer::dpi_scale()` либо явное хранение
  масштаба в overlay_manager рядом с вызовом `set_dpi_scale`.
- **Два типа прямоугольника без конверсии.** `hittest::DipRect` (ось-выровненный,
  x,y,w,h) и `selection::Box2D` (центр+поворот). Результат магнита —
  `DipRect` (`snap.rs:80`), а рендерить можно только `Box2D` через
  `solid_sprite`. Нет `From<DipRect> for Box2D`. Направляющие магнита
  (`SnapResult::vline/hline`, `snap.rs:60-63`) дают координаты, но готового
  визуала линий нет — overlay_manager строит их как тонкие квады.
- **Поворот — согласован.** Радианы по часовой стрелке в `hittest.rs:5-7`,
  формула `selection::rotate` (`selection.rs:131`) совпадает с `to_world`
  (`hittest.rs:42`) и шейдером. Здесь расхождения нет.
- **Несоответствия SPEC и константам кода** (надо поправить в M2):
  - SPEC 3.4 «Порог — 10 логических пикселей» против `SnapConfig::default()` =
    `8.0` (`snap.rs:26`).
  - SPEC 3.6 «Копия со смещением +20/+20 px» против `DUPLICATE_OFFSET` = `16.0`
    (`ops.rs:15`).

## 3. Ошибки и композиция

Четыре разрозненных типа ошибок: `CoreError` (конфиг), `ops::OpError` (только
`StickerNotFound`), `Win32Error`, `RenderError`. App-level enum в bin-крейте нет,
и текущий стиль — log-and-continue (`overlay_manager.rs:82,84,141,145`). Для M2
это терпимо: операции редактора либо «не нашли стикер» (OpError), либо «не
нарисовалось» (RenderError), и обе логируются. Но `ops.rs` и `undo.rs` не
склеены: `Command` (`undo.rs:23`) инкапсулирует изменение через захваченные
ссылки, а `ops.rs` — чистые функции на `&mut Config`. Готового моста нет, и
`Box<dyn Command>` не может держать `&mut Config`. Для тулбара придётся вручную
написать ~6 типов команд (delete→хранить удалённый стикер, duplicate→новый id,
move→старые cx/cy, opacity→старое значение, z-order→старые order'ы,
visibility→старый флаг) либо делать снапшот `Config` целиком. Рекомендация:
снапшот-команда для M2 (Config клонируется дёшево на 25 стикеров), затем при
необходимости — точечные команды.

## 4. Ввод и хоткеи: нет точек сшивки в `OverlayWindow` (главный блокер)

`OverlayWindow` владеет своим message pump и `wndproc` внутри (`overlay.rs:103-217`),
а `wndproc` обрабатывает только `WM_DESTROY`. При этом:

- `input.rs` рассчитан на то, что «wndproc скармливает сырые сообщения»
  (`input.rs:4`): `MouseCapture` и `CursorManager` обязаны жить на потоке окна
  (`HWND` — `!Send`). Пока в overlay.rs нет хука/callback'а на wndproc, получить
  `InputEvent` в overlay_manager неоткуда.
- `RegisteredHotkey` — `!Send` и обязан создаваться/уничтожаться на потоке с
  циклом сообщений (`hotkey.rs:163`). Но `WM_HOTKEY` при регистрации с
  `hwnd=NULL` приходит в очередь потока как сообщение с `hwnd=NULL`, и
  `DispatchMessage` его не разнесёт — текущий цикл (`overlay.rs:122-130`) просто
  его проглотит. `message_hotkey_id` (`hotkey.rs:218`) сейчас не вызывается нигде.
- В итоге в process уже два потока (поток `run` в overlay_manager + поток pump
  в OverlayWindow), и весь ввод/хоткей-ввод живёт на втором.

**Рекомендация (сшивка):** дать `OverlayWindow` способ установить wndproc-хук
или pre-loop callback (например, «установщик хоткеев и обработчиков сообщений»,
вызываемый на pump-потоке до `GetMessage`-цикла), и обрабатывать `WM_HOTKEY` с
`hwnd=NULL` в самом цикле до `DispatchMessage`. Это единственное место, где
придётся менять уже существующий код, а не просто комбинировать примитивы.

## 5. Мелочи, которые укусят

- `hittest::corners(placement, rotation)` и `aabb(placement, rotation)` берут
  голый `rotation: f64`, а `contains`/`contains_inflated` — `&Transform`
  (`hittest.rs:62,88,98`). Три разных сигнатуры для одного семейства; два
  вызова будут таскать `transform.rotation` руками. Унифицировать на `&Transform`.
- `DUPLICATE_OFFSET`/порог магнита — см. раздел 2 (расхождение со SPEC).
- `ops::bring_to_front`/`send_to_back` для тулбара не нужны (тулбар требует
  только step_up/step_down), но не конфликтуют — просто неиспользуемый дубль
  на будущее.

## 6. Итоговая таблица «что шить в overlay_manager»

| Узел | Статус примитивов | Что требуется |
|---|---|---|
| Хит-тест выделения/ручек | геометрия есть (`hittest`), зон нет | единый enum зоны + `Handle` в core |
| Курсор | `CursorZone::cursor_shape` готов | маппинг зоны→CursorZone, wndproc-хук |
| Захват мыши | `MouseCapture` готов | wndproc-хук (поток pump) |
| Хоткей | `HotkeyCombo`/`RegisteredHotkey` готовы | обработка `WM_HOTKEY(NULL)` в pump |
| Магнит | `snap_move`/`snap_placement` готовы | `From<DipRect> for Box2D`, визуал линий |
| Трансформации | только геометрия | ресайз/поворот за ручки — код в overlay_manager |
| Тулбар-операции | `ops` готовы | undo-команды (снапшот или 6 типов) |
| Ввод физика→DIP | — | `Renderer::dpi_scale()` + вызов `set_dpi_scale` |
| Буфер обмена | `read_image` готов | вызов по Ctrl+V в редакторе |

## 7. Проект ADR-014 «UI редактора — immediate-mode D3D11 в свапчейне оверлея»

Предложение формализовать рекомендацию `docs/M2_UI_NOTES.md` следующим ADR после
существующих (в `DECISIONS.md` последний — ADR-013, следующий номер — 14).

1. **Титул и статус.** ADR-014 «UI режима редактирования: immediate-mode D3D11
   в композиционном свапчейне оверлей-окна». Статус: принято (по факту
   подтверждает ARCHITECTURE.md, раздел 5.3). Запись — дополнение и уточнение
   ADR-002, со ссылкой на `docs/M2_UI_NOTES.md` как на исходный анализ.
2. **Контекст.** Тулбар стикера (SPEC 3.6) и панель у курсора (SPEC 3.8)
   появляются только в режиме редактирования, обязаны ехать за выделением в том
   же кадре и лежать в том же композиционном слое, что и стикеры. Три кандидата:
   нативные дочерние окна, D3D-immediate UI, отдельные Tauri-окна.
3. **Решение.** Весь UI режима редактирования (тулбар, панель у курсора, позднее
   панель выбора окон SPEC 4.2) рисуется рендерером `rst-render` как геометрия в
   конце списка отрисовки того же оверлей-окна. Хит-тест — теми же обратными
   аффинными преобразованиями, что и для выделения. Никаких дополнительных HWND.
4. **Отвергается: нативные дочерние окна.** `SetWindowPos` на каждый кадр
   перетаскивания даёт рассинхрон и мерцание; дочернее/topmost окно — борьба за
   z-order в полосе topmost и репарент при переносе между мониторами (M3);
   `WS_EX_TRANSPARENT` дублируется на каждое окно; отдельный DPI-контекст на
   смешанном DPI. Принято, что ценность «нативный EDIT» не окупает это.
5. **Отвергается: отдельные окна Tauri.** WebView2 — процесс на 40–80 МБ;
   позиционирование через IPC даёт задержку и мерцание; ещё одно topmost-окно в
   одной полосе с оверлеем; клик-сквозь остаётся оконно-широким. Это ровно
   мотивировка ADR-002.
6. **Следствия для `rst-render`.** Необходимо построить: (а) immediate-mode слой
   виджетов (панель, кнопка, ползунок, числовое поле, чекбокс) с хит-тестом;
   (б) DirectWrite → атлас глифов с кэшем (подписи, значения); (в) числовое поле
   как собственный виджет: фильтр «только цифры», Backspace, Enter, Esc, Ctrl+V,
   рисованная каретка, фокус — внутри ядра редактора; (г) иконки кнопок из
   `assets/` как спрайты.
7. **Следствия для координат/порядка.** UI проектируется в DIP и масштабируется
   тем же `scale`, что и стикеры (один DPI-контекст на монитор — DPI-задач для
   UI нет). z-order = порядок отрисовки: затемнение → стикеры → рамка/ручки →
   тулбар → панель. Маска перекрытия (M4) режет только спрайты-стикеры, UI не
   маскируется — это желаемое поведение (панели не «уходят» под окна).
8. **Ввод.** `WS_EX_TRANSPARENT` — оконно-широкий бинарный флаг: вне режима —
   всё окно клик-прозрачно (UI не рисуется), в режиме — окно принимает ввод на
   всей площади, а «прозрачность» тулбара — это промах хит-теста, после которого
   событие уходит стикеру/фону. Открытый вопрос из M2_UI_NOTES (раздел 9 —
   разделение клавиатуры между числовым полем и хоткеями) зафиксировать в ADR
   как требование перед реализацией.
9. **Взаимосвязи.** Дополняет ADR-002 (Tauri — только настройки/трей), опирается
   на ADR-006 (событийный рендер: UI не анимируется сам, перерисовка по событию),
   ADR-010 (DIP относительно монитора). При утверждении: внести пункты 6–8 в
   ARCHITECTURE.md 5.3 и закрыть раздел 9 в M2_UI_NOTES.

## 8. Сводка «что укусит» (если ничего не менять)

1. `Handle`/`HandleKind`/`Corner` — три типа вместо одного; порядок вариантов
   разный → ошибки по индексам при маппинге ручек.
2. `scale` рендерера не выставляется и не читается → неверный размер стикеров на
   не-100% DPI и нет конверсии ввода физика→DIP.
3. `OverlayWindow` не отдаёт wndproc/pump → `InputEvent`, `WM_HOTKEY`, захват
   мыши и курсоры не подключить без правки overlay.rs.
4. `WM_HOTKEY` с `hwnd=NULL` проглатывается текущим циклом сообщений.
5. `ops.rs` ↔ `undo.rs` не склеены — команды тулбара придётся писать вручную.
6. `DipRect`↔`Box2D` без конверсии; визуалов линий магнита нет.
7. Две константы расходятся со SPEC: порог магнита 8 vs 10, смещение дубликата
   16 vs 20.

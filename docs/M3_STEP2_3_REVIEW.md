# M3 — ревью шагов 2/3: Device/WindowTarget split, per-monitor overlay, WM_DPICHANGED и ручная сшивка координатора

Статус: **независимое ревью, без изменений кода**. Ветка `feat/m2-edit-mode`, коммиты:
`ad8bc18` (rst-render: `Renderer` → `Device` + `WindowTarget`, +292/−203),
`3f336cc` (rst-win32: `create_on_monitor`/единый хоткей/`WM_DPICHANGED`, overlay.rs +313/−68)
и `b14c68e` (координатор: локальная обёртка `Renderer` + обработка `OverlayEvent::DpiChanged`,
overlay_manager.rs +79/−8). Прочитаны диффы всех трёх коммитов и актуальные файлы:
`crates/resticker/src/overlay_manager.rs` (2433 строки), `crates/rst-render/src/device.rs`,
`crates/rst-render/src/window_target.rs`, `crates/rst-win32/src/overlay.rs` (в состоянии HEAD —
в рабочей копии rst-win32 есть **незакоммиченный WIP параллельной сессии** (WM_DISPLAYCHANGE/
WTSSESSION/POWERBROADCAST в overlay.rs + Cargo.toml), он в ревью не входит, см. §3). Сверено
с `docs/M3_PREP_NOTES.md` §3.6/§4. Интерактивного прогона нет (только build/clippy/test/launch-smoke,
зафиксированные в коммитах; реальный WM_DPICHANGED и мультимонитор не проверялись).

**Общий вердикт:** разделение `Device`/`WindowTarget` чистое, семантика владения
и порядок дропа корректны; `WM_DPICHANGED`-цепочка (rst-win32: SetWindowPos →
событие; координатор: locals → set_dpi_scale → resize → rebuild_ui_panels → redraw)
секвенсирована **без stale-read окна** — все локальные `width/height/scale`
обновляются до любого использования, канал событий FIFO, рассинхронизированных
кадров между применением rect'а окна и ресайзом цепочки не возникает (единственный
артефакт — суб-кадровый DComp-stretch старого backbuffer). Проблемы — две живых
(обe на стороне координатора, обе проявляются только в момент смены DPI):
UI-кэш растров (`UiTextureCache`) не перерастеризует текст/иконки под новый
масштаб, и `edit.cursor_pos` (DIP от старого scale) оставляет панель у курсора
смещённой до следующего rebuild-события. Плюс три пограничных замечания.

## 1. Проверено по явным вопросам задачи

### 1.1 Секвенсинг `resize`-on-`DpiChanged` — stale-read окна нет

Обработчик (overlay_manager.rs:649-664):

```rust
width = size.0;                  // 655 — сначала локали
height = size.1;                 // 656
scale = dpi as f32 / 96.0;       // 657
renderer.set_dpi_scale(scale);   // 658
renderer.resize(width, height);  // 659-661
rebuild_ui_panels(...);          // 662
need_redraw = true;              // → redraw(...) на 710-721 читает те же локали
```

Порядок правильный: **локали обновляются до** `set_dpi_scale`/`resize`/`rebuild_ui_panels`/
`redraw`, а не после. Одно сообщение = одна итерация цикла, `redraw` в конце итерации
читает уже новые значения — внутри координатора stale-read невозможен.

Остаётся только «внешнее» окно: `SetWindowPos` в rst-win32 (overlay.rs:564-572) применяет
рекомендованный rect **сразу в wndproc**, а ресайз цепочки происходит позже, когда
координатор дойдёт до события. Между этими двумя моментами окно нового размера с
цепочкой старого — но кадр в этом промежутке отрисован быть не может: кадры рисуются
только из цикла координатора, события приходят по одному каналу через один поток-мост
(FIFO), и `DpiChanged` обрабатывается до любых последующих `Input`/`Key`. Единственный
артефакт — DComp растягивает старый backbuffer на новый размер окна (режим
`DXGI_SCALING_STRETCH` уже был в desc) в течение [SetWindowPos … resize] — суб-кадровый,
невидимый. Также корректно: `size()` из события (рекомендованный rect) совпадает с
`overlay.size()` (`GetWindowRect` после `SetWindowPos`), так что последующие ресайзы
идут с той же геометрией; стартовый `WindowTarget::new(&device, hwnd, width, height)`
строится по актуальному `overlay.size()` — даже если WM_DPICHANGED прилетел раньше,
чем координатор прочитал размер, цепочка создастся под новый размер, а прилетевшее
событие даст resize-no-op (одинаковый размер).

### 1.2 `rebuild_ui_panels` с актуальными `(width, height, scale)` — да, но панель у курсора строит по устаревшему `cursor_pos`

Вызов (662) идёт после обновления локалей, `screen_dip_rect(width, height, scale)`
(1421) получает новые значения — сам по себе вызов корректен. Тулбар пересобирается
по DIP-геометрии стикера (масштаб на неё не влияет) — корректен. **Панель у курсора
строится по `edit.cursor_pos` (1407), а это DIP от старого масштаба** — см. §2.2.

### 1.3 Прочие пути, читающие старые фиксированные `width/height/scale` — не найдены

Все точки потребления геометрии в координаторе берут цикловые локали, которые
`DpiChanged` обновляет до обработки любого следующего сообщения: `toggle_edit_mode`
(629-630), хоткей toggle-all (644), `handle_key` (686-687), `handle_input`
(`scale` 694, `overlay_size` 697, `monitor` 1726-1731 от тех же локалей), `redraw`
(718-720), `screen_dip_rect`/`selection_center_or_screen` (1360, 1466-1467) — всё от
передаваемых аргументов. `OverlayEvent` в состоянии HEAD — ровно 6 вариантов
(ToggleEditMode, ToggleAllStickers, HotkeyConflict, DpiChanged, Input, Key), матч в
`run()` (608-707) исчерпывающий — непокрытых вариантов нет.

Прямых читателей живой геометрии окна (`overlay.size()`/`overlay.dpi()`) вне старта два:
`add_sticker` (2403) — см. §2.3, и `file_dialog::pick_image_file(overlay.hwnd())` (1601)
— по хэндлу, без геометрии. Оба безвредны по механике, первый — с оговоркой.

### 1.4 Шатдаун: порядок дропа `Device`/`WindowTarget`/окна корректен

- **Локальные переменные** `run()`: `overlay` объявлен раньше `renderer`; обратный
  порядок дропа → `renderer` (Device+WindowTarget) дропается **до** `overlay` — DComp-
  target/visual и swapchain освобождаются, пока HWND ещё жив; затем `Drop overlay`
  шлёт `WM_CLOSE` и ждёт поток (overlay.rs:291-307). Комментарий на 724-725 верен.
- **Внутри обёртки** `struct Renderer { device: Device, target: WindowTarget }` (67-69)
  поля дропаются в порядке объявления: **`device` раньше `target`**. Это безопасно:
  swapchain и RTV держат собственные ссылки на D3D11-устройство (DXGI-цепочка
  удерживает устройство, D3D11-чанки — тоже), DComp target/visual удерживают
  `dcomp_device`, swapchain — `factory`; дроп `Device` лишь декрементит счётчики,
  реальное уничтожение произойдёт после освобождения `target`. Использования
  устройства после дропа нет (контекст/шейдеры живут внутри `Device` и дропаются
  вместе с ним; устройство D3D11 держат живым его чанки).
- **Текстуры**: `white_tex`/`black_tex`/`sprites`/`ui_cache` объявлены **после**
  `renderer` → дропаются **раньше** него — GPU-ресурсы умирают до устройства. Порядок
  идеальный.

### 1.5 `draw` с рассинхроном target size vs placement math — не найден

`Device::draw` берёт `w/h` из `target.size()` и `scale` из `target.dpi_scale()`
(device.rs:222, 264) — **согласованная пара из одного объекта**. Кадр после
`DpiChanged` рисуется после `renderer.resize` → новый размер цепочки + новая шкала
вместе. Спрайты (DIP-placement) мапятся новой шкалой, вьюпорт — новый размер,
RTV пересоздан под новый backbuffer. Пути «старый размер цепочки + новая шкала» не
существует: до `resize` шкала тоже старая, после — обе новые. Исключение — ошибка
самого `resize` (§2.4), но и там draw безопасен (RTV = None → no-op).

## 2. Найденные проблемы

### 2.1 UI-кэш растров (`UiTextureCache`) не перерастеризуется при смене DPI — текст и иконки остаются в старой плотности

- **Где:** `UiTextureCache::text_texture` (overlay_manager.rs:377-399), `icon_texture`
  (401-419); ключи кэша — `(text, color)` (384) и `icon` (405), **без масштаба**.
- **Что:** кэш живёт весь сеанс в `run()`. Текст растрируется с `text_scale =
  scale.round() as u32` (2241), иконки — с `size_px = rect.w × text_scale` (463).
  После `WM_DPICHANGED` (125/150/200%) `rebuild_ui_panels` пересобирает панели, шкала
  новая, но кэш возвращает старые растры: надписи «Delete N sticker(s)?», цифры
  числового поля и иконки рисуются в DIP-прямоугольниках новой физической плотности
  со старой пиксельной — **размытие/неверный размер до перезапуска**. До этих трёх
  коммитов масштаб никогда не менялся на лету — баг «приехал» вместе с поддержкой
  `WM_DPICHANGED`.
- **Фикс:** включить масштаб в ключи — `(text, color, text_scale)` и `(icon, size_px)`
  (память: ~десяток строк × варианты масштабов — незначительно), либо очищать
  `texts`/`icons` в ветке `DpiChanged` (649-664). `fills` (1×1) масштабонезависимы —
  трогать не надо.

### 2.2 `edit.cursor_pos` устаревает при смене DPI — панель у курсора остаётся смещённой

- **Где:** `edit.cursor_pos = to_dip(pos, scale)` (1858), `rebuild_cursor_panel`
  использует `edit.cursor_pos` (1407), вызов из `DpiChanged` (662), hover-ветка
  MouseMove (1908-1914) панель **не пересобирает**.
- **Что:** `cursor_pos` — DIP от **старого** scale. После смены DPI `rebuild_ui_panels`
  ставит панель в этот устаревший DIP: физическое смещение от реального курсора —
  `cursor_pos × (new_scale/old_scale)`. Хуже: hover-ветка лишь обновляет hover-состояние
  существующей панели, rebuild по свежему `cursor_pos` не делает, поэтому смещение
  **не самозалечивается на ближайшем MouseMove** — панель висит не на месте до
  следующего события, которое триггерит `rebuild_ui_panels` (драг сцены, смена
  выделения, undo/redo, ещё одна смена DPI). Тулбар этой болезни не имеет — его
  геометрия от стикера, а не от курсора.
- **Фикс:** в ветке `DpiChanged` пересчитать позицию панели: хранить последние
  **физические** координаты мыши (или пересобирать панель на каждом hover-Move —
  то, что срез 6 осознанно упростил, но тогда это закрыло бы и это), либо при
  `DpiChanged` сдвигать существующую панель на коэффициент `new/old` и обновлять
  `cursor_pos` тем же коэффициентом.

### 2.3 (низкое, pre-existing) `add_sticker` кладёт центр вставки по физическому размеру окна — с live-геттером теперь реагирует на DPI

- **Где:** `add_sticker` (overlay_manager.rs:2403): `let (screen_w, screen_h) =
  overlay.size(); … Sticker::new_pasted(…, screen_w as f64 / 2.0, screen_h as f64 / 2.0, …)`.
- **Что:** placement — DIP, а центр считается `физический размер / 2` вместо
  `(физический/scale)/2` — при 100% совпадает, при 150% вставка уходит на 75%
  ширины вместо центра. До M3 `size()` был фиксирован на создание и баг был
  «заморожен»; теперь это живой `GetWindowRect` (overlay.rs:228-241) — после смены
  DPI/переезда окна центр вставок скачет. Вне scope трёх коммитов, но становится
  видимым ровно благодаря им.
- **Фикс:** `(overlay.size()/scale)/2` через уже существующие `screen_dip_rect`.

### 2.4 (низкое) Ошибка `renderer.resize` оставляет новые локали при старой цепочке

- **Где:** ветка `DpiChanged` (659-661).
- **Что:** если `ResizeBuffers`/`create_rtv` упали (редко: DEVICE_REMOVED и т.п.),
  `WindowTarget::resize` уже выставил `size` и обнулил `rtv` (window_target.rs:123-125)
  — последующие кадры становятся no-op (`rtv = None`, device.rs:223-225): пустой
  экран оверлея до следующего события. Локали при этом уже новые — последующая
  перерисовка затемнения/геометрии нарисована не будет. Не паника, но и не
  восстановление: окно остаётся «слепым», пока не придёт ещё один WM_DPICHANGED.
  Ошибка логируется — приемлемо как деградация, но стоит задокументировать, что
  после сбоя `resize` нужен повторный триггер (или пересоздание цели целиком —
  задел из ARCHITECTURE §11).

### 2.5 (замечание) Смена DPI во время активного UI-жеста (драг ползунка)

- **Где:** `DpiChanged` → `rebuild_ui_panels` (662) при `pointer_owner == Toolbar`.
- **Что:** панель подменяется посреди драга: `Slider.dragging`/`Panel.capture` старой
  панели умирают вместе с ней, `pointer_owner` и `ui_pending_snapshot` (если драг уже
  менял opacity) остаются. На `MouseUp` `handle_toolbar_up` закоммитит отложенный
  снимок — драг честно фиксируется, а не теряется; новый ползунок показывает
  актуальное значение (rebuild читает `cfg`). Никакого вреда — просто отметка, что
  DPI-событие «проглатывает» середину жеста ползунка без явного решения.
- **Симметрично для жестов сцены:** `GestureStart`/марка — DIP, смена DPI их не
  инвалидирует; `monitor`-rect для snap/clamp пересчитывается на каждом Move (1726-1731)
  — драг продолжается в новой геометрии корректно.

## 3. Что проверено и корректно (не тратить время на повторную проверку)

- **rst-win32 `WM_DPICHANGED`:** `handle_dpi_changed` — чистая функция с тестами
  (overlay.rs:864-920): `LOWORD(wParam)` как DPI, рекомендованный rect применяется
  через `SetWindowPos` с `SWP_NOZORDER|SWP_NOACTIVATE` (topmost/фокус не трогаются),
  событие уходит после применения rect'а; нулевой DPI — `None`, окно не трогается,
  lParam не читается. `size()`/`dpi()` — живые геттеры (`GetWindowRect`/`GetDpiForWindow`),
  корректны с любого потока (окно владеется потоком, хэндл — числом, `Send+Sync`
  обоснованы комментарием).
- **Единый хоткей:** `edit_hotkey: Option<HotkeyCombo>` регистрируется только на
  одном окне (overlay.rs:373-387); тест `window_without_hotkey_does_not_conflict`
  проверяет отсутствие конфликта и событий. Совместимая `create()` (199-213) —
  тонкая обёртка над `create_on_monitor` с `GetSystemMetrics` и безусловным хоткеем.
- **`create_window(bounds_px)`:** неосновной монитор с отрицательными координатами
  виртуального десктопа проходит (передаётся как `i32` позиция); нулевой размер —
  ошибка создания (overlay.rs:498-503). Тест `window_uses_given_bounds` проверяет
  позицию (1920,120).
- **Шатдаун:** порядок дропа корректен (§1.4); `WM_DESTROY`→`PostQuitMessage` +
  `WM_NCDESTROY`→дроп `WndState` — без изменений и без утечек.
- **rst-render split:** текстуры живут на `Device` и рисуются на любой `WindowTarget`
  (draw берёт размер/шкалу цели, device.rs:222/264) — заявленный блокер M3 закрыт;
  `resize` пересоздаёт только swapchain/RTV (window_target.rs:118-142), текстуры не
  трогает; `DXGI_ERROR_DEVICE_REMOVED/RESET` → `RenderError::DeviceLost` (157-161);
  `gpu_smoke` покрывает create→draw→resize→(0,0) на реальном окне.
- **Согласованность `scale`:** локаль `scale` и `target.dpi_scale()` синхронны
  (оба обновляются в ветке `DpiChanged`; `set_dpi_scale` клампит, для реальных
  dpi ≥ 96 расхождения нет).
- **Прочие ветки цикла** (toggle_edit_mode, toggle-all, handle_key, handle_input,
  redraw) читают только обновляемые локали (§1.3) — регрессий нет.

## 4. Приоритеты для координатора

1. **UI-кэш растров под новый масштаб (§2.1)** — масштаб в ключи
   `text_texture`/`icon_texture` (или очистка кэша в `DpiChanged`): без этого любая
   реальная смена DPI даёт размытые подписи/иконки до перезапуска.
2. **Панель у курсора после смены DPI (§2.2)** — `cursor_pos` в DIP старого масштаба;
   пересчёт позиции/пересборка по физической позиции мыши.
3. **Центр вставки (§2.3)** — `add_sticker` через `screen_dip_rect`; заодно снимает
   DPI-зависимость.
4. **Задокументировать деградацию при сбое `resize` (§2.4)** и поведение
   DpiChanged-посреди-жеста (§2.5) — оба приемлемы, но неявны.

Примечание по рабочей копии: `crates/rst-win32/src/overlay.rs` и `Cargo.toml` содержат
незакоммиченный WIP параллельной сессии (WM_DISPLAYCHANGE/WTSSESSION/POWERBROADCAST →
новые варианты `OverlayEvent`). Когда он закоммитится, матч в `run()` перестанет быть
исчерпывающим — координатору понадобятся ветки под новые события; это вне рамок трёх
ревьюируемых коммитов, но стоит держать в голове.

## 1. Где живёт панель в архитектуре виджетов/событий

**Решение: новый модуль `crates/resticker/src/window_picker.rs` (чистый
билдер + типы состояний, как `cursor_panel.rs`/`confirm_dialog.rs`) и новое
поле `EditState.window_picker: Option<WindowPickerState>`, открывается новой
кнопкой тулбара.**

Точный паттерн — `ConfirmState`, а не `Option<Panel>`: панели выбора нужно
держать больше, чем собранный `Panel`, — снимок окон и состояние скролла:

```text
struct WindowPickerState {
    sticker_id: Uuid,            // правило редактируется у ОДНОГО стикера
    panel: Panel,                // собранная панель (билдером ниже)
    snapshot: Vec<WindowInfo>,   // снимок на момент последней сборки
    scroll: usize,               // сдвиг списка (строк, не DIP) — §7.4
    monitor_id: MonitorId,       // «домашний» монитор, как у ConfirmState
}
```

- **Открытие**: кнопка «Слои видимости» в тулбаре (SPEC 3.6 п. 3; `Icon::Layers`
  уже есть в rst-render — icons.rs:25, widgets.rs:50-51; кнопки в тулбаре нет —
  добавляется в toolbar.rs). По клику ядро создаёт `WindowPickerState` (снимок —
  из `window_snapshot`, см. §5) и вставляет в `edit.window_picker`. Повторный
  клик той же кнопки закрывает панель (переключатель); `Esc` тоже закрывает
  (паттерн модала, handle_key:1879-1886).
- **Роутинг событий**: пока панель открыта, `MouseDown/Move/Up` на ней идут в
  неё. Добавить вариант `PointerOwner::WindowPicker` (602-607) и ветку в
  `handle_input`: после проверки модала, **до** панели у курсора/тулбара
  (панель выбора — поверх тулбара, она из него открыта). В `MouseMove`
  добавить `PointerOwner::WindowPicker` в match (3169-3186). Хит-тест — только
  на «домашнем» мониторе (`edit.window_picker.monitor_id == *monitor_id`), как
  для остальных панелей (M3_STEP4_REVIEW.md, пункт 2.1).
- **Отрисовка**: в `redraw` — после тулбара и панели у курсора, до модала
  (3833-3865). Открытая панель блокирует сцену? — **открытый вопрос** (§7.7):
  модал модален целиком (3026-3033), а панель выбора скорее «прилипшая
  панель». Рекомендация: НЕ блокировать сцену; панель в приоритетном списке
  хит-теста перед панелью у курсора.
- **Клавиши**: `Esc` — закрыть (без выхода из режима редактирования; тот же
  приоритет, что у модала, — до хоткеев ядра). Стрелки вверх/вниз — скролл
  (§7.4), если добавим.

Действия чекбоксов мутируют `cfg` и обязаны проходить стандартный путь
изменений: `commit_undo_snapshot` + `config::save` + `rebuild_ui_panels` —
ровно как кнопки тулбара (2791-2827). Каждое переключение — отдельный шаг
истории.

## 2. Модель данных: UI-состояние и round-trip в `VisibilityRule`

### 2.1 Единственный источник истины — `cfg`, не копия состояний в панели

Состояние чекбоксов **не хранится** в `WindowPickerState`. Вместо этого
панель каждый раз собирается заново из текущего `sticker.visibility.rules`
(тот же паттерн «пересборка дёшева», что у `rebuild_cursor_panel`): чекбокс
строки/процесса «выбран» ⇔ правило, которое её матчит, **уже есть** в `rules`.
Это автоматически даёт: правку правил вне панели (undo/redo, загрузка
конфига) — и панель при пересборке отобразит актуальное состояние; новые окна
уже выбранного процесса появляются отмеченными (§3).

Для этого нужна чистая функция «окно матчится правилом» — она уже есть в
occluders.rs, но приватная (`rule_matches`, 67-79). **Нужно
`pub`-экспортировать её** (или обёртку `rule_matches_rule(rule,
&OccluderCandidate)`) из rst-core, чтобы панель (crates/resticker) могла
определять «выбран ли чекбокс окна/процесса» тем же предикатом, которым маска
решает про окклюдер — иначе панель и маска могут разойтись во мнениях.

### 2.2 Отображение «чекбокс → правило» (SPEC §4.1)

SPEC 4.1: цель — «конкретное окно (по HWND в текущей сессии) или процесс
(по пути к исполняемому файлу, для восстановления между запусками)».
Модель `OverlapRule` умеет выражать только **процесс** (`process_name`) и
**заголовок** (`title_pattern`). Отсюда:

| Чекбокс | Создаваемое правило | Комментарий |
|---|---|---|
| Процесс P (группа) | `OverlapRule { process_name: Some(короткое_имя_exe), title_pattern: None }` | Переживает рестарты (по пути, не по pid); матчит и текущие, и будущие окна (SPEC 4.2: «все будущие окна этого процесса») |
| Окно W (строка) | `OverlapRule { process_name: None, title_pattern: Some(точный_заголовок_W) }` | Приближение «конкретного окна» через заголовок: HWND в модели нет. **Открытый вопрос** (§7.5) |

Снятие чекбокса = удаление из `rules` всех правил, которые матчат окно/процесс
тем же предикатом (исключительно точное совпадение: для окна — правила с
`title_pattern == точный_заголовок`; для процесса — правила с
`process_name == имя_exe`; правила с wildcard-паттернами **не трогаем** — они
могут быть вручную прописаны в конфиге, панель их не должна «съедать»).

### 2.3 Режим и крайние случаи

- **`mode` при открытии**: панель редактирует список правил. Если у стикера
  `Always` — список пуст; открытие панели показывает все чекбоксы снятыми.
  Первое же включение чекбокса переводит стикер в `OverlapAllowlist` (иначе
  правило не применится — `is_occluder` для `Always` всегда false). Решение:
  при первом изменении панели, если `mode == Always`, ставим
  `mode = OverlapAllowlist` (часть того же шага истории).
- **Сняли всё** → пустой `rules` при `OverlapAllowlist`. По occluders.rs:60-61
  пустой allow-list тождествен `Desktop` (тест
  `allowlist_empty_rules_is_desktop_equivalent`). Оставляем `OverlapAllowlist`
  с пустым списком (семантически «только рабочий стол»), не переключаем режим
  обратно — сохраняем намерение пользователя.
- **Окно без `exe_path` и без `title`** (protected process, `OpenProcess`
  отказал — window_enum.rs:264-266): ни одно правило не может его выразить.
  Чекбокс строки — **disabled** (рисуется без хит-теста, как «нельзя»).
  Окно без `exe_path`, но с заголовком: чекбокс активен, работает через
  `title_pattern` (процесс-группа для него недоступна — нет имени; окно
  попадает в группу «процесс неизвестен», см. §3).
- **Окно без заголовка, с `exe_path`**: работает через процесс-правило
  (строка отмечена, если процесс отмечен); индивидуальный чекбокс окна
  (title-правило) — disabled, т.к. пустой заголовок не матчится ничем
  осмысленным.
- **`never_overlap_taskbar`** (SPEC 4.3): панель задач — окно, которое даже в
  allow-list принудительно остаётся окклюдером (occluders.rs:53-55, 288-297).
  **Открытый вопрос** (§7.8): показывать ли `Shell_TrayWnd` в списке (SPEC 4.3
  «обычное окно и участвует в списке»), и что означает её чекбокс, раз правило
  всё равно не сработает.

## 3. Группировка по процессам

**Решение: группировочный ключ — короткое имя `exe_path` (file_name), не pid.**

Обоснование — дословно SPEC 4.2: «Чекбокс на уровне процесса выбирает все его
окна **и все будущие окна** этого процесса». Pid — сессионный: рестарт
приложения даёт новый pid, и «будущие окна» по pid не набрать. `exe_path`
(полный путь) переживает рестарты и совпадает с тем, что матчит
`rule_matches`/`path_eq_ignore_case` (occluders.rs:84-90 — матчит и полный
путь, и короткое имя). Короткое имя выбрано потому, что
`OverlapRule::process_name` в модели — короткое имя (CONFIG.md), а
`path_eq_ignore_case` умеет и то и то.

- **Два pid с одним `exe_path`** (несколько экземпляров одного приложения):
  одна группа, один чекбокс (SPEC: «все его окна» — приложение, не инстанс).
  Случай «два РАЗНЫХ приложения с одним путём» (path-коллизия, переустановка)
  неразличим моделью — принимаем как есть: одна группа.
- **Пустой `exe_path`** (protected process): отдельная группа
  «процесс неизвестен» в конце списка; процесс-чекбокса у неё нет
  (нечего записать в `process_name`), только строки окон с title-правилами.
- **Порядок групп**: по имени процесса, алфавитно (стабильно; z-order меняется
  от жизни окон, имена — нет). Внутри группы — по `z_order` окна (как в
  Alt+Tab). Заголовок группы — имя exe + количество окон (текстом — но см.
  проблему шрифта §7.2).

**Открытый вопрос (§7.6)**: строки окон внутри группы — зачем они, если
процесс-чекбокс выбирает всё? Две роли: (а) показать, какие окна процесса
есть; (б) выборочно снять ОДНО окно из процесса (SPEC: «Для каждой строки…
чекбокс» — окно-уровень существует). Если (б) — то «выбрать все окна
процесса» через процесс-чекбокс и «выбрать все будущие» конфликтуют с
window-level title-правилами (окно процесса без title-правила в allow-list
всё равно матчится процесс-правилом). Разрешение: чекбокс окна внутри
отмеченного процесса показывает «снят» только если для него есть явное
решение «не выбирать» — но модель не умеет «исключить» из процесса.
**Рекомендация**: v1 — окно-чекбокс в отмеченной группе отображается
отмеченным и некликабельным-на-снятие (выбор на уровне процесса); снятие
возможно только через снятие процесса целиком. Это урезание SPEC «Для каждой
строки: … чекбокс» — зафиксировать в ROADMAP как осознанный лимит,
альтернативы — в §7.6.

## 4. «Выбрать все» — дословная семантика SPEC

SPEC.md §4.2 (строки 209-211), дословно:

> Наверху панели — кнопка **«Выбрать все»**, работающая как переключатель:
> - если выбрано **не всё** → выбрать всё
> - если выбрано **всё** → снять выделение полностью

«Выбрано всё» = **все чекбоксы строк** (окон), т.е. состояние, в котором
любое окно снимка матчится правилом (через процесс или title). Реализация
через пересборку из `rules` (§2.1) тривиальна: посчитать `all_checked` по
снимку, инвертировать:

- `all_checked == false` → построить полный набор правил: на каждую непустую
  группу процессов — `process_name`-правило; на окна из группы «процесс
  неизвестен» — `title_pattern`-правила (по одному на окно);
  `mode = OverlapAllowlist` (если был `Always`).
- `all_checked == true` → `rules.clear()` (и `mode` не трогаем, см. §2.3).

Кнопка — обычный `Button::Label` в шапке панели; состояние «всё выбрано»
отображается внешним видом кнопки (вариант переключателя — как `BTN_TOGGLE_ALL`
в cursor_panel.rs:66-70, где иконка зависит от состояния).

## 5. Живые обновления: что добавить в `Windows(Changed)`

Сейчас ветка `OverlayMessage::Windows(TrackerWindowEvent::Changed(windows))`
(overlay_manager.rs:1550-1559) делает:

```text
window_snapshot = windows;
occluder_cache = refresh_occlusion(&cfg, &monitor_bounds, &window_snapshot);
need_redraw = true;
```

**Дополнительно, когда панель открыта**: снимок в `WindowPickerState` устарел —
панель собрана из старого снимка. Нужно:

```text
if let Some(picker) = &mut edit.window_picker {
    picker.snapshot = windows.clone();      // новый снимок
    picker.panel = build_picker_panel(...); // пересборка (дёшева, ~30 окон)
    // scroll: кламп к новой длине списка
}
```

`need_redraw = true` уже стоит — пересобранная панель отрисуется в этом же
кадре. Точка вставки — конец ветки, до выхода из match. Это покрывает «панель
обновляется в реальном времени при появлении и закрытии окон» (SPEC 4.2) без
изменения трекера: он и так шлёт полный снимок на SHOW/HIDE/DESTROY
(window_tracker.rs:532-538).

**Два подводных камня, обязательных к фиксации в задаче реализации:**

1. **Гейт хуков трекера (ADR-005)**: хуки стоят только когда
   `mask_needed(&cfg)` (overlay_manager.rs:2317-2321, 1564-1570) — т.е. когда
   хоть у одного стикера `mode != Always`. Если у пользователя **все** стикеры
   `Always` (по умолчанию!), а он открыл панель выбора — трекер спит, снимок
   пуст и живым не станет. Решение: пока `edit.window_picker.is_some()`, гейт
   принудительно держать включённым: `mask_needed(&cfg) || picker_open` (одна
   строка в месте пересчёта гейта, 1564-1570). Закрытие панели возвращает гейт
   к прежнему значению — идемпотентно.
2. **Снимок на момент открытия**: `handle_toolbar_up` (2732-2841) не видит
   `window_snapshot` — это локальная переменная `run()` (972). Открытие панели
   происходит в `handle_toolbar_up` по клику `TB_LAYERS`. Варианты: (а)
   пробросить `&window_snapshot` параметром в `handle_toolbar_up` (там уже ~10
   параметров — некрасиво, но честно); (б) открывать панель не в
   `handle_toolbar_up`, а флагом, который обрабатывает `run()` при следующем
   проходе цикла, где снимок в руках. Рекомендация: (б) — флаг
   `pending_open_picker: bool` в EditState (или `Option<Uuid>`), обработка в
   цикле `run()` рядом с веткой Windows — минимум пламбинга, снимок свежий.

Известный остаточный пробел (не этого среза): `EVENT_OBJECT_NAMECHANGE`
(смена заголовка) в трекере не подписан (M4_WINDOW_TRACKER_DESIGN.md:136) —
заголовки в панели могут быть на шаг позади до следующего полного
перечисления; title-правила после смены заголовка перестают матчить
(M4_PREP_NOTES §6). Зафиксировать в ROADMAP.

## 6. Иконки окон — зависимость, не решать здесь

SPEC 4.2: «Для каждой строки: иконка приложения…». `WindowInfo.icon` —
`Option<WindowIcon>` с `width/height/rgba`, но собиратель всегда ставит `None`
(window_enum.rs:81-82); в документации типа — «Заполняется отдельным срезом
(`ExtractIconExW`/`SHGetFileInfoW`)» (window_enum.rs:47-54). Это
**предсуществующий известный пробел**, и его закрытие — отдельная задача
(получение иконки по `pid`/`exe_path`, кэш, размер для DIP-масштаба).

Для панели: v1 рисует placeholder (пустой квадрат в тоне `theme::BUTTON_BG`
или `Icon::Layers` как «приложение»). Дизайн панели должен предусмотреть
колонку иконки слева (фиксированная ширина, квадрат `theme::BUTTON_SIZE`),
чтобы срез иконок потом заполнил её без перевёрстки. Инфраструктурно иконка
окна — это динамическая RGBA-текстура, а `Primitive::Icon` завязан на enum
`Icon` из assets (widgets.rs:45-78) — понадобится либо новый примитив
(например, `Primitive::Rgba { rect, rgba_key }`), либо проброс готовой
`Texture` в слой отрисовки панели (спрайты панели строятся в `redraw` — см.
`primitives_to_sprites`, 3836-3865). Отметить в задаче среза иконок, не
проектировать здесь.

## 7. План реализации (по шагам) и открытые вопросы

### 7.1 Порядок работ (для следующего исполнителя)

1. **Шрифт** (блокер, см. 7.2): расширить GLYPHS до латиницы+кириллицы (или
   подключить DirectWrite-атлас). Без этого панель нечитаема — шаг ДО всего
   остального.
2. **rst-render**: новый виджет `Checkbox` (квадрат + галочка, состояние,
   `take_changed` — по образцу `Button::take_click`; не Label-кнопка — глифов
   «☐»/«☑» в шрифте нет, рисуем примитивами `Fill`). Признак disabled
   (без хит-теста).
3. **rst-render**: скролл для панели — либо `Panel` получает опциональный
   сдвиг содержимого и клип, либо панель выбора строит только видимый срез
   строк по `scroll` (рекомендация: срез строк в билдере — проще и не трогает
   `Panel`, хит-тест автоматически честен). Кнопки-стрелки ▲/▼ (новые
   варианты `Icon` или `Button::Label` «^»/«v» — глифы в шрифте есть? нет;
   новые иконки `Icon::ScrollUp`/`ScrollDown` в icons.rs) либо колесо мыши
   (см. 7.4).
4. **rst-core**: `pub`-экспорт предиката совпадения окна с правилом
   (§2.1). Юнит-тесты round-trip «правила → чекбоксы → правила» и режимов.
5. **resticker**: `window_picker.rs` — `WindowPickerState`, билдер панели
   (группировка §3, чекбоксы §2, шапка с «Выбрать все» §4, скролл §7.3),
   обработка кликов (мутация `cfg` через стандартный путь §1). Юнит-тесты
   билдера (как у toolbar.rs/cursor_panel.rs).
6. **resticker/toolbar.rs**: кнопка «Слои видимости» — `Icon::Layers`, новый
   `TB_LAYERS` (ид 8), по SPEC 3.6 порядок: слайдер, поле, «Слои видимости»,
   глаз, порядок, дубликат, удалить. Обновить константы ширины
   (`TOOLBAR_WIDTH`, `TOOLBAR_WIDTH_MULTI`) и тесты.
7. **overlay_manager.rs**: поле `window_picker` в EditState; обработка клика
   `TB_LAYERS` (открыть/закрыть, флаг §5.2); ветка `PointerOwner::WindowPicker`
   в `handle_input`/`handle_key`; `Esc`; пересборка панели в ветке
   `Windows(Changed)` (§5); гейт трекера `|| picker_open` (§5.1); отрисовка в
   `redraw` (§1); закрытие панели при выходе из режима редактирования
   (в `toggle_edit_mode`, как `edit.confirm = None` — 1654).
8. **Тесты**: билдер (группировка, порядок, disabled-строки), round-trip
   правил, «выбрать все» инверсия, гейт трекера с открытой панелью,
   пересборка на `Windows(Changed)`.
9. **Ручной QA**: открыть панель при всех `Always`-стикерах (трекер спит —
   панель будит его); открыть/закрыть окно при открытой панели (строка
   появляется/исчезает); смена заголовка (известный лаг, §5).

### 7.2 Шрифт — главный блокер

`text.rs:11-15`: глифы — только цифры, `%`, `.`, `+`, `-`, пробел; «для
русских подписей панели 3.8 шрифт придётся дополнить кириллицей либо заменить
на DirectWrite». Панель выбора без букв нечитаема: заголовки окон и имена
процессов — это буквы, часто кириллица (пользователь должен отличать окна друг
от друга). Два пути:

- расширить таблицу GLYPHS (8×8 битмапы вручную: латиница ~52 + кириллица
  ~66 — заметный, но конечный труд; кэш текстур уже есть);
- DirectWrite-атлас (в M2-задаче был допустимым вариантом; сейчас выбран
  битовый шрифт — text.rs:1-9: «DirectWrite не используется»).

Это решение **должно** быть принято человеком ДО старта реализации панели —
без него шаги 2-9 бессмысленны. Рекомендация: начать с расширения GLYPHS
(минимум изменений, существующий пайплайн), DirectWrite — отдельной вехой,
если понадобятся другие строки с произвольным текстом.

### 7.3 Чекбокс как виджет

Отдельный `Checkbox` в rst-render (состояние + `take_changed`), потому что
(а) шрифт не имеет глифов «☐»/«☑» — рисуем рамку и галочку `Fill`-примитивами;
(б) `Button::Label` несёт текст, а текст панели — шрифтовая проблема 7.2;
(в) disabled-состояние не выразить существующими виджетами. Хит-тест и
`pointer_event` — как у `Button` (armed/clicked), состояние хранится в виджете,
ядро забирает изменения `take_changed` и пишет их в `cfg`.

### 7.4 Скролл

Рекомендация: виртуализация строк в билдере — билдер получает `scroll` и
строит только строки, попадающие в окно панели; хит-тест автоматически честен,
`Panel` не трогаем. Управление: кнопки-стрелки ▲/▼ (новые `Icon` в icons.rs)
и/или колесо мыши — **в `InputEvent` колеса нет** (input.rs:64-78: только
Down/Move/Up/CaptureLost), т.е. колесо = отдельный мини-срез rst-win32
(`WM_MOUSEWHEEL` → новое событие → `handle_input`). v1: кнопки-стрелки; колесо
— если станет нужным, отдельным срезом.

### 7.5 «Конкретное окно» — HWND не выразим моделью (главный джуджмент-колл)

SPEC 4.1 обещает цель «конкретное окно (по HWND в текущей сессии)»; модель
`OverlapRule` имеет только `process_name`/`title_pattern`. Отображение «окно →
точный title_pattern» хрупко: заголовок меняется (браузер: вкладка/URL; документ
с названием) — правило тихо перестаёт матчить, стикер начинает прятаться.
Варианты для решения человеком:

1. Принять title-приближение и задокументировать (v1, рекомендация).
2. Расширить модель: `OverlapRule { hwnd: Option<u32>, .. }` (сессионный,
   не переживает рестарт — против духа SPEC «восстановление между запусками»).
3. Считать window-уровневые чекбоксы чисто отображательными (см. 7.6) — и
   тогда проблема title-правил отпадает: выбор всегда на уровне процесса.

### 7.6 Окно-чекбокс внутри отмеченного процесса

«Снять одно окно из выбранного процесса» моделью не выразить (нет
«исключения»). Варианты: (а) v1 — окно-чекбоксы показывают состояние
процесса, не кликабельны на снятие; (б) окно-чекбокс = title-правило (7.5.1) —
и «будущие окна процесса» уже не все выбраны (новое окно с другим заголовком
не матчится); (в) долой окно-чекбоксы, только процессы (урезание буквы SPEC).
Рекомендация: (а) + зафиксировать лимит в ROADMAP.

### 7.7 Модальность панели

Модал подтверждения блокирует всю сцену (3026-3033). Панель выбора — рабочий
инструмент; рекомендация: не блокировать сцену, клик мимо панели её не
закрывает (иначе «выбрать окно, потом подвинуть стикер» требует повторного
открытия). Клик по кнопке «Слои видимости» и `Esc` — закрытие. Требует
решения человека: закрывать ли панель кликом мимо (как комбо-дропдауны) —
если да, то клик мимо должен НЕ уходить в сцену.

### 7.8 Панель задач в списке

SPEC 4.3: `Shell_TrayWnd` «обычное окно и участвует в списке». При
`never_overlap_taskbar = true` (по умолчанию?) её чекбокс ничего не даст —
окно останется окклюдером (occluders.rs:53-55). Варианты: показывать строку
без чекбокса (метка «панель задач»), показывать чекбокс disabled, или
показывать и чекбокс, и подпись «всегда перекрывает» при включённой настройке.
Рекомендация: показывать строку с disabled-чекбоксом, когда
`never_overlap_taskbar` включён (честно: правило не применимо), с активным
чекбоксом, когда выключен.

# M3 — ревью обработки блокировки сессии и сна (SPEC.md §9)

Статус: **независимое ревью, без изменений кода**. Ветка `feat/m2-edit-mode`, коммит
`46cd101` (координатор: ветки `SessionLocked`/`SessionUnlocked`/`SystemSuspending`/
`SystemResumed` + helper `reenumerate_monitors`; overlay_manager.rs +42). Прочитаны
дифф коммита целиком и актуальные файлы: `crates/resticker/src/overlay_manager.rs`
(3805 строк — включая полный hot-plug диффинг `MonitorsChanged`, `Tick`, автомат
ADR-011), `SPEC.md` §9, `docs/M3_HOTPLUG_DESIGN.md` §7 (открытые вопросы), а также
предыдущие ревью (`M3_DEVICE_RECOVERY_REVIEW.md`, `M3_STEP5_6_REVIEW.md`,
`M3_STEP8_REVIEW.md`), на которые код ссылается. Сверено поведение с событийной
моделью цикла (ADR-006) и каналами. Живого сна/блокировки нет (автор: smoke-запуск
и compile-time проверки; сценарии сна не воспроизводились).

**Общий вердикт:** коммит корректно закрывает SPEC.md §9 существующей машинерией и
реализует ровно ту страховку, которую M3_HOTPLUG_DESIGN.md §7 (стр. 503-506) называл
желательной: на `SessionUnlocked`/`SystemResumed` — повторное перечисление мониторов
тем же путём, что и настоящий `WM_DISPLAYCHANGE` (постинг в общий канал → обработка
на следующей итерации, без реентрантности), на `SystemResumed` — принудительный
`need_redraw`, гарантирующий немедленную попытку `present` и, при потере устройства,
срабатывание `recover_device`. `SessionLocked`/`SystemSuspending` — no-op, что
соответствует SPEC: экран блокировки скрывает окна сессии сам, пауза декодера — M5.
Проблем, ломающих поведение, не найдено; есть четыре замечания низкой тяжести:
N-кратное дублирование событий при N окнах (идемпотентно, но лишняя работа), семантика
20-секундного таймера ADR-011 через сон (отсчёт стартует с пробуждения, а не с
момента фактического отключения монитора), отсутствие ретраев при неудачном
восстановлении устройства сразу после пробуждения, и порядок «redraw по старой
топологии до обработки переперечисления». Подробности — ниже.

## 1. Проверено по ключевым вопросам

### 1.1 `reenumerate_monitors` — без реентрантности, идемпотентно, с правильным тегом

- **Механика:** helper (2154-2164) зовёт `monitors::enumerate()` синхронно и постит
  `OverlayMessage::Event(primary_id.clone(), MonitorsChanged(infos))` в `tx` — тот же
  канал, что читает цикл `run()`. Канал — `mpsc::channel` (безграничный, 433), постинг
  из того же потока не блокирует — **дедлока нет**, сообщение обрабатывается на
  следующей итерации `match`, т.е. без рекурсии в текущий кадр. Комментарий в коде
  описывает ровно это.
- **Тег монитора** (`primary_id`) веткой `MonitorsChanged` игнорируется (`_`,
  1102) — значение не важно; внутри диффа `new_primary_id` вычисляется заново из
  снапшота (1117-1122) и на шаге 6 присваивается локальной `primary_id` (1327) —
  последующие `reenumerate_monitors` используют уже новый primary. Замкнуто.
- **Пустой снапшот** от `enumerate()` отклоняется в ветке `MonitorsChanged`
  (1109-1114, `continue`) — отправка пустого списка безопасна. Ошибка перечисления —
  warn-лог без события (2162-2163) — деградация без последствий (следующий триггер
  повторит).
- **Полный путь диффа:** постинг идёт в ту же ветку, что и `WM_DISPLAYCHANGE` —
  снос/создание окон, миграция primary и хоткея (шаг 1, 1131-1172), автомат потери
  монитора (шаг 5, 1317-1325) — всё это переиспользуется без дублирования логики.

### 1.2 `SessionLocked`/`SystemSuspending` — no-op корректен

- SPEC §9: «на экране блокировки стикеры не отображаются (обеспечивается ОС — оверлеи
  принадлежат сессии пользователя)» — блокировка скрывает окна сессии, включая
  TOPMOST-оверлеи, на secure desktop; кода не требуется. Хоткеи на secure desktop не
  срабатывают — тоже забота ОС.
- Пауза декодирования видео/звука (SPEC «ДОЛЖНА») — честно отложена до M5: декодера
  нет (ROADMAP M5), приостанавливать нечего. Зафиксировано в комментарии и ROADMAP.
- `SystemSuspending` — ничего не делает; потеря устройства обрабатывается на
  пробуждении (см. 1.3), состояние сохраняется самой моделью (cfg на диске).

### 1.3 `SystemResumed` — принудительный redraw доставляет потерю устройства в `recover_device`

- `need_redraw = true` (1377) → в конце той же итерации срабатывает
  `if need_redraw && redraw_all(...) && recover_device(...) { redraw_all(...) }` —
  немедленная попытка `present`; если устройство потеряно во сне (адаптер
  перезапустился — типичный случай), `redraw_all` возвращает `DeviceLost`,
  `recover_device` пересоздаёт устройство/цели/текстуры, повторный `redraw_all`
  рисует. Ровно то, что требует SPEC §9 («переинициализация ресурсов D3D»), и то,
  что ревью M3_DEVICE_RECOVERY_REVIEW.md называл «ленивым» — здесь попытка
  гарантирована, а не отложена до несвязанного события.
- Если устройство НЕ потеряно (сон без перезапуска адаптера) — redraw_all просто
  рисует кадр: лишней перезаливки нет.

### 1.4 Перекрытие с hot-plug машинерией — идемпотентность уже заложена

- Ветка `MonitorsChanged` документированно идемпотентна к дубликатам
  (1104-1108): «WM_DISPLAYCHANGE рассылается КАЖДОМУ живому окну, на одну смену
  топологии приходит N одинаковых событий» — дифф против живого `monitors_map`.
  Постинг `reenumerate_monitors` — тот же класс событий, та же защита.
- Автомат потери монитора (`loss_tracker.on_monitor_snapshot(..., Instant::now())`,
  1319) при N подряд идущих одинаковых снапшотах (миллисекунды между ними) —
  идемпотентен: таймеры сравниваются с одинаковым `now`, сроки не истекают между
  дубликатами — двойной миграции нет.

## 2. Найденные замечания (все низкой тяжести)

### 2.1 N-кратное дублирование: каждое окно шлёт свои `SessionUnlocked`/`SystemResumed`

- **Где:** каждое окно регистрируется на сессионные уведомления
  (`WTSRegisterSessionNotification`, overlay.rs) и получает `WM_POWERBROADCAST`; с N
  окнами на одно системное событие в канал приходят **N** `SessionUnlocked` и **N**
  `SystemResumed` → **N** синхронных `monitors::enumerate()` + **N** постингов
  `MonitorsChanged` + **N** полных диффов и **N** `need_redraw` (каждый из которых
  гонит полную `redraw_all`).
- **Что:** корректности не ломает (идемпотентность §1.4), но на пробуждении
  выполняется N× лишней работы: перечисление, диффинг, полный редрав всех мониторов.
  При 2-4 мониторах — миллисекунды, незаметно.
- **Фикс (опционально):** обрабатывать только первый из пачки (например, не
  постинговать, если последний `reenumerate_monitors` был < 1-2 с назад, или
  игнорировать `SystemResumed`, если в очереди уже есть `MonitorsChanged`).

### 2.2 20-секундный таймер ADR-011 через сон: отсчёт стартует с пробуждения

- **Где:** автомат потери монитора тикает только в бодрствующем цикле (`Tick`,
  1337-1350); `Instant::now()` на Windows монотонен и **не движется во сне**.
- **Что:** монитор, отключённый во время сна, будет замечен первым снапшотом после
  пробуждения (2.1-постинг), и 20-секундный таймер миграции начнётся **с момента
  пробуждения**, а не с момента фактического отключения; время сна в отсчёт не идёт.
  Это врождённо событийной модели (приложение во сне не исполняется) — не баг, но
  поведение стоит зафиксировать в комментарии к автомату: «20 секунд» — это 20
  секунд бодрствования после первого снапшота, где монитор уже отсутствует.

### 2.3 Неудачное восстановление сразу после пробуждения не ретраится

- **Где:** `SystemResumed` гарантирует **одну** попытку `redraw_all`; если
  `recover_device` провалится (адаптер ещё «оседает» после выхода из сна —
  `Device::new()` может не создаться с первого раза), повторная попытка произойдёт
  только на следующем redraw-событии, которого может не быть (hover-движения без
  изменений `need_redraw` не выставляют) — оверлей останется чёрным до первого
  реального триггера.
- **Фикс (опционально):** после `SystemResumed` при провале `recover_device`
  запланировать 2-3 повторные попытки с короткой задержкой (или расширить уже
  существующий `Tick`-механизм: держать флаг «нужно восстановление», пока он не
  сработает). Расширение замечания «ленивое восстановление» из
  M3_DEVICE_RECOVERY_REVIEW.md.

### 2.4 Порядок: redraw по старой топологии до обработки переперечисления

- **Где:** `SystemResumed` выставляет `need_redraw` в текущей итерации, а постинг
  `MonitorsChanged` обрабатывается только на следующей. Если во сне сменилась
  топология (монитор отключён), текущая итерация рисует кадр по старому
  `monitors_map` — включая окно отключённого монитора. Безвредно: либо `Present`
  этой цели вернёт ошибку/устройство потеряно (пойдёт по recovery-пути), либо кадр
  просто не будет показан (окно на отключённом дисплее); следующий дифф снесёт окно
  и перерисует. Замечание-фиксация, а не проблема.

### 2.5 (примечание) Активный жест, переживший сон

- Если сон начался во время жеста (драга), `EditState.gesture`/`pointer_owner`
  переживают сон; судьба захвата мыши после пробуждения решается ОС
  (обычно `WM_CAPTURECHANGED` → `CaptureLost` → откат жеста). Отдельной обработки
  в коммите нет — полагается на существующий путь `CaptureLost`. Стоит
  держать в голове при ручном тесте «сон посреди драга»; вне скоупа коммита.

## 3. Что проверено и корректно (не тратить время на повторную проверку)

- **Соответствие SPEC §9:** «скрытие на блокировке — ОС» ✓; «пауза декодера» —
  честно отложена до M5 (деколера нет) ✓; «восстановление в прежнем виде» —
  переперечисление + редрав + (при потере) recover_device ✓; «переинициализация D3D
  на пробуждение» — принудительный `need_redraw` ✓.
- **Реализация рекомендации M3_HOTPLUG_DESIGN.md §7** (стр. 503-506) — ровно тот
  сценарий («смена primary без WM_DISPLAYCHANGE») закрыт: переперечисление на
  `SessionUnlocked`/`SystemResumed`.
- **Нет реентрантности** (§1.1): постинг в безграничный канал, обработка на
  следующей итерации; тег монитора игнорируется; `primary_id` обновляется диффом
  до следующего постинга.
- **Идемпотентность дубликатов** (§1.4): дифф против живого состояния + автомат с
  одинаковым `now`.
- **Миграция primary и хоткея при смене во время блокировки/сна** — через шаг 1
  диффа (снос/пересоздание окна-владельца хоткея) — переиспользовано, не
  дублировано.
- **`SessionUnlocked` без `need_redraw`** — правильно: если дифф ничего не изменил,
  редрав не нужен; если изменил — дифф сам выставит.
- **Ошибки перечисления** — warn-лог, событие не постится, состояние не трогается.

## 4. Приоритеты для координатора

1. **§2.1** — дедупликация пачки `SessionUnlocked`/`SystemResumed` при N окнах
   (опционально; сегодня только лишняя работа).
2. **§2.3** — ретраи `recover_device` после пробуждения (чёрный экран при
   «оседающем» адаптере до первого триггера) — самое заметное из замечаний.
3. **§2.2/§2.4/§2.5** — задокументировать семантику таймера через сон, порядок
   redraw-до-диффа и судьбу жеста через сон (комментарии; кода не требуют).

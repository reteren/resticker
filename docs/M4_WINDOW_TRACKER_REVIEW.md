# M4 — ревью среза: WindowTracker (инкрементальный кэш окон на WinEvent-хуках)

Статус: **независимое ревью, без изменений кода**. Ветка `feat/m2-edit-mode`,
коммит `cc1c33b` (новый `crates/rst-win32/src/window_tracker.rs` +960 строк,
`window_enum.rs` +5/−1, `error.rs` +4, `lib.rs` +1, `Cargo.toml` +1 фича;
дизайн-док `docs/M4_WINDOW_TRACKER_DESIGN.md` +294). Прочитаны дифф коммита
целиком и актуальные файлы: `window_tracker.rs` (960 строк, включая тесты),
`window_enum.rs` (415 строк), `docs/M4_WINDOW_TRACKER_DESIGN.md` (294 строки),
`docs/M4_PREP_NOTES.md` §2–3, §7–9, `crates/rst-win32/src/overlay.rs`
(эталонный паттерн «поток+pump+message-only/оверлей»). Сверено с ADR-004/005
и ARCHITECTURE.md §3.2–3.5. Проверено прогоном: `cargo clippy -p rst-win32
--all-targets -- -D warnings` — чисто; `cargo fmt --check` — чисто;
`RUST_MIN_STACK=67108864 cargo test -p rst-win32` — 85 passed, 8 ignored
(из них 4 — реальный десктоп для window_tracker, конвенция крейта).

**Общий вердикт:** срез качественный и по делу — архитектура 1-в-1 по
дизайн-доку (свой поток + message-only окно, fast path по ADR-005,
дебаунс 16 мс, заморозка на блокировке сессии, чистая фильтрация
«это сам HWND, не его часть»), код в конвенциях крейта (русские доки,
SAFETY-комментарии, юнит-тесты без окон + ignored-интеграционные).
**Живых блокеров нет — координатор (следующий срез) этот модуль ещё не
потребляет.** Найдено две проблемы средней тяжести и три-четыре замечания,
все — на границе «не сейчас, но следующий срез споткнётся»:

1. **устаревший `WM_TIMER` после `set_mask_needed(false)` может эмитить
   пустой снимок** — реальная ловушка для координатора, сейчас безвредна;
2. **семантика частичной неудачи установки хуков сломана**: если падает
   первый диапазон (а в нём SHOW/HIDE/DESTROY/LOCATIONCHANGE), кэш
   навсегда устаревает молча;
3. **ядро дебаунса (`flush_pending` + классификация колбэка) не покрыто
   юнит-тестами** — вопреки обещанию дизайн-дока §9;
4. **непрофильтрованные SHOW/HIDE дёргают полное перечисление на каждый
   тултип/дропдаун**, а полное перечисление может встать до 5 с на
   залипшем окне (`GetWindowTextW` = SendMessage в чужой поток) — риск для
   отзывчивости маски, смягчать лучше в `window_enum`, вне этого коммита;
5. **WTS-заморозка не тестируется** (ветки `frozen` в wndproc) и
   `set_mask_needed(true)` на заблокированной сессии ставит хуки и
   перечисляет вопреки духу «на блокировке не перечислять».

Подробности, со строками — ниже.

## 1. Проверено по явным вопросам задачи

### 1.1 Паттерн «поток + pump + канал» повторён правильно

`start()` → `(Self, Receiver<WindowEvent>)`, `Drop` → `WM_CLOSE` + join —
дословно паттерн `OverlayWindow` (window_tracker.rs:84–139). Message-only
окно `HWND_MESSAGE` + `WS_EX_NOACTIVATE` (:270–289) — правильный якорь для
`SetTimer`/WTS без попадания в перечисление (`is_real_window` отбраковал бы
его и так, но так честнее). `GWLP_USERDATA`-состояние + `reclaim_state`
после pump (:235–244) — тот же безопасный паттерн, что у трея; ошибка
`ready_tx.send` после `DestroyWindow` корректно освобождает состояние.
Оба новых варианта `Win32Error` — по образцу существующих. Ок.

### 1.2 Fast path (ADR-005) — идемпотентность и очистка на месте

`set_mask_needed` — `PostMessage(WM_APP_SET_MASK_NEEDED)` с потока
координатора, обработчик идемпотентен по `needed != state.mask_needed`
(:557); `true` → `install_hooks` + немедленный полный снимок (:564–565),
`false` → снять хуки, убить таймер, сбросить pending, очистить кэш
(:567–570). `install_hooks` защищён «уже установлены» (:320–322). Всё как в
дизайне §5. Хук-колбэк действительно не делает ничего, кроме классификации
+ `SetTimer` (:525–533) — требование дизайна §2 соблюдено, DWM/перечисления
только в `WM_TIMER`.

### 1.3 Дебаунс и коалесцирование — семантика верная, покрытие нет (см. §2.3)

Единственный `SetTimer(16)` на первый dirty-событие, `WM_TIMER` → kill →
`flush_pending` (:576–590). Приоритет в `flush_pending`: `needs_full`
(SHOW/HIDE) отменяет все дельты (:412–413); destroyed pre-empt'ит
minimize/location для того же hwnd (:423–425, :435–436); minimized
pre-empt'ит location, а `MINIMIZEEND` заодно перечитывает rect через DWM
(:431–432) — «быстрый minimize+restore схлопывается в no-op», как и
задумано. `refresh_rect_or_destroy` — `IsWindow`-гард против hwnd-reuse
(:449–458) — тот самый «verify» из открытых вопросов дизайна §11, сделан.
Логика верная, но целиком живёт в нетривиальном нетest'ируемом коде —
см. §2.3.

### 1.4 WINEVENT_SKIPOWNPROCESS снят — обоснованно

Дизайн §3 ставил `OUTOFCONTEXT | SKIPOWNPROCESS`; реализация сняла SKIP с
письменным обоснованием (коммит + :311–318): собственные оверлеи и так
отсекаются `is_real_window` (WS_EX_NOACTIVATE), а SKIP сделал бы трекер
принципиально нетестируемым из того же процесса. Согласен с обоими
аргументами. Единственный нюанс: будущие окна resticker без `NOACTIVATE`
(панель выбора? диалоги?) будут давать колбэки — горсть окон, накладные
расходы ничтожны, и фильтр членства в кэше всё равно их не пускает.

### 1.5 Интеграционные тесты и их вклад

`RealWindow` с собственным pump-потоком (:780–860) — правильное решение:
без него кросс-поточные `GetWindowTextW`/`DwmGetWindowAttribute` виснут на
классическом 5-секундном таймауте «зависшего окна» (это ровно тот риск,
который см. §2.4 для боевого кода). Тест полного жизненного цикла
SHOW → MoveWindow → DestroyWindow и fast-path-выключение — по дизайну §9.
`recv_until` с ограниченным поиском вместо одного `recv_timeout` — честная
работа с шумом реального десктопа. Хорошо.

### 1.6 Прочее

- `window_enum.rs`: только `pub(crate)` для `extended_frame_bounds` — точечный
  минимум для инкрементального rect (:219–222). Ок.
- `Cargo.toml`: ровно одна новая фича `Win32_UI_Accessibility` — как в
  дизайне §10. Ок.
- Модуль не подключён в `overlay_manager.rs` (сшивка — следующий срез) —
  соответствует скоупу коммита.
- `WindowEvent::Changed(Vec<WindowInfo>)` — полный снимок вместо диффа,
  решение дизайна §1 (25–30 окон, копия дёшева). Ок.

## 2. Находки

### 2.1 Устаревший `WM_TIMER` после `set_mask_needed(false)` эмитит пустой снимок (средняя)

`KillTimer` не убирает уже поставленные в очередь `WM_TIMER`-сообщения
(документированное поведение Windows). При этом `WM_TIMER` — низкий
приоритет диспетчеризации: если между армом таймера (burst
`LOCATIONCHANGE`) и его срабатыванием координатор шлёт
`set_mask_needed(false)`, `WM_APP_SET_MASK_NEEDED` обработается **раньше**
устаревшего `WM_TIMER`. Тот приходит с `mask_needed == false`, `pending`
уже сброшен, кэш очищен — и `flush_pending` (:581) с чистыми множествами
делает `state.cache.clone()` → эмитит `Changed(vec![])` (:443).

Воздействие сейчас: нулевое (координатор снимки ещё не потребляет).
В следующем срезе: координатор на мгновение увидит «нет ни одного окна» и
сбросит окклюдеры/маску — до следующего полного снимка. Редко (нужен
активный burst при выключении маски), но ловушка на ровном месте.

**Исправление** (одна строка): в ветке `WM_TIMER` после
`kill_debounce_timer` — `if !state.mask_needed { state.pending =
Pending::default(); return; }` (или тот же гард в начале `flush_pending`).
Заодно это закрывает симметричный случай: stale `WM_TIMER` после
`set_mask_needed(true)` → немедленный снимок уже ушёл из обработчика
`:564–565`, а stale-таймер потом эмитит повторный (пустой) — безвредно,
но лишний emit.

### 2.2 Частичная неудача установки хуков молча оставляет кэш мёртвым (средняя)

`install_hooks` ставит два диапазона независимо; при неудаче любого —
`warn` и `continue` (:332–340). Если упадёт **первый** диапазон
(`DESTROY..LOCATIONCHANGE`), а в нём же `SHOW`/`HIDE` — источники всех
полных перечислений! — то второй (`MINIMIZE`) встанет, трекер будет «жить»,
но кэш больше никогда не обновится: ни инкрементальных дельт (хук мёртв),
ни полных перестроек (SHOW/HIDE мёртв). Навсегда устаревший список окон,
молча. Практически `SetWinEventHook(OUTOFCONTEXT)` почти не падает, но
если уж код обрабатывает эту ветку — деградация должна быть осознанной.

**Варианты:** (а) при неудаче любого диапазона — снять все успешно
поставленные и выставить флаг «broken» с warn-логом (трекер живёт в fast
path-эквиваленте без эмиссии — честно); (б) повторить попытку на следующем
`set_mask_needed(true)`; (в) событие-ошибка наружу. Любой из трёх лучше
полурабочего состояния.

### 2.3 Ядро дебаунса не покрыто юнит-тестами — вопреки дизайн-доку (замечание)

Дизайн §9 обещал чистые предикаты: «логика дебаунса — чистый предикат
`should_emit`; фильтр колбэка — предикат `accept_event`». Реализация
вместо этого держит классификацию в `win_event_proc` (:498–520) и порядок
применения дельт в `flush_pending` (:411–444) — оба места нетривиальны и
покрыты только ignored-интеграцией (реальный десктоп). Приоритеты
destroyed > minimized > location и «needs_full отменяет дельты» — ровно та
логика, где живут регрессии, и она бесплатна к тестированию.

**Предложение** (для следующего ревью-цикла, не обязательное в этом
коммите): вынести (а) классификацию события → чистая функция
`fn classify_event(event: u32, target: usize, in_cache: bool) ->
Option<PendingOp>` (`PendingOp::Full | Destroyed | Minimized(bool) |
Location`), (б) применение дельт → чистая функция над
`(&mut Vec<WindowInfo>, Pending)`. Тогда табличные тесты «DESTROY +
MINIMIZEEND одного окна в одном окне дебаунса → удалено, не минимизировано»
пишутся без окон, как и `apply_*`.

### 2.4 Полное перечисление на каждый SHOW/HIDE: тултипы и 5-секундный сталл (замечание, смягчать в window_enum)

`SHOW`/`HIDE` не фильтруются членством в кэше (:499–501) — по дизайну
(фильтр был обещан только для `LOCATIONCHANGE`), но следствие: любой
транзиентный top-level (тултип `tooltips_class32`, дропдаун, меню) — это
`needs_full`, т.е. полное перечисление. Полное перечисление, в свою
очередь, делает на каждое окно `GetWindowTextW` (= `SendMessage` в чужой
поток, `window_enum.rs:243–254`) и `OpenProcess` (:277). Одно залипшее
окно в z-order → трекер-поток (а с ним дебаунс и вся эмиссия) встаёт на
классические ~5 с — в худшем случае маска застывает на 5 с при активном
перетаскивании чужого окна.

Смягчение — вне этого коммита, но зафиксировать здесь: в `window_enum`
`window_text` перевести на `SendMessageTimeoutW(..., SMTO_ABORTIFHUNG, ~100
мс)` (титул всё равно панели, не маске — нулевая потеря), либо в трекере
фильтровать `SHOW/HIDE` по дешёвой проверке в `flush` (окно живо и
видимо?) до решения о полном перечислении. Отдельно: тултипы проходят
`is_real_window` целиком (top-level + visible, без NOACTIVATE/TOOLWINDOW) —
они будут и в кэше, и (в следующем срезе) в маске как транзиентные
окклюдеры; это к маске, не к трекеру, но ожидаемо.

### 2.5 WTS-заморозка: ветки не тестируются, `set_mask_needed(true)` игнорирует frozen (замечание)

- `session_change_action` (чистый разбор) покрыта, но ветки wndproc
  (:591–608) — `frozen = true` (дроп накопленного, без эмиссии) и
  `frozen = false` (rebuild + emit) — не покрыты никак. Дёшевый тест:
  постинг `WM_WTSSESSION_CHANGE` прямо на hwnd трекера (окно существует —
  пост доступен из теста; окно не реальное, но для прямого PostMessage это
  неважно). Плюс вопрос к реальному железу: доставляет ли WTS
  `WM_WTSSESSION_CHANGE` на `HWND_MESSAGE`-окно — регистрация идёт на
  конкретный hwnd и доставка прямым сообщением, так что должна, но ни
  один тест (даже ignored) этого не проверяет. В QA-чеке
  блокировки сессии с активной маской добавить.
- `WM_APP_SET_MASK_NEEDED` при `frozen == true` ставит хуки и делает
  полное перечисление с заблокированной сессии (:559–565) — ровно то,
  что §2.5/дизайн §7 называет «дорого и бессмысленно». Край (координатор
  вряд ли дёрнет маску под блокировкой), но гард в одну строку
  (`if !state.frozen { rebuild... }` с эмиссией «догоню на разморозке»)
  снял бы вопрос.

### 2.6 Мелочи

- **z_order устаревает в инкрементальном режиме**: удаления/минимизации не
  сдвигают z_order соседей, вставок (кроме полных перечислений) нет.
  Для маски неважно (ADR-004 §4.7), для панели — важно; дизайн §8 это уже
  отложил в panel-режим. Не баг, зафиксировать.
- **Коммит-месседж «steps 1–3» неточен**: процесс-кэш `pid → exe_path`
  из дизайна §4/§10-шаг-3 не реализован (полное перечисление продолжает
  делать `OpenProcess` на каждое окно). Пропуск легитимен — это открытый
  вопрос дизайна §11 («по замерам доли промахов»), но формулировка
  переоценивает сделанное; при подключении маски измерить частоту полных
  перечислений и решить.
- **`state.pending = Pending::default()` в конце `flush_pending`** (:442) —
  избыточен (все множества уже `mem::take`-нуты), но безвреден.
- **O(n) поиск по кэшу в колбэке на каждый `LOCATIONCHANGE`** (:514) —
  25–30 элементов, ок; не менять.
- **`WindowTrackerHookFailed` из дизайна §1** не добавлен — выбрана ветка
  «warn + жить без хуков», дизайн допускал обе; см. §2.2 про осознанность
  деградации.

## 4. Вердикт

Срез готов к сшивке. Архитектура, стиль и тестовый вклад — на уровне
прошлых M3-срезов; обещание «колбэк хука ничего не делает, кроме
SetTimer» выполнено буквально, и это главное свойство ADR-005. Блокеров
нет; перед подключением координатора закрыть пункты §2.1 (одна строка),
§2.2 (семантика деградации хуков) и — по желанию — §2.3 (вынести
классификацию/flush в чистые функции для тестов). §2.4 решается в
`window_enum` и рекомендован к включению в срез маски.

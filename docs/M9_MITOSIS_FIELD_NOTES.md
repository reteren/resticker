## 3. Пробы на второй экземпляр

### 3.1 notepad.exe (Win11)

| Параметр | Значение |

| Новое окно появилось | **через 329 мс** |
| pid нового окна | **11104** (НЕ равен дочернему 1788) |
| Новое окно == дочерний pid? | Нет |
| Дочерний процесс жив после +300 мс? | Нет, вышел (ExitCode 0) |
| exe нового окна | Notepad.exe (UWP: Microsoft.WindowsNotepad_11.2606.15.0) |

Вывод: на Win11 `notepad.exe` — тонкий стаб. Запущенный нами процесс
(1788) сразу выходит, а настоящее окно создаётся в ОТДЕЛЬНОМ UWP-процессе
(11104), который живёт дальше. Поиск нового окна по pid запущенного
дочернего процесса НЕ сработает — нужна ветка по exe/пути.

Команда: `Start-Process -FilePath notepad.exe -PassThru`; поллинг
`EnumWindows` каждые 20 мс до появления нового окна с этим exe; таймер
Stopwatch; WM_CLOSE для закрытия; остаток закрыт `Stop-Process -Id 11104`
(процесс, созданный пробой). [MEASURED]

Вывод (важно, опровергает допущение дизайна): Проводник здесь НЕ открыл
новое окно в уже живущем процессе (8828), а запустил НОВЫЙ процесс
explorer.exe (41248), который живёт и держит новое окно. Запущенный нами
дочерний 31588 при этом вышел. То есть и для проводника, и для notepad
наблюдается одинаковая картина: дочерний процесс-посредник умирает, а
новое окно появляется в отдельном процессе с тем же exe. Поиск нового окна
по одному pid (дочернему) не работает; по живому shell pid (8828) тоже не
работает. Единственный надёжный признак — НОВЫЙ pid с совпадающим exe-путём.
Отличие от гипотезы в M9_WINDOW_MITOSIS_DESIGN.md п.4.2 (ветка «Проводник
открывает окно в уже живущем процессе») на этой машине НЕ подтвердилось.

Команда: как в 3.1, но exe=explorer.exe. Созданный пробой процесс 41248
закрыт `Stop-Process -Id 41248 -Force`; shell 8828 не трогался. [MEASURED]

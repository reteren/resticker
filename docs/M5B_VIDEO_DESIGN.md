# M5b — видео (FFmpeg, программный декод): дизайн

Статус: в работе, 2026-08-05, дневная сессия с пользователем на связи (в
отличие от M5a — здесь решения по продукту приняты в разговоре, не
предположены). Пишется по тому же шаблону, что `M5A_ANIMATION_DESIGN.md`.

## 0. Что реально нужно (сузили в разговоре)

Пользователь явно сформулировал минимум: **мотать (seek), играть/пауза,
громкость.** Ничего про прозрачное видео, HDR, множественные аудиодорожки
или точную профессиональную A/V-синхронизацию не просилось — это НЕ
уменьшенная версия ROADMAP M5b, это осознанно урезанный скоуп под
конкретную задачу. Ключевые решения этого разговора:

1. **FFmpeg собирается из исходников**, LGPL-only (`--disable-gpl
   --disable-nonfree`), тулчейн — MSYS2/mingw-w64 (в системе не было ни
   компилятора, ни `make`, ни `pacman` — ничего; MSYS2 разворачивается в
   `W:\msys64`, вне репозитория).
2. **Только программный декод в этом срезе.** Аппаратный (`d3d11va`,
   zero-copy `ID3D11Texture2D`) — ROADMAP M5c, отдельная веха ПОСЛЕ этой.
   CPU-цена программного декода принята осознанно (SPEC.md §13: одно видео
   1080p30 программным декодом — до ~8% CPU; для одного стикера-видео это
   приемлемо).
3. **Видео с альфа-каналом декодируется КАК ОБЫЧНОЕ, непрозрачное видео.**
   Осознанное решение пользователя: не пытаться доставать/использовать
   отдельный альфа-поток вообще — ни программной, ни гибридной
   (цвет-аппаратно/альфа-программно) обработки. Каждый видеофайл идёт по
   ОДНОМУ универсальному быстрому пути; там, где была бы прозрачность,
   остаётся то, что реально лежит в цветовых плоскостях исходника (для
   WebM VP9 c альфа-потоком это на практике чаще всего чёрный — цветовой
   трек таких файлов обычно уже закомпонован на чёрном для плееров без
   поддержки альфы; для ProRes4444/qtrle гарантий нет, но пользователь
   явно принял этот риск как «на крайняк сойдёт», лишь бы файл не
   отказывался открываться). Убирает целый пласт сложности из скоупа
   насовсем (не только из этого среза) — SPEC.md §7.2 (прозрачное видео)
   этим срезом сознательно не реализуется и не имеет смысла реализовывать
   позже, раз продукту это не нужно.
4. **Звук — часть ЭТОГО среза, не отдельная веха M5d.** Пользователь назвал
   громкость одним из трёх обязательных пунктов — без звука регулировать
   нечего. `cpal` (как и было заложено в ARCHITECTURE.md/ROADMAP M5d) —
   решение принято сейчас, не отложено.

## 1. Сборка FFmpeg (делаю сам, не воркеры)

- Тулчейн: MSYS2 в `W:\msys64` (вне репо), пакеты
  `mingw-w64-x86_64-gcc`/`nasm`/`pkgconf`/`make`/`diffutils`.
- Конфигурация (примерно, уточняется по ходу):
  ```
  ./configure --toolchain=... --disable-gpl --disable-nonfree \
    --disable-programs --disable-doc --disable-avdevice --disable-avfilter \
    --disable-swscale --enable-shared --disable-static \
    --disable-encoders --disable-muxers \
    --prefix=/path/to/install
  ```
  Обоснование флагов:
  - `--disable-programs`/`--disable-doc` — не нужны `ffmpeg.exe`/`ffprobe`/
    `ffplay`, только библиотеки.
  - `--disable-swscale` — YUV→RGB не через `sws_scale` на CPU
    (ARCHITECTURE.md, «Как не убить процессор»), конвертация в шейдере
    `rst-render` (см. §3).
  - `--disable-avfilter`/`--disable-avdevice` — не нужны (нет фильтр-графа,
    не захватываем устройства).
  - `--disable-encoders`/`--disable-muxers` — только проигрывание, не
    запись/перекодирование.
  - Оставляем: `libavformat` (демукс), `libavcodec` (декод), `libavutil`,
    `libswresample` (ресемплинг звука под устройство).
- MinGW-собранные shared-библиотеки (`.dll` + сгенерированные `.lib` через
  `dlltool`) линкуются к Rust на MSVC ABI — рабочая, стандартная для
  Windows-сообщества комбинация (см. `ffmpeg-sys-next`/`ffmpeg-next`
  документацию), не блокер.
- Итог сборки — `.dll`/`.lib`/заголовки в известном пути; переменные
  окружения (`FFMPEG_DIR` или аналог, под конкретный биндинг-крейт) для
  `build.rs` крейта `rst-video` (см. §2). DLL-ки при рантайме должны лежать
  рядом с `resticker.exe` (или в PATH) — иначе процесс не запустится.
- Проверка лицензии перед тем, как считать сборку готовой: `ffmpeg
  -version` (если временно собрать бинарник для проверки) или разбор
  `--enable-*`/`--disable-*` строки конфигурации на предмет отсутствия
  `gpl`/`nonfree` компонентов.

## 2. Новый крейт `rst-video` (декод, без GPU/окна)

Изолирует всю unsafe-работу с FFmpeg FFI в один крейт — `rst-render` и
остальные не тянут FFmpeg как зависимость вообще, тем же принципом
разделения, что `rst-media` (декодирование) vs `rst-render` (GPU) в M5a.

Биндинг — `ffmpeg-sys-next` (сырой FFI, bindgen), не `ffmpeg-next`:
низкоуровневый доступ к декодированным Y/U/V-плоскостям и PTS нужен
напрямую, обёртка `ffmpeg-next` для этого не обязательна и добавляет
лишний слой абстракции без выгоды на этом срезе (zero-copy GPU handoff —
не в этом срезе, см. §0.2).

```rust
pub struct VideoSource { /* дескриптор открытого файла + поток-декодер */ }

pub struct DecodedVideoFrame {
    pub y: Vec<u8>, pub u: Vec<u8>, pub v: Vec<u8>,
    pub width: u32, pub height: u32,
    pub pts: Duration, // относительно начала потока
}

pub enum VideoError { /* ... */ }

impl VideoSource {
    pub fn open(path: &Path) -> Result<Self, VideoError>;
    pub fn play(&self);
    pub fn pause(&self);
    pub fn is_paused(&self) -> bool;
    pub fn seek(&self, to: Duration) -> Result<(), VideoError>;
    pub fn set_volume(&self, volume: f32); // 0.0..=1.0, PlaybackSettings.volume
    /// Последний готовый кадр (неблокирующе) — вызывается координатором
    /// перед каждым redraw, не в декодер-потоке.
    pub fn try_recv_frame(&self) -> Option<DecodedVideoFrame>;
    pub fn has_audio(&self) -> bool;
}
```

- Свой поток на файл (тот же паттерн, что `WindowTracker`/`Tick`/
  планировщик анимации в `overlay_manager.rs`): демукс + декод в цикле,
  очередь на 2-3 готовых видеокадра (ARCHITECTURE.md), не блокирует
  координатор.
- Аудио: декодированные+ресемплированные (через `libswresample`, под
  формат/частоту устройства вывода) сэмплы кладутся в кольцевой буфер,
  который читает cpal-колбэк (см. §4) — колбэк вызывается аудио-драйвером
  в реальном времени, это и есть эталонные часы потока (если звук есть).
- Часы без звука (mute/нет аудиодорожки): `Instant`-якорь, видео-кадр
  показывается, когда `elapsed >= кадр.pts` — тот же принцип, что
  `AnimationClock`, но по PTS из контейнера, а не по фиксированным
  задержкам.
- Пауза: декодер-поток перестаёт продвигать часы (не тянет новые пакеты
  вообще — не тратит CPU впустую, тот же принцип «не декодировать
  невидимое», ARCHITECTURE.md §4.3, применённый и к «на паузе»).
- Луп: `loop_mode == Loop` (дефолт) → на EOF `av_seek_frame` в начало,
  продолжаем. `Once`/`HoldLastFrame` для видео — та же неопределённость
  семантики, что для GIF (см. `MEMORY/CHANGES.md` M5a, «Отложено») — не
  реализуется в этом срезе, `Loop` работает всегда независимо от
  `loop_mode` до отдельного решения.
- Скрытые/полностью перекрытые стикеры — трекер уже знает про occluder
  per-стикер (M4); декодер-поток видео получает сигнал «сейчас невидим» и
  ставит декод на паузу тем же путём, что explicit `pause()` — экономит
  CPU по тому же принципу, что анимация M5a (`animation_should_tick`).

## 3. `rst-render`: YUV-текстуры и конвертация в шейдере

- Три отдельных R8-текстуры на кадр: Y (полное разрешение), U/V (половина
  по каждой оси — 4:2:0, самый частый формат вывода декодера H.264/VP9).
  Обновляются `UpdateSubresource` каждый показанный кадр (не atlas —
  видео меняется каждый кадр, а не по фиксированному набору, здесь ближе
  к обычной динамической текстуре).
- Новый пиксельный шейдер (или ветка существующего `mainPS` по флагу) —
  сэмплирует Y/U/V, конвертирует в RGB матрицей BT.709 (упрощение для
  этого среза: не читаем цветовые метаданные контейнера, всегда BT.709 —
  корректно для подавляющего большинства современных исходников;
  BT.601-контента может слегка «поплыть» цвет, задокументировано как
  известное упрощение, не баг).
- `Device::create_video_textures(y, u, v, width, height) -> VideoTextures`,
  `Device::update_video_textures(&mut VideoTextures, y, u, v)` (переиспользует
  существующие текстуры вместо пересоздания каждый кадр — дешевле).
- Драится тем же `Sprite`-путём, что и всё остальное (UV по умолчанию —
  вся текстура, как у статичных картинок) — координатор строит `Sprite`
  поверх `VideoTextures`, `redraw()` не должен знать про разницу между
  видео/картинкой/анимацией на уровне отрисовки самого спрайта (тот же
  принцип единообразия, что уже сработал для атласа M5a).

## 4. Звук — `cpal`, один общий выходной поток

- Один общий `cpal::Stream` на весь процесс (не по потоку на стикер) —
  микшер в колбэке суммирует ресемплированные сэмплы всех сейчас играющих
  видео-стикеров, умножает на `PlaybackSettings.volume` каждого и на
  глобальный mute/громкость (SPEC.md §7.1 — обязателен глобальный
  переключатель «Заглушить все» и хоткей для него; в этом срезе — минимум:
  сам микшер и per-стикер громкость, глобальный тумблер/хоткей — если
  останется время, иначе отдельный маленький срез позже).
- Ресемплинг под формат устройства — `libswresample` на выходе декодера,
  до попадания сэмплов в общий буфер микшера (микшер работает в одном
  формате, не должен ресемплировать сам).
- Простое сложение с клэмпом по границам `i16`/`f32` (в зависимости от
  формата устройства) — не полноценный DSP-микшер, достаточно для
  «несколько стикеров одновременно», не для профессионального сведения.

## 5. Схема данных / что НЕ меняется в `rst-core`

- `MediaType::Video` уже существует в модели (`rst-core::model`), просто
  никогда не выставлялся — как и `Animation` до M5a.
- `PlaybackSettings` уже несёт `volume`/`speed`/`loop_mode` — используются
  как есть (кроме `loop_mode`/`speed`, см. §2 «отложено»).
- **Новое поле нужно**: `PlaybackSettings` не несёт состояния play/pause
  вообще — а пользователь явно просил именно play/pause как управляемую
  функцию (не просто «всегда играет»). Добавляется `paused: bool`
  (дефолт `false` — автовоспроизведение при добавлении, миграция схемы
  v1→v2 в `rst-core::config` тем же паттерном, что `migrate_v0_to_v1`).
  UI-переключатель — новая кнопка тулбара (по аналогии с `TB_LAYERS`) или
  жест по самому стикеру (клик play/pause по видео-стикеру в режиме
  редактирования) — решается на срезе сшивки, не блокирует decode/render
  слои.

## 6. Сшивка в координатор (делаю сам, как и M5a §5)

- `VideoPlayback` — локальная структура `run()` (та же схема, что
  `StickerAnimation`): `source: rst_video::VideoSource` + текущие
  `VideoTextures`.
- `add_sticker`: `MediaType::Video` (по расширению файла на первом этапе —
  надёжного «понюхать по содержимому» без реального открытия файла
  декодером через FFmpeg нет дешёвого способа, в отличие от анимаций;
  можно завести `rst_video::probe(path) -> bool` тонким открытием
  контейнера без полного декода первого кадра, если понадобится более
  надёжно отличать видео от картинки на основе содержимого, а не
  расширения).
- Redraw: `try_recv_frame()` перед каждым `redraw()` для каждого видео-
  стикера, `update_video_textures` при новом кадре, иначе — рисуем
  последний загруженный (не блокируем кадр в ожидании декодера).
- Play/pause кнопка → `VideoSource::play()`/`pause()` + `paused` в
  `PlaybackSettings` (персистентность через рестарт).
- Seek — UI для «мотать» не специфицирован пользователем детально
  (прогресс-бар? стрелки перемотки?) — технический слой (`seek(Duration)`)
  готов с этого среза, конкретный UI-виджет — отдельное решение с
  пользователем, когда дойдём до сшивки (не блокирует decode/render/audio
  слои, которые независимы от конкретного виджета).

## 7. Порядок работы

1. Сборка FFmpeg (я, сейчас, MSYS2 в `W:\msys64`, вне репо).
2. Три параллельных среза воркерам (как M5a): (A) `rst-video` крейт —
   FFI-биндинг, демукс/декод-поток, аудио-ресемплинг, играть/пауза/сик/
   громкость — блокируется на готовности собранного FFmpeg; (B)
   `rst-render` YUV-текстуры+шейдер — НЕ блокируется на FFmpeg, контракт
   (3 плоскости Y/U/V, 4:2:0, R8) известен заранее; (C) `cpal`-микшер —
   частично независим (устройство/поток можно поднять и протестировать
   синтетическим сигналом до готовности decode-слоя).
3. Сшивка в координатор — я, после ревью A/B/C, тем же процессом, что M5a
   §5/§6.

## 8. Отложено явно

- Аппаратный декод (`d3d11va`, zero-copy) — ROADMAP M5c, отдельно.
- Настоящая прозрачность в видео (SPEC §7.2) — сознательно не делается
  вообще, продукту не нужно (см. §0.3).
- `speed`/`loop_mode` (кроме дефолтного `Loop`) — та же отложенная
  семантика, что у GIF (M5a, `MEMORY/CHANGES.md`).
- Множественные аудиодорожки (`PlaybackSettings.audio_track`) — берём
  первую/лучшую дорожку, выбор дорожки не реализуется.
- Точная профессиональная A/V-синхронизация (дрейф на длинных сессиях,
  сложные форматы контейнеров с B-кадрами вне стандартного порядка) — из
  коробки FFmpeg decode+PTS-based clock достаточно для стикера на
  рабочем столе, не для монтажной программы.

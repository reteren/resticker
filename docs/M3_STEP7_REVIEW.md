# M3 — ревью шага 7: перепривязка стикера к другому монитору по завершении драга

Статус: **независимое ревью, без изменений кода**. Ветка `feat/m2-edit-mode`, коммит
`0027b0f` (координатор: `monitor_bounds`-снапшот + вызов
`monitor_rebind::rebind_monitor_by_center` в конце `Drag`, overlay_manager.rs +73/−4;
ROADMAP.md — галки «привязка по центру bbox» и «перетаскивание между мониторами»).
Прочитаны дифф коммита целиком и актуальные файлы: `crates/resticker/src/overlay_manager.rs`
(2924 строки), `crates/rst-core/src/monitor_rebind.rs` (294 строки, включая тесты),
`crates/rst-core/src/snap.rs` (`clamp_min_visible`, `MIN_VISIBLE_FRACTION`),
`crates/rst-core/src/transform_ops.rs` (`resize` — движение центра). Сверено с
`docs/M3_PREP_NOTES.md` §5.4 и `docs/M3_STEP4_REVIEW.md` §1.1. Интерактивного
перетаскивания между мониторами нет (заявлено автором; только build/clippy/test +
launch-smoke).

**Общий вердикт:** сшивка на главных путях корректна — свертка перепривязки в тот же
шаг истории, что и драг, работает ровно (один `Ctrl+Z` возвращает и позицию, и
монитор; `Ctrl+Y` симметричен); `CaptureLost` перепривязки не требует (весь драг
откатывается к стартовой паре «позиция+монитор»); пересечения с чужими событиями
нет (захват мыши + один поток координатора + гард клавиатуры); спрайт и модель не
расходятся; тулбар сразу уезжает на новый монитор. **Найдено две живые проблемы
средней тяжести**: (1) обоснование «только Drag» неверно — ресайз тоже двигает центр
стикера (до 0.4·w за край источника), но перепривязка на его завершении не делается,
и стикер остаётся с устаревшим `monitor_id`; (2) после перепривязки значимая часть
bbox стикера (до ~половины) может остаться над монитором-источником, и эта видимая
часть **не хит-тестится** (фильтр `hit_sticker_at`/`resolve_zone` по `monitor_id`) —
клик по ней снимает выделение/начинает марку вместо выбора стикера. Плюс три
замечания (клик без движения может молча перепривязать и сжечь шаг истории; при
пересечении DPI-границы физический размер стикера скачком меняется; обслуживание
`monitor_bounds` из размера окна, а не из перечисления). Подробности — ниже.

## 1. Проверено по явным вопросам задачи

### 1.1 Свежесть `monitor_bounds` — в текущем мире расхождения нет, два допущения стоит зафиксировать

- **«Позиция x/y не меняется сменой DPI» — допущение корректно.** Смена масштаба
  монитора не двигает его в координатах виртуального десктопа; смена разрешения/
  расположения приходит `WM_DISPLAYCHANGE`-ом, который в этом срезе не подключён
  (только лог) — значит `monitor_bounds` и `monitors_map` устаревают **согласованно**,
  расхождения между ними нет. Единственный путь обновления (`DpiChanged`, 854-859)
  правит обе карты из одних и тех же `ms.width/height/scale`.
- **Оговорка 1:** `bounds_px.w/h` берутся из **размера окна** после `SetWindowPos` на
  рекомендованный прямоугольник, а не из повторного перечисления границ монитора.
  Сегодня окно оверлея покрывает монитор 1:1, и рекомендованный rect для
  полноэкранного popup равен границам монитора — эквивалентно. Но при сценарии, где
  рекомендованный rect меньше монитора (уменьшение DPI масштабирует rect вниз),
  математика перепривязки молча начала бы пользоваться границами окна вместо границ
  монитора. Стоит задокументировать инвариант «окно == монитор» или перечитывать
  `monitors::enumerate()` в ветке `DpiChanged`.
- **Оговорка 2 (безопасная деградация):** `filter_map` (686-694) опускает мониторы,
  чьи окна не создались на старте. Для источника это недостижимо (без окна нет и
  событий — драг с такого монитора невозможен); для цели — перепривязка просто не
  срабатывает (`rebind_monitor_by_center` не найдёт монитор в `others`), стикер
  остаётся на источнике с центром над «мёртвым» монитором — то же поведение, что
  для разрыва между мониторами. Приемлемо; стоит упомянуть в комментарии.

### 1.2 Свертка в историю undo — ровно один шаг, проверено пошагово

Последовательность для драга, пересекающего границу:

1. `MouseDown` на стикере: `pending_snapshot = Some(cfg.clone())` — **до** драга:
   старый `monitor_id`, старая позиция (2191).
2. `MouseMove`-ы: `apply_gesture` правит `cfg` (позиция, монитор прежний).
3. `MouseUp`: блок перепривязки (2470-2498) правит `cfg.stickers[id].placement` и
   `sprites[id].placement` — новый монитор, DIP в его координатах; затем
   `edit.gesture.take()` и `if before != *cfg { commit_undo_snapshot(edit, before) }`
   (2499-2510) — `before` — снимок **пункта 1**, включающий старый монитор.

`Ctrl+Z` → `perform_undo` → `cfg = before` (старая позиция **и** старый монитор) +
`resync_sprites` (спрайт перечитан из cfg) — один шаг снимает и позицию, и
перепривязку, ровно. `Ctrl+Y` → `redo_stack` содержит пост-драг cfg (новый монитор) —
симметрично восстанавливает. Сравнение `before != *cfg` верно, потому что
`rebind_monitor_by_center` **всегда** возвращает либо неизменный клон, либо полную
перепривязку (монитор+координаты вместе) — частичных изменений нет, сравнение по
`monitor_id` (2486) — корректный прокси «что-то изменилось».

### 1.3 `CaptureLost` — перепривязка не нужна, рассинхрона нет

`CaptureLost` (2519-2581) идёт отдельной веткой и **не выполняет** блок перепривязки
(тот — только в `MouseUp`). Откат: `apply_transform(cfg, sprites, start.id,
start.placement.clone(), start.transform)` — восстанавливает **стартовую** пару
«позиция + `monitor_id`» в модели и спрайте одним значением; `pending_snapshot`
отбрасывается. Перепривязка на этом пути невозможна по построению — стикер не может
остаться с рассогласованной парой. Единственное, что стоит зафиксировать: если драг
успел увести центр за край, `CaptureLost` вернёт стикер целиком (включая монитор) —
ожидаемо и консистентно.

### 1.4 Чужие события между последним Move и MouseUp — не могут мутировать стикер

Перепроверено рассуждение M3_STEP4_REVIEW §1.1 для нового пути мутации:

- **Указатель:** `SetCapture` на `MouseDown` (input.rs) держит все Move/Up на окне
  владельца жеста — событие `MouseUp`, выполняющее перепривязку, приходит с того же
  окна/монитора, что и весь драг. Чужое окно в это время мышь не видит.
- **Координатор однопоточен:** события разбираются последовательно в одном цикле
  `run()`; между последним Move и Up не может вклиниться обработка, мутирующая
  `placement` этого id: клавиши блокированы гардом `handle_key` (`gesture.is_some()`),
  `ToggleAllStickers` меняет только `visible`, `DpiChanged` — только геометрию/масштаб,
  `MonitorsChanged`/session/power — только лог.
- **`ToggleEditMode` посреди драга:** откатывает жест (gesture = None) — ветка
  `MouseUp` потом не увидит `Gesture::Drag`, перепривязка не выполнится; консистентно.
- Итог: мутация «чужим» событием между последним Move и перепривязкой невозможна.

### 1.5 `resync_sprites` и прочие пути — всегда от `cfg`, рассинхрона нет

Прямая запись `sprites.iter_mut()` в блоке перепривязки (2490-2492) кладёт в спрайт
тот же клон `rebound`, что и в `cfg.stickers` — попарно согласовано. Прочие пути,
трогающие спрайты: `apply_transform` (модель+спрайт одним значением), `resync_sprites`
(перечитывает placement из cfg), `add_sticker` (пушит из свежесозданного стикера),
`duplicate` (через `resync_sprites`). Источника `placement`-а спрайта, отличного от
cfg, нет — рассинхрон невозможен. Если спрайт id отсутствует (не загрузился на
старте), `iter_mut()` просто ничего не пишет — cfg при этом корректен, а будущий
`resync_sprites` создаст спрайт из cfg.

### 1.6 Свежесть `toolbar_monitor` после перепривязки — подтверждено

`rebuild_ui_panels` (1731-1750) читает `toolbar_monitor(&edit.selection, cfg)`
(1638-1642) — **из cfg**, а блок перепривязки правит cfg **до** вызова (2487-2495):
тулбар пересобирается с новым `monitor_id` и его геометрией (`monitor_geometry` по
новому монитору), `redraw` затем рисует его на новом мониторе (фильтр в `redraw` тоже
читает cfg). `edit.selection` хранит только id — перепривязка его не трогает,
`single_selected_id` продолжает работать. Панель у курсора пересобирается по
`cursor_monitor` — курсор всё ещё над монитором-источником — корректно. Свежесть
подтверждена; отдельного «кэша монитора тулбара» нет.

## 2. Найденные проблемы

### 2.1 (средне) Обоснование «только Drag» неверно: ресайз тоже выводит центр за границу источника — и оставляет устаревший `monitor_id`

- **Где:** комментарий к блоку перепривязки (2462-2469): «`Resize`/`Rotate` не двигают
  центр стикера настолько, чтобы это было нужно (их клампит `clamp_min_visible` в
  границах своего монитора)»; аналогично в сообщении коммита.
- **Что на самом деле:** `transform_ops::resize` без `Alt` держит якорь
  (противоположную грань/угол) неподвижным — **центр смещается** на половину дельты
  (transform_ops.rs:105-115). А `clamp_min_visible` (snap.rs:189-204) зажимает только
  bbox с `MIN_VISIBLE_FRACTION = 0.1`: `center ∈ [monitor.x − 0.4·w, monitor.x +
  monitor.w + 0.4·w]` — центр может оказаться **до 0.4·w за краем** источника (и у
  драга та же математика: «90% bbox за краем» в сообщении коммита относится к
  bbox-краю, сам центр — максимум 40%). Ресайз за ручку у края монитора оставляет
  стикер с центром на чужом мониторе и **прежним** `monitor_id`: перепривязка на его
  завершении не выполняется, тулбар остаётся у стикера на источнике, а «дом»
  стикера расходится с его физическим положением до следующего завершённого драга
  (который уже перепривяжет — а простой клик, см. §2.3, сработает как
  перепривязывающий).
- **Фикс:** выполнять ту же проверку на завершении `Resize` (центр из `start` и
  текущего placement) либо поправить формулировку и принять как известное
  ограничение. `Rotate` действительно безопасен — центр не двигается.

### 2.2 (средне) После перепривязки видимая часть стикера на мониторе-источнике мёртва для ввода

- **Где:** перепривязка происходит, когда центр **за** краем источника (2486);
  bbox при этом перекрывает границу: на стороне источника остаётся от 10% (минимум
  `clamp_min_visible` по инварианту драга) до **~половины** стикера (центр только-только
  за краем). После смены `monitor_id` на B этот остаток продолжает рисоваться окном A
  (фильтр `redraw` по B его не берёт — он физически над A), но `hit_sticker_at`/
  `resolve_zone` фильтруют по `monitor_id == A` (1455-1462, 1474-1516) — **клик по
  видимой части на A не попадает в стикер**: `resolve_zone` возвращает `Background`,
  `MouseDown` начинает марку, простой клик **снимает выделение** вместо выбора
  стикера; курсор над остатком — Arrow, а не Move.
- **Что:** рутинный сценарий — каждый межмониторный драг оставляет такой «огрызок»
  на источнике; пользователь видит часть стикера, но не может её ни выбрать, ни
  схватить. Корень — пер-мониторный фильтр хит-тестов (шаг 4) в сочетании с
  перепривязкой (шаг 7): «стикер, перекрывающий границу» нигде не смоделирован.
- **Фикс (варианты):** в `hit_sticker_at`/`resolve_zone` учитывать стикеры, чей
  физический bbox пересекает границы окна, по геометрии (`monitor_bounds` уже есть);
  или при перепривязке дожимать стикер целиком на новый монитор (корректировка
  центра, чтобы bbox полностью влез) — проще и избавляет от «полуторамониторных»
  стикеров вовсе; или хотя бы задокументировать.

### 2.3 (низкое-среднее) Простой клик без движения может молча перепривязать стикер и сжечь шаг истории

- **Где:** блок перепривязки (2470-2498) выполняется на **каждом** `MouseUp` с
  `Gesture::Drag`, включая клик без единого Move. Условие срабатывания — только
  «центр вне источника по текущему placement».
- **Что:** если центр стикера уже был за краем источника **до** этого клика (драг,
  завершившийся в разрыве между мониторами — перепривязка тогда была no-op; или
  смена DPI/масштаба после такого драга сдвинула физический центр), простой клик
  перепривяжет стикер (физическая позиция сохранится, но он «переедет» на соседний
  монитор) и создаст шаг истории: `before != *cfg` (2507) — нарушение инварианта
  «клик без движения не тратит шаг» (M2_SLICE_REVIEW, пункт 1). Само действие
  безвредно (позиция не меняется), но история получает пустой по сути шаг, а стикер
  неожиданно меняет монитор.
- **Фикс:** гейтить перепривязку реальным движением — сравнивать текущий placement
  с `start.placement` (`GestureStart` уже хранит его) и выполнять блок только при
  отличии.

### 2.4 (низкое, примечание) Пересечение DPI-границы скачком меняет физический размер стикера

- `rebind_monitor_by_center` переносит `w/h` в DIP без изменений (monitor_rebind.rs:44-45,
  задокументировано как решение). При источнике 100% и цели 150% стикер после
  перепривязки рендерится в **1.5× большем физическом размере** (redraw растягивает
  DIP-размер масштабом цели). Сообщение коммита обещает «точную физическую позицию» —
  позиция сохраняется, размер — нет; пользователь видит скачок размера ровно в момент
  пересечения границы. Вариант: сохранять физический размер (`w_new = w ·
  src_scale/dst_scale`) или оставить как есть, но тогда это поведение надо явно
  зафиксировать в UI-заметках.

### 2.5 (низкое, примечание) Тай-брейк перекрывающихся мониторов зависит от порядка `HashMap`

- `others` собирается итерацией `monitor_bounds` (2479-2483) — порядок `HashMap`
  неспецифицирован; `rebind_monitor_by_center` документирует «порядок списка —
  ответственность вызывающего кода» (monitor_rebind.rs:50). При клонированных
  мониторах (одинаковые границы) выбор цели недетерминирован между запусками.
  Практически косметика, но обещанная ответственность не выполнена — стоит
  упорядочить список (например, по id) для стабильности.

## 3. Что проверено и корректно (не тратить время на повторную проверку)

- **Свертка в историю** (§1.2): один `Ctrl+Z` возвращает и позицию, и `monitor_id`;
  `Ctrl+Y` симметричен; сравнение по `monitor_id` — точный прокси «изменилось ли
  что-то» (перепривязка атомарна).
- **`CaptureLost`** (§1.3): перепривязка не выполняется и не нужна — откат к
  `start.placement` восстанавливает согласованную пару; `pending_snapshot` сбрасывается.
- **Отсутствие чужих мутаций** (§1.4): `SetCapture` + однопоточный цикл координатора +
  гард `handle_key`; `ToggleEditMode` убирает жест до ветки `MouseUp`.
- **Спрайт/модель** (§1.5): все пути записи `placement` спрайта идут от cfg;
  прямая запись блока перепривязки дублирует cfg ровно.
- **Тулбар** (§1.6): `rebuild_ui_panels` читает `toolbar_monitor` из cfg после
  перепривязки — новый монитор и его геометрия подхватываются сразу.
- **Геометрия перепривязки** (monitor_rebind.rs, покрыта тестами): центр bbox =
  центр placement при любом повороте; DIP→физика→DIP с сохранением физической позиции
  проверен round-trip-тестами на смешанном DPI (в обе стороны); полуоткрытые границы,
  разрывы, NaN, вырожденные цели — корректные no-op.
- **`monitor_bounds` согласован с `monitors_map`** (§1.1): один источник
  (`monitor_infos`), одна точка обновления (`DpiChanged`), одинаковый фильтр
  «окно создано».
- **Вызовы**: `monitor_bounds` проброшен только в `handle_input` (единственная точка
  потребления) — прочие обработчики его не трогают, сигнатуры не раздуты.

## 4. Приоритеты для координатора

1. **Мёртвый «огрызок» на источнике (§2.2)** — после каждого межмониторного драга
   видимая часть стикера на старом мониторе не выбирается и кликается как фон
   (снимает выделение/начинает марку). Самый заметный UX-дефект шага.
2. **Ресайз без перепривязки (§2.1)** — поправить обоснование и/или применить ту же
   проверку на завершении `Resize` (центр движется до 0.4·w за край).
3. **Гейт перепривязки по движению (§2.3)** — клик без движения не должен менять
   монитор и жечь шаг истории.
4. **Физический размер при пересечении DPI-границы (§2.4)** — решить и
   задокументировать (скачок 1.5× сейчас неявный).
5. **Детерминированный тай-брейк (§2.5)** и оговорки по `monitor_bounds` (§1.1) —
   комментарии/порядок списка.

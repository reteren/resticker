# M3 — ревью шага 8: ресайз окна монитора при смене разрешения (WM_DISPLAYCHANGE, шаг 3.5)

Статус: **независимое ревью, без изменений кода**. Ветка `feat/m2-edit-mode`, коммит
`6b5e39b` (координатор: шаг 3.5 в ветке `MonitorsChanged` — перестановка/ресайз окна
выживших мониторов, overlay_manager.rs +65/−9; rst-win32: `OverlayWindow::set_bounds`,
overlay.rs +51). Прочитаны дифф коммита целиком и актуальные файлы:
`crates/resticker/src/overlay_manager.rs` (3647 строк), `crates/rst-win32/src/overlay.rs`
(1147 строк), сверено с `docs/M3_STEP5_6_REVIEW.md` §2.5 (закрываемый gap),
`docs/M3_STEP2_3_REVIEW.md` §2.2/2.4 (эталон поведения ветки `DpiChanged`),
`docs/M3_DEVICE_RECOVERY_REVIEW.md` (флаг `broken`). Интерактивного прогона нет
(build/clippy/test + launch-smoke зафиксированы в коммите; реальная смена разрешения/
перестановка мониторов не проверялась).

**Общий вердикт:** основная механика верна и самосогласована — шаг 3.5 идемпотентен
относительно N одинаковых `MonitorsChanged` (WM_DISPLAYCHANGE рассылается каждому
окну), сходится с веткой `DpiChanged` при любом порядке событий (пересчёт `cursor_pos`
через `old_scale/ms.scale` от текущего состояния не задваивается), шаг 4 после него
строит `monitor_geometry` и `monitor_bounds` из одного снимка — заявленный gap §2.5
для смены размера действительно закрыт. **Найдена одна живая проблема средней
тяжести: проверка «изменился ли монитор» сравнивает только w/h/scale, но не позицию
(x/y) — чистая перестановка монитора в виртуальном десктопе (размер и масштаб те же)
окно не двигает**, хотя коммит заявляет «changes resolution or position». Плюс
четыре замечания (панели UI не пересобираются после шага 3.5, stale-чтение dpi(),
потенциальный ping-pong с рекомендованным rect'ом WM_DPICHANGED, failure-пути).

## 1. Проверено по явным вопросам задачи (аналоги шага 2/3)

### 1.1 Секвенсинг шага 3.5 и идемпотентность по дубликатам

Шаг 3.5 (overlay_manager.rs:1193-1243) выполняется в ветке `MonitorsChanged` между
сносом пропавших (шаг 3) и пересборкой снимков (шаг 4). Порядок операций внутри
итерации: сравнение состояния → `set_bounds` (движение+ресайз окна) → обновление
`ms.width/height/scale` → `set_dpi_scale` + `target.resize` → пересчёт `cursor_pos`.
Локальное состояние (`ms.*`) обновляется до шага 4, который строит оба снимка из
живого `monitors_map` и свежих `new_infos` — `monitor_geometry` и `monitor_bounds`
после шага 3.5 не расходятся (gap §2.5 закрыт для случая «размер/масштаб изменились»).

Идемпотентность по дубликатам: первый `MonitorsChanged` приводит `ms.width/height/scale`
в точное соответствие `info.bounds_px` (и `set_bounds` применяет те же границы), поэтому
повторные события того же burst'а (по одному на окно) уходят в `continue` на 1209-1213.
Исключение — см. §2.4 (если рекомендованный rect WM_DPICHANGED разойдётся с
`bounds_px`, каждый следующий дубликат переприменит `bounds_px`).

### 1.2 Сходимость с веткой `DpiChanged` при любом порядке событий

Смена разрешения почти всегда сопровождается `WM_DPICHANGED` (если поменялся и
масштаб). Порядок `WM_DISPLAYCHANGE`/`WM_DPICHANGED` не гарантирован — проверены оба:

- **DPI-не изменился (чистая смена разрешения):** `WM_DPICHANGED` не приходит;
  `dpi()` корректен; шаг 3.5 делает set_bounds + resize, `ms.scale` не трогает,
  `cursor_pos` не трогает (ratio = 1.0) — всё сходится за один проход. ✓
- **Изменились и размер, и DPI, сначала `MonitorsChanged`:** `dpi()` может быть
  устаревшим (§2.3) → `ms.scale` временно старый → прилетевший `WM_DPICHANGED`
  исправляет scale и `cursor_pos` своим ratio от уже обновлённого `ms.scale` —
  задвоения пересчёта нет (каждая ветка считает ratio от текущего состояния).
- **Сначала `DpiChanged`:** ветка уже привела `ms.*` к рекомендованному rect'у;
  шаг 3.5 либо no-op (rect == bounds), либо повторно применяет `bounds_px` —
  `cursor_pos` при этом не трогается (ratio = 1.0). Сходится. ✓

`cursor_pos` в итоге сходится к правильному значению во всех четырёх комбинациях —
задвоенный/пропущенный пересчёт невозможен (ratio всегда от текущего `ms.scale`).

### 1.3 Координатные системы и захват мыши

Окно покрывает монитор целиком (WS_POPUP без рамок), клиентские координаты событий
мыши == монитор-локальные (ADR-010). Перемещение окна (`set_bounds`) систему координат
не ломает: клиентские координаты остаются относительными к новому положению окна, т.е.
к новым границам монитора. Активный жест/марка (DIP, монитор-локальные) переживают
ресайз без инвалидации; `monitor`-rect для snap/clamp пересчитывается на каждом
событии из обновлённых `ms.width/height/scale`. Захват мыши (Win32) остаётся у окна
при его перемещении — события продолжают приходить. ✓

### 1.4 Взаимодействие с `broken`/`recover_device`

`recover_device` (3511-3547) пересоздаёт цели с `ms.width/height` и `ms.scale` —
значения, обновлённые шагом 3.5, переживают потерю устройства без рассинхрона.
Ресайз `broken`-цели в шаге 3.5 упадёт с ошибкой устройства — залогируется, `broken`
останется, `redraw_all` её пропускает (без вторичного DeviceLost). Противоречий нет. ✓

## 2. Найденные проблемы

### 2.1 (среднее) Чистая смена позиции монитора не двигает окно — проверка сравнивает только w/h/scale

- **Где:** шаг 3.5, условие пропуска (overlay_manager.rs:1209-1213):
  `info.bounds_px.w == ms.width && info.bounds_px.h == ms.height && scale-равен`.
- **Что:** `MonitorState` хранит только `width/height/scale` — позиция (x/y) не
  кэшируется вовсе, поэтому сравнение физически не может обнаружить монитор, который
  **только переехал** (перестановка в «Параметры → Дисплей»: размер и DPI те же,
  изменились x/y). `WM_DISPLAYCHANGE` при перестановке приходит, шаг 3.5 проходит
  проверку и делает `continue` — окно остаётся на старой позиции виртуального
  десктопа и перестаёт покрывать свой монитор. Шаг 4 при этом строит
  `monitor_bounds` из свежих `new_infos` (новая позиция) — расхождение «окно ==
  монитор», которое коммит заявляет закрыть, для оси позиции остаётся, а
  `rebind_monitor_by_center` снова считает по границам, которых окно не покрывает.
  Закроется только переподключением монитора или перезапуском.
- **Это противоречит сообщению коммита**: «changes resolution **or position**
  previously kept its old window size/target» — позиция заявлена, но не проверяется.
- **Фикс:** хранить позицию в `MonitorState` (или фактический `GetWindowRect` окна)
  и включать x/y в условие (равенство всех четырёх + scale); либо вызывать
  `set_bounds` безусловно для выживших мониторов (движение и ресайз — один дешёвый
  `SetWindowPos`; идемпотентность от дубликатов сохранится). Кандидат на вынос в
  чистую функцию `should_reposition(ms, info) -> bool` с юнит-тестом — сейчас
  решающая логика встроена в обработчик и именно поэтому не покрыта тестами
  (rst-win32 тест `set_bounds_moves_and_resizes_window` проверяет только сам
  `SetWindowPos`, не решение о вызове).

### 2.2 (низкое-среднее) После шага 3.5 панели UI не пересобираются — асимметрия с веткой `DpiChanged`

- **Где:** ветка `MonitorsChanged` (1069-1283) в целом; ветка `DpiChanged` (1059)
  — эталон.
- **Что:** `DpiChanged` после ресайза зовёт `rebuild_ui_panels` (1059); шаг 3.5
  делает то же самое по сути (set_bounds + resize + scale + cursor_pos), но
  `rebuild_ui_panels` в ветке `MonitorsChanged` не вызывается нигде (grep: только
  301/1059/1457/1631/… — все вне этой ветки). Последствия: (а) тулбар стикера на
  ресайзнутом мониторе продолжает жить с **старым** `screen_h` — решение «под/над
  рамкой» для стикеров у края принимается по прежней DIP-высоте; (б) панель у
  курсора не пере-клампится в новые границы (после смены разрешения она может
  торчать за краем); (в) пересчитанный в 1236-1242 `cursor_pos` «спит» до
  следующего события, триггерящего пересборку (hover-ветка панель не пересобирает —
  зафиксировано в M3_STEP2_3_REVIEW §2.2), т.е. при смене масштаба панель остаётся
  смещённой.
- **Фикс:** `rebuild_ui_panels(&mut edit, &cfg, &monitor_geometry)` в конце ветки
  `MonitorsChanged` (перед `need_redraw = true`), там же, где это делает `DpiChanged`.

### 2.3 (низкое, транзиент) `ms.overlay.dpi()` может быть устаревшим при порядке «сначала WM_DISPLAYCHANGE»

- **Где:** 1208 — `new_scale = ms.overlay.dpi() as f32 / 96.0` читается **до**
  `set_bounds` (1215).
- **Что:** DPI окна (PMv2) обновляется системой в момент доставки `WM_DPICHANGED`,
  а не `WM_DISPLAYCHANGE`. Если первым приходит `WM_DISPLAYCHANGE` (порядок не
  гарантирован), `dpi()` вернёт старый масштаб, шаг 3.5 сочтёт scale неизменившимся
  и оставит `ms.scale`/цель на старом масштабе; кадры будут рендериться в
  неправильном масштабе до прихода `WM_DPICHANGED`, который всё исправит (сходимость
  доказана в §1.2). Комментарий «Доверяем живому DPI окна» переоценивает «живость»
  в этом порядке событий. Вреда нет, но стоит либо читать `dpi()` **после**
  `set_bounds` (движение окна само спровоцирует `WM_DPICHANGED` и обновление DPI),
  либо опираться на `info.dpi` из перечисления (всегда свежий).

### 2.4 (низкое, зависит от железа) Потенциальный ping-pong между `bounds_px` и рекомендованным rect'ом `WM_DPICHANGED`

- **Где:** шаг 3.5 применяет `info.bounds_px` (1215), ветка `DpiChanged` — rect из
  `WM_DPICHANGED`; дубликаты `MonitorsChanged` (по числу окон) повторяют шаг 3.5.
- **Что:** если рекомендованный rect системы (для полноэкранного popup — границы
  монитора, но на практике возможны расхождения в 1-2 px и при работе с не-рабочей
  областью) отличается от `bounds_px`, события чередуются: каждый следующий
  `MonitorsChanged` возвращает окно/цель на `bounds_px`, каждый `WM_DPICHANGED` — на
  рекомендованный rect. Каждое такое переключение — лишний `SetWindowPos` +
  `ResizeBuffers` + пересоздание RTV (мигание, микрофризы). Для окна, ровно
  покрывающего монитор, rect'ы должны совпадать — проверить на реальном железе со
  смешанным DPI; запасной вариант — шаг 3.5 после `set_bounds` сверять с
  `GetWindowRect` и не ресайзить без фактического расхождения.

### 2.5 (низкое) Failure-пути: `set_bounds` упал — расхождение остаётся до следующего события

- **Где:** 1215-1221 (`continue` при отказе `SetWindowPos`) и 1227-1233 (ошибка
  `target.resize`).
- **Что:** при отказе `set_bounds` `ms.*` не обновляются, а шаг 4 всё равно строит
  `monitor_bounds` из свежих `new_infos` — окно и снимок снова расходятся (мини-gap
  §2.5 в failure-ветке), лечится только следующим `WM_DISPLAYCHANGE`. При ошибке
  `resize` (rtv=None) монитор гаснет до следующего события/восстановления устройства —
  ровно поведение, задокументированное для ветки `DpiChanged` в
  M3_STEP2_3_REVIEW §2.4. Оба пути логируются; приемлемо, но стоит зафиксировать,
  что после сбоя шага 3.5 монитор остаётся «слепым» до следующего триггера.

## 3. Что проверено и корректно (не тратить время на повторную проверку)

- **`set_bounds`** (overlay.rs:332-345): те же флаги `SWP_NOZORDER|SWP_NOACTIVATE`,
  что у `handle_dpi_changed` (653) — TOPMOST и фокус не трогаются; отрицательные
  координаты виртуального десктопа проходят (i32); тест
  `set_bounds_moves_and_resizes_window` (899) проверяет перемещение+ресайз живого
  окна и `size()` после.
- **Идемпотентность по дубликатам** и **сходимость `cursor_pos`** при любом порядке
  событий (§1.1, §1.2) — задвоения пересчёта нет, все четыре комбинации сходятся.
- **Шаг 4** после шага 3.5 строит оба снимка из одного состояния; для изменивших
  размер/масштаб мониторов gap §2.5 закрыт; `recover_device` переживает новые
  значения (`ms.width/height/scale`).
- **Совместимость с `broken`/device recovery**: ресайз упавшей цели безопасен,
  `redraw_all` пропускает её без вторичного DeviceLost.
- **Координаты мыши/жестов** при перемещении окна не ломаются (§1.3).

## 4. Приоритеты для координатора

1. **Позиция монитора в проверке (§2.1)** — хранить x/y (или `GetWindowRect`) в
   `MonitorState` и включать в условие; вынести решение в чистую функцию с тестом.
   Иначе заявленная «position»-часть коммита не работает вовсе, а расхождение,
   которое коммит закрывает для размера, остаётся открытым для перестановок.
2. **`rebuild_ui_panels` в конце ветки `MonitorsChanged` (§2.2)** — симметрия с
   `DpiChanged`; иначе тулбар/панель у курсора живут со старой геометрией после
   смены разрешения.
3. **Порядок чтения dpi() (§2.3)** — читать после `set_bounds` или из `info.dpi`;
   транзиент, но устраняется дёшево.
4. **Зафиксировать §2.4 (ping-pong с рекомендованным rect) и §2.5 (failure-пути)**
   — проверить на реальном железе; задокументировать «монитор гаснет до следующего
   события» при сбое шага 3.5.

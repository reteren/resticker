# M2 — ревью среза 4 / 4b: overlay_manager.rs (марка, модал удаления, Ctrl+V, Shift+клик)

Статус: **ревью, без изменений кода**. Коммиты `54d517c` («M2 integration (slice 4)»)
и `25f5372` («M2 integration (slice 4b)») + незакоммиченная правка рабочей копии
(Shift+клик в `MouseDown` и обработка `OverlayEvent::HotkeyConflict`). Прочитан
целиком `crates/resticker/src/overlay_manager.rs` (1407 строк); call-site'ы сверены
с `rst_core::selection_set` (`rubber_band`/`bounds`), `rst_core::ops`
(`delete`/`suppress_delete_confirmation`), `confirm_dialog.rs`, `rst_render::widgets`
(`Panel`/`Button`/`PointerEvent`), `rst-win32::{input,overlay,clipboard}`,
`rst-media::paste`, `rst-core::model` (`StickerSource`). Интерактивного прогона
мыши/клавиатуры не было (только build/clippy/test + запуск exe, как в
`54d517c`/`25f5372`).

**Общий вердикт:** сшивка корректна по основным путям — модал блокирует сцену и
историю, марка дешёвая и живёт только в `SelectionSet`, `Ctrl+V` даёт один снимок
на вставку. Проблемы — по убыванию важности: неиспользуемая семантика
`StickerSource::Pasted` для материализованных вставок (SPEC 2.5), снапшот модала,
откатывающий глобальный тумблер при undo, и три асимметрии в границах марки и
модала.

## 1. Главное: материализованные вставки создаются как `File`, а не `Pasted` — файлы в `pasted/` никогда не удаляются (SPEC 2.5)

`paste_from_clipboard` (overlay_manager.rs:803-853) материализует PNG/BMP в
`%APPDATA%\resticker\pasted\<uuid>.png` (rst-media::paste::materialize,
paste.rs:47) и передаёт путь в `add_sticker`. Но `add_sticker` всегда строит
стикер через `Sticker::new_file` (overlay_manager.rs:1391) →
`StickerSource::File { path, media_type }`. В модели уже есть выделенный под это
вариант `StickerSource::Pasted { path }` (model.rs:185, комментарий — «Вставка из
буфера, материализованная в pasted/<uuid>.png (SPEC 2.1)»), и его никто не создаёт
(проверено grep'ом: конструктора нет нигде).

Следствия:

- **Файлы накапливаются навсегда.** SPEC 2.5: «Удаление стикера не удаляет
  исходный файл (**за исключением материализованных вставок из буфера** — они
  удаляются вместе со стикером)». `ops::delete` (ops.rs:131) только убирает
  стикер из списка — на диск не смотрит. Удаление вставленного стикера (модал
  или быстрый путь `begin_delete`, overlay_manager.rs:1076-1079) оставляет файл.
  Undo вставки (`Ctrl+Z`) тоже оставляет файл: `perform_undo` восстанавливает
  конфиг и спрайты, но не трогает диск. Каждая вставка скриншота навсегда
  занимает место в `%APPDATA%\resticker\pasted\`.
- **Конфиг врёт о природе стикера**: вставленный из буфера пишется как
  `"kind": "file"`, хотя модель предусматривает `"kind": "pasted"` (пример —
  `config_v1_example.json`). Никакой код не может отличить «оригинал» от
  «вставки» — а это ровно то, на что завязана чистка.

**Рекомендация:** в ветке `Png/Bmp` создавать стикер с `StickerSource::Pasted`
(а не через `Sticker::new_file`); ветка `Files` остаётся `File` (оригиналы, их
SPEC 2.5 не велит удалять). Тогда `ops::delete` (и undo удаления) для `Pasted`
удаляют файл; заодно `StickerSource::Pasted` надо учесть в загрузке спрайтов —
`resync_sprites` (overlay_manager.rs:563-583) и стартовой загрузке
(overlay_manager.rs:400) матчат только `File`.

## 2. Undo удаления через модал откатывает глобальный тумблер «Больше не спрашивать»

`begin_delete` берёт снимок **при открытии** модала (`snapshot: cfg.clone()`,
overlay_manager.rs:660), а коммитит его по «Удалить» (overlay_manager.rs:1076).
Между этими моментами единственный способ изменить `cfg` — клик по тумблеру
«Don't ask again», который мутирует `cfg.settings.skip_delete_confirmation`
(overlay_manager.rs:1093).

Трассировка:
1. `Delete` → модал, `snapshot` содержит `skip_delete_confirmation = false`.
2. Клик «Don't ask again» → `suppress_delete_confirmation(cfg)` → флаг `true`,
   сохранено в config.json.
3. Клик «Delete» → `commit_undo_snapshot(edit, confirm.snapshot)` — в стек уходит
   снимок со `skip = false` — и удаление.
4. `Ctrl+Z` → `perform_undo` заменяет `cfg` снимком → флаг снова `false`;
   `config::save` записывает это в config.json.

Пользователь, отключивший подтверждение, после undo снова получает диалоги
удаления — глобальная настройка откатывается невидимо, вместе с удалением. Это
единственное место, где внутри «окна» снимка можно изменить settings: снимок
должен быть снимком удаляемого, а не всех вложенных изменений.

**Рекомендация:** при коммите удаления синхронизировать настройки снимка с
текущим `cfg` (например, перед `commit_undo_snapshot` скопировать
`confirm.snapshot.settings = cfg.settings.clone()`), либо — если «Больше не
спрашивать» вообще не должно жить в undo — исключить `settings` из снимков
(снимок только `stickers`). Второй вариант чище: тумблер — глобальная настройка,
которую сегодня нельзя отменить ничем, и откатывать её в составе удаления
нелогично.

## 3. `CaptureLost` при марке не возвращает выделение — асимметрия с остальными жестами

`CaptureLost` (overlay_manager.rs:1132-1157) — путь «отменить жест». Для
`Drag`/`Resize`/`Rotate` модель откатывается к `GestureStart`. Для марки
(`Gesture::start() == None`) сбрасываются только `edit.marquee`/`marquee_started`,
а `edit.selection`, который `rubber_band` менял на каждом `MouseMove`
(overlay_manager.rs:1178), **не восстанавливается**.

Сценарий: марка по фону выбрала несколько стикеров → Alt+Tab (или другое окно
забирает захват) → `CaptureLost`. Марка-визуал исчезла, но «частичное» выделение
осталось висеть без всякого контекста. Для остальных жестов инвариант
«потеря захвата = откат» соблюдён, для марки — нет; фактически марка получает
семантику «CaptureLost = коммит», о которой ничего не сказано.

Это не рассинхрон модели (выделение — эфемерное состояние редактора, в undo не
попадает), но поведение несогласованное, и оно заметно на практике.

**Рекомендация:** хранить в `Gesture::Marquee` снимок выделения на `MouseDown`
(он там ещё не тронут — выделение живёт только с первого порогового `Move`) и на
`CaptureLost` восстанавливать его; либо осознанно зафиксировать «марка =
выделение остаётся» и синхронно с этим не чистить `marquee`-визуал без причины.
Выбор зафиксировать в плане.

## 4. Марка после старта не ужимается ниже порога — выделение и рамка «замерзают»

Ветка марки в `apply_gesture` (overlay_manager.rs:1172-1181) проверяет порог
(`|dx| >= 4 || |dy| >= 4`) на **каждом** `MouseMove`, а не только при переходе в
`marquee_started`:

- Пока порог не превышен — ни `edit.marquee`, ни `rubber_band` не обновляются
  (это правильно для отличения клика от протяжки).
- Но **после** старта порог продолжает блокировать: если пользователь «сжал»
  рамку обратно до размера меньше 4×4 (например, выделил много, затем стянул в
  точку), марка и выделение остаются на последней надпороговой позиции.
  `MouseUp` видит `marquee_started == true` и оставляет это устаревшее выделение
  — ужать рамку марки до «ничего» нельзя, и рисуемый прямоугольник больше не
  соответствует курсору.

**Рекомендация:** порог должен гейтить только переход «клик → марка»
(установку `marquee_started`), а после старта обновлять `edit.marquee` и
`rubber_band` на каждом `MouseMove` безусловно.

## 5. Марка выделяет скрытые стикеры, которые нельзя ни кликнуть, ни утащить (SPEC 3.7)

`rubber_band` (selection_set.rs:104) не фильтрует `visible` — марка включает
скрытые стикеры в выделение. При этом `hit_sticker_at` фильтрует `visible`
(overlay_manager.rs:863), и `resolve_zone` для мультивыделения падает именно на
`hit_sticker_at` (overlay_manager.rs:841-847): скрытый стикер в мультивыделении
нельзя снять Shift+кликом, нельзя двигать, у него нет ручек — только рамка и
(в будущем) кнопки тулбара.

Это давняя известная недоработка (шахматка скрытых и интерактивность — SPEC 3.7 —
отложены; M2_SLICE_REVIEW, пункт 7), но марка **делает её новой**: раньше скрытый
стикер вообще нельзя было выбрать, теперь марка выделяет его «вслепую». На
поверхность выходит вопрос, чего ждать пользователю от рамки по скрытым
элементам.

**Рекомендация:** на этом срезе зафиксировать решение (марка пропускает скрытых
до появления шахматки, либо включает — и тогда последующий срез обязан дать им
интерактивность). Текущее «выделяет, но трогать нельзя» — худший вариант.

## 6. Клик мимо модала (и по тексту сообщения) закрывает диалог — отклонение от M2_WIRING_PLAN §5

`MouseUp` при открытом модале (overlay_manager.rs:1061-1101) опрашивает только
`ID_DELETE` и `ID_DONT_ASK`; всё прочее — `ID_CANCEL`, клик по сообщению или
**клик мимо модала** — «закрыть без изменений», модал выпадает. При этом
`MouseDown` мимо модала уже проглочен веткой (overlay_manager.rs:960-964),
в сцену не уходит — то есть случайный клик в любом месте экрана отменяет
удаление, не коснувшись ни одной кнопки.

M2_WIRING_PLAN.md, раздел 5: «клик мимо модала — ничего, в сцену не пускать
(модал модален)» — по тексту «ничего» означает, что диалог должен остаться.
Реализация его закрывает. Плюс отдельный штрих: сообщение «Delete N stickers?»
— это большая Label-кнопка в центре модала (confirm_dialog.rs:85-90); клик по
нему тоже отменяет диалог, что неожиданно.

Это может быть осознанным выбором «клик мимо = отмена», но он расходится с
планом и заслуживает фиксации.

**Рекомендация:** либо закрывать только по `ID_CANCEL`/Esc (соответствует
«модал модален»), либо оставить клик-мимо-отмену, но убрать `ID_MESSAGE` из
числа «отменяющих» и задокументировать поведение.

## 7. Пустой/частичный шаг undo при вставке, если `add_sticker` не смог загрузить файл

`paste_from_clipboard` коммитит снимок **до** `add_sticker` (overlay_manager.rs:830
и 842), а `add_sticker` при неудаче `renderer.load_image` молча выходит
(overlay_manager.rs:1381-1386), не добавив стикер. Если все файлы из `CF_HDROP`
имеют «подходящее» расширение, но не декодируются рендерером (0-байтный `.png`,
переименованный `.txt` → `.png`), в историю уходит снимок, под которым ничего не
изменилось → `Ctrl+Z` становится no-op (та же болезнь, что в M2_SLICE_REVIEW,
пункт 1, только уже у вставки).

**Рекомендация:** коммитить снимок только после того, как реально добавлен хотя
бы один стикер (или откатывать снимок, если все `add_sticker` не сработали).

## 8. Автоповтор Esc во время модала: удержание закрывает диалог и выходит из режима

`handle_key` разбирает Esc в две ветки: пока модал открыт — «закрыть модал»
(overlay_manager.rs:708-711), после закрытия — «выход из режима»
(overlay_manager.rs:716-719). При удержании Esc `WM_KEYDOWN` повторяется
(автоповтор системы, `pressed: true` каждый раз): первый повтор закрывает модал,
второй — выходит из режима редактирования. Однократный Esc работает верно;
проблема только в повторе (и в том, что «закрыть диалог» и «выйти из режима» на
одной клавише конфликтуют для этого случая).

Та же болезнь, что уже отмечалась для `Ctrl+D`/`Ctrl+Z` (M2_SLICE_REVIEW,
пункт 9): повторные `pressed: true` не дебаунсятся.

**Рекомендация:** дебаунсить повтор того же `vk` (координатор или wndproc), что
заодно закрывает и это, и старое замечание.

## 9. Мелочи

- **`HotkeyConflict` — только warn-лог.** Обработчик (overlay_manager.rs:454-458)
  фиксирует конфликт хоткея в лог — это лучше, чем тихая потеря (срез закрыл
  пункт M2_SLICE_REVIEW, пункт 9), но пользователю по-прежнему ничего не
  сообщается; окно работает, в режим редактирования войти нельзя. Сознательное
  упрощение (нужен канал в Tauri/трей), зафиксировать как открытую задачу.
- **`paste_from_clipboard` блокирует message-loop координатора.** Чтение буфера
  (`clipboard::read_image`, clipboard.rs:48) при занятом буфере ждёт до ~500 мс
  (25 × 20 мс), плюс `materialize` — диск + декод. Всё это синхронно в
  `run`-цикле (overlay_manager.rs:435-505): пока вставка идёт, события мыши/клавиш
  копятся в канале. Не гонка и не потеря — просто задержка обработки; пометить
  для будущего выноса с основного цикла.
- **Shift+клик держит Win32-захват мыши до отпускания** без жеста
  (overlay_manager.rs:980-986): `MouseMove` с `dragging=true` после shift-клика
  уходят в `apply_gesture`, который с `gesture == None` возвращает `false`
  (overlay_manager.rs:1182-1184). Безвредно, но лишний захват — задел для
  будущего мульти-драга (там Shift+клик должен, видимо, начинать групповой драг).

## 10. Что проверено и корректно (не тратить время на повторную проверку)

- **Модал блокирует сцену и историю по всем входам**: `MouseDown`/`MouseMove`/
  `MouseUp` в `handle_input` (overlay_manager.rs:960-964, 1046-1051, 1061-1102),
  клавиши в `handle_key` (overlay_manager.rs:707-714) — мимо модала ничего не
  проходит; `Ctrl+Z`/`Ctrl+D`/`Ctrl+V`/повторный `Delete` во время модала
  игнорируются. `toggle_edit_mode` корректно сбрасывает `confirm`
  (overlay_manager.rs:536).
- **Марка не трогает `Config`** — только `edit.selection`/`edit.marquee`, поэтому
  не мешает снапшотной undo-модели и не откатывается через `apply_transform`;
  `Gesture::start()` честно возвращает `None` для `Marquee`
  (overlay_manager.rs:160-168).
- **Один снимок на батч-удаление и на `Ctrl+D`**: `begin_delete`
  (overlay_manager.rs:665) и `Ctrl+D` (overlay_manager.rs:775) — по одному
  `commit_undo_snapshot` на всю операцию; `Ctrl+Z` снимает пачку целиком.
- **`paste_from_clipboard`**: `Files` фильтрует по расширению до коммита
  (overlay_manager.rs:821-827), пустая вставка → `false` без снимка; `Png`/`Bmp`
  материализуются с атомарной записью (paste.rs:78-89); один снимок на пачку
  файлов — согласуется с M2_WIRING_PLAN §9Б. Ошибки чтения буфера и
  материализации логируются, состояние не меняется.
- **Shift+клик**: `changed` считается по `before != ids` (overlay_manager.rs:986);
  тумблинг добавления/удаления — по контракту `shift_click` (SPEC 3.2); жест не
  начинается (мульти-драг вне среза) — документировано.
- **`confirm_dialog`** корректно переиспользует существующие примитивы
  (`build(count, center)`, `message_for`), центр модала — центр `selection.bounds()`
  с фолбэком на центр экрана (overlay_manager.rs:763-768).
- **Марка рисуется между стикерами и рамками выделения** (overlay_manager.rs:1309-
  1340), модал — самый верх (overlay_manager.rs:1354-1366); порядок слоёв совпадает
  с M2_WIRING_PLAN §11.
- **`prune` после удаления/undo** (overlay_manager.rs:1080, 605) не даёт выделению
  ссылаться на мёртвые id; ресет `marquee`/`confirm`/`pending_snapshot` при выходе
  из режима — симметричный и полный.

## 11. Приоритеты для координатора

1. `StickerSource::Pasted` для материализованных вставок + удаление файла при
   delete/undo (п. 1) — SPEC 2.5, накапливание мусора на диске.
2. Синхронизировать settings в снапшоте модала (или исключить settings из
   снимков) — undo не должен откатывать «Больше не спрашивать» (п. 2).
3. Зафиксировать/починить границы марки: восстановление выделения на
   `CaptureLost` (п. 3) и обновление марки после старта без порога (п. 4).
4. Решить судьбу скрытых стикеров в марке (п. 5) и «клик мимо модала закрывает
   диалог» против плана (п. 6).
5. Мелочи из п. 7–9 — по остатку времени.

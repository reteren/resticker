# M3 — ревью шагов 5/6: hot-plug (WM_DISPLAYCHANGE) + автомат ADR-011, и фикс цикла восстановления устройства

Статус: **независимое ревью, без изменений кода**. Ветка `feat/m2-edit-mode`,
коммиты `1d08b7a` («M3 hot-plug wiring — WM_DISPLAYCHANGE diff + ADR-011 tick»,
overlay_manager.rs +457/−68) и `3f2dc47` («stop persistent full-GPU-reload loop on
partial recovery failure», +37/−2; вошёл в ревью как предшествующий фикс того же
файла). Прочитаны диффы обоих коммитов целиком и актуальный код
`crates/resticker/src/overlay_manager.rs` (3544 строки): `create_monitor_state`/
`teardown_monitor_state`, ветки `MonitorsChanged`/`Tick`/`DpiChanged`, цикл `run()`
(тик-поток, `Shutdown`), MouseUp-коммит жеста (`on_user_edit`), `redraw_all`/
`recover_device` (флаг `broken`), `redraw` (марка и фильтры), `toggle_edit_mode`;
`crates/rst-core/src/monitor_loss.rs` (автомат: `prev_snapshot`, `losses`, `edited`).
Сверено с дизайном `docs/M3_HOTPLUG_DESIGN.md` (§1–§5) и `docs/M3_PREP_NOTES.md`
(§3.6, §5.3). Интерактивного unplug/replug и смены primary вживую нет (автор:
build/clippy/test + smoke-launch).

**Общий вердикт:** сшивка по главным путям корректна и следует дизайну — тик даёт
таймеру ADR-011 истечь, дифф «против живого состояния» делает N дубликатов
`WM_DISPLAYCHANGE` идемпотентными, перерегистрация хоткея строго через снос окна
(join гарантирует `UnregisterHotKey` до `RegisterHotKey`), системные действия
структурно вне undo, `on_user_edit` подключён в единственную точку. Фикс `broken`
убирает бесконечный цикл полного GPU-восстановления корректно. **Найдено одно
живое средне-тяжёлое несоответствие**: ветка отмены марки в `teardown_monitor_state`
недостижима (порядок переназначения `cursor_monitor`), и четыре замечания ниже
(асимметрия undo ↔ память трекера, teardown на живом мониторе при смене primary,
потеря хоткея при неудаче создания окна, расхождение снимков при смене разрешения).

---

## 1. Проверено по явным вопросам

### 1.1 Тик и таймер ADR-011 — корректно, ADR-006 не нарушен

Поток-«будильник» (`LOSS_TICK_PERIOD = 1 с`) — тот же паттерн «поток + сообщение
в общий канал», что у пер-мониторных форвардеров; выходит сам по ошибке `send`
(координатор завершился). Ветка `Tick` зовёт `on_monitor_snapshot` с
`last_snapshot` — снимок не меняется между `MonitorsChanged`, дифф внутри трекера
no-op, работают только таймеры. `need_redraw` выставляется только при реальных
действиях — «перерисовать по таймеру» в кодовой базе нет. Стартовый прогон
трекера присутствует (обязателен: иначе первый `MonitorsChanged` принял бы живые
с старта мониторы за пропавшие — `prev_snapshot` инициализируется).

### 1.2 Дубликаты `MonitorsChanged` — идемпотентны, проверено по шагам

`WM_DISPLAYCHANGE` рассылается каждому окну; дифф идёт по `monitors_map` (живое
состояние), не по копии. Второй дубликат: шаг 1 пропущен (`primary_id` уже
обновлён первым событием), шаг 2 — все id уже в карте, шаг 3 — `gone` пуст, шаг 5 —
`prev_snapshot == current` внутри трекера → действий нет. Единственный след —
лишний `need_redraw = true`. Трекер при этом получает тот же снимок — повторных
`HideSticker`/`Migrate` не выдаёт (переходы считаются только между разными
снимками).

### 1.3 Порядок перерегистрации хоткея — безопасен

Смена primary: `teardown_monitor_state(old_primary)` → `OverlayWindow::drop`
шлёт `WM_CLOSE` и **join'ит** pump-поток → `RegisteredHotkey` (тип `!Send`)
дропается на своём потоке → `UnregisterHotKey` выполнен строго до
`RegisterHotKey` нового окна. `HotkeyConflict` на «переезде» невозможен. Старый
primary, оставшийся подключённым, пересоздаётся с `(None, None)`; новый — с
хоткеями; прочие появившиеся — без хоткеев. Стартовый цикл и hot-plug идут через
один `create_monitor_state` (поведение старта не изменилось: `edit_active = false`,
как и раньше).

### 1.4 `apply_loss_actions` — структурно вне undo, спрайты синхронны

Вызывается ровно из двух мест (ветки `MonitorsChanged`/`Tick`), ни одно не
касается `undo_stack`/`redo_stack`/`pending_snapshot`; `config::save` выполняется.
`HideSticker`/`RestoreVisibility` не трогают спрайты (видимость читается из cfg
при redraw); `Migrate`/`ReturnHome` пишут placement/rotation в cfg **и** в спрайт
синхронно. `apply_transform`-а (и, значит, undo-снимков) на этом пути нет —
гарантия «системная миграция не отменяема Ctrl+Z» соблюдена.

### 1.5 `on_user_edit` — единственная точка, гейты корректны

`gesture_sticker_id` захватывается **до** `edit.gesture.take()`; ветка под гейтом
`before != *cfg` (клик без движения не триггерит); Rotate попадает намеренно
(ReturnHome восстанавливает `origin.rotation`); `ClearOrigin` эмитится только при
`origin.is_some()`. Совпадает с дизайном §4.1; toolbar/клавиатура placement не
мутируют — точек там нет, как и задумано.

### 1.6 `broken` (3f2dc47) — цикл устранён, повторные попытки возможны

`redraw_all` пропускает `broken`-мониторы — их `present` не вызывается, второй
`DeviceLost` от устаревшей цели невозможен; второй `redraw_all` после
`recover_device` не зацикливается. `recover_device` при следующей потере
устройства пробует `WindowTarget::new` для **всех** мониторов (включая `broken`),
снимая флаг на успехе; в `Err`-ветке `continue` не даёт тронуть устаревшую цель
(`set_dpi_scale` для неё не вызывается). Дополнительно: hot-plug replug сломанного
монитора идёт через `teardown` + `create_monitor_state` → свежее окно+цель на
текущем устройстве, `broken: false` — replug лечит флаг без потери устройства.

## 2. Найденные проблемы

### 2.1 (средне) Отмена марки в `teardown_monitor_state` — недостижимый код из-за порядка переназначения `cursor_monitor`

- **Где:** overlay_manager.rs:242-254. Сначала `if edit.cursor_monitor == *id {
  edit.cursor_monitor = new_primary_id; cursor_pos = (0,0); }`, **потом**
  `Some(Gesture::Marquee { .. }) => edit.cursor_monitor == *id`.
- **Что на самом деле:** для активной марки `cursor_monitor` **всегда** равен её
  монитору — каждый `MouseMove` окна ставит `edit.cursor_monitor = monitor_id`
  (overlay_manager.rs:2672), а марка живёт только на своём окне. Переназначение
  выше выполняется ровно в этом же случае → сравнение `edit.cursor_monitor == *id`
  после него всегда `false` → ветка отмены марки недостижима именно тогда, когда
  должна сработать. Дизайн (M3_HOTPLUG_DESIGN §2, чек-лист: «незавершённый жест
  стикера пропавшего монитора — отменить как CaptureLost») и комментарий в коде
  (203-204) намеревались обратное.
- **Следствие при сносе монитора посреди марки:** `Gesture::Marquee` (с `before`),
  `edit.marquee`, `marquee_started` и частичное выделение остаются висеть;
  `redraw` рисует марку на новом `cursor_monitor` (`if edit.cursor_monitor ==
  *monitor_id`, overlay_manager.rs:3280) — «призрачная» рамка с координатами
  мёртвого монитора в DIP нового; тулбар при этом скрыт (`edit.marquee.is_some()`
  → `rebuild_toolbar` возвращает `None`, overlay_manager.rs:2107); следующий
  `MouseUp` где угодно молча «коммитит» stale-выделение. `Drag`/`Resize`/`Rotate`
  отменяются корректно — проверка по `monitor_id` стикера, от курсора не зависит.
- **Фикс:** вычислять `cancel_gesture` **до** переназначения `cursor_monitor`
  (или запомнить `let cursor_was_here = edit.cursor_monitor == *id;` до блока
  переназначения).

### 2.2 (низкое-среднее) Undo не откатывает память трекера — асимметрия `edited` после `on_user_edit` + `Ctrl+Z`

- **Где:** MouseUp-коммит (overlay_manager.rs:2982-2989) + `MonitorLossTracker::edited`
  (monitor_loss.rs). `on_user_edit` навсегда (для сессии) добавляет id в `edited`;
  снимок жеста (`before`, взят на `MouseDown`) содержит `origin = Some`, если стикер
  был смигрирован.
- **Сценарий:** стикер смигрирован (origin=Some) → пользователь тащит его
  (on_user_edit: origin=None, id в `edited`) → `Ctrl+Z` → cfg восстановлен:
  placement до драга, **origin снова Some** → монитор-«дом» возвращается →
  автовозврат (ветка (d) автомата) пропускает стикер: `edited` его держит, хотя
  правка «отменена». Стикер остаётся на месте миграции с «мёртвым» origin,
  домой не возвращается. Обратная сторона «системное — не undo-емо»: память
  трекера не участвует в undo, и впервые это проявляется внутри одной транзакции.
- Тяжесть низкая (консервативно: стикер никуда не теряется), но поведение
  неочевидно. Варианты: документировать как ограничение; либо при undo
  перепрогонять трекер по восстановленному cfg (сложно); либо не гейтить
  автовозврат по `edited` при `origin.is_some()`.
- Мелочь того же блока: дизайн §4.1 ставит `on_user_edit` **до**
  `commit_undo_snapshot`, реализация — после. На снимок это не влияет (коммитится
  `before` с MouseDown в обоих случаях) — косметическое расхождение.

### 2.3 (низкое) Смена primary, когда старый primary остался подключён — teardown «бьёт» по живому монитору

- **Где:** шаг 1 ветки `MonitorsChanged` (overlay_manager.rs:1081-1116) зовёт
  `teardown_monitor_state(old_primary)` **до** проверки «остался ли монитор в
  new_infos». Для ещё подключённого (просто переставшего быть primary) монитора
  это означает: prune выделения стикеров **живого** монитора, сброс
  `cursor_monitor`/`cursor_pos` в (0,0), отмену активного жеста — только ради
  переезда хоткея.
- **Следствие:** пользователь в режиме редактирования при смене primary в
  настройках Windows теряет выделение и позицию панели у курсора; стикеры при
  этом не тронуты (правильно), но disruption заметен. Дизайн сознательно реюзнул
  teardown для пересоздания окна (§2 «Хоткей»), но побочный эффект на edit-state
  живого монитора не отметил.
- **Вариант:** параметр «не трогать edit-state» (для hotkey-пересоздания) либо
  отдельная лёгкая ветка «пересоздать окно без хоткея».

### 2.4 (низкое) Потеря хоткея при неудаче создания окна нового primary

- **Где:** шаг 1: `create_monitor_state` нового primary вернул `None` (окно/цель
  не создались) → шаг 2 увидит монитор не в карте и создаст его окно с
  `(None, None)` — **без хоткея**, а старый primary уже снесён (и, если он ещё
  подключён, пересоздан тоже без хоткея). Глобальный хоткей остаётся
  незарегистрированным до следующей смены primary.
- Degraded-путь (неудача создания окна — редкий системный сбой, логируется), но
  потеря регистрации молчаливая. Вариант: в шаге 2 не пересоздавать монитор,
  только что назначенный primary (либо повторить создание с хоткеем).

### 2.5 (низкое, расширение known-gap) Смена разрешения рассинхронизирует `monitor_bounds` и окно

- Заявленный в коммите gap: «монитор, остающийся подключённым при смене
  разрешения, сохраняет старый размер окна/цели». Уточнение: `WM_DISPLAYCHANGE`
  при смене разрешения **тоже** приходит, и шаг 4 ветки обновляет
  `monitor_bounds` из `new_infos` (новые `bounds_px`) при **старом** размере
  окна/цели → перепривязка (`rebind_monitor_by_center`) начнёт считать по новым
  границам, а окно рисует старую область; `monitor_geometry` и `monitor_bounds`
  расходятся. В `DpiChanged` обе копии обновляются согласованно — в смене
  разрешения нет. Плюс: если новые `bounds_px` при этом меньше окна, rebind
  предложит координаты, которых окно не покрывает.
- Тяжесть — в рамках признанного gap (отложен), но зафиксировать расхождение
  именно снимков стоит: одно «окно == монитор» инвариантом больше не является.

### 2.6 (замечание) Все мониторы `broken` = тихий чёрный экран до рестарта

- Если `WindowTarget::new` падает **для всех** мониторов в одном `recover_device`,
  все получают `broken`, следующий `redraw_all` ничего не рисует и возвращает
  `false` → `recover_device` больше не вызывается (детект потерь идёт от
  `present` здоровой цели) → вечный чёрный экран с единственным логом. До фикса
  была бы бесконечная дорогая петля; теперь — тихая остановка. На практике
  маловероятно (устройство только что создано), но «последний монитор тоже
  сломан» не имеет пути восстановления, кроме рестарта — стоит упомянуть в
  комментарии к флагу.

## 3. Что проверено и корректно (не тратить время на повторную проверку)

- **Хоткей** (§1.3): снятие регистрации строго до новой через join pump-потока;
  появление/пропажа мониторов — по одному коду `create_monitor_state`/
  `teardown_monitor_state`; не-primary окна без хоткеев; `set_interactive` для
  новых окон при `edit.active` (и распространение через `toggle_edit_mode`).
- **Дубликаты и идемпотентность** (§1.2); стартовый прогон трекера (§1.1);
  `Tick` без лишних redraw (ADR-006).
- **Undo-безопасность системных действий** (§1.4): оба вызова `apply_loss_actions`
  не касаются истории; save выполняется; спрайты синхронны в `Migrate`/
  `ReturnHome`.
- **`on_user_edit`** (§1.5): одна точка, гейт по `before != *cfg`, захват id до
  `gesture.take()`, Rotate включён.
- **teardown** (кроме п. 2.1): порядок дропа `target` → `overlay` безопасен
  (M3_STEP4_REVIEW п. 2.3); форвардер завершается сам; prune выделения и отмена
  Drag/Resize/Rotate по `monitor_id` стикера — корректны; стикеры не трогает
  (это трекер); `rebuild_ui_panels` вызывается.
- **`broken`** (3f2dc47): skip в `redraw_all`, установка/снятие в `recover_device`,
  повторная попытка при следующей потере устройства, hot-plug replug лечит флаг;
  `continue` в Err-ветке не трогает устаревшую цель.
- **Жизненный цикл потока тика**: `Shutdown => break` (overlay_manager.rs:949)
  завершает цикл несмотря на вечно живой Sender тика; тик-поток и форвардеры
  выходят сами по ошибке `send`.
- **`primary_id`** обновляется в шаге 6 и используется `AddSticker`/фолбэками;
  `monitor_bounds` фильтруется по «окно создано» (как на старте).

## 4. Приоритеты для координатора

1. **Недостижимая отмена марки (п. 2.1)** — порядок строк в `teardown_monitor_state`:
   вычислить `cancel_gesture` до переназначения `cursor_monitor`. Единственный
   живой баг среднего веса.
2. **Асимметрия undo ↔ память трекера (п. 2.2)** — решить судьбу `edited`/origin
   при undo или зафиксировать как ограничение.
3. **teardown на живом мониторе при смене primary (п. 2.3)** — не трогать
   edit-state при hotkey-пересоздании.
4. **Потеря хоткея при неудаче создания окна (п. 2.4)** и расхождение снимков при
   смене разрешения (п. 2.5) — закрыть или задокументировать шире заявленного gap.
5. Мелочи: п. 2.6 (комментарий к `broken`), косметика порядка `on_user_edit` в
   MouseUp-коммите.

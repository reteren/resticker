# Окно настроек (Tauri) — дизайн и решения

M0 построил только пустой каркас вкладок (`ui/index.html`, четыре кнопки без
содержимого). Реального окна настроек по SPEC.md §10 не было вообще — этот
срез добавляет его целиком: стилистику, все четыре вкладки с реальным
содержимым (кроме «Пресетов» — см. §5) и Rust-слой команд.

## 1. Источник стилистики

По прямому запросу пользователя — 1:1 копия того же визуального языка, что
уже используется в его проекте `reteren/Reshot` (окно настроек на Tauri,
локально — `W:\Reshot\src\reshot-tauri`), который сам портирует
Half-Life 2 / Source VGUI диалоги из референса
`github.com/arlagonix/half-life-screen`.

- `crates/resticker/ui/styles.css` — CSS-переменные, классы (`.wrapper`,
  `.tab`, `.button`, `.checkboxWrapper`, `.numberInput`/`.textInput`, `.slider`
  и т.д.) скопированы дословно из Reshot; акцент — тот же тил `#3c9898`
  (сам Reshot заменил им референсный HL2-оранжевый `#ff9c00`).
- Шрифт — Roboto (тот же, что у Reshot), но не через npm/`@fontsource`
  (у resticker нет бандлера для UI — `frontendDist: "ui"`, статика без
  сборки): шесть `.woff2`-файлов (latin+cyrillic, вес 100/300/700)
  скопированы напрямую из `node_modules/@fontsource/roboto/files` в
  `ui/fonts/` и подключены через локальный `@font-face`.
- Окно — frameless/transparent/acrylic (`tauri.conf.json`:
  `decorations: false`, `transparent: true`, `windowEffects: ["acrylic"]`),
  как у Reshot — не скруглено дополнительно через DWM
  (`DWMWA_WINDOW_CORNER_PREFERENCE`), т.к. `border-radius: 8px` панели плюс
  acrylic-фон дают приемлемый результат без него; Reshot скругляет через DWM
  дополнительно — здесь сочтено избыточным для среза (можно добавить позже,
  если визуально не устроит).
- Три SVG (`close.svg`, `radio_default.svg`, `radio_checked.svg`) тоже
  скопированы из Reshot as-is — radio-кнопки пока не используются ни в одной
  вкладке, скопированы про запас (тот же словарь компонентов).

## 2. Архитектура: единственный писатель `config.json`

Ключевой принцип, продиктованный уже существующей архитектурой координатора
(`overlay_manager.rs`): **координатор (поток оверлея) — единственный, кто
пишет `config.json`**, тем же паттерном, что уже был у `add_sticker`
(единственная команда, существовавшая до этого среза).

- `get_config` (Tauri-команда) читает файл **напрямую с диска** — не через
  координатор. Это безопасно: координатор сохраняет `config.json` сразу
  после КАЖДОЙ своей мутации `cfg` (в overlay_manager.rs таких точек
  сохранения уже несколько десятков), так что свежий файл на диске и есть
  текущее состояние с точностью до миллисекунд.
- Все остальные новые команды (`update_settings`, `update_hotkeys`,
  `set_sticker_enabled`, `delete_sticker`, `reset_sticker_position`,
  `reset_sticker_transform`, `relink_sticker`, `reset_all_stickers`,
  `delete_all_stickers`) — тонкие обёртки, которые ТОЛЬКО парсят
  аргументы (`Uuid::parse_str` и т.п.) и шлют `OverlayCommand` в
  координатор через уже существующий канал (`OverlayHandle::send`,
  тот же механизм, что `add_sticker`). Всю мутацию `cfg` +
  `config::save` + пересборку спрайтов/окклюдеров делает координатор в
  `run()`, тем же кодом, что и жесты редактирования.
- `reveal_in_explorer` — единственное исключение: чисто читающее действие
  над файловой системой (`explorer.exe /select,<path>`), `cfg` не
  трогает вообще, поэтому Tauri выполняет его сам, без похода в
  координатор.

Так весь класс гонок «Tauri-поток и координатор оба пишут файл
одновременно» структурно исключён — тот же принцип, что уже применялся к
видео (`VideoSource`/`AudioSource` синхронизируются из `cfg`, а не
наоборот, см. `docs/M5B_VIDEO_DESIGN.md` и коммит `0f2b1ec`).

## 3. Вкладка «Стикеры»

Список стикеров (превью — генерическая иконка типа медиа, не декодированный
кадр: см. §5, «отложено») с действиями на каждый:
- включить/выключить — реюзает существующий `sticker.visible`
  (`ops::set_visible_many`), НЕ отдельное поле `Sticker.enabled` — ~~это
  последнее существует в модели, но не читается нигде в коде (мёртвое
  поле, не введённое ни одной фичей M1-M5); заводить вторую, независимую
  от уже работающей систему «показать/скрыть» сочли ненужным усложнением.~~
  **Догнано после среза (2026-09-16):** утверждение о мёртвом поле устарело:
  `Sticker.enabled` читается координатором в фильтрах стикеров
  (поле определено в `crates/rst-core/src/model.rs:349-364`, чтение —
  `crates/resticker/src/overlay_manager.rs:10344-10347` и `10401-10404`),
  поэтому поле не является «нигде не читаемым».
- удалить / сбросить позицию / сбросить размер и поворот / показать в
  проводнике / переуказать файл — SPEC.md §10, реализованы через новые
  `rst_core::ops::{reset_position, reset_transform_and_size, relink_file}`
  плюс `OverlayCommand`-обёртки.
- «Сбросить размер» берёт натуральный размер из УЖЕ загруженного `Sprite`
  (`sticker_natural_size` в overlay_manager.rs читает `sprite.texture`/
  `sprite.video.y` width/height) — не передекодирует файл заново, дёшево.
- Массовые действия «Сбросить всё»/«Удалить всё».

## 4. Вкладка «Общие»

Все существующие поля `Settings` получили реальные контролы. Два из них —
не просто чтение/запись флага, а настоящая enforcement-логика,
добавленная этим же срезом:

- **«Скрывать от захвата экрана»** — `OverlayWindow::set_capture_affinity`
  (новый метод в rst-win32, `SetWindowDisplayAffinity`/
  `WDA_EXCLUDEFROMCAPTURE`), применяется при создании каждого окна
  монитора (`create_monitor_state`, все 4 точки вызова получили новый
  параметр) И живьём при изменении настройки
  (`OverlayCommand::UpdateSettings` перебирает `monitors_map` и
  переприменяет). Проверяет результат через `GetWindowDisplayAffinity`
  (SPEC.md §8: «программа СЛЕДУЕТ проверять результат») — логирует
  предупреждение, если Windows молча не применила флаг.
- **«Не перекрывать панель задач»** — enforcement уже существовал
  (`occluders::is_occluder` и `refresh_occlusion` в overlay_manager.rs
  давно принимают `never_overlap_taskbar`), просто не было способа
  включить настройку из UI. Этот срез добавляет только сам чекбокс;
  `OverlayCommand::UpdateSettings`-обработчик пересчитывает
  `occluder_cache` сразу же, не дожидаясь следующего `Windows(Changed)`.

## 5. Вкладка «Управление» (хоткеи)

Три поля (режим редактирования, показать/скрыть все, заглушить всё) —
захват комбинации кликом по полю + `keydown`, формат строки собирается
JS-стороной под словарь `rst_win32::hotkey::HotkeyCombo::parse`
(`Ctrl`/`Alt`/`Shift`/`Win` + одна буква/цифра/`F1`-`F24`).

**Догнано после среза (2026-09-16):** живая перерегистрация
`RegisterHotKey` сделана, отложенной больше не числится. `Применить`
отправляет `OverlayCommand::UpdateHotkeys`, координатор пишет
`config.json` и зовёт `OverlayWindow::reload_hotkeys` у окна основного
монитора; окно снимает прежний набор и ставит новый на своём потоке
(`WM_APP_REREGISTER_HOTKEYS`, снятие строго до регистрации — иначе
комбинация конфликтовала бы сама с собой), а итог возвращает событием
`OverlayEvent::HotkeysReloaded` (занятые комбинации — одним тостом).

Набор для регистрации собирает ОДНА функция —
`rst_win32::overlay::all_hotkey_combos(&cfg.hotkeys)`, — и её же зовёт
создание окна монитора (`create_monitor_state` принимает готовый список,
а не пять отдельных комбинаций). До этого координатор держал разобранные
комбинации в локальных переменных, посчитанных один раз при старте: после
живой смены бинда первое же переподключение монитора или смена основного
экрана возвращали старый хоткей. Второй копии набора больше нет.

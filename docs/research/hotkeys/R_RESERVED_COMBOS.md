# R: Зарезервированные и «молча не работающие» сочетания клавиш Windows

**Документ:** `docs/research/hotkeys/R_RESERVED_COMBOS.md`
**Статус:** разведка + измерения (H2)
**Дата:** 2026-08-26
**Ветка:** `feat/m2-edit-mode`
**Цель:** Собрать и обосновать список сочетаний, которые Windows либо зарезервировала
за собой, либо обрабатывает раньше слоя глобальных хоткеев (`RegisterHotKey`/`WM_HOTKEY`),
и на этом основании построить предупреждение пользователю в настройках. Повод: пользователь
назначил себе `Alt+Shift+S`, `RegisterHotKey` вернул успех, но нажатие ни разу не дошло
до программы (измерено пользователем).

**Измерительный стенд:** `spike/hotkey_probe` (отдельный крейт, в workspace не входит).
Машина: Windows 11 Pro, сборка 26200 (24H2+), языки ru + en-US, по одной раскладке на
язык. Ключ `HKCU\Keyboard Layout\Toggle` на машине **отсутствует** (то есть Windows
использует настройки по умолчанию). Все «ИЗМЕРЕНО» ниже — с этого стенда, если не сказано
иное; эмуляция нажатий — через `SendInput`.

Пометки: **ИЗМЕРЕНО** — проверено на стенде; **ДОК** — из документации Microsoft и
достоверных отчётов; **ОТЧЁТЫ** — массовые отчёты пользователей (не единичный случай).

## 1. Резюме: что можно брать, что нельзя

| Категория | Примеры | Исход | Что делать |
|---|---|---|---|
| Переключатель языка/раскладки (Alt+Shift, Ctrl+Shift) | `Alt+Shift+S`, `Ctrl+Shift+1` | Регистрация **успешна**, нажатие на многих машинах **не доходит** | Предупреждать, читая реестр `HKCU\Keyboard Layout\Toggle` |
| Сочетания с Win | `Win+D`, `Win+R`, `Win+S`, `Win+Space` | Регистрация **отвергается системой** (`ERROR_HOTKEY_ALREADY_REGISTERED`), часть обрабатывается до слоя хоткеев | Предупреждать (текст + список) |
| Alt+<буква> | `Alt+S` | Регистрация успешна, **доходит** (измерено) | Не предупреждать |
| Низкоуровневый хук другого приложения | любой хоткей, чью клавишу хук глотает | Регистрация **успешна**, нажатие **не доходит** | Не предсказать из реестра — это природа хуков; упомянуть в доке |
| Прочее системное | `Alt+Tab`, `Ctrl+Esc`, `Alt+F4`, `Ctrl+Alt+Del`, `PrtScr`, `F12` | Регистрация **отвергается** (измерено на стенде, кроме документированных исключений) | В парсер `HotkeyCombo` эти клавиши не входят (кроме `F12`) — предупреждать только F12 |

Главный вывод: **успешная регистрация не гарантирует, что нажатие дойдёт**. Есть два
независимых класса тихого отказа: (а) системный слой ввода съедает клавиши (переключатель
раскладки, часть Win-комбинаций) — и `RegisterHotKey` при этом может вернуть успех;
(б) низкоуровневый хук другого приложения глотает клавишу — `RegisterHotKey` **всегда**
вернёт успех, потому что о хуках он не знает (измерено, §6).

## 2. Переключатель раскладки: Alt+Shift / Ctrl+Shift

### 2.1. Что это и как работает

Windows умеет переключать язык ввода и раскладку клавиатуры по горячей клавише.
По умолчанию **Left Alt+Shift переключает язык ввода**, а Ctrl+Shift — раскладку внутри
языка (историческое поведение; при одной раскладке на язык Ctrl+Shift ничем себя не
проявляет). С Windows 8 появился и второй переключатель — `Win+Space`.

Ключевой механизм (**ДОК**, Раймонд Чен, The Old New Thing 2026-05-13): переключение
языка по хоткею инициируется **системным слоем ввода** — приложение получает
`WM_INPUTLANGCHANGEREQUEST` в фоновое окно, а не само нажатие. То есть переключатель
живёт **ниже** слоя `RegisterHotKey`/`WM_HOTKEY`: клавиши, образующие комбинацию
переключателя, могут быть съедены ещё до поиска хоткея. Отсюда и «молчаливый» отказ:
`RegisterHotKey` не имеет никакого отношения к переключателю и не может ни узнать о нём,
ни отказать.

Практика подтверждает (**ОТЧЁТЫ**): на Windows 11 комбинации `Ctrl+Shift+<клавиша>`
не доходят до приложений, даже когда переключатель формально снят
(«ctrl+shift+0 input is not received by win32 apps», Microsoft Q&A 3846917); про
`Alt+Shift` в приложениях — десятки жалоб (Microsoft Q&A 4098979 и др.).

### 2.2. Реестр: `HKCU\Keyboard Layout\Toggle`

Значения (тип `REG_SZ`):

| Значение | «1» | «2» | «3» |
|---|---|---|---|
| `Hotkey` (легаси, Win10 ещё читает) | Left Alt+Shift | Ctrl+Shift | выключено |
| `Language Hotkey` (переключение языка) | Alt+Shift | Ctrl+Shift | выключено |
| `Layout Hotkey` (раскладка внутри языка) | Alt+Shift | Ctrl+Shift | выключено |

Источники: **ДОК** — Microsoft Q&A 4354667 (Hotkey: 1/2), Winaero 2018 (Hotkey: 1..4,
где 4 — клавиша `\``), gist «Disable Language Hotkey» и Super User 698037
(Language/Layout Hotkey: 1/2/3). Пробелы в значениях возможны (`" 3 "`) — при чтении
нужен trim.

**Если ключа нет вовсе** — Windows применяет настройку по умолчанию: язык переключается
Alt+Shift (**ИЗМЕРЕНО** на стенде: голый `Shift+Alt` без зарегистрированного хоткея
переключил раскладку `04090409 → 04190419`; дополнительно — **ДОК**: диалог «Сочетания
клавиш ввода языка» показывает Left Alt+Shift как значение по умолчанию).

### 2.3. Измерения на стенде (Win11 26200, ключа Toggle нет)

Прогон `spike/hotkey_probe` (эмуляция через `SendInput`, все порядки модификаторов,
задержки 5–50 мс, состояния Toggle: отсутствует / =1 / =2):

* `Alt+Shift+S`, `Alt+Shift+F24`, `Ctrl+Shift+S`, `Ctrl+Shift+F24` — **зарегистрировались
  и WM_HOTKEY пришёл** во всех прогонах и при всех настройках Toggle (включая явный =1 и =2).
  То есть на ЭТОЙ сборке зарегистрированный хоткей выигрывает у переключателя.
* Голый (без хоткея) `Shift+Alt` один раз из трёх прогонов переключил раскладку —
  переключатель активен, но эмуляция через `SendInput` срабатывает нестабильно
  (само по себе наблюдение о таймингах переключателя).
* `Win+Space` без регистрации переключает раскладку (измерено).

**Вывод по измерениям:** поведение «переключатель съел хоткей» зависит от сборки Windows
и настроек пользователя: на одном и том же сочетании у одного пользователя всё работает,
у другого молча не работает (случай пользователя из задачи). Поэтому предупреждение
обязано читать **реальную настройку** из реестра и формулироваться как «на многих
машинах не доходит», а не как абсолютная истина. Настройка по умолчанию (ключ отсутствует)
трактуется как активный Alt+Shift — это подтверждено измерением.

### 2.4. Что именно съедается

Когда `Alt+Shift` назначен переключателем и срабатывает, съедается **нажатие Shift
(или Alt) в момент завершения комбинации** — раскладка переключается, а последующее
нажатие основной клавиши (`S`) приходит в систему уже «после переключения»: совпадения
с зарегистрированным хоткеем может не найтись, потому что состояние модификаторов,
участвовавших в переключателе, для слоя хоткеев уже не то. Плюс известный артефакт —
«залипшие» модификаторы после переключения (жалобы в Microsoft Q&A 4098979: после
Alt+Shift раскладка переключается с задержкой, клавиши ведут себя странно). Точная
микромеханика сборко-зависима; для продукта важно одно: **регистрация успешна,
доставки нет**.

## 3. Сочетания с Win

**ДОК** (RegisterHotKey, параметр `MOD_WIN`): «Keyboard shortcuts that involve the
WINDOWS key are reserved for use by the operating system». То есть Win-комбинации —
собственность ОС. На практике (**ИЗМЕРЕНО** на стенде, `RegisterHotKey` без эмуляции):

| Комбинация | Результат регистрации |
|---|---|
| `Win+L`, `Win+Space`, `Win+Tab`, `Win+D`, `Win+R`, `Win+E`, `Win+Shift+S`, `Win+PrtScr` | **ОТКАЗ** `ERROR_HOTKEY_ALREADY_REGISTERED` (0x80070581) |
| `Win+Shift+F24` (не системная) | успех, WM_HOTKEY приходит (измерено) |

То есть оболочка регистрирует «свои» Win-сочетания через тот же `RegisterHotKey` —
поэтому наш вызов честно падает с «уже зарегистрировано». А `Win+Space` обрабатывается
слоем ввода (как переключатель раскладки, §2) — он **не регистрируется и переключает
раскладку** (измерено).

Список системных Win-комбинаций (документированное поведение Windows 10/11, частично
измерено на стенде): `Win` (одна), `Win+L` (блокировка), `Win+D`, `Win+M`, `Win+Home`,
`Win+E`, `Win+R`, `Win+S`/`Win+Q` (поиск), `Win+I` (Параметры), `Win+A`, `Win+N`, `Win+W`,
`Win+X`, `Win+P`, `Win+K`, `Win+G` (игровая панель), `Win+Alt+R` (запись), `Win+V`,
`Win+H`, `Win+Z` (сетки Snap), `Win+Tab`, `Win+Ctrl+D`/`Win+Ctrl+←/→`/`Win+Ctrl+F4`
(виртуальные рабочие столы), `Win+Space` (язык), `Win+Shift+S` (фрагмент экрана),
`Win+PrtScr`/`Alt+PrtScr` (снимок), `Win+1..0` (панель задач), `Win+T`, `Win+B`, `Win+F`,
`Win+Pause`, `Win+↑↓←→` (привязка окон), `Win+Shift+↑↓←→` (перенос окна на монитор).

Примечание: часть «системных» сочетаний уходит в оболочку не через `RegisterHotKey`,
а через её собственные хуки и обработчики (например, `Win` в одиночку) — такие сочетания
могут зарегистрироваться формально, но нажатие перехватит оболочка раньше. Поэтому
предупреждение про Win должно быть категоричным, но без перечисления «работает/не
работает» для каждого сочетания.

## 4. Alt+<буква> и акселераторы меню

**ИЗМЕРЕНО** на стенде: `Alt+S` (и `Ctrl+S`) регистрируются и WM_HOTKEY приходит.
Одиночный Alt+<буква> — штатный механизм мнемоник меню, но это **прикладной**, а не
системный слой: мнемоника обрабатывается приложением, которому адресовано нажатие.
Глобальный хоткей (WM_HOTKEY) система порождает раньше и вместо доставки клавиши
фокусному окну — то есть зарегистрированное `Alt+S` перехватывает нажатие у любого
приложения с меню (**ДОК**: RegisterHotKey, «When a key is pressed, the system looks
for a match against all hot keys»).

Реальные риски Alt+<буква>:
* конфликт с прикладными хоткеями и мнемониками фокусного приложения — но не «тихий
  отказ»: наш хоткей выигрывает;
* вводные методы (китайские/японские IME) могут перехватывать Alt+<буква> для своих
  целей — **ОТЧЁТЫ**, массово не подтверждено;
* `Alt+Tab`, `Alt+Esc`, `Alt+F4`, `Alt+Space` — системные Alt-сочетания (см. §7).

Вывод: Alt+<буква> предупреждения не требует.

## 5. Alt+Tab, Alt+Esc, Alt+F4, Ctrl+Esc, Ctrl+Alt+Del, PrtScr, F12

**ИЗМЕРЕНО** на стенде (регистрация без эмуляции):

| Комбинация | Результат |
|---|---|
| `Alt+Tab` | ОТКАЗ (уже зарегистрировано) |
| `Alt+Esc` | успех (формально) |
| `Alt+F4` | ОТКАЗ (уже зарегистрировано) |
| `Alt+Space` | успех (формально) |
| `Ctrl+Esc` | ОТКАЗ (уже зарегистрировано) |
| `Ctrl+Alt+Del` | ОТКАЗ (уже зарегистрировано) |
| `PrtScr` | ОТКАЗ (уже зарегистрировано) |
| `F12` | ОТКАЗ на этом стенде; **ДОК**: F12 зарезервирован для отладчика «at all times» |

Практические источники: `Alt+F4` возвращает 1409 (`ERROR_HOTKEY_ALREADY_REGISTERED`) —
Microsoft Q&A 1020405. В парсер `HotkeyCombo` эти клавиши (Tab, Esc, Space, Del, PrtScr)
**не входят** — их нельзя назначить, поэтому предупреждение нужно только для `F12`
(клавиша входит в парсер как `F1..F24`).

## 6. Низкоуровневый хук другого приложения и RegisterHotKey

Вопрос из задачи: «Что делает RegisterHotKey, когда комбинацию уже держит
низкоуровневый хук другого приложения?»

**ИЗМЕРЕНО** на стенде: установлен `WH_KEYBOARD_LL`-хук, возвращающий 1 на keydown
`F24`. `Ctrl+Alt+F24` при живом хуке **зарегистрировался успешно**, но WM_HOTKEY **не
пришёл**; после снятия хука то же нажатие **пришло** (та же комбинация, тот же поток).

Ответ: **ошибку RegisterHotKey не возвращает**. Хуки и таблица хоткеев — два разных
механизма: `RegisterHotKey` лишь пишет запись в глобальную таблицу, а низкоуровневый
хук вызывается в потоке ввода (RIT) при обработке клавиши и, вернув ненулевое значение,
не даёт системе обработать клавишу дальше — включая поиск хоткея (**ДОК**:
LowLevelKeyboardProc: «If the hook procedure returns a nonzero value, the system does
not pass the message to the rest of the hook chain or the target window procedure»).
Поэтому любой «перехватчик» (PowerToys Keyboard Manager, AutoHotkey-подобные утилиты,
утилиты от клавиатурных вендоров) может молча съесть нашу комбинацию — регистрация
останется успешной. Из реестра это не предсказать; это вторая (и неустранимая из кода
частично) причина, почему предупреждение пользователю не может давать гарантий.

## 7. Выводы для продукта

1. Предупреждение строится на **трёх честных источниках**:
   * реестр `HKCU\Keyboard Layout\Toggle` — реальная настройка переключателя
     (Alt+Shift при значениях «1» и при отсутствии ключа/значений по умолчанию;
     Ctrl+Shift при значениях «2»);
   * статический факт: Win-сочетания в большинстве зарезервированы ОС;
   * статический факт: F12 зарезервирован отладчиком.
2. Формулировки предупреждений не дают абсолютных гарантий («на многих машинах не
   доходит», а не «не работает»): на стенде (Win11 26200) зарегистрированный
   `Alt+Shift+S` срабатывал, а у пользователя из задачи — нет.
3. Сигнатура функции (реализована в `crates/rst-win32/src/hotkey_check.rs`):

   ```rust
   /// Читает реальную настройку переключателя из HKCU и возвращает
   /// предупреждение, если комбинация рискованна.
   pub fn check_risky_combo(combo: HotkeyCombo) -> Option<HotkeyWarning>;

   /// Чистая версия: настройка передаётся явно (для тестов и UI).
   pub fn check_risky_combo_with_toggle(
       combo: HotkeyCombo,
       toggle: LayoutToggleConfig,
   ) -> Option<HotkeyWarning>;

   pub struct HotkeyWarning {
       pub combo: String,          // каноничный вид, напр. «Alt+Shift+S»
       pub explanation: &'static str, // объяснение на русском для пользователя
   }

   /// Реальная настройка переключателя раскладки.
   pub struct LayoutToggleConfig {
       pub alt_shift: bool,  // Alt+Shift назначен переключателем
       pub ctrl_shift: bool, // Ctrl+Shift назначен переключателем
   }
   pub fn read_layout_toggle() -> LayoutToggleConfig;
   ```

4. К UI функция **не подключена** — это делает координатор.

## TL;DR — честные вердикты

| Хотелка | Вердикт |
|---|---|
| Группы «как в Hyprland» (табы в одном слоте раскладки) | **Да, реально.** Наша модель + наш оверлей, чужие API почти не нужны. |
| Группа одной записью в **системном** Alt+Tab | **Нет поддерживаемого способа.** Все механизмы «убрать окно из Alt+Tab» бьют по панели задач/поведению окна и дерутся с приложением-владельцем. |
| Свой переключатель (LL-хук Alt+Tab + оверлей с превью) | **Реально, средний риск.** Перехват доказан AutoHotkey/PowerToys; превью — WGC или PrintWindow; активация окон — главная боль (foreground lock). |
| Анимации перемещения пошаговым SetWindowPos | **Условно да** для маленьких окон; **плохо** для ресайза тяжёлых приложений (браузеры/Electron). |
| Трюк «анимируем снимок, окно телепортируем» | **Реально и выглядит отлично** — весь рендер-стек уже есть. Ломается на DRM/части GPU-приложений и на скрытии оригинала. |
| Рамка активного окна | **Да, на нашем оверлее** (примитивы уже есть, `window_highlight.rs`), с клиппингом по z-order. DWMWA_BORDER_COLOR — бонус на Win11, но не замена. |

## 1. Группы: два прочтения

### 1а. Группа как слот раскладки с табами (Hyprland `group`)

Несколько окон делят один тайл; видно одно, переключение — нарисованной нами
панелью табов. **Это полностью в нашей власти:**

- Модель группы — чистая логика `rst-core` (платформенно-чистый крейт).
- Показ/скрытие участников: активное окно ставим на место тайла
  (`SetWindowPos`, кросс-процессно уже работает — `crates/rst-win32/src/window_pin.rs:139-166`
  пинит чужие окна тем же вызовом), неактивные прячем. Варианты «прятать»:
  - `ShowWindow(SW_MINIMIZE)` — побочки: анимация сворачивания, смена z-order,
    `iconic`-флаг (`crates/rst-win32/src/window_enum.rs:94`), приложение узнаёт
    о сворачивании и может остановить рендер/таймеры.
  - Увод за экран `SetWindowPos` — дёшево, окно «видимо» для приложения
    (рендер продолжается), но ломает программы, читающие свою позицию.
    [ПРЕДПОЛОЖЕНИЕ]
  - **Cloaking** (`DwmSetWindowAttribute(hwnd, DWMWA_CLOAK, DWM_CLOAKED_APP)`) —
    окно перестаёт рендериться DWM, но остаётся логически «видимым» (не iconic;
    мы уже читаем `DWMWA_CLOAKED` и отбрасываем такие окна —
    `crates/rst-win32/src/window_enum.rs:155,256-266`). Так UWP прячет фоновые
    окна. Побочка: окно пропадает и из Alt+Tab, и с панели задач — для фоновых
    табов группы это скорее желаемо.
    **[ИСТОЧНИК: learn.microsoft.com DWMWINDOWATTRIBUTE]**; кросс-процессность —
    [ПРЕДПОЛОЖЕНИЕ], см. §1б.
- Панель табов — наш оверлей: есть Panel/Button/Label/ScrollBar
  (`crates/resticker/src/window_pick_list.rs:24-27`), иконки окон уже умеем
### 1б. Буквально: группа одной записью в системном Alt+Tab

Чем управляется появление окна в Alt+Tab:

1. Алгоритм представителя: для видимого окна идём к root-owner, затем вниз по
   цепочке last-active-popup до видимого; окно попадает в список, если оно —
   представитель своего «кластера владения».
   **[ИСТОЧНИК: Raymond Chen, «Which windows appear in the Alt+Tab list?»,
   devblogs.microsoft.com/oldnewthing/20071008-00]**
2. `WS_EX_TOOLWINDOW` — «окно не появляется ни в панели задач, ни в Alt+Tab»
   (дословно). **[ИСТОЧНИК: learn.microsoft.com «Extended Window Styles»]**
3. `WS_EX_APPWINDOW` — форсирует кнопку на панели задач у видимого окна
   (и запись в Alt+Tab у owned-окна). [Там же]
4. `ITaskbarList::DeleteTab(hwnd)` — удаляет кнопку **с панели задач**; про
   Alt+Tab документация молчит — Alt+Tab перечисляет окна, а не кнопки панели,
   поэтому на системный Alt+Tab вызов **не влияет**.
   **[ИСТОЧНИК: learn.microsoft.com ITaskbarList::DeleteTab]** + [ПРЕДПОЛОЖЕНИЕ]
   о невлиянии.
5. Cloaking — убирает окно и из Alt+Tab, и с панели задач (у окна нет живой
   поверхности). [ПРЕДПОЛОЖЕНИЕ по практике UWP; отдельной строки про Alt+Tab
   в доке не нашёл.]
6. Смена владельца (`SetWindowLongPtr(GWLP_HWNDPARENT)`) — меняет «кластер»
   из п.1: owned-окно уступает запись владельцу.

Можно ли это делать с **чужим** окном? Технически `SetWindowLongPtr` на окне
другого процесса работает (мы уже пишем чужим окнам свойства —
`crates/rst-win32/src/window_pin.rs:81-82,139-166`), а в документации
`DwmSetWindowAttribute` оговорок про чужие окна **нет** (прочитал страницу
целиком — [ИСТОЧНИК: learn.microsoft.com DwmSetWindowAttribute]); надёжность
кросс-процессного `DWMWA_CLOAK` — [ПРЕДПОЛОЖЕНИЕ], нужен прототип.

Побочные эффекты (почему это плохая идея на чужих окнах):

- `WS_EX_TOOLWINDOW` убирает окно **и с панели задач тоже** — пользователь
  теряет привычную точку входа. При выходе из группы стиль надо вернуть
  (`SWP_FRAMECHANGED`), а приложение могло само переписать стили (браузеры и
  Electron правят их при смене режимов окна) — состояние разойдётся.
  [ПРЕДПОЛОЖЕНИЕ]
- Смена владельца меняет z-порядок, сворачивание (owned сворачивается с
  владельцем) и поведение при закрытии — самый инвазивный вариант.
  [ПРЕДПОЛОЖЕНИЕ]
- Cloak делает окно невидимым вообще — годится только для уже спрятанных
  табов, а не для «свернуть запись в группу».
- Главное: ни один механизм не создаёт **одну запись на группу**. Системный
  Alt+Tab не имеет понятия «группа», его рисует shell, и API для вмешательства
  в его содержимое нет. [«API не нашёл» — обратное ссылкой не докажешь.]

**Вердикт 1б: НЕТ. Честный ответ пользователю — «системный Alt+Tab не трогаем;
вместо этого свой переключатель (§2), где группа реально одна запись».** Хаки
системного списка дадут мерцающие кнопки панели задач и войну стилей с чужими
приложениями.

  (`crates/rst-win32/src/window_icon.rs:39`, кэш `window_enum.rs:110`).

**Вердикт 1а: реально, без хаков. Рекомендую cloaking для фоновых табов,
fallback — увод за экран.**
## 2. Свой Alt+Tab (перехват + свой оверлей)

### Перехват клавиш

- `RegisterHotKey(MOD_ALT, VK_TAB)` **не сработает**: комбинация зарезервирована
  системой, регистрация вернёт `ERROR_HOTKEY_ALREADY_REGISTERED`.
  [ПРЕДПОЛОЖЕНИЕ — прямого теста не гонял; общеизвестное поведение.]
- Рабочий путь — `WH_KEYBOARD_LL`: хук видит и может подавить и keydown, и
  keyup Tab/Alt (паттерн AutoHotkey и PowerToys Keyboard Manager).
  **[ИСТОЧНИК: learn.microsoft.com «LowLevelKeyboardProc»]** Нужна конечная
  автоматика: нажат Alt → Tab (подавить) → повторные Tab листают → отпускание
  Alt (подавить) → активировать выбранное. Подводные камни:
  - Таймаут хука `LowLevelHooksTimeout` — медленный колбэк → Windows перестаёт
    вызывать хук, клавиши «залипают». Колбэк обязан быть O(мкс).
    **[ИСТОЧНИК: learn.microsoft.com «LowLevelHooksTimeout»]**
  - Защищённый рабочий стол (UAC, экран блокировки) — хук там не работает,
    системный Alt+Tab остаётся; несоответствие поведения. [ИЗМЕРЕНО-знанием;
    считать [ИСТОЧНИК: общие свойства LL-хуков]]
  - У нас принято архитектурное решение **не использовать** `WH_KEYBOARD_LL`:
    «Низкоуровневый хук `WH_KEYBOARD_LL` не используется даже как fallback
    (ADR-009)» — `crates/rst-win32/src/hotkey.rs:6-7`. Перехват Alt+Tab —
    сознательный пересмотр ADR-009, это надо зафиксировать отдельным ADR.
- Альтернатива без пересмотра ADR-009: **своя комбинация** (`Alt+``,
  `Win+Tab` занят; `Alt+Q` и т.п.) через существующий `RegisterHotKey`
  (`hotkey.rs:92+`). UX «не тот самый Alt+Tab», зато нулевой риск залипаний.

### Активация выбранного окна — самое больное место

`SetForegroundWindow` из фонового процесса блокируется foreground lock
(`SPI_GETFOREGROUNDLOCKTIMEOUT`): окно лишь мигнёт на панели задач.
Обходы, которые реально применяют: `AttachThreadInput` к текущему
foreground-потоку + `SetForegroundWindow`, либо недокументированный
`SwitchToThisWindow`. [ПРЕДПОЛОЖЕНИЕ; паттерн из AutoHotkey/PowerToys.]
Если переключатель открыт нашим LL-хуком, формального «последнего ввода» у
нас нет — хук не передаёт foreground-права. Надо прототипировать первым делом.

### Превью окна

- **Иконка — уже есть**: `WindowInfo.icon` (`window_enum.rs:98`), извлечение
  `window_icon.rs:39-53`, кэш по exe `window_enum.rs:110-132`, отрисовка в
  панелях (`window_pick_list.rs:59-62`). Список в стиле «иконка + заголовок»
  можно собрать сегодня.
- **DwmRegisterThumbnail** — живое превью, композитит сам DWM: источником
  может быть **любое top-level окно**, а вот destination обязано быть окном
  **нашего процесса**. **[ИСТОЧНИК: learn.microsoft.com DwmRegisterThumbnail]**
  Ограничение: превью рисуется DWM **в клиентскую область нашего окна**, а не
  отдаётся текстурой — наш рендер D3D11+DirectComposition с попиксельной
  прозрачностью (`WS_EX_NOREDIRECTIONBITMAP`, `crates/rst-win32/src/overlay.rs:49-50,971-973`)
  с thumbnail-регионами не стыкуется напрямую. [ПРЕДПОЛОЖЕНИЕ — вопрос
  совместимости DComp-окна с DWM thumbnails надо проверять прототипом; скорее
  всего придётся рисовать thumbnails в отдельное «нормальное» окно-подложку.]
  Плюс: свёрнутые окна дают статичный/пустой thumbnail.
- **PrintWindow(PW_RENDERFULLCONTENT)** — статичный снимок в HDC → заливаем
  как текстуру (пайплайн «BGRA→текстура» уже есть в `window_icon.rs:141-180`).
  `PW_RENDERFULLCONTENT` (0x2, Windows 8.1+) **в документации PrintWindow не
  описан** (там только `PW_CLIENTONLY`) — флаг недокументирован, но
  общепринят. **[ИСТОЧНИК: learn.microsoft.com PrintWindow]** Стоимость —
  миллисекунды–десятки миллисекунд на окно, синхронно; зависшее окно может
  подвесить вызов (см. наш bounded-fetch заголовка, `window_enum.rs:694-708`).
  Часть GPU-окон отдаёт чёрный прямоугольник. [ПРЕДПОЛОЖЕНИЕ]
- **Windows.Graphics.Capture** (interop `CreateForWindow`) — живые кадры
  **как D3D11-текстуры**: идеальный стык с `rst-render`. Без диалога согласия
  при программном `CreateForWindow` (поэтому так снимает OBS).
  [ИСТОЧНИК: learn.microsoft.com Windows.Graphics.Capture + практика OBS —
  помечаю как [ПРЕДПОЛОЖЕНИЕ] для нашего случая.] Ограничения: DRM-контент
  чёрный; свёрнутое окно кадров не даёт (последний кадр остаётся); сессия
  захвата на каждое превью — память/VRAM, на 20+ окон дорого.
  **Рекомендация: иконки + PrintWindow-снимки на открытии переключателя;
  WGC — опционально для 1-2 «фокусных» превью.**

### Что уже готово

## 3. Анимации перемещения

### 3.1 Пошаговый SetWindowPos — честная оценка

- Сам вызов дешёв: в нашем коде зафиксирован замер «`SetWindowPos(HWND_TOPMOST,
  SWP_NOACTIVATE)` — 14–16 мкс» (`crates/rst-win32/src/overlay.rs:599`).
  **[ИЗМЕРЕНО в этом репозитории]**
- Но стоимость не в вызове, а в **перерисовке чужого окна**: каждый кадр с
  новым размером — это `WM_WINDOWPOSCHANGING`/`WM_SIZE`, relayout приложения,
  пересоздание swapchain/redirection-поверхности у DWM. Тяжёлые приложения
  (браузеры, Electron, IDE) не успевают за 60 fps → видны чёрные/серые поля,
  «резиновость», рывки. Лёгкие окна (Блокнот, мессенджеры) шагают нормально.
  [ПРЕДПОЛОЖЕНИЕ по общеизвестному поведению; на конкретных приложениях
  не измерял.]
- Реальная частота: перемещение (без ресайза) — 60–144 шагов/с ок; ресайс —
  лучше 30–60 шагов/с и только для небольших окон. Такт у нас уже есть:
  `DwmFlush`-синхронизация с композицией (`crates/rst-win32/src/dwm.rs:24-27`)
  ровно для того, чтобы кадр не отставал на период.
- Что делают другие: **komorebi** — анимаций перемещения нет (сознательно,
  есть только border-окна); **GlazeWM** — анимаций нет; **FancyWM** — заявляет
  анимированные переходы. [ИСТОЧНИК: README/доки проектов komorebi (LGUG2Z),
  GlazeWM (glzr-io), FancyWM (fancywm.com); кода их анимаций я не читал —
  «не проверял» детали реализации.]

### 3.2 Трюк «анимируем картинку, окно телепортируем»

Схема: (1) снять снимок окна, (2) скрыть настоящее окно, (3) анимировать
снимок как спрайт на нашем оверлее (спрайты/текстуры/шейдеры уже есть —
`crates/rst-render/src/sprite.rs`, `texture.rs`, `widgets.rs`), (4) в конце
`SetWindowPos` реальному окну в финальную позицию и показать обратно.

Чем снимать:

- `PrintWindow(PW_RENDERFULLCONTENT)` → HBITMAP → текстура. Дёшево для одного
  окна (миллисекунды–десятки мс), синхронно, без сессий. Нет альфы по
  округлым углам Win11 — снимок прямоугольный, углы будут с «вклеенным»
  фоном. [ПРЕДПОЛОЖЕНИЕ про углы; флаг недокументирован — см. §2.]
- `Windows.Graphics.Capture` → D3D11-текстура с альфой, корректные углы;
  дороже на старте (создание сессии+frame pool ~ первые кадры), зато живое.
  Для одноразового снимка избыточно, для «анимируем живое окно» — единственный
  правильный путь. [ПРЕДПОЛОЖЕНИЕ]

Как скрыть оригинал на время анимации:

- Cloak (`DWMWA_CLOAK`) — окно исчезает мгновенно, без анимации сворачивания,
  логически остаётся видимым; uncloak в конце. Идеальный инструмент, но
  кросс-процессность недокументирована (§1б) — прототип. Риск: мерцание на
  границе cloak→teleport→uncloak. [ПРЕДПОЛОЖЕНИЕ]
- Альтернатива: телепорт окна в финал сразу + рисовать снимок поверх старой
  позиции. Тогда скрывать не надо, но в финале окно уже стоит на месте под
  нашим оверлеем — стык незаметен, если снимок точно совпал с текущим кадром.
  Окно при этом один кадр «прыгает» раньше времени — при topmost-оверлее
  снимок его закрывает. Это самый надёжный вариант: ноль недокументированных
  вызовов. [ПРЕДПОЛОЖЕНИЕ]

Где ломается:

1. Окна, отдающие чёрный снимок (DRM-видео, часть GPU-приложений при
   PrintWindow) → чёрный летящий прямоугольник. Детект: средняя яркость
   снимка ≈ 0 → fallback на мгновенный телепорт. [ПРЕДПОЛОЖЕНИЕ]
2. Ресайс: снимок имеет старый размер — при изменении размера картинку придётся
   растягивать (мыла при сильном ресайзе) или обрезать. Hyprland-эффект
   «окно перетекает в новый тайл» идеально не получится; визуально приемлемо
   при растяжении с затуханием. [ПРЕДПОЛОЖЕНИЕ]
3. Снимок устаревает: за 5–50 мс захвата видео в окне уйдёт вперёд —
   заметно только на видео.
4. Зависшее окно: PrintWindow синхронен и может подвесить рендер-поток —
   выносить захват в отдельный поток (тот же урок, что bounded-fetch
   заголовка, `window_enum.rs:694-708`).
5. Оверлей topmost — анимированный спрайт пролетит **поверх** окон, которые
   реально выше анимируемого. Для 200–300 мс эффекта приемлемо. [ИЗМЕРЕНО
   topmost: `overlay.rs:971-973`]

**Вердикт §3: базово — мгновенный телепорт (как komorebi). Первый уровень
полироля — пошаговый move-only (без ресайза) для лёгких окон. Уровень
«вау» — снимок-спрайт с телепортом в финал: технически у нас всё для него
есть, главный риск — чёрные снимки и стоимость захвата.**

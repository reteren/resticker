# REVIEW: Win32-слой T2/T3 (keyboard_guard, tiling_apply, сшивка в координаторе)

Ревью трёх модулей, написанных координатором без ревью: `crates/rst-win32/src/keyboard_guard.rs`,
`crates/rst-win32/src/tiling_apply.rs`, `crates/resticker/src/tiling.rs` (+ врезка в
`overlay_manager.rs`). Код не правился. Проверка каждого пункта — по опорным материалам
(R3, R4, доккомент мышиного стража window_pin.rs:807-886) и по чтению кода.

Проверено, что ревьюируемый код компилируется: `cargo test -p rst-win32` — 225 passed,
keyboard_guard и tiling_apply участвуют в сборке.

## 1. БЮДЖЕТ КОЛБЭКА — ПОДОЗРЕНИЕ

Что проверил: `hook_proc` (keyboard_guard.rs:301-377) построчно, декларацию «никаких
аллокаций» (keyboard_guard.rs:18), путь с таблицей из 30–60 биндов, поведение `try_read`.

Трасса типичного пути (проглатывание):
1. `kb.flags & LLKHF_INJECTED` — чтение, 0 аллокаций. ОК.
2. `modifier_bit(vk)` + `MODS.with` — Cell, 0 аллокаций. ОК.
3. `chord_from` — копия 5 полей. ОК.
4. `should_swallow` → `SWALLOW.try_read()` + `Vec::contains` — линейный скан, 30–60
   биндов × 5 полей = сотни наносекунд. `try_read` при активной записи координатора
   падает быстро и означает fail-open (клавиша проходит) — деградация безопасная.
5. `TX.with(... tx.send(chord))` — **`std::mpsc::Sender::send` аллоцирует узел
   неограниченной очереди** (первое нажатие — malloc). Нарушение заявленного «никаких
   аллокаций»; на практике единицы микросекунд, но декларация неверна.
6. `SWALLOWED_DOWN.push(vk)` — **`Vec::push` может аллоцировать**. Тот же комментарий.
7. `mask_windows_key()` → `SendInput` — системный вызов (не блокирует); самый дорогой
   элемент трассы, порядок десятков микросекунд [ПРЕДПОЛОЖЕНИЕ, не замерено], в рамках
   бюджета 1 мс.

Вердикт: бюджет в целом выдерживается (типичный путь — единицы–десятки микросекунд), но:
- декларация «никаких аллокаций» не соблюдена (две аллокации: `mpsc::send`, `Vec::push`);
- **нет watchdog'а переустановки хука** — в отличие от мышиного стража, где сторож
  замечает тишину и просит помп переустановить хук (window_pin.rs:880-881, 1051-1141).
  Здесь, если Windows молча снимет `WH_KEYBOARD_LL` по превышению `LowLevelHooksTimeout`
  (1 мс, window_pin.rs:863), клавиатура тайлинга умрёт навсегда до перезапуска процесса.
  R4 §2.3 требует watchdog явно.
- длинная таблица: при 60 биндах `contains` — сотни нс, деградация линейная, не страшная.

## 2. КОРРЕКТНОСТЬ ГЛОТАНИЯ — БАГ (два)

### Находка №1 (КРИТИЧЕСКАЯ): голые клавиши submaps и Escape глотаются В ГЛОБАЛЬНОМ режиме

**Симптом: при включённом тайлинге клавиши H, J, K, L и Escape исчезают для ВСЕХ
приложений — пользователь не может их печатать.**

Механика:
- `BindTable::swallow_set` (binds.rs:175-200) возвращает плоский набор комбинаций
  **всех режимов сразу** — включая голые H/J/K/L из submap-биндов и голый Escape
  (добавляется безусловно при наличии любого submap, binds.rs:187-195).
- `TilingState::swallow_set` (resticker/src/tiling.rs:167-179) отдаёт этот набор хуку
  **ровно один раз при включении** (overlay_manager.rs:2813). При входе/выходе из
  submap таблица `SWALLOW` не обновляется (намеренно, binds.rs:30-33).
- `hook_proc` (keyboard_guard.rs:352-371) не знает о режиме: глотает всё, что есть в
  таблице, и возвращает `LRESULT(1)`.
- В глобальном режиме `resolve` (binds.rs:122-162) для голого H/Escape не находит
  бинда (голые живут только в submap "resize") и возвращает `PassThrough` — **но
  клавиша уже проглочена и потеряна**: координатор не может «вернуть» её приложению.

Сценарий воспроизведения: включить тайлинг с дефолтными биндами (а они содержат
resize-submap с голыми H/J/K/L, resticker/src/tiling.rs:603-650), открыть редактор или
браузер с vim-навигацией, нажать `h` — буква не печатается; нажать Escape в
полноэкранном видео — выход из полноэкранного режима не сработает.

Правка (минимальная, в координаторе): при каждой смене режима (`Resolution::ModeChanged`
из `resolve_key`, resticker/src/tiling.rs:186-202) переставлять набор перехвата через
`keyboard_guard::set_swallow_set`: в глобальном режиме — только глобальные бинды (без
голых и без Escape); в submap — глобальные + бинды этого submap + Escape. Место вызова
уже есть — ветка `OverlayMessage::TilingKey` (overlay_manager.rs:3641-3648). Либо (хуже)
научить хук читать атомарный флаг текущего режима.

### Находка №4 (средняя): утечка `SWALLOWED_DOWN` при автоповторе

**Симптом: удержание проглоченной клавиши >0.5 с накапливает мусор; следующий `up`
той же клавиши глотается ложно — приложение получает `down` без `up` (залипшая клавиша).**

Механика: при каждом `down` делается `push(vk)` без проверки дубликата
(keyboard_guard.rs:366). Автоповтор шлёт `down, down, ..., up` (модификатор всё время
зажат, комбинация всё время в таблице): 3–5 push, один `up` снимает одну запись
(`swap_remove`, keyboard_guard.rs:339-348) — остальные висят навсегда. Дальше любой
`up` клавиши H (в т.ч. с НЕпроглоченным `down`) попадает в `was_swallowed` и
проглатывается.

Сценарий воспроизведения: держать Alt+H >0.5 с, отпустить; затем нажать и отпустить H
в приложении (в конфиге без submap-биндов голый H не глотается при down) — отпускание
H пропадёт, приложение увидит залипшую клавишу. Мусор не чистится ничем, кроме смерти
потока-помпы.

Правка: перед `push` — проверка `contains` (список короткий), либо хранить не список.

Что проверил и НЕ нашёл проблем:
- **Модификатор отпущен раньше основной клавиши**: Alt down (не глотается, MODS+=alt),
  H down (проглочен, push), Alt up (не глотается, MODS-=alt), H up (was_swallowed →
  LRESULT(1)). Симметрично, приложение не видит «чужого» up. Корректно.
- **Отпускание вне фокуса нашего процесса**: `WH_KEYBOARD_LL` видит все события
  сессии, фокус ни при чём — up дойдёт до хука. Корректно.
- **Снятие хука между down и up**: `SWALLOWED_DOWN` — `thread_local` потока-помпы,
  умирает вместе с ним; парность не ломается.
- **Оборванный канал**: `delivered == false` → клавиша не глотается (fail-open),
  документировано (keyboard_guard.rs:362-365). Корректно.

## 3. МАСКИРУЮЩАЯ КЛАВИША — ВСЁ ЧИСТО (две оговорки)

Что проверил:
- **Петля через собственный хук**: маска отправляется с `LLKHF_INJECTED`, а `hook_proc`
  пропускает всё инжектированное (keyboard_guard.rs:312-315) — петли нет. Корректно.
- **Win зажат, несколько комбинаций подряд**: каждый проглоченный win-chord шлёт свою
  пару down+up `MASK_VK`; между Win down и Win up всегда есть посторонние события —
  «одинокий Win» не возникает, меню Пуск не откроется. Корректно.
- **Win зажат до включения тайлинга**: `initial_mods()` (keyboard_guard.rs:217-235)
  снимает состояние модификаторов при старте; последующая маска всё равно ложится
  между исходным Win down и его up. Корректно.
- **Комбинации без Win**: маска не вызывается вовсе (`chord.win` false) — дефолтные
  бинды (Alt) её не триггерят. Корректно.

Оговорки (не баги):
- **`MASK_VK = 0xE8` — OEM-диапазон** (0xE8–0xFF — «OEM-specific»). На раскладках
  US/RU не назначен, но R4 §2.2 рекомендовал гарантированно пустой `VK_F24` (0x87).
  Дёшево заменить — рекомендация.
- **Маскирование внутри колбэка хука** (SendInput) — единственный системный вызов на
  трассе глотания (см. п.1). В рамках бюджета.

## 4. ФОКУС — ПОДОЗРЕНИЕ (SetFocus)

Функция `focus` (tiling_apply.rs:142-179) разобрана по шагам:
1. `IsWindow` → ранний выход. ОК.
2. `SetForegroundWindow` → успех = выход. ОК.
3. `GetForegroundWindow` + `IsHungAppWindow` (защита от присоединения к зависшей
   очереди, R3 §6.2). ОК.
4. `AttachThreadInput(us, fg_thread, true)` → SFW + `SetFocus` → detach при успехе attach.

**Симметричность отвязки — ВСЁ ЧИСТО**: все ранние выходы (IsWindow-false, SFW-ok,
fg-null, hung, fg_thread==0/==us) — ДО attach; после attach ровно один выход — detach
(tiling_apply.rs:174-177); между attach и detach нет ни ранних return, ни паникующих
операций.

**Смерть целевого окна между проверками**: SFW и SetFocus на уже уничтоженный hwnd —
безопасный возврат false/NULL, не UB. ОК.

**ПОДОЗРЕНИЕ по `SetFocus(Some(target))`** (tiling_apply.rs:171):
- SetFocus требует, чтобы окно было присоединено к очереди ввода ВЫЗЫВАЮЩЕГО потока.
  Мы присоединились к потоку ПЕРЕДНЕГО окна (`fg_thread`), а не к потоку target. Если
  target в третьем потоке — SetFocus гарантированно вернёт NULL; после успешного SFW
  фокус уже передан — то есть вызов либо бесполезен, либо избыточен.
- Хуже: если SFW вернул `false`, а SetFocus всё же сработал (target в `fg_thread`),
  окно получит фокус КЛАВИАТУРЫ без активации — пользователь печатает в окно, которое
  не на переднем плане, а `focus()` вернул `false` и координатор считает переключение
  неудавшимся (рассинхронизация возврата с реальным состоянием).
- Риск блокировки: SetFocus имеет SendMessage-семантику (шлёт WM_KILLFOCUS/SETFOCUS).
  Между `IsWindow`/`IsHungAppWindow(foreground)` и SetFocus целевое окно может
  зависнуть — SendMessage к зависшему потоку способен заблокировать поток координатора
  (та же ловушка, что в R3 §6.2, только вход другой; `IsHungAppWindow` проверяет
  ПЕРЕДНЕЕ окно, а не target).

Правка-рекомендация: убрать `SetFocus` (SFW сам передаёт фокус при успехе), либо
вызывать его под отдельной проверкой `IsHungAppWindow(target)` и учитывать результат
в возврате.

## 5. ЖИЗНЕННЫЙ ЦИКЛ — ВСЁ ЧИСТО (две мелочи)

Что проверил:
- **`KeyboardGuard::Drop` (keyboard_guard.rs:178-187)**: `PostThreadMessageW(WM_QUIT)` →
  `pump()` выходит (GetMessageW возвращает 0) → `UnhookWindowsHookEx` → `TX=None` →
  `join()`. Порядок корректен: хук снимается на потоке-владельце до выхода из потока,
  `join` дожидается. `WM_QUIT` не потеряется: поток-помпа либо в `GetMessageW`
  (получит WM_QUIT), либо внутри колбэка (WM_QUIT дождётся в очереди).
- **Поток уже умер**: `join()` возвращает Err — проигнорировано, не зависает. ОК.
- **Двойное включение/выключение подряд** (overlay_manager.rs:2812-2841): повторное
  включение при живом guard — no-op (`is_none` проверка, второй хук не ставится);
  выключение — `keyboard_guard = None` → Drop синхронно на координаторе; повторное
  включение сразу после — старый поток уже присоединён. Два потока-помпы невозможны.
- **Канал при Drop**: мост-поток (overlay_manager.rs:2820-2828) умирает вместе с
  `keys`-Receiver; `send` вернёт Err → fail-open. ОК.
- **`set_swallow_set(Vec::new())` в Drop** — после join, читать таблицу уже некому;
  thread_local-мусор умирает с потоком. ОК.

Мелочи:
- **Паника в `hook_proc` убьёт процесс**: `extern "system"` колбэк с паникой — abort.
  Паникующие операции в колбэке: `RefCell::borrow_mut` (SWALLOWED_DOWN) — паника при
  реентерабельном вызове. Реентерабельности сейчас нет (SendInput доставляет маску
  асинхронно), но это хрупкое место без защиты.
- **Неудачный `start()`**: при отказе `SetWindowsHookExW` поток уже завершился, а
  `JoinHandle` бросается без join (keyboard_guard.rs:165-174) — утечка дескриптора,
  разовая и при ошибке. Незначительно.

## 6. СШИВКА — БАГ (два), ПОДОЗРЕНИЕ (одно)

### Находка №2 (СЕРЬЁЗНАЯ): счётчик неудач НЕ отсекает главный класс неуправляемых окон — они получают команды бесконечно

Замысел (resticker/src/tiling.rs:71-77): окно, которое не доезжает, после
`MAX_FAILED_ATTEMPTS = 3` отказов признаётся неуправляемым и больше не трогается.
Комментарий прямо называет elevated-окна (UIPI).

Проблема: счётчик растёт только для `report.refused` (tiling.rs:369-375), а `refused`
заполняется только когда `WindowPins::set_dwm_bounds` вернул `false`. Но
`set_dwm_bounds` (window_pin.rs:701-753) **игнорирует результат SetWindowPos и
возвращает `true` почти всегда** — в т.ч. при UIPI-отказе (это документировано в самом
tiling_apply.rs:32-33: «`set_dwm_bounds` возвращает `true` даже когда система
отказала»). Пути `false`: окно мертво (IsWindow) или сломан GetWindowRect; плюс для
развёрнутого окна `move_resize` возвращает `Err(PinAccessDenied)` под UIPI
(window_pin.rs:720-736) — то есть maximized-elevated окно таки попадёт в refused.

Итог: **не-развёрнутое elevated-окно и окно с минимальным размером больше плитки
получают команду навсегда**: `reconcile` вечно выдаёт move (окно не доезжает),
settle-окно (250 мс, tiling.rs:62) лишь замедляет команды до ~4/с, но не прекращает.
Сценарий воспроизведения: открыть Диспетчер задач (elevated), включить тайлинг —
Диспетчер задач будет получать SetWindowPos каждые 250 мс бесконечно, пока тайлинг
включён.

Правка: считать неудачи по факту «reconcile снова выдал move окну, которому мы уже
отправляли команду и оно не доехало за N заходов» — т.е. вести второй счётчик рядом с
`last_command` (сбрасывать при совпадении observed с целью в пределах эпсилона), а не
по `refused`. `gave_up` при этом должен убирать окно из дерева (или переводить в
floating), иначе оно продолжит занимать плитку.

### Находка №3 (средняя): `failed` никогда не сбрасывается — окно навсегда застревает в «неуправляемых», оставаясь в дереве

Симметричная дыра: `failed` растёт только вверх (tiling.rs:369-375), единственный путь
сброса — `forget()` при исчезновении окна из managed (tiling.rs:384-389). Сценарий:
окно дало 3 `refused` подряд (например, временно свернулось/завис GetWindowRect) —
после этого оно навсегда лишено команд, но остаётся в дереве воркспейса и занимает
плитку; даже если пользователь сам перетащил его (reconcile даст move) — команда не
уйдёт (`failed >= 3` → continue, tiling.rs:351-353). Раскладка «сломана» до закрытия
окна.

Правка: сбрасывать `failed` при (а) совпадении observed с целью (окно само доехало),
(б) ручном действии пользователя над окном (драг — `is_user_dragging` уже проверяется
рядом, tiling.rs:348-350), (в) смене воркспейса/пересоздании раскладки.

### ПОДОЗРЕНИЕ: аварийный выход из submap (Escape) в глобальном режиме

`BindTable::resolve` (binds.rs:147-160) выходит из submap по голому Escape ТОЛЬКО когда
`current_submap.is_some()`. Из-за находки №1 голый Escape глотается всегда, но в
глобальном режиме он просто теряется (PassThrough после проглатывания). После правки
находки №1 (перестановка набора при смене режима) это уйдёт само.

### ПОДОЗРЕНИЕ: таймаут бездействия submap не реализован

R4 §5.1 требует авто-выход из модального режима по таймауту бездействия (10 с) и
сброс при потере фокуса/клике мимо. `BindTable::reset()` (binds.rs:167-169)
существует, но не вызывается нигде в overlay_manager (проверено grep'ом). Пользователь
вошёл в resize-режим и забыл — голые клавиши продолжают перехватываться, индикатор
режима (T5) ещё не нарисован — впечатление «сломанной клавиатуры» (риск из R4 §6).
Отчасти маскируется находкой №1, но после её правки станет самостоятельной дырой.

## ИТОГ: находки по убыванию серьёзности

1. **[БАГ, критический]** Голые клавиши submaps и Escape глотаются в глобальном
   режиме — h/j/k/l/Escape пропадают для всех приложений при включённом тайлинге с
   submap-биндами (а они в дефолтах). Корень: плоская таблица всех режимов в хуке без
   знания текущего режима. (keyboard_guard.rs:352-371 + binds.rs:175-200 +
   resticker/src/tiling.rs:167-179 + overlay_manager.rs:2813)
2. **[БАГ, серьёзный]** Счётчик неудач не работает для главного класса неуправляемых
   окон: `set_dwm_bounds` возвращает `true` при UIPI-отказе → elevated-окна и окна с
   большим min-size получают команды каждые 250 мс бесконечно. (tiling.rs:351-375 +
   window_pin.rs:701-753)
3. **[БАГ, средний]** `failed`-счётчик без сброса: окно, давшее 3 `refused` подряд,
   навсегда застревает в «неуправляемых», оставаясь в дереве и занимая плитку.
   (tiling.rs:351-353, 369-375, 384-389)
4. **[БАГ, средний]** Утечка `SWALLOWED_DOWN` при автоповторе (push без проверки
   дубликата): ложное проглатывание `up` → залипшая клавиша в приложении.
   (keyboard_guard.rs:366)
5. **[ПОДОЗРЕНИЕ]** `SetFocus` в `focus()`: почти всегда бесполезен, может
   рассинхронизировать возврат с реальным состоянием фокуса и потенциально
   блокировать координатор на зависшем окне. (tiling_apply.rs:171)

   трассе колбэка при декларации «никаких аллокаций». (keyboard_guard.rs)
7. **[ПОДОЗРЕНИЕ]** Таймаут бездействия submap не реализован: `BindTable::reset` не
   вызывается нигде. (binds.rs:167-169)
8. **[ПОДОЗРЕНИЕ]** `MASK_VK = 0xE8` — OEM-диапазон; R4 рекомендовал `VK_F24` (0x87).

# REVIEW: T4/T6 — cloak, превью окон, индикаторы, счётчик неудач, видимость, математика раскладки

Ревью кода, написанного ПОСЛЕ первого ревью (REVIEW_WIN32_T2_T3.md, 8 находок — все закрыты):
`crates/rst-win32/src/cloak.rs`, `crates/rst-win32/src/window_thumb.rs`,
`crates/resticker/src/tiling_ui.rs`, новые части `crates/resticker/src/tiling.rs`
(build_overlay, judge_pending, apply_visibility, expire_submap, tabbed_containers, to_dip),
и починенные функции `crates/rst-core/src/tiling/layout.rs`. Код не правился.

Проверка сборки: `cargo test -p rst-win32` — 239 passed, 1 fail
(`single_instance` — среда: живое приложение держит именованный мьютекс, не связано с ревью);
тесты cloak (5) и window_thumb (12) — зелёные. `cargo test -p rst-core` НЕ собирается из-за
незавершённой правки координатора (`config.rs:485` — структурный литерал без нового поля
`own_alt_tab`); layout-функции под ревью до этого прошли фаззинг инвариантов
(`tiling_invariants.rs`, 7/7) — см. п.6.

## 1. CLOAK И ПОТЕРЯ ОКОН — БАГ (один), всё остальное чисто

Что проверил: все пути «окно может остаться скрытым навсегда» из задания.

**Падение между маркером и скрытием — ЧИСТО.** `cloak` ставит маркер ДО вызова DWM
(cloak.rs:72-92). Худший исход при смерти процесса между ними — маркер на видимом окне;
`recover_orphans` его снимет, `uncloak` на видимом окне — no-op. Обратный порядок (скрытие
без маркера) был бы потерей — он исключён. Тот же порядок защищён и при отказе DWM:
`cloak` откатывает маркер (cloak.rs:82-91).

**Отказ DWM при `uncloak` — БАГ (средний).** Зеркальная дыра к аккуратной обработке в
`cloak`:
```rust
// cloak.rs:101-105
let ok = set_cloaked(target, false);
let _ = RemovePropW(target, CLOAK_PROP);   // маркер снимается БЕЗУСЛОВНО
ok
```
Если `DwmSetWindowAttribute(DWMWA_CLOAK, false)` вернёт ошибку, окно остаётся скрытым,
а маркер уже снят — `recover_orphans` такое окно не найдёт, и оно потеряно навсегда.
Вероятность отказа невелика (окно живое и проверено `IsWindow`; UIPI до нас уже не
дотягивается, раз мы смогли его спрятать), но это единственный путь, на котором маркерная
схема перестаёт работать, а инвариант модуля сформулирован жёстко: «скрытое окно не видно
нигде» (cloak.rs:23-26). Предлагаемая правка — зеркальная: снимать маркер только при
`ok`, при неудаче оставлять окно в списке скрытых (попытка показа повторится в следующем
такте `apply_visibility`).

**Окно закрылось скрытым — ЧИСТО.** Окно — объект своего процесса: процесс умер, окно
уничтожено, маркер ушёл вместе с ним. Заглушка в `cloaked`-списке (tiling.rs:157) со
временем вычистится: HWND переиспользуется, `apply_visibility` для нового окна с этим
hwnd вызовет `uncloak` (no-op для видимого) и уберёт запись (tiling.rs:627-632). Случай,
когда переиспользованный HWND НЕ должен быть показан (окно на неактивном воркспейсе), —
невозможен, пока скрытие неактивных воркспейсов не подключено (см. наблюдение в конце).

**Тайлинг выключили в момент переключения — ЧИСТО.** `set_enabled(false)` первым делом
разворачивает весь `cloaked` (tiling.rs:280-289), до `release` и очистки состояния. Скрытое
окно после выключения не остаётся скрытым ни на одном пути.

**Два запуска resticker одновременно — ЧИСТО.** `recover_orphans` вызывается в
overlay-потоке (overlay_manager.rs:2164), а проверка единственности — раньше, в main.rs:450-457:
второй экземпляр умирает до старта overlay-потока и до уборки. Уборка не может развернуть
скрытые окна ЖИВОГО первого экземпляра — то, что защищает комментарий у clear_orphan_markers
(overlay_manager.rs:2136-2141).

**`recover_orphans` видит скрытые окна — ЧИСТО.** `EnumWindows` перечисляет top-level окна
десктопа БЕЗ фильтра видимости: `IsWindowVisible` не вызывается внутри перечисления, его
обязан проверять вызывающий (именно поэтому свой обход вместо `window_enum::enumerate`,
который отбраковывает cloaked, — window_enum.rs:163-165, cloak.rs:35-38). DWM-cloaked окно
остаётся в списке окон Win32 (cloaking — атрибут презентации, а не видимости), так что
уборка его видит. [ИСТОЧНИК: Microsoft Learn, EnumWindows — «enumerates all top-level
windows»; фильтра видимости в API нет — подтверждено поведением всех WM под Windows.]

**Наблюдение (не баг ревью):** `cloaked` сейчас наполняется только фоновыми табами групп —
скрытие окон НЕАКТИВНЫХ воркспейсов (`WorkspaceSet::hidden_windows`, workspace.rs:392) к
координатору не подключено (grep `hidden_windows|visible_windows` по resticker — ноль
вызовов). Это статус T4 в работе координатора, а не дефект ревьюируемого кода; когда
подключится, `set_enabled(false)` уже покрывает его своим `drain`.

## 2. УТЕЧКИ GDI В window_thumb.rs — БАГ (малый), остальное чисто

Что проверил: каждый созданный объект на каждом пути; паника между созданием и удалением;
размеры DIB и обход строк.

**Утечка DC при отказе `CreateDIBSection` — БАГ (малый).** Комментарий утверждает «между
созданием и освобождением нет ни одного раннего return» (window_thumb.rs:106-110) — это
неверно:
```rust
// window_thumb.rs:119
let (hbm, bits) = create_dib_section(dc, w, h)?;   // ← ранний return при None
```
`create_dib_section` возвращает `None` при ошибке GDI или нулевом битмапе
(window_thumb.rs:196-213), и в обоих случаях `?` выходит из `capture`, не вызвав `DeleteDC`
(он вызывается только в финальном блоке, window_thumb.rs:153-156). DC — GDI-объект
процесса, лимит порядка 10 000 хэндлов: одиночный сбой не страшен, но при исчерпании
системной памяти `CreateDIBSection` может отказывать подряд, и утечка становится
накопительной. Правка: обрабатывать `Option` без `?` (или удалять DC в `create_dib_section`
при отказе — тогда контракт «DC остаётся на вызывающем» надо поменять на «DC всегда
удаляется внутри»).

**Все остальные пути — ЧИСТО.** `DeleteObject(hbm)` + `DeleteDC(dc)` в конце — единственная
точка выхода после создания (проверено по коду: отказы `PrintWindow` и чёрный кадр
выражаются значением `result`, а не return'ом). Паникующих операций между созданием и
удалением нет: `from_raw_parts(len)` с корректным `len = w*h*4`, `chunks_exact`,
`downscale_bilinear` с клампом координат (window_thumb.rs:293-297). Паника в этих чистых
функциях невозможна; аварийный abort процесса и так вернул бы хэндлы ОС.

**Размеры DIB и обход строк — ЧИСТО.** 32 bpp `BI_RGB`, отрицательная высота → top-down
(window_thumb.rs:183-190): строка 0 = верх, порядок строк совпадает с RGBA-текстурами
оверлея; stride для 32 bpp BI_RGB = `w*4` без паддинга (выравнивание 4 байта соблюдено
автоматически) — `len = w*h*4` корректен. `PrintWindow` пишет в координатах окна —
обрезает по DC, биты соответствуют прямоугольнику `GetWindowRect` (window_thumb.rs:98).

## 3. ГЕОМЕТРИЯ ИНДИКАТОРОВ (to_dip) — ВСЁ ЧИСТО (одна косметика)

Что проверил: отрицательный origin монитора, масштаб ≠ 100%, согласованность с
координатами раскладки.

- **Отрицательные координаты**: `x = (r.x - monitor.bounds_px.x) / scale` — перевод в
  локальные координаты монитора ДО деления на масштаб (tiling.rs:856-865). Монитор слева
  от primary (bounds.x = −1920) и окно на нём дают корректный положительный DIP. ЧИСТО.
- **Масштаб ≠ 100%**: `w/h` делятся на `scale = dpi/96` (tiling.rs:478, 862-863). Рамка и
  таб-бар на 125%-мониторе совпадают с физическим окном. ЧИСТО.
- **Рамка на втором мониторе не уедет**: перевод — строго по своему монитору (bounds),
  индикаторы каждого монитора считаются с его собственным `scale` (build_overlay,
  tiling.rs:474-478). ЧИСТО.
- **Согласованность с раскладкой**: раскладка считается по `monitor.work_area_px`
  (tiling.rs:397), а origin у work_area и bounds один и тот же (таскбар лишь ужимает
  область снизу) — разнобоя координат нет. ЧИСТО.

Косметика (не баг): полоса воркспейсов и индикатор режима позиционируются по `bounds`
(вся область монитора, tiling.rs:479-484), а не по work_area: на мониторе с таскбаром
снизу полоса воркспейсов (нижний край, отступ 16 DIP, tiling_ui.rs:223) может оказаться
под таскбаром. Стоит пересчитать по `work_area` — или принять как есть.

## 4. СЧЁТЧИК НЕУДАЧ (judge_pending) — БАГ (средний), одна закрытая дыра

Что проверил: сценарии «застревает навсегда» и «никогда не признаётся», смена монитора
между командой и вердиктом.

**Закрытые находки ревью-1 (№2 и №3) — ЧИСТО.** Вердикт теперь выносится по факту
«доехало/не доехало» (`pending` + `arrived`), а не по `refused` (tiling.rs:136-144);
недоехавшее окно выбрасывается из дерева и освобождается (tiling.rs:603-613); обратно в
дерево не берётся — `managed_windows` фильтрует `failed >= MAX` (tiling.rs:693-696);
`failed` сбрасывается при доезде (tiling.rs:597-599). Elevated-окно больше не получает
команды бесконечно.

**Драг пользователя = гарантированное выбрасывание — БАГ (средний).** `judge_pending` не
учитывает `is_user_dragging` (в отличие от `relayout_with`, где он проверяется,
tiling.rs:422). Сценарий: пользователь схватил затайленное окно и тянет >3 периодов
выдержки (~750 мс при `SETTLE_MS = 250`, tiling.rs:62) — на каждом судействе окно «не
доехало» (оно едет за мышью), `failed` растёт до 3, окно выбрасывается из дерева и
`release`-ится ПРЯМО ВО ВРЕМЯ драга (tiling.rs:608-612). Итог: окно выпадает из управления.
Возврата нет: `failed` не сбрасывается ничем, кроме доезда (а команд окну больше не
шлётся) — окно навсегда вне раскладки до переключения тайлинга туда-обратно или
перезапуска приложения. Для тайлинга, где драг — штатное действие, это неожиданное
поведение.

**Смена монитора между командой и вердиктом — тот же корень.** Окно, переехавшее на
другой монитор (пользователь перетащил, или сработала миграция монитора), судится по
СТАРОЙ цели старого воркспейса: `managed` отдаёт его актуальный rect (tiling.rs:590-595),
но target — из старой раскладки; окно «не доезжает» и выбрасывается. В следующем снимке
`managed_windows` уже его не отдаст (failed ≥ 3) — в раскладку нового монитора оно не
попадёт.

Предлагаемая правка: (а) пропускать судейство, пока `window_pin::is_user_dragging(hwnd)`
(сдвигая выдержку), (б) сбрасывать `failed` при смене монитора/воркспейса окна и (в)
сбрасывать `failed` при совпадении observed с ЛЮБОЙ целью раскладки, а не только с
текущей командой.

## 5. ВИДИМОСТЬ (apply_visibility) — ВСЁ ЧИСТО

Что проверил: порядок «показать-потом-спрятать», кадр «не видно ничего», окно в обоих
списках, повторные попытки.

- **Порядок**: `to_show` обрабатывается раньше `to_hide` (tiling.rs:621-648), и оба —
  синхронные DWM-вызовы в одном такте. Кадра «ничего не видно» при переключении табов не
  существует: новое окно появляется, пока старое ещё на экране. ЧИСТО.
- **Окно и в to_show, и в to_hide**: невозможно — оба списка строятся одним проходом
  `reconcile` по placements, где у каждого окна ровно один `visible`-флаг (reconcile.rs:111-135).
  ЧИСТО.
- **Повторные попытки**: `uncloak`/`cloak` возвращают `bool`; неуспех НЕ записывается в
  `cloaked` (tiling.rs:627-647) — окно останется в списках reconcile и повторится в
  следующем такте. Ошибка не превращается в «молча показано/скрыто». ЧИСТО.
- **Неуправляемое окно всегда видимо**: `forget` разворачивает окно из `cloaked`
  (tiling.rs:657-661); `sync_tree` не выкидывает скрытые нами окна из дерева (tiling.rs:720-726,
  иначе они никогда не показались бы обратно). ЧИСТО.

## 6. МАТЕМАТИКА РАСКЛАДКИ — ВСЁ ЧИСТО (после починки фаззером)

Что проверил по каждому краевому значению из задания:

- **`fitting_gap` (layout.rs:444-456)**: отрицательный `requested` → 0; `n <= 1` → `requested`
  (гэп не нужен); `room = span - n*1 <= 0` → 0; иначе `min(requested, room/slots)`. Ключевое
  следствие: `available = span - (n-1)*gaps >= n*1` ВСЕГДА — то есть в `split_span`
  недобор места бывает только при `gaps == 0`, а суммарный размер детей никогда не
  превышает контейнер. ЧИСТО.
- **`split_span` (layout.rs:333-431)**: `n == 1` → `available.max(0)`; `available < n*min_px`
  → `spread_evenly(available.max(0), n)` — нулевые плитки вместо переполнения
  (документированное решение, layout.rs:344-355); компенсация min_px с финальным
  `clamp_to_span` (layout.rs:424-428) — неоплаченный дефицит не вылезает за контейнер.
  Плюс арифметика в `layout_node`: `cur_x += width + gaps` ровно до правого края
  контейнера, никогда за него (layout.rs:143-159, 167-183). Проверено и живым фаззером
  инвариантов (`tiling_invariants.rs`, 7/7 — в т.ч. тест, воспроизводивший старый баг).
  ЧИСТО.
- **`spread_evenly` (layout.rs:459-471)**: `n >= 1` (в `split_span` n==0 отсечён выше);
  `span` неотрицателен (вызывается с `available.max(0)`); сумма В ТОЧНОСТИ равна `span`,
  остаток по первым. ЧИСТО.
- **`clamp_to_span` (layout.rs:476-486)**: срезает с самых больших, не уводя ниже нуля;
  завершается (каждая итерация уменьшает `total`); `span.max(0)` не даёт отрицательной
  цели. Переполнение i32 нереалистично: части ≤ ширины контейнера (порядка 10^4), сумма
  того же порядка. ЧИСТО.

Одна оговорка (не баг): в ветке `available < n*min_px` нулевые плитки могут оказаться за
границей контейнера по координатам (у них нет пикселей, пересечений не создают) —
координатору стоит не слать нулевые плитки в `SetWindowPos` (они всё равно никогда не
доедут и уйдут в `judge_pending`), но это оптимизация, а не корректность.

## ИТОГ: находки по убыванию серьёзности

1. **[БАГ, средний]** Драг затайленного окна >~0,75 с выбрасывает его из управления
   навсегда: `judge_pending` не учитывает `is_user_dragging` и смену монитора, `failed`
   не сбрасывается, возврата в раскладку нет. (tiling.rs:575-615, 693-696)
2. **[БАГ, средний]** `uncloak` снимает маркер даже при отказе DWM: скрытое окно без
   маркера теряется для `recover_orphans` навсегда — зеркальная дыра к аккуратной
   обработке в `cloak`. (cloak.rs:101-105)
3. **[БАГ, малый]** Утечка DC в `window_thumb::capture` при отказе `CreateDIBSection`
   (ранний `?` минует `DeleteDC`); комментарий про «единственный путь» неверен.
   (window_thumb.rs:106-119)
4. **[ПОДОЗРЕНИЕ]** Коллизия WidgetId при воркспейсе № ≥199: кнопки воркспейсов
   (601+num) попадают в диапазон табов (800+). (tiling_ui.rs:23-37, 251)
5. **[ПОДОЗРЕНИЕ]** Полоса воркспейсов считается по `bounds`, а не `work_area` — на
   мониторе с таскбаром может оказаться под ним. (tiling.rs:479-484)
6. **[НАБЛЮДЕНИЕ]** Скрытие неактивных воркспейсов (`hidden_windows`) ещё не подключено
   к координатору: `cloaked` покрывает только фоновые табы групп; status T4, не дефект.

# R5 — Дизайн движка раскладок (tiling) для rst-core

Исследование, не реализация. Модуль проектируется под `crates/rst-core`
(платформенно-чистый крейт, `crates/rst-core/src/lib.rs:5-7` — «никаких
зависимостей от Windows или рендера»). Рабочее название модуля: `tiling`.

## 0. Рамки и опоры на существующий код

- HWND приходит в ядро как `isize` — точный прецедент `PinnedWindow.hwnd`
  (`crates/rst-core/src/pinned_window.rs:75-78`: «крейт платформенно-чистый,
  конвертация в/из `HWND` — на границе `rst-win32`»). Движок раскладок
  оперирует тем же примитивом.
- Геометрия внутри ядра — DIP относительно левого верхнего угла монитора
  (ADR-010), тип `DipRect` (`crates/rst-core/src/hittest.rs:11-19`). Для
  конфига есть целочисленный `Rect` в физических px
  (`crates/rst-core/src/model.rs:109-116`) — он остаётся форматом
  персистентности, внутри движка только `DipRect`.
- Привязка к монитору — `MonitorId(String)` (`model.rs:12-15`).
- Рабочая область (монитор минус таскбар) вычисляется вне ядра:
  `SPI_GETWORKAREA`/AppBar-запросы — это Win32, слой `rst-win32`; ядро
  получает готовый `work_area: DipRect` на вход `layout()`. Тот же приём,
  что в `occluders.rs:2-6`: окна приходят уже переведёнными в
  платформенно-чистый вид координатором.
- Правила матчинга окон переиспользуют `OverlapRule`
  (`model.rs:344-349`: `process_name` ИЛИ `title_pattern`) и его семантику
  матчинга (`occluders.rs:71-73`).

## 1. Соглашения rst-core, которым обязан следовать дизайн

1. Модульный doc-комментарий на русском со ссылками на SPEC/ADR/CONFIG
   (например `snap.rs:1-9`, `undo.rs:1-7`).
2. Чистые функции/типы без ввода-вывода и таймеров (`migration.rs:3-5`,
   `ops.rs:4-6`); всё, что требует ОС, приходит параметрами.
3. Ошибки — `thiserror`-enum с русскими сообщениями (`error.rs:4-22`,
   `ops.rs:17-27`). Для tiling: `TilingError`.
4. Сериализация: `#[serde(default)]` на структуре, обратная совместимость
   без бампа `CURRENT_SCHEMA_VERSION` (`model.rs:19,49`, прецедент
   `model.rs:451-457` для `Config.presets`).
5. Рантайм-состояние не сериализуется вообще, если это «чисто
   рантайм-механизм» — прецедент `PinnedWindow` (`pinned_window.rs:1-7`).
6. Тесты inline в `#[cfg(test)] mod tests` с русскими сообщениями assert'ов;
   property-тесты на детерминированном `Splitmix64` без внешних крейтов
   (`undo.rs:266-331`).
7. Инварианты структур документируются в doc-комментарии типа
   (`selection_set.rs:21-22`, `undo.rs:18-21`).

## 2. Выбор модели: BSP / master-stack / дерево контейнеров

Три кандидата:

**(а) BSP/dwindle (Hyprland dwindle).** Каждый лист делится пополам,
направление сплита чередуется или выбирается по соотношению сторон;
явных контейнеров нет, ratio — на каждом внутреннем узле бинарного дерева.
Плюсы: ноль ручного управления, минимум состояния. Минусы: `toggle_split`
неестественен (направление — следствие алгоритма, а не состояние); группы-
табы в dwindle не выражаются — в Hyprland «grouped windows» это отдельный
надстроенный механизм поверх layout'а, а не узел дерева [ПРЕДПОЛОЖЕНИЕ:
страницы wiki.hyprland.org «Dwindle Layout»/«Master Layout» при проверке
2026-08-24 вернули 404, детали не верифицированы]; структура бинарного
дерева зависит от истории вставок, а не от намерения пользователя, что
усложняет и сериализацию, и предсказуемость resize.

**(б) master-stack (dwm / Hyprland master).** Один master-регион + стек.
Плюсы: очень просто, предсказуемо. Минусы: нет вложенных сплитов вообще;
табы — снова надстройка; «полноценный WM уровня Hyprland» с деревьями
раскладок на master-stack не построить.

**(в) Дерево контейнеров с явной ориентацией (i3/sway).** Внутренний узел —
контейнер с одним из layout'ов: `splith`, `splitv`, `tabbed`, `stacking`
[ИСТОЧНИК: i3 User's Guide §2.2, https://i3wm.org/docs/userguide.html —
«A split container can have one of the following layouts: splith/splitv,
stacking, tabbed»]. Группа-табы — это просто контейнер с `layout=tabbed`:
требование пользователя про группы ложится в модель без надстроек.
`toggle_split` — смена `splith`/`splitv` у контейнера фокуса (в i3 это
`$mod+e` [ИСТОЧНИК: там же, §2.2]). Сериализация тривиальна: дерево с
именованными enum'ами. i3 хранит на контейнере и «фокусного ребёнка», что
даёт правильное восстановление фокуса при выходе/возврате в группу.

**Выбор: (в), дерево контейнеров в стиле i3/sway.** Обоснование:
(1) группы/табы — первоклассный узел, а не болт сбоку; (2) явная ориентация
делает `toggle_split` и resize-ratio осмысленными операциями над состоянием,
а не над эвристикой; (3) dwindle и master-stack выражаются поверх того же
дерева как *политики вставки* (dwindle ≈ бинарное дерево с авточередованием
ориентации при insert; master ≈ корневой `splith{master, splitv{стек}}`), то
есть выбор (в) не закрывает дверь режимам (а)/(б) в будущем, а выбор (а)/(б)
закрывает табы; (4) sway доказал масштабируемость модели на production
[ПРЕДПОЛОЖЕНИЕ].

## 3. Структуры данных (сигнатуры, без реализации)

```rust
//! crates/rst-core/src/tiling.rs (проект)

/// Стабильный id узла дерева внутри движка. Uuid — как у стикеров
/// (model.rs:147); hwnd для этого не годится: узлы-контейнеры окнами не
/// являются, а hwnd ОС теоретически может переиспользовать [ПРЕДПОЛОЖЕНИЕ,
/// документацию MS не проверял].
pub struct NodeId(pub Uuid);

/// Id воркспейса: порядковый номер (1..=N), как в i3 [ИСТОЧНИК: i3 guide §2.1,
/// переключение по номерам].
pub struct WorkspaceId(pub u32);

pub enum Direction { Left, Right, Up, Down }

/// Layout контейнера-сплита; Tabbed/Stacked — не ось, а способ показа
/// детей: все дети занимают один и тот же прямоугольник.
pub enum SplitLayout { Horizontal, Vertical, Tabbed, Stacked }

pub enum Node {
    Leaf(Leaf),
    Split(Split),
}

pub struct Leaf {
    pub id: NodeId,
    /// HWND чужого окна как число (прецедент pinned_window.rs:78).
    pub hwnd: isize,
}

pub struct Split {
    pub id: NodeId,
    pub layout: SplitLayout,
    pub children: Vec<Node>,
    /// Доли размеров детей вдоль оси; инвариант: `len == children.len()`,
    /// сумма == 1.0 (нормализуется после каждой мутации, §5).
    /// Для Tabbed/Stacked не используется в layout(), но хранится —
    /// при смене layout на Horizontal/Vertical дети получают осмысленные
    /// исходные доли вместо сброса в равные.
    pub ratios: Vec<f64>,
    /// Индекс последнего сфокусированного ребёнка (для Tabbed — активный
    /// таб; для сплитов — куда вернётся фокус при входе в контейнер).
    pub focused_child: usize,
}

/// Плавающее окно воркспейса: живёт вне дерева.
pub struct FloatingWindow {
    pub hwnd: isize,
    pub rect: DipRect,
    /// Счётчик поднятия; больше — выше (аналог `Sticker.order`, model.rs:151).
    pub z: u64,
}
```


```rust
pub struct Workspace {
    pub id: WorkspaceId,
    /// Привязка к монитору (ADR-010); миграция при отключении монитора —
    /// отдельная задача по образцу migration.rs (здесь не покрыта, §10).
    pub monitor: MonitorId,
    /// Корень — всегда Split или None (пустой воркспейс).
    pub root: Option<Split>,
    /// Лист с фокусом (None — фокус у floating-окна или воркспейс пуст).
    pub focused: Option<NodeId>,
    pub floating: Vec<FloatingWindow>,
    /// Не более одного fullscreen-листа на воркспейс (как в i3 — fullscreen
    /// вытесняет предыдущий [ИСТОЧНИК: i3 guide §2.3]).
    pub fullscreen: Option<NodeId>,
}

/// Корень состояния движка.
pub struct TilingState {
    pub workspaces: Vec<Workspace>,
    pub active: WorkspaceId,
    z_counter: u64,
}
```

Инварианты дерева (документируются на типах, как `selection_set.rs:21-22`):
`Split.children.len() >= 2` — при удалении, оставляющем одного ребёнка,
сплит **схлопывается**: ребёнок поднимается на место родителя; `ratios`
нормализованы; `focused_child < children.len()`. Инварианты проверяются
property-тестом (§7, тест 39).

## 4. Операции над деревом

```rust
/// Куда вставлять новое окно.
pub enum InsertPolicy {
    /// Рядом с фокусом: новый лист — sibling фокусного в ближайшем
    /// предке-Split; если фокусный лист в Tabbed-контейнере — новым табом
    /// в него (новое окно идёт в контейнер фокуса [ИСТОЧНИК: i3 guide §2.1]).
    /// Ориентация первого сплита — по `default_orientation` конфига
    /// (`Auto | Horizontal | Vertical`; i3 выбирает по соотношению сторон
    /// монитора [ИСТОЧНИК: i3 guide §2.1] — у нас это настройка).
    Auto,
    /// Принудительно новым табом в группу фокусного окна.
    AsTab,
    /// Dwindle-совместимая: делить фокусный лист с чередованием оси.
    /// Отложенный режим; заложен в enum, чтобы не менять сигнатуру insert.
    Dwindle,
}

impl TilingState {
    pub fn insert(&mut self, ws: WorkspaceId, hwnd: isize, policy: InsertPolicy)
        -> Result<NodeId, TilingError>;
    /// Удалить окно (закрыто/исключено). Схлопывает сплиты, чинит
    /// `focused`/`focused_child`, снимает fullscreen. None — окна не было.
    pub fn remove(&mut self, hwnd: isize) -> Option<NodeId>;
    /// Геометрический фокус по направлению (обоснование, почему не
    /// древовидный — §6): на вход — последний посчитанный LayoutOutput.
    pub fn focus_direction(&mut self, dir: Direction, layout: &LayoutOutput)
        -> Option<isize>;
    pub fn swap_direction(&mut self, dir: Direction, layout: &LayoutOutput)
        -> bool;
    pub fn move_to_workspace(&mut self, hwnd: isize, to: WorkspaceId)
        -> Result<(), TilingError>;
    /// Изменить ratio ближайшего предка-сплита, чья ось совпадает с `dir`;
    /// дельта в долях (например ±0.05), кламп в `MIN_RATIO..=1.0-MIN_RATIO`.
    pub fn resize(&mut self, dir: Direction, delta: f64);
    /// Horizontal <-> Vertical у контейнера фокуса (i3 `$mod+e`); на
    /// Tabbed/Stacked — перевод в сплит с сохранёнными ratios.
    pub fn toggle_split(&mut self);
    pub fn toggle_float(&mut self, hwnd: isize) -> Result<(), TilingError>;
    pub fn toggle_fullscreen(&mut self, hwnd: isize) -> Result<(), TilingError>;
    /// Собрать детей сплита фокуса в Tabbed/Stacked-контейнер
    /// (i3 `$mod+w`/`$mod+s` [ИСТОЧНИК: i3 guide §2.2]).
    pub fn group(&mut self, layout: SplitLayout) -> Result<NodeId, TilingError>;
    /// Распустить группу: дети поднимаются в родителя группы.
    pub fn ungroup(&mut self, hwnd: isize) -> Result<(), TilingError>;
    /// Активировать следующий/предыдущий таб группы фокуса, по кругу.
    pub fn cycle_group(&mut self, forward: bool) -> Option<isize>;
}
```

Замечания по семантике:
- `insert(Auto)`: новое окно встаёт **после** фокусного листа (справа/снизу)
  и получает долю `1/(n+1)` после перенормировки сплита — так ratio-сhistorия
  остальных окон сохраняет относительные пропорции.
- `resize`: идём от фокусного листа вверх до первого предка с нужной осью;
  если дошли до корня — no-op, это не ошибка (стиль no-op'ов `ops.rs:52-56`).
- `swap_direction`: внутри одного сплита — обмен позиций вместе с ratios;
  через границу контейнеров — переподвешивание, разрешённое только если оба
  сплита останутся с `>= 2` детьми (иначе нарушился бы инвариант), при
  невозможности возвращает `false`.


## 5. Гэпы и функция layout()

```rust
pub struct GapConfig {
    /// Между соседними окнами/контейнерами, DIP (i3 `gaps inner`
    /// [ИСТОЧНИК: i3 guide §4.34]).
    pub gaps_in: f64,
    /// От края рабочей области, DIP (i3 `gaps outer` [там же]).
    pub gaps_out: f64,
    /// Минимальный размер окна по каждой оси, DIP; ниже него дети сплита
    /// не опускаются (см. краевой случай 3).
    pub min_window: f64,
    /// Высота полосы табов/стека сверху прямоугольника группы, DIP
    /// (полосу рисует оверлей rst-render; ядро лишь резервирует место).
    pub tab_bar_height: f64,
}

/// Результат раскладки: порядок детерминирован (DFS по дереву), чтобы
/// тесты и z-порядок tiled-слоя были воспроизводимы.
pub struct LayoutOutput {
    pub tiled: Vec<(NodeId, isize, DipRect)>,
    pub fullscreen: Option<(NodeId, isize, DipRect)>,
}

pub fn layout(ws: &Workspace, work_area: DipRect, gaps: &GapConfig) -> LayoutOutput;
```

Алгоритм:
1. **Валидация.** Нечисловые/отрицательные гэпы → 0 (соглашение
   `snap.rs:89-91`: NaN эквивалентен отключению). Невалидная `work_area`
   (нулевая/NaN) → пустой `LayoutOutput`.
2. **Кламп гэпов к области.** Эффективный `gaps_out' = min(gaps_out,
   (dim - min_window) / 2)` по каждой оси; эффективный `gaps_in'` на уровне
   сплита из n детей: `min(gaps_in, (inner_dim - n*min_window) / (n-1))`,
   не ниже 0. Так «гэп больше половины экрана» не даёт отрицательных
   прямоугольников, а деградирует в тайлинг без гэпов.
3. **Outer gaps:** `area = work_area.inset(gaps_out')` — до рекурсии.
4. **Рекурсия `layout_node(node, rect)`:**
   - `Leaf` → `rect`.
   - `Tabbed`/`Stacked` → каждый ребёнок получает `rect` минус
     `tab_bar_height` сверху; все дети — один прямоугольник, видимость
     неактивных табов решает rst-win32 (hide/show), не ядро.
   - `Horizontal` → дети слева направо: `inner = rect.w - gaps_in'*(n-1)`,
     `w_i = inner * ratio_i`, `x` накапливается с шагом `w_i + gaps_in'`;
     `Vertical` — аналогично по Y. Последний ребёнок получает остаток
     (`rect.right - x`), чтобы погрешность f64 не оставляла щель/нахлёст.
5. **Fullscreen** обрабатывается отдельно от дерева: fullscreen-лист получает
   весь `work_area` без гэпов и без tab bar; дерево при этом раскладывается
   «под ним» как обычно (при выходе из fullscreen раскладка не потеряна).
   Поведение «гэпы в fullscreen» у Hyprland конфигурируемо [ПРЕДПОЛОЖЕНИЕ];
   у нас — всегда без гэпов, проще и предсказуемо.

Краевые случаи (все — тестами §7):
1. **Одно окно:** получает `area` целиком — действуют только `gaps_out`,
   `gaps_in` нечему делить (совпадает с i3 gaps [ИСТОЧНИК: i3 guide §4.34]).
2. **Окно меньше минимального размера:** `ratio_i` клампится так, что
   `w_i >= min_window`; недостающее забирается у соседей пропорционально их
   долям (один проход, затем перенормировка). Если `inner < n*min_window` —
   применён кламп из п.2 (гэпы ужаты), дети получают ровно `min_window`
   и остаток делится по ratio.
3. **Гэп больше половины экрана:** кламп п.2 — раскладка деградирует до
   «без гэпов», но не ломается и не выдаёт отрицательные/перевёрнутые rect.
4. **Пустой воркспейс** (`root: None`) → пустой `tiled`.

## 6. Плавающие окна и z-порядок

- Tiled и floating сосуществуют на одном воркспейсе: floating-окна хранятся
  в `Workspace.floating` со своим `rect` (его двигает пользователь мышью,
  ядро хранит и клампит к монитору) и в `layout()` не участвуют.
- `toggle_float`: лист удаляется из дерева (со схлопыванием), окно
  становится floating с прямоугольником, равным последнему тайловому;
  обратно — обычный `insert(Auto)` с сохранением места рядом с фокусом.
- **Z-порядок — три полосы:** tiled-слой (снизу, внутри — порядок DFS) <
  floating (внутри — `z` по last-raise, аналог `Sticker.order`/`bring_to_front`
  `ops.rs:47-57`) < fullscreen (всегда верх воркспейса). Всё выше/ниже
  обычных окон Windows и стикеров resticker решает rst-win32 — ядро
  отдаёт только относительный порядок внутри своих полос.
- `focus_direction` — **геометрический** по последнему `LayoutOutput` плюс
  floating-rect'ам (Hyprland-стиль), а не древовидный (i3-стиль):
  древовидный фокус непредсказуем на смешанных вложенностях, а у нас уже
  есть готовые rect'ы. Кандидат — окно, чей rect пересекает луч от центра
  текущего в направлении `dir`; при равенстве — ближайший по центру.
  Табы: геометрия группы одна, поэтому фокус «внутрь группы» попадает на
  активный таб; движение между табами — только `cycle_group`.

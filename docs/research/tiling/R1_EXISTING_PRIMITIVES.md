# R1: Инвентаризация существующих примитивов управления чужими окнами

Исследование кодовой базы resticker (ветка `feat/m2-edit-mode`, коммит `7d695f5`) для
проекта tiling. Всё, что уже умеет проект, — чтобы tiling не переписывал это заново.
Никакой код не менялся. Смежные отчёты: `R2_PRIOR_ART.md` (чужие тайлинги), `R3_WIN32_MECHANICS.md`
(механики Win32, в т.ч. `BeginDeferWindowPos` и «окно нельзя двигать»), `R4_KEYBINDS.md`.

Сокращения: СК — система координат. «DWM-координаты» = `DWMWA_EXTENDED_FRAME_BOUNDS`
(физические px виртуального десктопа, то, что реально рисует композитор). Все ссылки —
`файл.rs:строка`; «не проверял» — не читал код по этой теме.

## 1. crates/rst-win32/src/window_pin.rs — движок управления чужим окном (3693 строки)

Модуль-доккомент (window_pin.rs:1-69) описывает всю идеологию: пин — это НЕ отдельное
окно, а `WS_EX_TOPMOST` на самом целевом окне + window property-маркер `SetPropW`
(имя `resticker`, значение — `u64`-маркер вызывающего кода, window_pin.rs:92). Своих
WinEvent-хуков модуль НЕ ставит — смерть таргета ловит координатор через снимки трекера
(`handle_snapshot`). UIPI сознательно не обходится (window_pin.rs:24-27).

вызывает координатор на КАЖДОМ снимке трекера (overlay_manager.rs:7896). Тайлингу это
достанется бесплатно, если он живёт в той же ветке.

### 1.2 Почему `move_resize` = `SetWindowPlacement`, а не `SetWindowPos` — прямо нужно тайлингу

window_pin.rs:423-468. Пока у окна стоит `WS_MAXIMIZE` (`IsZoomed` — развёрнут на весь
монитор, включая borderless-fullscreen), Win32 **молча игнорирует** явный размер из
`SetWindowPos`: maximized-логика перетирает прямоугольник обратно, вызов возвращает успех,
окно не меняется (баг найден живым тестированием: «пин fullscreen-окна не ужимает его до 90%»).

Решение: один атомарный `SetWindowPlacement` с `showCmd = SW_SHOWNOACTIVATE` и целевым
`rcNormalPosition` — он и снимает `WS_MAXIMIZE`, и ставит нормальный прямоугольник сразу,
без промежуточного `ShowWindow(SW_RESTORE)` (лишний кадр/мерцание). Для не-maximized окна
это эквивалент `SetWindowPos` (showCmd на нормальном окне — no-op). Фокус не крадётся.
**Вывод для тайлинга**: всякий раз, когда окно может быть развёрнуто, класть его в плитку
нужно через `SetWindowPlacement`-паттерн (уже готов в `move_resize` и внутри `set_dwm_bounds`,
window_pin.rs:720-736). Голый `SetWindowPos` на maximized-окне = тихая потеря перестановки.

### 1.3 `set_dwm_bounds` — коррекция невидимых рамок, основа корректных гэпов

window_pin.rs:687-753. `SetWindowPos` работает в `GetWindowRect`-координатах, а у окон
Win11 они отличаются от DWM-границ на невидимые поля ресайза (сверху ~1 px, по бокам/снизу
~7-8 px). Складывать эти пространства напрямую = систематический промах на рамку + дрейф
при повторных применениях. Здесь смещение считается один раз:
`dx/dy/dw/dh = dwm_rect − gwr_rect` (window_pin.rs:712-716), затем `SetWindowPos` ставит
`target − смещение`, так что DWM-границы совпадут с целью.

Честные оговорки: (а) для maximized-окна уходит в `move_resize` (см. 1.2); (б) результат
`SetWindowPos` НЕ проверяется — метод возвращает `true`, даже если окно не поехало
(UIPI/мёртвое между проверкой и вызовом), window_pin.rs:737-752. Для тайлинга это означает:
после перестановки проверять фактическую геометрию следующим снимком (что и так делается —
snap-back/магнит живут на снимках), а не верить возврату.

Эта же СК-проблема была причиной вечного snap-back-цикла (~60 Гц) у move-lock, когда эталон
брался в `GetWindowRect`, а сравнение — в DWM-координатах (window_pin.rs:119-122, 601-607):
**все геометрические сравнения тайлинга обязаны быть в одной СК — DWM**.

### 1.4 Три эшелона move-lock — можно ли переиспользовать для тайлинга

Модуль `input_guard` (window_pin.rs:887-2013) — глобальный страж ввода, один `WH_MOUSE_LL`
на процесс, живёт на своём потоке-помпе `resticker-input-guard` (:1056-1058) вместе с
WinEvent-хуком `EVENT_SYSTEM_MOVESIZESTART`. Refcount по содержимому карты политик
(`Policy { move_locked, interact_locked }`, :921): хуки стоят только пока есть хоть одно
заблокированное окно (:988-1015). Три эшелона (window_pin.rs:824-834):

1. **Глотание button-down** (`guard_mouse_proc` :1184): hit-test точки даёт «взяться за окно»
   (`HTCAPTION`, рамки, `HTGROWBOX` — `is_move_ht` :1399) → возврат `LRESULT(1)`, событие
   выброшено до системного hit-testing/активации, драг не начинается вовсе. Hit-test —
   из кэша потока-пробника `resticker-ht-probe` (:1707-1709), который асинхронно шлёт
   `SendMessageTimeoutW(WM_NCHITTEST, SMTO_ABORTIFHUNG, 80 мс)` (:1828-1871); колбэк хука
   сам никогда не делает синхронных вызовов (бюджет `LowLevelHooksTimeout` = 1 мс на машине
   пользователя, window_pin.rs:863-878). Промах кэша — геометрическая оценка `ht_from_geometry`
   (:1504), **fail-open**: interact-lock глотает только доказанный `HTCLIENT`, иначе клик
   проходит (окна с собственным заголовком — Electron/Tauri — иначе теряли бы перетаскивание,
   :1229-1244). Признак «настоящий системный заголовок» — DWM-кэш `DWMWA_CAPTION_BUTTON_BOUNDS`
   (:1544-1620).
2. **`EVENT_SYSTEM_MOVESIZESTART` → `PostMessageW(WM_CANCELMODE)`** (`movesize_proc` :1338):
   ловит пути мимо LL-хука — тач/перо, Alt+Space → «Переместить», промах кэша. `DefWindowProc`
   на `WM_CANCELMODE` отпускает захват и выходит из цикла.
3. **Snap-back** (`enforce_move_lock` :657): для программных перемещений без мыши
   (чужой `SetWindowPos`, Win+стрелки, snap-раскладки). Не дерётся с живым драгом:
   `user_is_dragging_window` → пропуск тика, один возврат после отпускания (:646-656).

Сторож переустановки хука: если система молча сняла LL-хук по таймауту (уведомлений нет),
пробник замечает «мышь движется, а событий нет» и просит помп переустановить
(:1796-1821, `WM_APP_REINSTALL`).

**Ответ на вопрос задачи**: 
- «Нельзя утащить тайлинговое окно мышью» — **да, переиспользуется как есть**: `set_move_lock(hwnd, true)`
  захватывает текущие DWM-границы как эталон, и дальше координатор (уже это делает,
  overlay_manager.rs:7999-8009) дёргает `enforce_move_lock` по каждому location-change.
  Тайлингу достаточно того же вызова. НО: эталон = момент вызова, поэтому после КАЖДОЙ
  перестановки окна в новую плитку нужно `set_move_lock(hwnd, true)` заново — иначе первый
  же enforce откатит окно на старую плитку (документировано :589-595).
- «Разрешить драг для swap» — **прямого пути нет**: глотание завязано на per-hwnd политику
  без модификаторов; чтобы разрешить «тащить при зажатом модификаторе», надо либо дёргать
  `set_move_lock(hwnd,false)` в начале жеста (но жеста не будет — первый button-down уже
  проглочен), либо расширять `Policy` (например, «глотать только без модификатора» —
  колбэк уже имеет доступ к `GetAsyncKeyState`-подобным данным? — не проверял: колбэк
  читает только MSLLHOOKSTRUCT). Альтернатива: тайлинг ставит СВОЙ `WH_MOUSE_LL` (второй
  хук на процесс законен, цепочка через `CallNextHookEx`), который первым смотрит
  модификатор и решает, пропускать ли кнопку в guard.
- Ограничения, наследуемые тайлингом: elevated-окна не блокируются вовсе (UIPI, :855-858);
  клавиатура не блокируется; колесо вне окна при выключенной «прокрутке неактивных» уходит
  мимо (:859-861).

## 2. window_tracker.rs + window_enum.rs — хуки, снимки, фильтр окон

### 2.1 WindowTracker (window_tracker.rs, 1268 строк)

- Свой поток + message-only окно (`HWND_MESSAGE`, :271-290), паттерн как у OverlayWindow.
  `start()` → `(Self, Receiver<WindowEvent>)` (:85-103). `WindowEvent::Changed(Vec<WindowInfo>)` —
  **полный снимок, не дифф** (:57-60); сравнение «что изменилось» — забота координатора.
- **Fast path (ADR-005)**: пока `set_mask_needed(true)` не вызван, хуки вообще не стоят,
  поток крутит пустой pump (:9-11, :110-122). Гейт пересчитывается раз за итерацию цикла
  координатора (`tracker_mask_needed`, overlay_manager.rs:4069-4075). Тайлинг обязан вписаться
  в этот гейт (его окна должны держать хуки живыми, пока нужен layout).
- WinEvent-хуки, 4 диапазона (install_hooks :322-374), все `WINEVENT_OUTOFCONTEXT`, без
  `WINEVENT_SKIPOWNPROCESS`:
  1. `EVENT_OBJECT_DESTROY..EVENT_OBJECT_LOCATIONCHANGE` — захватывает и соседние
     `SHOW`/`HIDE` (:328);
  2. `EVENT_SYSTEM_MINIMIZESTART..MINIMIZEEND` (:329);
  3. `EVENT_SYSTEM_FOREGROUND` (:342) — добавлен для z-order-вычитания окклюдеров;
  4. `EVENT_SYSTEM_MOVESIZEEND` (:348) — нужен координатору для «ровно одного снимка
     после отпускания» (магнит/кламп).
- Классификация события (`classify_event` :554-567): `SHOW|HIDE|FOREGROUND` → полное
  перечисление; `DESTROY` → удаление; `MINIMIZESTART/END` → iconic-флаг (+свежий rect на
  END); `LOCATIONCHANGE|MOVESIZEEND` → обновление rect, но **только для окон уже в кэше**
  (иначе всплывашки будили бы дебаунс впустую). Колбэк не делает никаких Win32-вызовов,
  кроме `SetTimer` (:623-634): вся работа — в `WM_TIMER`.
- **Дебаунс 16 мс** (`DEBOUNCE_MS` :46), один раз в кадр @60 Гц. Между событиями
  накапливается `Pending` (:147-154): `needs_full` перекрывает всё; снятие приоритетов —
  чистая функция `resolve_pending` (:464-488). `flush_pending` (:493-521) шлёт полный снимок.
- Заморозка на блокировке сессии: `WTSRegisterSessionNotification`, `frozen` (:166-171,
  :601-603, :708-725) — на `WTS_SESSION_LOCK` кэш не копится, разморозка = полный ребилд.
- Наиболее близкий к тайлингу сервис: снимок уже несёт `rect` в DWM-координатах, `iconic`,
  монотонный `z_order` — всё, что нужно для layout-математики.

### 2.2 window_enum.rs — разовое перечисление и фильтр «реальных» окон (761 строка)

- `enumerate()` → `Vec<WindowInfo>` (:184-195). `WindowInfo` (:72-99): `hwnd` (usize-ключ),
  `rect` (DWM-границы, физические px), `pid`, `exe_path`, `title`, `class`, `z_order`
  (монотонный индекс СЫРОГО перечисления, с пропусками — :173-179, :91), `iconic`, `icon`.
- Фильтр `is_real_window` (:151-171) — по флагам (:137-147): отбрасываются невидимые,
  cloaked (`DWMWA_CLOAKED`), не-root (`GetAncestor(GA_ROOT) != hwnd`), `WS_EX_NOACTIVATE`
  (собственные оверлеи resticker!), toolwindow без `WS_EX_APPWINDOW`, owned без
  `WS_EX_APPWINDOW`. `iconic` не отбраковка, только отметка. Заголовок читается
  кросс-поточным `SendMessageTimeoutW(WM_GETTEXT, SMTO_ABORTIFHUNG, 500 мс)` (:38, :422-446);
  exe-путь через `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` (:459-496).
- `extended_frame_bounds` (:365-382) — `pub(crate)`, та же функция-источник для трекера,
  пинов и геометрии.
- `live_rect(hwnd)` (:350-363) — прямой опрос DWM мимо кэша (для живых драгов; тайлингу
  полезно для немедленных перестановок).
- `foreground_hwnd()` (:389-394), `monitor_of(hwnd)` (:404-410, `MONITOR_DEFAULTTONULL` —
  свёрнутое окно честно «нигде»).
- **`shell_switching()` (:318-337) — критичный гейт для тайлинга**: Alt/Win зажаты ИЛИ
  переднее окно из `SHELL_TRANSIENT_CLASSES` (:289-298: Alt+Tab-фреймы, TaskView, Пуск,
  поиск, панели задач). Пока true — координатор НЕ трогает чужие окна (иначе ломается
  переключатель, репорт 2026-08-22). Тайлинг обязан наследовать этот гейт.

## 3. monitors.rs — мониторы (273 строки)

- `MonitorInfo` (:39-52): `id: MonitorId` (стабильный device interface path
  `\\?\DISPLAY#...`, ADR-010), `friendly_name`, `bounds_px: Rect` (**`rcMonitor` — ПОЛНЫЕ
  границы, включая таскбар!** :111), `dpi` (`GetDpiForMonitor`, MDT_EFFECTIVE_DPI, :133-142),
  `is_primary`.
- **Рабочей области (work area, `rcWork`) НЕТ нигде в кодовой базе** — проверено
  grep'ом по `rcWork|work_area|MONITORWORKAREA`: единственные упоминания `GetSystemMetrics`
  — про размер экрана в overlay.rs:333-334 и про высоту заголовка в window_pin.rs:2930.
  Таскбар в геометрии учитывается ТОЛЬКО как оклюдер маски по классу `Shell_TrayWnd`
  (occluders.rs:13). Для гэпов от таскбара тайлингу придётся либо добавить `rcWork` в
  `MonitorInfo`, либо считать полосу таскбара отдельно.
- Hot-plug: состояние модуль не хранит, каждый вызов — свежий снимок; сравнение снапшотов —
  координатор (`MonitorLossTracker`, ADR-011; `WM_DISPLAYCHANGE` → `OverlayEvent::MonitorsChanged`,
  overlay.rs:223-227). Стабильный id позволяет привязывать воркспейсы/раскладки к монитору.

## 4. hotkey.rs — хоткеи (321 строка)

- Парсинг комбинации `"Ctrl+Alt+S"` (`HotkeyCombo::parse` :38-90): модификаторы
  Ctrl/Alt/Shift/Win + основная клавиша (латиница `A-Z`, цифра `0-9`, `F1-F24`);
  раскладкозависимые клавиши сознательно не поддерживаются (:36-37, `VkKeyScan` не юзается).
  Хоткей без модификаторов запрещён (:86-88). `display_string` — каноничный вид (:95-111).
- Регистрация: `RegisterHotKey(None, id, mods, vk)` на ТЕКУЩЕМ потоке (:178-199); тип
  `RegisteredHotkey` — намеренно `!Send`, создание и Drop на одном потоке с циклом
  сообщений (оверлей-поток). `MOD_NOREPEAT` всегда (:116-131). Конфликт →
  `Win32Error::HotkeyConflict` (:189-191) → баннер в UI.
- **Сколько может быть**: id из диапазона `0..=0xBFFF` (:180-184) — до 49152 на поток.
  Сейчас занято 7: `EDIT=1, TOGGLE_ALL=2, MUTE_ALL=3, PIN_FOCUSED=4, MEDIA=5,6,7`
  (overlay.rs:67-95). Для «биндов много» у tiling есть весь диапазон, но регистрация
  привязана к одному оверлей-потоку основного монитора (overlay.rs:269-279, только окно
  primary получает хоткеи).
- **Куда приходит WM_HOTKEY**: на поток оверлея с `msg.hwnd == NULL` (регистрация без
  окна) — специальная ветка в его msg-цикле до `DispatchMessageW` (overlay.rs:874-891),
  id из `wParam` → `OverlayEvent::{ToggleEditMode, ToggleAllStickers, ToggleMuteAll,
  PinFocusedWindow, MediaPlayPause, MediaVolumeUp, MediaVolumeDown}` → в общий канал
  координатора.

## 5. virtual_desktops.rs — виртуальные столы (185 строк)

- Реально доступно ровно одно: `is_window_on_current_desktop(hwnd)` (:54-68) через

## 9. ЧТО МЕНЯ БЕСПОКОИТ

1. **Нет рабочей области (work area) вообще**. `MonitorInfo` берёт `rcMonitor`, таскбар
   учитывается только как оклюдер маски стикеров. Гэпы «от края экрана» без учёта таскбара
   будут класть плитки под панель задач; честное решение — добавить `rcWork` в
   `monitors.rs` + следить за его сменой (таскбар автоскрывается/меняет размер — событий
   на это нет, только опрос).
2. **Move-lock vs анимации перестановок — конфликт по построению**. `enforce_move_lock`
   сравнивает ПОЛНЫЙ RECT и возвращает окно на эталон при ЛЮБОМ расхождении. Плавный
   переезд плитки (кадр за кадром через промежуточные позиции) будет читаться как
   «окно двигают» и откатываться первым же снимком. Либо анимации переезда идут через
   `set_dwm_bounds` при выключенном lock (и включаются с перезахватом эталона после),
   либо snap-back для тайлинговых окон нужен другой (сравнивать с ЦЕЛЬЮ, а не с эталоном
   прошлого вызова). История проекта уже содержит вечный snap-back-цикл из-за расхождения
   СК (window_pin.rs:119-122) — та же ловушка ждёт тайлинг на анимациях.
3. **UIPI и бюджет LL-хука — потолок «всё работает»**. Elevated-окна не двигаются и не
   блокируются (window_pin.rs:855-858, :24-27); LL-хук снимается системой молча при
   превышении 1 мс на машине пользователя. Hyprland-уровень «жёсткого» управления на
   чистом Win32 без драйвера/подкласса окон не достигается — надо честно заложить класс
   «окна, которые тайлинг не может ни закрепить, ни переставить».
4. **Однопоточный координатор**. Каждая перестановка окна порождает `LOCATIONCHANGE` →
   снимок через 16 мс → пересчёт окклюдеров + обслуживание пинов + (новое) обслуживание
   раскладки. Цикл уже несёт `enumerate()` и `SendMessageTimeout` в hot path (:2949,:4053).
   Рекурсия «переставил → снимок → переставил снова» обязана сходиться (исторический
   инцидент с петлёй окклюдеров это подтверждает). Нужен порог эпсилон-сходимости и
   подавление повторных перестановок.
5. **Alt+Tab/шелл-гейт**. `shell_switching()` (window_enum.rs:318) — единственное, что
   спасает переключатель от resticker'а. Тайлинг, дёргающий окна по `FOREGROUND`/`Key`
   без этого гейта, сломает Alt+Tab ровно тем же классом багов, что уже был у пинов
   (репорт 2026-08-22). Гейт обязан стать общим для всей подсистемы чужих окон.
6. **Воркспейсы упираются в приватные COM-интерфейсы**. Без `IVirtualDesktopManagerInternal`
   (порт комореби, R2 §2 — нестабильно между сборками Windows) воркспейсы останутся
   внутренней абстракцией resticker: переключение столов Windows не будет двигать плитки,
   и наоборот. Это архитектурное решение, которое надо принимать явно, а не по пути.
7. **Топмост-полоса уже занята**. Оверлеи resticker сами topmost (по окну на монитор),
   и есть даже z-order-война с пинами (`raise_above_pinned`, overlay_manager.rs:3500-3509).
   Тайлинговые окна в topmost-полосе (если кто-то решит «пинить» плитки) будут
   перепрыгивать оверлеи; «просто поверх всех» в Windows не существует без топмост-полосы
   или подкласса — надо заранее решить, кто выше: оверлей или тайлинговое окно.

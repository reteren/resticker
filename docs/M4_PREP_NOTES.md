# M4 — подготовительные заметки: слои видимости через маску перекрытия

Статус: **скопинг, без изменений кода**. Основание: ROADMAP.md «M4 — слои видимости»,
DECISIONS.md ADR-004 (маска в шейдере) и ADR-005 (WinEvent-хуки вместо опроса),
ARCHITECTURE.md разделы 3.2–3.4 и 4.1–4.3. Текущее состояние: редактор M2 готов,
но окно-перечисления в `rst-win32` нет, шейдер спрайта — один PS без маски,
в модели уже есть каркас `VisibilityRule`/`OverlapRule`.

Ниже — что именно надо построить, где и как оно стыкуется с существующим кодом.
Цель заметки — дать координатору карту, а не реализацию.

## 2. Новый модуль в `rst-win32`: перечисление и кэш окон

### 2.1 Сигнатура и данные

Новый модуль `crates/rst-win32/src/windows.rs` (или `window_list.rs`), публично:
`pub mod windows;` в `lib.rs`. Наружу — платформенно-чистые данные (как `input::InputEvent`
в M2), без `HWND` в публичном API координатора.

```rust
pub struct WindowInfo {
    pub hwnd: usize,          // только как ключ; координатор его не использует
    pub rect: DipRectOrRaw,   // DWMWA_EXTENDED_FRAME_BOUNDS, физические px
    pub pid: u32,
    pub exe_path: PathBuf,    // для сопоставления с OverlapRule::process_name
    pub title: String,        // для title_pattern и панели
    pub class: String,        // для панели/расширения правил
    pub z_order: u32,         // позиция в перечислении (топ → низ)
    pub iconic: bool,         // свёрнуто — прямоугольник мусорный, не оклюдер
}
```

Прямоугольник удобно держать как `hittest::DipRect`-совместимый (x,y,w,h), но
**физические** пиксели — маска живёт в физических (см. раздел 4). Перевод в DIP
при необходимости — на стороне координатора, как в M2 (`to_dip`).

### 2.2 Полное перечисление (`enum_windows()`)

Один проход `EnumWindows` (top-level, перечисляет в порядке z-order сверху вниз) +
фильтр `is_real_window(hwnd)` **дословно по ARCHITECTURE.md 3.3**:

- `IsWindowVisible` — нет → отбросить;
- `DwmGetWindowAttribute(DWMWA_CLOAKED)` ≠ 0 → отбросить (скрытые окна UWP);
- `GetAncestor(hwnd, GA_ROOT) != hwnd` → отбросить (не top-level);
- `WS_EX_NOACTIVATE` → отбросить;
- `WS_EX_TOOLWINDOW && !WS_EX_APPWINDOW` → отбросить;
- есть `GW_OWNER` и нет `WS_EX_APPWINDOW` → отбросить;
- `IsIconic` → отметить `iconic: true` (не оклюдер, но показать в панели).

Границы — только `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` (не
`GetWindowRect`): то, что видит DWM, ровно то, что вырезаем.

### 2.3 Новые зависимости `windows` (Cargo.toml)

Текущему `rst-win32` не хватает фич:
- `Win32_UI_Accessibility` — `SetWinEventHook`/`UnhookWinEvent` + константы событий;
- `Win32_Graphics_Dwm` — `DwmGetWindowAttribute` (`DWMWA_CLOAKED`,
  `DWMWA_EXTENDED_FRAME_BOUNDS`);
- `Win32_System_Threading` — `OpenProcess`/`QueryFullProcessImageNameW` для
  `exe_path` по `pid` (или `GetWindowThreadProcessId` + snapshot, см. открытые вопросы).

## 3. Инкрементальный кэш на WinEvent-хуках (ADR-005)

### 3.1 Поток и pump

`SetWinEventHook(..., WINEVENT_OUTOFCONTEXT, ...)` колбэком приходит в наш процесс,
но событие доставляется **в очередь сообщений потока, поставившего хук**
(хук с `WINEVENT_SKIPOWNPROCESS` + thread-id своего потока). Значит нужен поток с
работающим pump. Варианты:

- **А.** Отдельный поток трекера (свой `GetMessage`-цикл, как у трея/оверлея). Плюс:
  pump оверлея не раздувается, маска не связана с вводом. Минус: третий поток.
- **Б.** Встроить в существующий pump оверлея (`overlay.rs::run_message_loop`).
  Плюс: два потока вместо трёх. Минус: `WM_HOTKEY`/мышь уже перехватываются там,
  добавление фильтра событий окон усложнит цикл; и хуки должны ставиться/сниматься
  при переключении «fast path ↔ маска» — привязка к жизни окна неудобна.

Рекомендация для скопинга: **А** — отдельный `WindowTracker`, живущий в
`rst-win32`, с собственным циклом и каналом наружу (паттерн уже отработан в
`overlay.rs`/`tray.rs`: `create()` возвращает `(Self, Receiver<WindowEvent>)`).
Тогда время жизни трекера не зависит от оверлей-окна, и «нет ограничений → не
ставить хуки» управляется самим трекером (он может жить, но без хуков).

### 3.2 События и их обработка

| Событие | Действие |
|---|---|
| `EVENT_SYSTEM_FOREGROUND` | полный `enum_windows()` (изменился z-order) |
| `EVENT_OBJECT_SHOW` / `HIDE` | полное перечисление (окно появилось/ушло) |
| `EVENT_OBJECT_DESTROY` | убрать hwnd из кэша инкрементально |
| `EVENT_SYSTEM_MINIMIZESTART` / `MINIMIZEEND` | отметить `iconic` (полное/инкремент) |
| `EVENT_OBJECT_LOCATIONCHANGE` | **только** обновить прямоугольник конкретного hwnd; не перечислять |
| `EVENT_SYSTEM_MOVESIZESTART` / `MOVESIZEEND` | поднять/сбросить приоритет дебаунса (опц.) |

Фильтр для всех: `idObject == OBJID_WINDOW && idChild == CHILDID_SELF`; hwnd,
которого нет в кэше «реальных окон», на `LOCATIONCHANGE` отбрасывать сразу.

### 3.3 Дебаунс 16 мс и коалесцирование

`EVENT_OBJECT_LOCATIONCHANGE` при перетаскивании летит десятками в секунду.
Внутри трекера:

- колбэк хука только помечает «dirty» и кладёт hwnd в set изменённых;
- цикл спит на `MsgWaitForMultipleObjects` / waitable-таймере и просыпается на
  событие; пересчёт — не чаще 16 мс (один кадр @60 Гц);
- после дебаунса: применить отложенные изменения к `Vec<WindowInfo>`, затем
  отправить наружу **одно** событие `WindowEvent::Changed` (или `Vec<WindowInfo>`
  целиком — 25-30 окон, дёшево; решает вопрос «кто владеет копией»).

### 3.4 Fast path: хуки не ставятся

Правило из ADR-005: если **ни у одного** стикера нет ограничений
(`mode == Always` у всех), трекер не регистрирует хуки `LOCATIONCHANGE` вообще.
Требует, чтобы координатор сообщал трекеру «нужна маска?» при каждом изменении
конфига (см. раздел 6.4, `mask_needed`).

### 3.5 Отсечка перерисовки

Пересчитывать маску только если новый прямоугольник окна (или новый список)
меняет пересечения со стикерами: если и старый, и новый прямоугольник не
пересекаются ни с одним стикером — красро не запускать. Проверка пересечения
прямоугольника окна с bbox стикера — дёшево (axis-aligned), живёт на стороне
координатора.

### 3.6 Стыковка с координатором

`overlay_manager.rs` уже объединяет каналы (`OverlayMessage`). Для M4 добавить
`OverlayMessage::Event(OverlayEvent::Windows(WindowEvent))`-подобный вариант
(или второй приёмник), обрабатываемый как «вычислить маску и перерисовать».
Порядок событий мыши/окон в одном канале сохраняет FIFO — перерисовка маски
никогда не «проскакивает» перед обработанным перемещением окна.

## 4. Маска перекрытия и шейдер

### 4.1 Маска как текстура

- **Формат/разрешение:** одна R8-текстура на размер оверлея (физические
  пиксели), создаётся как offscreen render target (`create_mask_texture(w,h)` в
  `rst-render`). `1.0` = перекрыто, `0.0` = видно. Возможен вариант
  `R8G8B8A8_UNORM`, если так проще переиспользовать существующие пути рендера —
  для шейдера важен красный канал.
- **Проход рендера маски:** clear в 0; для каждого оклюдера (окно не из
  allow_list стикера — но маска **общая на экран**, см. 4.2) нарисовать
  скруглённый прямоугольник радиусом 8 px (ADR-004: компенсация углов Windows 11).

### 4.2 Общая маска против постикерной

Маска **общая на весь экран**, а не на стикер: рисуем объединение всех оклюдеров
всех стикеров один раз за кадр, затем каждый стикер-спрайт дискардится по ней.
Стикер с `mode == Always` маску не сэмплирует (ему нужна пустая). Если маска
пуста (нет оклюдеров) — спрайты идут без маски, быстрый путь (4.5).

### 4.3 Шейдер: `discard` по маске

В `SPRITE_HLSL` добавить второй слот текстуры/сэмплера:

```
Texture2D maskTex : register(t1);
SamplerState maskSamp : register(s1);
// в mainPS:
float2 px = i.pos.xy;                    // SV_Position = центр пикселя, физические px
if (maskTex.Sample(maskSamp, px).r > 0.5) discard;
return tex0.Sample(samp0, i.uv) * i.opacity;
```

- Маска сэмплится по **экранной позиции пикселя** (`SV_Position`), а не по `uv`
  стикера — вырез должен быть стабилен при движении/повороте стикера, это
  единственный корректный способ.
- Сэмплер — `MIN_MAG_MIP_POINT` + `CLAMP` (никаких фильтров по краям пикселей).
- `discard` после premultiplied-умножения недопустим (преждевременный выход с
  ненулевой альфой), поэтому порядок: сначала `discard`, потом `* opacity`.
- Одна PS на оба случая: при пустой маске биндим 1×1 чёрную текстуру
  (`.r == 0` → ничего не дискардится). Отдельный «без маски» шейдер не нужен.

### 4.4 Отрисовка скруглённых прямоугольников

Прецедент в коде — `solid_sprite` (квад + заливка). Для скругления 8 px без
тесселяции — маленький fill-PS с SDF скруглённого прямоугольника
(`max(|dx|,|dy|) − radius`), выводящий `1` внутри и `0` снаружи с 1-px AA
(smoothstep). Это же даёт честную альфу маски у краёв. Прямоугольники рисуются
в маску как обычные спрайты в проходе маски, координаты — физические.

### 4.5 Быстрый путь (ROADMAP: `allow_list == ALL`)

Если у всех стикеров `mode == Always`:
- маска не создаётся/не рендерится;
- спрайты биндят 1×1 чёрную маску (или отдельный «голый» PS — как договоримся
  в 4.3);
- **хуки `LOCATIONCHANGE` не ставятся** (ADR-005), перечисление окон не идёт
  вообще.
Условие проверяется на каждое изменение конфига (`mask_needed`, раздел 6.4).

### 4.6 Отсечение полностью перекрытых стикеров (ROADMAP)

Вычисляется по маске/оклюдерам, дешёво и консервативно: для стикера собрать
объединённый bbox пересекающихся с ним оклюдеров (их прямоугольники
axis-aligned); если этот bbox покрывает bbox стикера (`aabb`) — стикер
«невидим». Точнее (по пикселям маски) — только для решения о декодировании видео
(M5); для PNG достаточно консервативного rect-теста. Невидимые стикеры
пропускаются в `redraw` (и позже — не декодируются, `mute_invisible_stickers` уже
есть в модели).

### 4.7 Замечание про z-order

Для маски z-order **не нужен** (вырезаем объединение оклюдеров, относительный
порядок окон неважен — это свойство подхода ADR-004). `WindowInfo.z_order` нужен
только для панели выбора окон (сортировка) и, возможно, для будущего хит-теста.
Не тратить время на поддержание его в маске.

## 5. Кто владеет маской и пайплайн кадра

```
WinEvent → WindowTracker (dirty, debounce 16ms) → WindowEvent::Changed(Vec<WindowInfo>)
        → координатор (overlay_manager) → mask_needed?
              ├─ нет → (ничего, хуки и так не стоят)
              └─ да → occluders = { win | win ∉ allow_list(стикер) }  [для всех стикеров]
                      → redraw:
                          mask_needed? да →
                              renderer.draw_mask(&occluder_rects)   // R8, радиус 8
                          frame = [dim?] + [стикеры с bind(mask)] + [selection…]
                          renderer.draw(&frame)                      // t1 = маска
```

- Маска пересчитывается только при `WindowEvent::Changed` или изменении конфига,
  а не каждый кадр (ADR-006).
- `Renderer::draw` в M2 принимает `&[Sprite]`; для M4 нужен либо второй метод
  `draw_masked(sprites, mask_srv)`, либо расширение `Sprite` опциональной маской.
  Скопинг: предпочтительнее метод `draw_masked`, чтобы не трогать все вызовы M2.
- Один `Renderer` сейчас = одно устройство/один swapchain (M3 — общее устройство
  на несколько мониторов). Маска одна на оверлей; на M3 — по одной на монитор.

## 6. Доработки модели данных

### 6.1 Что уже покрывает ROADMAP

- Пер-стикерный allow-list окон: `VisibilityRule.rules: Vec<OverlapRule>`
  (`process_name` = путь процесса — ROADMAP «сохранение целей по пути процесса»).
- Три пресета уже выражаются без спецкейсов (ADR-004):
  - «Поверх всего» → `mode: Always` (allow всё) → **fast path**;
  - «Выборочно» → `mode: OverlapAllowlist` + `rules` = подмножество;
  - «Только рабочий стол» → `mode: Desktop` (пустой allow-list → оклюдеры = все окна);
- `NeverOverlap` ≈ «скрывать под любым перекрывающим окном» — тот же механизм,
  оставить как есть (или свести к `Desktop`, см. открытые вопросы).

### 6.2 Недостающее в `OverlapRule`

- **`process_name` должен хранить полный путь exe** (`C:\...\chrome.exe`), а не
  короткое имя: сопоставление с `exe_path` из `WindowInfo` и стабильность между
  запусками (ROADMAP). Сейчас имя поля провоцирует короткое имя — либо
  переименовать/задокументировать, либо добавить `exe_path`.
- **`window_class`**: панель и матчинг «это конкретное окно» часто требуют класс
  (`CabinetWClass` и т.п.). В CONFIG.md схема уже подразумевает более богатую цель
  (`match: process|window`, `exe_path`, `window_class`, `title_pattern`), а модель —
  нет. На M4 стоит привести `OverlapRule` к этой схеме: добавить
  `match_kind: enum { Process, Window }` и `window_class`, `title_pattern` оставить.
  Это **обратно-совместимо** (новые поля `#[serde(default)]`).

### 6.3 «Выбрать все» как состояние

ROADMAP: «Кнопка-переключатель „Выбрать все“ с двумя состояниями». В модели это
**не отдельный флаг**, а состояние = `mode: Always` (allow всё). Панель:
- переключатель «Выбрать все» вкл → пишем `mode: Always`, `rules` можно не трогать;
- выкл → возвращаем предыдущий `mode` (OverlapAllowlist) и список.
Корректность: fast path определяется одним условием `mode == Always` у всех
стикеров — не нужно согласовывать «пустой/полный список».

### 6.4 Быстрый путь как вычисляемое свойство

Координатору нужно простое предикативное значение:
`mask_needed = cfg.stickers.iter().any(|s| s.visibility.mode != VisibilityMode::Always)`.
Оно управляет и хуками (3.4), и рендером маски (4.5). Вычислять при каждом
изменении `cfg` (после undo/redo/редактирования конфига) и сообщать трекеру.

### 6.5 Настройки из ROADMAP

- **`Settings::hide_from_capture`** (`WDA_EXCLUDEFROMCAPTURE`) — не маска, а один
  вызов `SetWindowDisplayAffinity(overlay_hwnd, WDA_EXCLUDEFROMCAPTURE)` +
  проверка `GetWindowDisplayAffinity` (ROADMAP «с проверкой результата»). Правка
  `overlay.rs` при входе/выходе из режима не нужна — атрибут ставится на окно
  один раз при старте и при изменении настройки.
- **`Settings::never_overlap_taskbar`** — панель задач (`Shell_TrayWnd`) — обычное
  top-level окно. Смысл настройки: панель задач **всегда** в оклюдерах
  независимо от allow_list стикера (стикер никогда не лежит поверх панели).
  Реализация: при построении occluders добавлять `Shell_TrayWnd`, если настройка
  включена. (Альтернативная трактовка — «не наползать на панель» как ограничение
  placement — относится к M2-геометрии; здесь фиксируем маскую.)

## 7. Потребители кэша окон (панель выбора, ROADMAP)

- **Панель выбора окон** (список с иконками/заголовками, группировка по процессу,
  live-обновление) — это UI M4 поверх того же `WindowInfo`: иконка через
  `ExtractIconExW`/`SHGetFileInfoW` (из `Win32_UI_Shell`, уже подключена), live —
  из `WindowEvent::Changed`. Группировка по `exe_path`. Отдельная подзадача —
  immediate-mode виджет списка со скроллом (модуль `widgets` в rst-render уже
  появился как задел).
- Панель пишет `VisibilityRule.rules` → `config::save` → координатор
  пересчитывает `mask_needed` и occluders.

## 8. Порядок работ (для координатора)

1. **`rst-win32::windows`**: `enum_windows()` + `is_real_window` + `WindowInfo`
   (покрыть юнит-тестами фильтр на синтетических окнах — прецедент уже есть в
   `input.rs`/`overlay.rs` тестах с реальными `CreateWindowExW`).
2. **`WindowTracker`** (поток + хуки + debounce 16 мс + канал) — софт-зависимость
   от маски: сперва без fast path, потом гейт по `mask_needed`.
3. **`rst-render`**: `create_mask_texture` + `draw_mask(&rects)` (SDF-квады,
   радиус 8) + правка `SPRITE_HLSL` (`t1`, `discard`) + `draw_masked`.
4. **Сшивка в `overlay_manager`**: `mask_needed`, occluders по allow-list,
   отсечение полностью перекрытых, добавление `Shell_TrayWnd`.
5. **Модель**: расширение `OverlapRule` (`exe_path`/`match_kind`/`window_class`),
   миграция схемы не нужна (`#[serde(default)]`), пресет «рабочий стол».
6. **Панель выбора окон** (следующий шаг M4) + настройки `hide_from_capture` /
   `never_overlap_taskbar`.

## 9. Открытые вопросы и ограничения (из ADR-004/005 + ARCHITECTURE 3.5)

- **Тени DWM** выходят за extended frame bounds — сквозь них стикер виден.
  Принято как косметический артефакт (ADR-004).
- **Окна нестандартной формы** обрезаются по прямоугольнику — принято.
- **Получение `exe_path` по pid**: `QueryFullProcessImageNameW` требует
  `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` — в 64-битном процессе это
  работает для 32-битных окон, но с правами обычного процесса список
  ограничен. Альтернатива — кэш процессов через `CreateToolhelp32Snapshot` +
  сопоставление `pid → path` в трекере. Определить на этапе реализации.
- **`NeverOverlap` vs `Desktop`**: сейчас два режима с почти одинаковой
  семантикой (оба — «прятаться под любым окном»). Уточнить разницу по SPEC 7 или
  свести к одному, чтобы не плодить ветки в `mask_needed`.
- **DPI/мультимонитор (M3)**: маска в физических пикселях своего монитора;
  на M3 — своя маска на монитор, общий трекер. Не смешивать DIP-стикеры и
  px-маску на границах мониторов.
- **`WindowInfo.title` меняется** (`EVENT_OBJECT_NAMECHANGE`) — панели нужно
  live-обновление заголовков; добавить событие в фильтр трекера при реализации
  панели.
- **Замороженный кэш при загрузке/разблокировке сессии** (`WTS_SESSION_LOCK`) —
  часть M4 или переносится в M5; зафиксировать отдельно.

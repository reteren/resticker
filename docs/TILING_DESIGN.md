# M9 — Tiling window manager в resticker

Сводный архитектурный документ. Собран 2026-08-24 из шести параллельных
исследований (`docs/research/tiling/R1..R6`), каждое со своими ссылками на код
и источники. Здесь — только выводы и решения; доказательства в отчётах.

Цель, как её сформулировал пользователь: тайлинг уровня Hyprland — гэпы,
деревья раскладок, воркспейсы, группы с табами, много биндов, анимации, — а не
«ещё один FancyZones».

---

## 0. Почему это строится именно здесь

M6 («стикеры-окна») уже дал слой управления чужими окнами, отлаженный на живых
багах. Из ~22 потребностей тайлинга **17 закрыты существующим кодом** (полная
таблица — R1 §8). Ключевое:

| Что нужно тайлингу | Где уже есть |
|---|---|
| Двигать чужое окно, включая развёрнутое | `WindowPins::move_resize`, `window_pin.rs:444` — через `SetWindowPlacement`, потому что `SetWindowPos` на `WS_MAXIMIZE` молча игнорируется |
| Позиционировать по ВИДИМОМУ прямоугольнику (гэпы) | `set_dwm_bounds`, `window_pin.rs:701` — коррекция `DWMWA_EXTENDED_FRAME_BOUNDS` |
| Не дать утащить окно мышью | три эшелона move-lock, `window_pin.rs:807+` |
| Живой кэш окон на WinEvent | `WindowTracker`, `window_tracker.rs:85`, дебаунс 16 мс |
| Гейт «не трогать окна во время Alt+Tab» | `window_enum::shell_switching:318` |
| Мониторы: стабильный id, DPI, hot-plug | `monitors.rs:39` |
| Матчинг окон по процессу/заголовку (правила) | `occluders.rs:71` |
| Гашение системных переходов | `DWMWA_TRANSITIONS_FORCEDISABLED`, `window_pin.rs:230` |
| Прозрачный D3D11-оверлей на каждом мониторе | весь `rst-render` |

Последняя строка — то, чего нет ни у кого. komorebi и GlazeWM создают отдельные
слоёные окна, чтобы нарисовать рамку активного окна. У нас композитор уже свой:
рамки, таб-бар группы, бар воркспейсов, превью зоны при драге и собственный
Alt+Tab рисуются в нём же.

**Процесс уже PerMonitorV2** (`crates/resticker/resources/resticker.exe.manifest:6`)
— правильный режим DPI для WM, менять нечего.

## 1. Принятые решения

### Р1. Воркспейсы — свои, через cloak. Путь A.

Публичный `IVirtualDesktopManager` умеет только `IsWindowOnCurrentVirtualDesktop`;
перечисления столов нет, а `MoveWindowToDesktop` на чужом окне даёт
`E_ACCESSDENIED` (R2 §2). Приватный `IVirtualDesktopManagerInternal` ломается
почти на каждом обновлении Windows 11. komorebi, GlazeWM и Whim все выбрали свой
стек + скрытие окон — берём то же.

Скрытие: `DwmSetWindowAttribute(DWMWA_CLOAKED)` (как у GlazeWM), не `SW_HIDE`
(ломает Electron) и не `SW_MINIMIZE` (окна прыгают в таскбаре).

**Обязательное следствие, а не опция: watchdog.** Если resticker упадёт с
скрытыми окнами, пользователь получит «пропавшие окна». GlazeWM держит для
этого отдельный процесс. У нас — маркер `SetPropW` на каждом cloaked-окне (тот
же приём, что у пинов, `window_pin.rs:90`) + снятие cloak со всех помеченных окон при
старте, плюс `clear_orphan_markers`-аналог. Без этого фичу выпускать нельзя.

Цена решения, которую надо сказать пользователю честно: Task View, Win+Tab и
системный Alt+Tab про наши воркспейсы не знают. Отсюда — свой переключатель (Р3).

### Р2. Тайлится всё, кроме исключений

Поведение Hyprland. Нужен фильтр `is_tileable`, строго более жёсткий, чем
текущий `is_real_window` (`window_enum.rs:151`). Отбрасываем: `WS_CHILD`,
`WS_EX_TOOLWINDOW`, `WS_EX_NOACTIVATE`, cloaked-окна, owned-окна и модальные
диалоги, splash-экраны, `Progman`/`WorkerW`, окна без `WS_THICKFRAME`
(неизменяемый размер), окна с большим `ptMinTrackSize` — они физически не
влезут в тайл и должны автоматически уходить в floating, а не ломать сетку.

Поверх — window rules по exe/классу/заголовку (инфраструктура матчинга уже
есть в `occluders.rs:71`): `float`, `workspace N`, `ignore`.

Полноэкранные игры детектируются и не трогаются вообще — попытка менять z-order
у Exclusive Fullscreen роняет игру через `DXGI_ERROR_DEVICE_RESET` (R3 §8.5).

### Р3. Группы — контейнер с табами; системный Alt+Tab не трогаем

Заставить системный Alt+Tab показать группу одной записью **невозможно**
поддерживаемым способом (R6 §1б): его рисует shell, API вмешательства нет, а все
обходные пути (`WS_EX_TOOLWINDOW`, смена владельца) бьют по панели задач и
дерутся с приложением за стили.

Поэтому: группа = контейнер дерева с `layout = tabbed` (см. Р4), фоновые табы
скрываются cloak'ом, таб-бар рисуем на оверлее. Плюс **свой переключатель**:
перехват Alt+Tab клавиатурным хуком, оверлей с превью, где группа — одна
карточка. Превью: `PrintWindow(PW_RENDERFULLCONTENT)` для снимка, иконки уже
есть (`window_icon.rs:39`).

Больное место своего переключателя — активация выбранного окна: foreground lock
(R3 §6). Планировать сразу, а не обнаруживать потом.

### Р4. Модель раскладки — дерево контейнеров i3/sway

Не BSP/dwindle и не master-stack. Обоснование (R5 §2): в дереве контейнеров
с явной ориентацией (`splith` / `splitv` / `tabbed` / `stacking`) **группа-табы
— первоклассный узел**, а не надстройка сбоку; `toggle_split` и resize-ratio
становятся операциями над состоянием, а не над эвристикой; и главное — dwindle
и master выражаются поверх той же модели как *политики вставки*, тогда как
обратное неверно: выбрав dwindle, мы закрываем себе табы.

Движок живёт в `rst-core`, Win32 в нём нет ни строчки, покрытие — юнит-тестами.

### Р5. Анимации — v1 без них; фаза 2 — снимок на оверлее

v1: мгновенная перекладка с погашенными системными переходами. Это уже выглядит
опрятно, и ровно так живут komorebi и GlazeWM.

Фаза 2 — трюк, доступный только нам: анимировать не окно, а его **снимок** на
нашем оверлее. Причём в самой надёжной форме, без единого недокументированного
вызова: окно телепортируется в финальную позицию сразу, а снимок летит поверх
старой позиции на topmost-оверлее и скрывает стык. Fallback при чёрном снимке
(DRM-видео, часть GPU-приложений) — мгновенный телепорт; детект по средней
яркости.

Пошаговый `SetWindowPos` как основной путь отвергнут: сам вызов дёшев (14–16 мкс,
замерено в `overlay.rs:599`), но каждый шаг заставляет чужое приложение
перекладывать вёрстку и пересоздавать swapchain — браузеры и Electron мажут.

## 2. Куда что ложится

```
rst-core/src/tiling/          НОВОЕ, платформенно-чисто, только тесты
  tree.rs        дерево контейнеров, узлы, focus-child
  layout.rs      layout(tree, work_area, gaps) -> Vec<(WindowId, Rect)>
  ops.rs         focus/move/swap/resize/split/float/fullscreen/group
  policy.rs      политики вставки: dwindle | master | manual
  workspace.rs   воркспейсы, привязка к монитору
  rules.rs       window rules (поверх матчинга occluders.rs)

rst-win32/src/
  monitors.rs        + rcWork (СЕЙЧАС ЕГО НЕТ — пробел R1 §9.1)
  window_enum.rs     + is_tileable
  tiling_apply.rs    НОВОЕ: применение раскладки, пакетность, конвергенция
  keyboard_guard.rs  НОВОЕ: WH_KEYBOARD_LL рядом с существующим input_guard
  cloak.rs           НОВОЕ: DWMWA_CLOAKED + маркеры + watchdog

resticker/src/
  overlay_manager.rs врезка в единый канал и deadline-цикл
  tiling_ui.rs       НОВОЕ: рамка активного окна, таб-бар, бар воркспейсов,
                     свой Alt+Tab, индикатор submap
```

## 3. Три ловушки, которые убьют реализацию, если не заложить сразу

**1. Move-lock против анимаций — конфликт по построению** (R1 §9.2).
`enforce_move_lock` возвращает окно на эталон при ЛЮБОМ расхождении RECT.
Плавный переезд плитки будет прочитан как «окно двигают» и откачен первым же
снимком. У проекта уже был вечный snap-back-цикл на 60 Гц из-за расхождения
систем координат (`window_pin.rs:119`). Решение: для тайлинговых окон snap-back
сравнивает с **целью раскладки**, а не с эталоном прошлого вызова, и все
геометрические сравнения — строго в DWM-координатах.

**2. Петля «переставил → снимок → переставил»** (R1 §9.4).
Каждая перестановка рождает `LOCATIONCHANGE` → снимок через 16 мс → пересчёт.
Нужен эпсилон сходимости и подавление повторного применения, иначе координатор
войдёт в резонанс — исторический прецедент с окклюдерами в проекте уже был.

**3. Бюджет клавиатурного хука — 1 мс** (R4 §2.3, замерено в `window_pin.rs:863`).
`LowLevelHooksTimeout` на машине пользователя = 1 мс; превышение = Windows
**молча** снимает хук. Значит колбэк — только чтение снимка таблицы биндов,
никаких аллокаций, локов (только `try_lock`) и синхронных вызовов; вся работа
уходит в поток координатора. Плюс masking key, чтобы подавленная Win-комбинация
не открывала меню Пуск.

## 4. Что честно не выйдет

- **Blur/прозрачность содержимого чужих окон.** DWM не пускает между фоном и
  окном. Максимум — `SetLayeredWindowAttributes` на всё окно.
- **Анимация содержимого** (slide/scale контента, как в Hyprland). Мы не
  рендерим чужие окна; анимировать можно позицию, размер и снимок.
- **Elevated-окна.** UIPI: без прав администратора Диспетчер задач и
  терминалы «от админа» тайлингу недоступны. А запуск resticker от админа
  ломает автозапуск из `Run` и drag-and-drop картинок из проводника (R3 §8.6) —
  то есть ломает основную функцию приложения. Вывод: **работаем от обычного
  пользователя, elevated-окна честно помечаем как неуправляемые.**
- **Интеграция воркспейсов с Task View / Win+Tab.** Плата за путь A.
- **Свайпы тачпадом** как в Hyprland — война с системными жестами, которую
  штатно не выиграть.
- **Snap Layouts Windows 11** будут мешать. Отключаются только пользователем в
  настройках системы; программно лезть в реестр — неприемлемо.

## 5. Юридическое

Код **komorebi копировать нельзя**: лицензия Komorebi 2.0.0 — форк PolyForm
Strict, только личное использование, запрет редистрибуции (R2 §5). Идеи —
можно, код — нет, включая «позаимствовать алгоритм из его исходников».
GlazeWM, Whim, workspacer, FancyWM, PowerToys — MIT, оттуда код брать можно с
сохранением copyright notice. Hyprland — BSD-3, но его код завязан на Wayland и
полезен только как спецификация поведения.

## 6. Вехи

| Веха | Содержание | Проверяемый результат |
|---|---|---|
| **T0** | `rcWork` в мониторах, `is_tileable`, общий гейт `shell_switching` для всей подсистемы чужих окон | тесты фильтра; рабочая область не заезжает под таскбар |
| **T1** | движок раскладок в `rst-core` целиком | 25–40 юнит-тестов; Win32 не задействован |
| **T2** | применение раскладки к живым окнам на одном мониторе, без биндов (кнопка «затайлить монитор») | окна встают в сетку с ровными гэпами, петли нет |
| **T3** | клавиатурный слой, бинды, submap-режимы | 30+ биндов, Win-комбинации не открывают Пуск |
| **T4** | воркспейсы, cloak, watchdog восстановления | переключение мгновенное; убийство процесса не теряет окна |
| **T5** | UI на оверлее: рамка активного окна, бар воркспейсов, индикатор режима | видно, что активно и где ты |
| **T6** | группы-табы + свой Alt+Tab с превью | группа — одна карточка в переключателе |
| **T7** | анимации снимком, scratchpad, стикеры как жители раскладки | — |

T1 не зависит ни от чего и делается параллельно T0/T2 — это чистая логика.

**Стикеры как жители раскладки (T7)** — единственный ответ на вопрос «почему
тайлинг живёт в resticker, а не отдельной программой»: картинка, видео или
заметка занимает тайл наравне с окном. Ни один существующий тайлер под Windows
этого не может.

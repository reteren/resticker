# M2 — ревью четырёх билдеров UI (toolbar / cursor_panel / confirm_dialog / paste)

Статус: **ревью, без изменений кода**. Ветка `feat/m2-edit-mode`, коммиты
`9b00bdc` и `5ed61b6`. Прочитаны целиком `crates/resticker/src/toolbar.rs` (268
строк), `crates/resticker/src/cursor_panel.rs` (277), `crates/resticker/src/confirm_dialog.rs`
(382), `crates/rst-media/src/paste.rs` (233); контракты сверены с
`rst_render::widgets` (Button/Slider/NumericField/Panel), `rst_core::ops`,
`rst_win32::clipboard`, SPEC 3.6/3.8/2.1, `docs/M2_INTEGRATION_PLAN.md` §11/14 и
`docs/M2_UI_NOTES.md` §8–9. Прогон: `cargo build/clippy/test --workspace` — чисто
(16 сюит ok, clippy `-D warnings` без замечаний). Интерактивной вёрстки
(координатор + билдеры) не было — все четыре модуля в рантайм не подключены.

**Общий вердикт:** все четыре билдера корректно конструируют виджеты rst-render;
геометрия DIP-осознанная (ADR-010); ид-константы и `take_click`/`take_changed`/
`take_submitted` дают координатору ровно то, что нужно для опроса и маршрутизации
в `ops::*`. Ни одной ошибки геометрии, ломающей вёрстку, не найдено. Найденные
проблемы — в основном «что API не покрывает и что координатор обязан помнить при
подключении»: мультивыделение не представимо текущей сигнатурой `build_toolbar`,
у модала нет модальной семантики (Esc/клик-вне), `Button` не умеет ни пассивный
текст, ни checked-состояние, диапазон ползунка расходится с полем и SPEC,
`paste::materialize` трактует `Files` как ошибку, а `resticker` пока не зависит от
`rst-media`. Ниже — по убыванию важности для среза 4.

---

## 1. API `build_toolbar` не покрывает мультивыделение (SPEC 3.6)

`build_toolbar(selection: &SelectionBox, opacity: f64, screen_h: f64)` всегда
добавляет ползунок и числовое поле (`toolbar.rs:100-111`). SPEC 3.6: «При
мультивыделении ползунок прозрачности и числовое поле **не отображаются**.
Остальные кнопки применяются ко всему выделению».

Следствие: координатор не может построить тулбар мультивыделения этим билдером —
ни флага, ни отдельного билдера нет, а `opacity` одного стикера при мультивыделении
не определена. Ид-константы кнопок (`TB_EYE`..`TB_DELETE`) пригодны и для мульти —
проблема только в слайдере/поле.

**Рекомендация:** параметр `show_opacity: bool` (или отдельный билдер) + явно
задокументировать, какое значение `opacity` передавать при мультивыделении
(например, среднее или значение самого высокого по `order`); либо — если
мультивыделение в срезе 4 остаётся за скобками — зафиксировать это в плане, чтобы
не оказалось сюрпризом при вёрстке.

---

## 2. Модал без модальной семантики: Esc и клик-вне — за координатором

`confirm_dialog::build` возвращает `Panel`, но:

- `Panel::key_event` роутит клавиши только сфокусированному виджету
  (`widgets.rs:1073-1081`); кнопки фокус не берут (`wants_focus` — false). Поэтому
  `Esc` в диалоге уйдёт в существующий `VK_ESCAPE`-обработчик `overlay_manager`
  и **выйдет из режима редактирования**, а не отменит диалог.
- Клик вне модала не поглощается (`click_outside_modal_not_consumed` это
  подтверждает) — сцена продолжит обрабатывать жест/выделение, пока координатор
  не заблокирует хит-тест сцены.
- `build(0, …)` даёт «Delete 0 stickers?» — диалог для пустого выделения.

При вёрстке координатор обязан сам: (а) перехватывать `Esc`/клик-вне как «Отмена»,
(б) блокировать сцену, пока модал жив, (в) не вызывать `build` при `count == 0`.
Это не баг билдера, но контракт «верни `Panel`, а модальность организуй сам»
стоит зафиксировать в комментарии, иначе рискованно потеряется.

## 3. `Button` не умеет ни пассивный текст, ни checked-состояние — упирается в rst-render

- **Сообщение модала — Label-кнопка** (`confirm_dialog.rs:83-90`): текстового
  виджета в rst-render нет, поэтому сообщение сделано `Button::Label`. Следствие —
  за текстом рисуется фон `BUTTON_BG`, а на hover/нажатии сообщение подсвечивается
  как кнопка, хотя это пассивный элемент.
- **Тумблер «не спрашивать»** (`confirm_dialog.rs:93-99`): `Button` не хранит
  checked, а `ButtonContent` иммутабелен (поля `content` приватны, сеттера нет).
  Координатор ведёт bool по `take_click`, но визуально «проверено» (☑) показать
  нечем — подпись статична.

Обе проблемы решаются в rst-render (отдельная задача): Label-виджет (или
примитив-надпись в `Panel::draw`) и `checked`-состояние / `content_mut` у `Button`.
Билдерам это не мешает, но при вёрстке модал будет выглядеть как «кнопка-сообщение»
и «тумблер без галочки».

## 4. Диапазон ползунка 0–100 расходится с полем и SPEC 3.6 (1–100)

`build_toolbar` использует `Slider::opacity` (диапазон **0–100**, `widgets.rs:410-421`)
и `NumericField::opacity` (**1–100**). SPEC 3.6: «Диапазон 1–100».

Следствия:
- слайдер можно увести в 0 → прозрачность 0.0, а поле покажет 1 (clamp) — два
  виджета показывают разные значения;
- квантование по 1% теряет хвост: opacity 0.004 → слайдер 0, поле показывает 1
  → повторное применение пишет 0.01 (SPEC допускает только 1–100, т.е. ≥0.01).

Тест `toolbar_opacity_clamped_to_percent_range` (`toolbar.rs:220-228`) закрепляет
эту асимметрию (слайдер 0 vs поле 1), а не проверяет её. **Рекомендация:** слайдер
собирать через `Slider::new(.., 1, 100, v)`, чтобы оба виджета жили в 1–100 по SPEC.

## 5. Тулбар не зажимается по краям экрана (третий случай SPEC 3.6 не сделан)

- Вертикаль (`toolbar.rs:64-71`): если снизу места нет — тулбар уходит **над**
  рамку, даже в отрицательные координаты. Третий случай SPEC («прижимается к
  ближайшему свободному краю», когда нет места и сверху) — задел. Высокий стикер
  почти на весь экран → тулбар за верхней кромкой.
- Горизонталь (`toolbar.rs:85`): центрирование без зажима; у стикера у края
  тулбар частично уходит за экран. Параметра `screen_w` в сигнатуре нет вообще.

Тесты покрывают «под»/«над» и границу включительности, но не «ни туда ни сюда»
и не горизонтальные края. **Рекомендация:** переиспользовать зажим
`cursor_panel::clamp_to_screen` (логика там уже протестирована таблицей и grid) —
вынести его в общий модуль (например, `rst-render::selection` или новый хелпер),
а `build_toolbar` принимать `screen: &DipRect`, а не `screen_h: f64`.

## 6. `paste::materialize`: `Files` — «ошибка, которая не ошибка»

`materialize(&ClipboardImage, &Path) -> Result<PathBuf, PasteError>` для
`ClipboardImage::Files` возвращает `Err(PasteError::UnsupportedFiles)`. Но `Files` —
штатный исход чтения буфера (SPEC 2.1: пути → файловые стикеры), а не сбой.
Вызывающий вынужден ветвиться **после** ошибки, достав пути из переданного по
ссылке `image` (владеет им вызывающий — композиция рабочая, но хрупкая: легко
прочитать как «вставка не удалась» и залогировать вместо создания стикеров).

Также при вёрстке Ctrl+V координатор обязан добавить
`rst-media = { path = "../rst-media" }` в `crates/resticker/Cargo.toml` — сейчас
`resticker` от `rst-media` **не зависит** (зависимости в Cargo.toml: rst-core,
rst-win32, rst-render). Без этого `use rst_media::paste::materialize` не скомпилируется.

**Рекомендация:** заменить `Result<PathBuf, PasteError>` на enum исхода, где
`Files` — вариант, а не ошибка:

```rust
pub enum Materialized { Png(PathBuf), Files(Vec<PathBuf>) }
pub fn materialize(image: &ClipboardImage, target_dir: &Path)
    -> Result<Materialized, PasteError>;
```

Тогда call-site-матчинг принудителен и читаем. Если оставить как есть — явно
прописать ветку `Files` в док-комментарии у места вызова.

## 7. `paste.rs` — мелочи композиции

- **`create_dir_all` до проверки варианта** (`paste.rs:49`): на пути `Files`
  каталог `pasted/` создаётся как побочный эффект «ошибки». Безвредно
  (идемпотентно), но строго — эффект на не-ошибке.
- **fsync файла, но не каталога** (`paste.rs:85`): для durability rename на
  Windows обычно нужно `fsync` родительского каталога. `config::save` того же не
  делает — вопрос унификации, не блокер.
- **`PasteError::Image` без контекста** (`paste.rs:29`): `image::ImageError` не
  несёт ни пути, ни формата — лог при битой вставке будет «не удалось обработать
  изображение» без деталей. Для M2 достаточно, но диагностику стоит усилить.
- **tmp-файл на падении** между `create` и `rename` (`paste.rs:78-88`) остаётся
  в `pasted/`. Редкий случай; при желании — писать во временный каталог системы.
- **Pasted-файлы не чистятся при удалении стикера**: `ops::delete` удаляет запись
  из конфига, но не файл; SPEC 2.1 требует удалять материализованные вставки вместе
  со стикером. Зона `ops`/координатора, но вёрстка Ctrl+V обязана это учесть
  (иначе `pasted/` копится бесконечно).

## 8. Мелочи и несогласованности

- **Ид-пространства пересекаются**: toolbar 0–7, cursor_panel 100–104,
  confirm_dialog 100–104. Запросы идут per-panel (`Panel::widget` ищет в своей
  панели) — рантайм-безопасно, но числовые коллизии cursor/confirm путают и
  взрывоопасны при будущем едином реестре виджетов. Развести диапазоны
  (toolbar 0–9, cursor 100–109, dialog 200–209) — дёшево сейчас.
- **Два механизма `allow(dead_code)`**: cursor_panel — внутренний
  `#![allow(dead_code)]` в файле (`cursor_panel.rs:13`), toolbar/confirm_dialog —
  `#[allow(dead_code)]` на `mod` в `main.rs`. При вёрстке в cursor_panel-файле
  останется лишний allow. Унифицировать.
- **`opacity` NaN в тулбаре** (`toolbar.rs:100`): `NaN.clamp(..) * 100` → `as u32`
  → 0 (насыщение NaN в 0). Не падает, но стикер с NaN-прозрачностью молча
  получает 0% вместо дефолта 100%. Рендерер такие стикеры и так отбрасывает —
  косметика, но стоит знать.
- **Сообщение модала шире панели при гигантском `count`**: ширина Label-кнопки
  растёт с текстом; для 6+ знаков выйдет за `DIALOG_W = 320`. Практически
  недостижимо, но зажим `text_w` по ширине не помешает.
- **Зажим центра модала по экрану отсутствует**: `build` центрирует строго в
  переданной точке; если координатор передаст центр у края (не штатный случай) —
  модал вылезет за экран. Контракт не защищён от этого.

## 9. Что проверено и корректно (не тратить время на повторную проверку)

- **Опрос и маршрутизация**: все четыре API отдают ид-константы; `take_click`/
  `take_changed`/`take_submitted` доступны через `Panel::widget_mut`. Координатор
  может различить любую кнопку и сопоставить её с `ops::*` (глаз → `toggle_visibility`,
  выше/ниже → `step_up/step_down`, дубликат → `duplicate`, удалить →
  `should_confirm_delete` + `delete`; слайдер/поле → `transform.opacity`).
- **Ретейн-семантика**: билдеры конструируют состояние; чтобы `take_click` не
  терялись, координатор обязан держать один экземпляр `Panel` между кадрами и
  роутить `pointer_event` в него, а не пересобирать панель на каждый `redraw`
  (retained-состояния, M2_UI_NOTES §8).
- **Единицы**: везде DIP; `screen_h`/`screen`/`center` — логические пиксели,
  физику→DIP делает координатор (как `overlay_manager::to_dip`).
- **cursor_panel**: зажим `clamp_to_screen` корректен — NaN/inf → центр экрана,
  нулевой/отрицательный размер экрана не паникует, табличные тесты краёв + grid-
  свойство «панель всегда на экране»; ненулевое начало координат (задел M3)
  покрыто.
- **toolbar**: AABB повёрнутого стикера учтён (`toolbar_uses_rotated_aabb`);
  граница «под/над» включительна (`toolbar_below_boundary_is_inclusive`);
  кнопки в порядке SPEC слева направо; opacity-зеркалирование в слайдер/поле.
- **confirm_dialog**: клики Delete/Cancel/тумблер изолированы (срабатывает только
  соответствующая кнопка), клик по сообщению поглощён и не трогает действия,
  клик вне — не consumed; `translate` переносит модал целиком; сообщение в
  единственном/множественном числе.
- **paste**: PNG roundtrip точными байтами (альфа/метаданные сохраняются),
  BMP→PNG без потерь, битый PNG не пишется вовсе, UUID уникален на каждую
  вставку, каталог `pasted/` создаётся, запись атомарная (tmp+rename).
- **Слои зависимостей**: `rst-media` зависит от `rst-win32` (тип `ClipboardImage`),
  `rst-core` Windows не знает — «Правило зависимостей» соблюдено.

## 10. Приоритеты для координатора (при вёрстке среза 4)

1. **Мультивыделение**: решить судьбу тулбара 3.6 без слайдера/поля — флаг или
   отдельный билдер (п. 1).
2. **Модальная семантика** confirm_dialog: `Esc`/клик-вне → «Отмена», блокировка
   сцены, `count == 0` — не показывать (п. 2). Здесь же — фокус поля и `Esc`
   (M2_UI_NOTES §9).
3. **Слайдер/поле в единый диапазон 1–100** по SPEC (п. 4).
4. **Зажим тулбара по краям** — вынести `clamp_to_screen` в общий модуль и дать
   `build_toolbar` `screen: &DipRect` (п. 5).
5. **Добавить `rst-media` в зависимости `resticker`** и решить судьбу `Files`
   (исход-енум или документированная ветка) до подключения Ctrl+V (п. 6).
6. **Задача в rst-render**: Label-виджет и checked-состояние/`content_mut` у
   `Button` (п. 3) — отдельно от билдеров.
7. Мелочи: развести ид-диапазоны, унифицировать `allow(dead_code)`, чистка
   `pasted/` при удалении (п. 7–8) — по остатку времени.

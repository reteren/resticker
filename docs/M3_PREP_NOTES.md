## 1. Текущая отправная точка

Сегодня в процессе ровно **один** оверлей-прослоек на **основной** монитор,
а идентификатор монитора везде — заглушка `MonitorId::default()` (пустая
строка):

- `overlay_manager.rs:884` — `redraw()` передаёт заглушку в `solid_sprite`
  для затемнения и рамки выделения;
- `overlay_manager.rs:946` — `add_sticker()` кладёт заглушку в
  `Sticker::new_file`; рядом комментарий «M3: реальный device interface path
  монитора; M1 — один монитор, заглушка»;
- `model.rs:91` — `MonitorRecord::default()` с пустым `MonitorId`; секция
  `monitors` конфига сейчас не заполняется нигде;
- `overlay.rs:367–368` — `create_window()` берёт геометрию через
  `GetSystemMetrics(SM_CXSCREEN/SM_CYSCREEN)` (основной монитор, позиция
  `(0, 0)`);
- `overlay.rs:163–165` — `dpi()` читается один раз через `GetDpiForWindow`;
  `WM_DPICHANGED` не обрабатывается.

При этом **модель данных уже готова к M3**: `Sticker.placement` — DIP
относительно монитора (ADR-010), у `Sticker` есть `origin` (ADR-011),
`Config.monitors: Vec<MonitorRecord>` со всеми нужными полями (`id`,
`friendly_name`, `last_seen`, `last_bounds`, `last_scale`, `is_primary`).
Схему менять не надо — надо начать её наполнять.

Чек-лист ROADMAP M3 (строки 87–95): окно на монитор с корректной геометрией;
привязка стикера к монитору по центру bbox; стабильный id через device
interface path; `WM_DPICHANGED` + тест на смешанном DPI 100/150/200;
перетаскивание между мониторами; `WM_DISPLAYCHANGE`; сценарий отключения
(таймер 20 с, миграция, `origin`, автовозврат); `DEVICE_REMOVED`;
`WTS_SESSION_LOCK`/`UNLOCK` и сон.

## 2. Модуль перечисления мониторов (`rst-win32`, новый модуль)

### 2.1. Что он должен возвращать

Один вызов → снапшот текущих мониторов, независимый от окон:

```rust
struct MonitorInfo {
    id: MonitorId,        // стабильный device interface path
    friendly_name: String,
    bounds_px: Rect,      // физические пиксели, виртуальный десктоп
    dpi: u32,             // scale = dpi / 96.0
    is_primary: bool,
}
```

Снапшот напрямую мапится на `rst_core::model::MonitorRecord` (`last_seen` =
момент снапшота, `last_bounds = bounds_px`, `last_scale = dpi/96.0`).

### 2.2. Рецепт API (совпадает с ARCHITECTURE.md §7)

1. **`EnumDisplayMonitors`** (без HDC и клипа) → по одному `HMONITOR` на
   дисплей. `HMONITOR` сессионный — не хранить, не сериализовать.
2. **`GetMonitorInfoW`** с `MONITORINFOEXW`:
   - `rcMonitor` — границы в физических пикселях в координатах виртуального
     десктопа (у основного монитора левый верхний угол `(0, 0)`, у остальных
     — смещение, возможно отрицательное);
   - `dwFlags & MONITORINFOF_PRIMARY` — флаг основного;
   - `szDevice` — GDI-имя `\\.\DISPLAY1`: **нестабильно**, используется
     только как вход для шага 3.
3. **Стабильный id — `EnumDisplayDevicesW(szDevice, 0, EDD_GET_DEVICE_INTERFACE_NAME)`**:
   поле `DeviceID` результата — device interface path вида
   `\\?\DISPLAY#GSM5B09#5&1a2b3c4d&0&UID4353#{e6f07b5f-...}` (пример —
   CONFIG.md, строка 74). Стабилен при переподключении и смене номера
   монитора (ADR-010). Это и есть `MonitorId`.
   - Альтернатива (богаче): `QueryDisplayConfig` +
     `DisplayConfigGetDeviceInfo(DISPLAYCONFIG_DEVICE_INFO_GET_TARGET_NAME)` →
     `DISPLAYCONFIG_TARGET_DEVICE_NAME` даёт тот же `monitorDevicePath`
     **плюс** `monitorFriendlyDeviceName` («LG ULTRAGEAR» в фикстуре
     config_v1_example.json) для `MonitorRecord.friendly_name`. Требует фичи
     `Win32_Devices_Display` в `rst-win32/Cargo.toml` (сейчас не включена).
4. **DPI — `GetDpiForMonitor`** (`MDT_EFFECTIVE_DPI`) → `scale = dpiX / 96.0`.
   Для существующего окна остаётся `GetDpiForWindow`; при смене масштаба —
   `WM_DPICHANGED`.

Фичи windows-crate: шаги 1–3 и 4 — `Win32_Graphics_Gdi` и `Win32_UI_HiDpi`,
**обе уже включены** в `rst-win32/Cargo.toml`; только альтернативный путь
через DisplayConfig требует новой фичи.

### 2.3. Политика обновления

- Перечисление при старте, **переперечисление на `WM_DISPLAYCHANGE`** (и
  `EVENT_SYSTEM_DESKTOPSWITCH`, ARCHITECTURE §7, строка 369).
- Сопоставление «старый список ↔ новый список» — **только по device
  interface path**; никогда по индексу/GDI-имени/`HMONITOR`.
- Результат мерджится в `Config.monitors`: новые добавляются, виденные
  обновляют `last_seen/last_bounds/last_scale`, пропавшие **остаются** в
  списке (они — «дом» стикеров для ADR-011, раздел 5.3).
- Первичный монитор может смениться (настройки Windows, RDP) — `is_primary`
  читается каждый раз из снапшота, не кэшируется.

## 3. Один `OverlayWindow` на монитор (`rst-win32/src/overlay.rs`)

### 3.1. Что меняется в `create_window()`

Сейчас геометрия захардкожена под основной монитор
(`overlay.rs:367–368, 382–397`). `create()` должен принимать границы
монитора `(x, y, w, h)` в физических пикселях и передавать их в
`CreateWindowExW` (позиция `rcMonitor.left/top`, не `(0, 0)`). Класс окна
процесс-wide — повторная регистрация уже корректно проглатывается через
`ERROR_CLASS_ALREADY_EXISTS` (`overlay.rs:357–362`), так что N окон одного
класса работает как есть. Стили (`TOPMOST/TOOLWINDOW/NOACTIVATE/
TRANSPARENT/NOREDIRECTIONBITMAP`) не меняются.

### 3.2. Потоки: одно окно — один pump-поток

Сейчас каждое `OverlayWindow` несёт свой `GetMessage`-цикл (ADR-013,
`overlay.rs:131, 234`). Минимально инвазивный путь M3 — **сохранить
«поток на окно»** (2–4 потока, копейки). Альтернатива — один pump-поток,
владеющий всеми окнами (GetMessage обслуживает все окна потока, wndproc
уже общий через класс): меньше потоков, но переделка `Drop`-протокола
(`WM_CLOSE` на каждое окно) и `WndState`-мапы. Рекомендация: поток на окно.

### 3.3. Глобальный хоткей — ровно один на процесс

`RegisterHotKey` на одну и ту же комбинацию дважды не регистрируется
(второй вызов — конфликт). Сейчас хоткей режима регистрирует единственное
окно (`overlay.rs:249`). С N окнами хоткей должен регистрировать **один**
из них (логично — окно основного монитора), остальные создаются без
хоткея: `create()` принимает `Option<HotkeyCombo>` или вынос регистрации
наружу. То же касается будущих глобальных хоткеев из `Config.hotkeys`
(toggle_all_stickers, mute_all).

### 3.4. События помечаются монитором

Каждое окно отдаёт `OverlayEvent` в свой канал; координатор сливает их
(`overlay_manager.rs:204–210`). События мыши приходят в координатах
**своего** окна, а перевод физика→DIP идёт через **его** масштаб — значит,
событие должно нести идентификатор окна/монитора (обёртка
`(MonitorId, OverlayEvent)` при слиянии каналов), иначе ввод на втором
мониторе будет интерпретирован в чужом масштабе и чужих координатах.

### 3.5. Фокус и клик-прозрачность в режиме редактирования

`set_click_through(false)` снимает `TRANSPARENT|NOACTIVATE` и забирает
фокус (`SetForegroundWindow`, `overlay.rs:186`). С N окнами: клик-
прозрачность снимается **со всех** (иначе мышь на соседних мониторах
проваливается сквозь режим), но фокус может иметь одно окно — то, что под
курсором. Клавиатура (`Key`-события: `Ctrl+Z`, `Delete` и т.п.) приходит
с окна в фокусе — обработчику всё равно, с какого монитора пришла клавиша.

### 3.6. `WM_DPICHANGED` и `WM_DISPLAYCHANGE`

- `WM_DPICHANGED`: `wParam` — новый DPI, `lParam` — рекомендованный
  прямоугольник. Реакция: `SetWindowPos` по рекомендованному rect,
  обновить `size`, `Renderer::set_dpi_scale`. Манифест уже
  `PROCESS_PER_MONITOR_DPI_AWARE_V2` (M0, ADR-010 «Последствия») — ОС
  окно не растянет, за геометрию отвечаем мы.
- `WM_DISPLAYCHANGE`: окно ушедшего монитора **уничтожается сразу**
  (ARCHITECTURE §7, строка 371), окно нового создаётся; смена разрешения
  — `SetWindowPos` + ресайз цепочки композиции (см. 4.3). Сообщения
  ловятся в wndproc любого из окон (или одном невидимом message-only
  окне координатора — проще централизовать).

## 4. Рендерер: разделить «устройство» и «окно»

### 4.1. Сегодня

`Renderer::new(hwnd, w, h)` создаёт **своё** D3D11-устройство, контекст,
DirectComposition-цепочку и swapchain (`renderer.rs:54–144`) — одно окно =
одно устройство. Комментарий в `renderer.rs:50–53` уже фиксирует план M3:
«один рендерер = одно устройство; на процесс с несколькими мониторами
устройство будет общим» (ARCHITECTURE §1, строки 41, 71: «Один
D3D11-девайс на процесс, по одной цепочке композиции на монитор»,
«3 HWND на 3 монитора»).

### 4.2. Целевая раскладка

- **Общее на процесс** (`Device`): `ID3D11Device`, `ID3D11DeviceContext`,
  скомпилированные шейдеры, sampler, blend state, constant buffer. Текстуры
  живут на устройстве.
- **На монитор** (`WindowTarget`): DirectComposition target/visual на HWND,
  swapchain + RTV, размер в физ. пикселях, DPI-масштаб. (DComp-device тоже
  можно общий — dcomp target создаётся на конкретный HWND.)

**Ключевое следствие:** текстура спрайта грузится **один раз** и рисуется
на любом мониторе — перетаскивание стикера между мониторами не требует
перезаливки на GPU. Оставить устройство на окно = дублировать каждую
текстуру на каждый монитор (память ×N + CPU-загрузка при каждом
пересечении границы). Поэтому разделение «устройство/окно» — **блокер
для остального M3** и должно идти первым.

### 4.3. `DEVICE_REMOVED` и смена разрешения

Потеря устройства (сон, драйвер, `dxcap` — ARCHITECTURE §12, строка 290/415)
при общем устройстве чинится в одном месте: пересоздать `Device`, затем по
списку `WindowTarget` пересоздать swapchain/RTV и все текстуры. Смена
разрешения — `ResizeBuffers` + пересоздание RTV только на затронутом окне.

## 5. `overlay_manager.rs`: что остаётся глобальным, что становится per-monitor

### 5.1. Глобальное (один на процесс)

| Состояние | Почему глобальное |
|---|---|
| `cfg: Config`, `config_path` | Модель едина; стикеры разных мониторов живут в одном списке, у каждого свой `placement.monitor_id`. |
| `undo_stack`/`redo_stack` | Снимки **всего** `Config` (`overlay_manager.rs:167–177`) — глобальны по построению и правильно: любое действие (даже перетаскивание между мониторами) отменяется одним `Ctrl+Z`. |
| `EditState.active` | Один режим редактирования на весь десктоп: один глобальный хоткей, затемнение на всех мониторах одновременно. |
| `selection: SelectionSet` | Набор id глобален: `Ctrl+A` выделяет все стикеры всех мониторов; резиновая рамка — жест конкретного окна, но пишет в глобальный набор. |
| `snap: SnapConfig` | Настройка, не состояние окна. |
| Состояние ADR-011 (таймеры, скрытые стикеры) | По ARCHITECTURE §7 (строка 371) живёт в ядре: «состояние монитора и таймер на 20 секунд живут в ядре, окно уничтожается сразу, данные стикеров — нет». |

Текстуры затемнения/рамки (`white_tex`/`black_tex`) — device-bound: при
общем устройстве (раздел 4) становятся фактически глобальными.

### 5.2. Per-monitor (один на монитор)

| Состояние | Что именно |
|---|---|
| `OverlayWindow` | Окно, его pump-поток, клик-прозрачность, форма курсора (`post_cursor_shape` — на конкретный HWND). |
| Цель рендера | `WindowTarget` (swapchain/RTV/dcomp на HWND), размер окна в физ. px, `scale` (DPI монитора). |
| Кадр (`frame: Vec<Sprite>`) | Формируется **для каждого монитора свой**: `redraw()` фильтрует `cfg.stickers` по `placement.monitor_id == monitor.id && visible`, сортировка по `order` не меняется (z-order глобален, внутри одного окна сортировка та же). Заглушка `MonitorId::default()` (`overlay_manager.rs:884`) заменяется реальным id монитора кадра. |
| Граница для `clamp_min_visible` | Монитор берётся из геометрии **этого** окна (`DipRect` его DIP-размеров), а не из `(width, height)` единственного окна. |
| Затемнение/рамка выделения | Размеры затемнения — DIP-размеры своего окна; рамки рисуются только для стикеров своего монитора (вопрос для стикера «посередине перетаскивания» — см. 5.4). |

### 5.3. ADR-011: автомат пропавшего монитора

Состояние: `HashMap<MonitorId, LossState>` в координаторе (глобально, но
по одному на пропавший монитор). По снапшоту перечисления (раздел 2.3):

1. Монитор пропал → стикеры его `monitor_id` скрываются (не удаляются),
   окно уничтожается, запускается таймер 20 с (SPEC 6.1 п.1).
2. Вернулся вовремя → всё как было (п.2).
3. Не вернулся → миграция на **текущий** основной: пропорциональное
   масштабирование позиции + `snap::clamp_min_visible` («правило границ»,
   SPEC 6.1 п.3), исходные монитор и координаты — в `origin` (поле уже
   есть в модели).
4. Вернулся позже → автовозврат из `origin`, если пользователь не двигал
   стикер (п.4). Точка очистки `origin` — любая пользовательская правка
   `placement` (жест/тулбар): там же, где сегодня применяются
   `transform_ops`.
   Миграция/автовозврат — **системные** события, а не жест пользователя:
   в undo-историю не кладутся (иначе `Ctrl+Z` воскрешал бы стикеры на
   физически отсутствующем мониторе).

### 5.4. Перетаскивание между мониторами (открытый вопрос механики)

Захват мыши остаётся у окна-источника (`MouseCapture`), координаты приходят
в его пространстве. Два варианта:

- **Плавный:** переводить курсор в координаты виртуального десктопа
  (через `bounds_px` окон), при пересечении границы перепривязывать
  `placement.monitor_id` по центру bbox (ROADMAP, строка 88) и пересчитывать
  DIP в новый монитор; рамку выделения в переходе рисовать на обоих окнах.
- **Простой (рекомендация для первой итерации):** ограничивать драг своим
  монитором (`clamp_min_visible` уже это делает), перепривязку делать по
  центру bbox на `MouseUp`.

Решить до начала среза; влияет только на координатора, не на rst-win32.

## 6. Предлагаемый порядок работ

1. **`rst-win32::monitors`** — перечисление (раздел 2); юнит-тест на CI с
   одним монитором (непустой список, ровно один primary, непустой id).
2. **Разделение `Device`/`WindowTarget` в `rst-render`** (раздел 4) —
   блокер для текстур на N окнах.
3. **`OverlayWindow` по границам монитора + хоткей один раз** (раздел 3).
4. **Per-monitor runtime в `overlay_manager`** (раздел 5.1–5.2): таблица
   мониторов, маршрутизация событий по id, `redraw` на монитор.
5. **`WM_DPICHANGED` / `WM_DISPLAYCHANGE`** (раздел 3.6) + ресайз цепочек.
6. **ADR-011-автомат** (раздел 5.3) + тесты всех четырёх веток SPEC 6.1.
7. **Перетаскивание между мониторами** (раздел 5.4).
8. `DEVICE_REMOVED` (раздел 4.3), `WTS_SESSION_LOCK`/`UNLOCK`, сон.

Тестовая матрица уже зафиксирована в ARCHITECTURE §12 (строки 412–415):
виртуальные дисплеи (`usbmmidd`), смешанный DPI 100/150/200, hot-plug
кабелем и RDP, потеря D3D-устройства через `dxcap`.

## 7. Что точно не меняется

- Схема конфига и миграции (`Config.monitors` и `origin` уже в модели).
- ADR-010 (DIP относительно монитора) — подтверждён, реализация следует.
- Однопроцессная модель потоков (ADR-013) — только потоков-окон станет N.
- Вся платформенная логика — в `rst-win32`; ядро (`rst-core`) и
  координатор оперируют `MonitorId` как строкой и не знают про Win32
  (CONTRIBUTING.md, «Правило зависимостей»): снапшот мониторов идёт в
  координатор как данные, перечисление и Win32-API — только в `rst-win32`.

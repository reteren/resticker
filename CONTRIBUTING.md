# Участие в разработке resticker

## Окружение

Нужно:

| Компонент | Версия | Примечание |
|---|---|---|
| Windows | 11 (22H2+) | Windows 10 не поддерживается |
| Rust | stable, MSVC toolchain | `rustup default stable-x86_64-pc-windows-msvc` |
| Visual Studio Build Tools | 2022 | С компонентом «Desktop development with C++» и Windows 11 SDK |
| Node.js | 20+ | Для фронтенда настроек |
| pnpm | 9+ | `npm i -g pnpm` |
| FFmpeg dev | 7.x, LGPL shared | См. ниже |

### FFmpeg

Нужны заголовки и import-библиотеки, собранные **без GPL-компонентов**. Если собираете сами:

```
--disable-gpl --disable-nonfree --disable-encoders --disable-muxers
--disable-programs --disable-doc --enable-shared --disable-static
--enable-d3d11va --enable-dxva2
```

Готовые LGPL shared-сборки берутся из BtbN/FFmpeg-Builds (вариант `lgpl-shared`).

Распаковать и указать путь:

```powershell
$env:FFMPEG_DIR = "C:\dev\ffmpeg-lgpl-shared"
```

DLL из `bin\` должны лежать рядом с исполняемым файлом или быть в `PATH`.

Почему такие ограничения — [DECISIONS.md](DECISIONS.md), ADR-008. Коротко: GPL-сборка FFmpeg обязала бы весь проект стать GPL, а нам нужен MIT. Кодировщики не нужны вообще: мы только декодируем.

## Сборка

```powershell
git clone https://github.com/<user>/resticker
cd resticker
pnpm install
cargo build --workspace
cargo run -p resticker
```

Релизная сборка:

```powershell
cargo build --release -p resticker
```

Профиль релиза в `Cargo.toml` воркспейса:

```toml
[profile.release]
lto = "fat"
codegen-units = 1
panic = "abort"
opt-level = 3
strip = "debuginfo"
```

Для профилирования есть отдельный профиль с символами:

```toml
[profile.profiling]
inherits = "release"
debug = true
strip = "none"
```

## Структура репозитория

```
crates/
├─ resticker/     bin. Точка входа, инициализация, склейка потоков
├─ rst-core/      Модель данных, состояние, undo, конфиг, миграции.
│                 Не зависит ни от Windows, ни от рендера. Тестируется на любой ОС.
├─ rst-win32/     Все unsafe-обёртки Win32: окна, WinEvent-хуки, хоткеи,
│                 перечисление окон, DPI, мониторы, трей, Always On Top
├─ rst-render/    D3D11, DirectComposition, шейдеры, immediate-mode UI редактора
├─ rst-media/     Загрузка изображений, GIF, FFmpeg, кэш даунскейла
└─ rst-audio/     Микшер WASAPI через cpal
ui/               Фронтенд окна настроек (Tauri, TypeScript)
```

**Правило зависимостей:** `rst-core` не знает про Windows. Всё платформенное живёт в `rst-win32`. Это не про кроссплатформенность (её не будет), а про тестируемость: логику undo, порядка стикеров и миграций конфига можно проверять юнит-тестами без окон и GPU.

## Правила работы с unsafe

Большая часть Win32 требует `unsafe`. Дисциплина:

1. **`unsafe` не выходит за пределы `rst-win32` и низкоуровневой части `rst-render`.** Остальные крейты работают с безопасными обёртками.
2. **Каждый `unsafe`-блок сопровождается комментарием `// SAFETY:`**, объясняющим, почему инварианты соблюдены.
3. **HWND, HANDLE, COM-указатели оборачиваются в newtype с `Drop`.** Никаких сырых хендлов, гуляющих по коду.
4. **Возвраты Win32-функций проверяются всегда.** `SetWindowPos` может тихо провалиться из-за UIPI, `SetWindowDisplayAffinity` — из-за особенностей сборки Windows. Игнорировать результат нельзя.
5. `#![deny(unsafe_op_in_unsafe_fn)]` во всех крейтах.

## Стиль

- `cargo fmt` перед коммитом, конфигурация по умолчанию
- `cargo clippy --workspace --all-targets -- -D warnings` должен проходить
- Ошибки: `thiserror` в библиотечных крейтах, `anyhow` в bin
- Логирование: `tracing`. Никаких `println!` в коде, кроме отладочных спайков
- Имена — английские. Комментарии и документация — русские, кроме публичных doc-комментариев крейтов

## Тестирование

```powershell
cargo test --workspace           # юниты и интеграционные
cargo test -p rst-core           # логика без Windows-зависимостей
```

Что обязательно покрывается тестами:

- Миграции конфига — на реальных файлах из `tests/fixtures/`
- Undo/Redo — property-based: случайная последовательность операций, N отмен, N повторов → исходное состояние
- Порядок стикеров — property-based на команды «выше»/«ниже»
- Правило границ и магнит — табличные тесты
- Логика ADR-011 (пропавший монитор) — все четыре ветки сценария

Что тестируется только вручную, но обязательно перед релизом — таблица в [ARCHITECTURE.md](ARCHITECTURE.md), раздел 11.

## Профилирование

- **CPU:** `superluminal` или Windows Performance Analyzer. Профиль `profiling`.
- **GPU:** PIX for Windows. Проверять количество draw call и время кадра.
- **Idle:** отдельный обязательный замер. Запустить с 10 статичными стикерами, оставить на час, посмотреть суммарное процессорное время процесса в диспетчере задач. Целевое значение — единицы секунд за час, в идеале ноль.
- **Память:** `heaptrack`-аналоги под Windows либо просто наблюдение за рабочим набором в течение 24-часового прогона с 25 видео.

## Как предлагать изменения

1. Для заметных изменений архитектуры — сначала issue с обсуждением, потом код. Возможно, потребуется новая запись в [DECISIONS.md](DECISIONS.md).
2. PR должен содержать: что изменено, зачем, как проверялось. Скриншот или короткая гифка для визуальных изменений очень желательны.
3. Изменения в поведении отражаются в [SPEC.md](SPEC.md) в том же PR.
4. Новое поле в конфиге = новая версия схемы + миграция + тест миграции. Без исключений.

## Отладка специфичных вещей

**Окна и стили.** Spy++ из состава Visual Studio или WinSpy. Позволяет увидеть реальные стили окна, класс, иерархию и проверить, почему фильтр «реальных окон» что-то пропустил.

**DirectComposition и DWM.** Если оверлей полностью прозрачный и ничего не видно — почти всегда проблема в premultiplied alpha или в том, что swapchain создан не через `CreateSwapChainForComposition`. Проверять через PIX, что рисуется в бэкбуфер.

**WinEvent-хуки.** Логировать все приходящие события с именами окон в отдельный файл. Частая ошибка — забыть отфильтровать `idObject != OBJID_WINDOW` и получить поток событий от элементов управления внутри окон.

**Потеря D3D-устройства.** Воспроизводится принудительно через `dxcap -forcetdr` либо обновлением драйвера видеокарты. Обязательно проверить перед релизом, иначе выход из спящего режима будет ломать программу.

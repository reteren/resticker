# rst-video

Программный декод видео через FFmpeg для стикеров resticker (M5b,
`docs/M5B_VIDEO_DESIGN.md` §2): демукс + декод + ресемплинг звука. Без GPU
и окон — `rst-render` (задача B среза) получает плоскости Y/U/V и
конвертирует в шейдере; микшер звука (задача C) берёт готовые f32-сэмплы.

## Требования к сборке

1. **Пресобранный FFmpeg** (LGPL-only, MinGW-w64, `docs/M5B_VIDEO_DESIGN.md`
   §1): заголовки и импортные библиотеки в
   `W:/ffmpeg_build/install/{include,lib}`, DLL в `bin/`. В сборке должны
   быть libavformat/libavcodec/libavutil/libswresample; swscale/avdevice/
   avfilter могут отсутствовать (именно так собрана эта).
2. **Переменная окружения `FFMPEG_DIR`** на время любой сборки воркспейса
   (читается `build.rs` крейта `ffmpeg-sys-next` для bindgen и линковки):

   ```
   set FFMPEG_DIR=W:/ffmpeg_build/install
   cargo build --workspace
   ```

3. **libclang** для bindgen (генерирует FFI-биндинги при сборке): здесь —
   MSYS2 clang64 (`W:/msys64/clang64/bin`), нужно, чтобы `libclang.dll` и её
   зависимости были видимы:

   ```
   set LIBCLANG_PATH=W:/msys64/clang64/bin
   set PATH=W:/msys64/clang64/bin;%PATH%
   ```

4. **DLL в рантайме**: `avcodec-61.dll`, `avformat-61.dll`, `avutil-59.dll`,
   `swresample-5.dll` (и всё, от чего они зависят — этой сборке хватает
   msvcrt) должны лежать рядом с exe или в `PATH`. Для тестов:

   ```
   copy W:/ffmpeg_build/install/bin/*.dll target/debug\
   ```

## Почему в репозитории лежит `vendor/ffmpeg-sys-next`

`ffmpeg-sys-next 7.1.3` (последняя версия под FFmpeg 7.1) закрепляет
`bindgen ^0.70`; на libclang 21/22 его кодген не видит определения структур
FFmpeg, объявленных впереди использования (`struct AVOption;` в `log.h`
→ определение в `opt.h`), и генерирует их пустыми (`_address: u8` —
compile-time ошибки в layout-тестах). bindgen 0.72 это чинит. Патч — только
`bindgen = "0.72"` в `Cargo.toml` и два `#![allow]` для линтеров
сгенерированного кода; сам крейт не тронут. Подключение — `[patch.crates-io]`
в корневом `Cargo.toml` воркспейса.

## Модель (кратко, подробно — дизайн-док §2)

- `VideoSource` — дескриптор файла + поток-декодер на файл. Кадры и звук —
  неблокирующие очереди (`try_recv_frame`, `try_recv_audio_samples`).
- Кадр: `DecodedVideoFrame { y, u, v, width, height, pts }` — YUV420P,
  плотно упакованные плоскости, PTS от начала потока.
- Звук: `DecodedAudioSamples { samples }` — f32 **interleaved** `[L,R,…]`,
  **48 000 Гц**, 2 канала (фиксированный целевой формат ресемплера —
  микшер работает в одном формате и сам не ресемплирует).
- Часы показа — зона координатора: этот крейт отдаёт кадры с правильным
  PTS, а «показывать сейчас или ждать» решает вызывающий код. Декодер сам
  держит темп ≈ PTS (не декодирует файл разом) и не читает пакеты на паузе.
- Зацикливание: всегда (срез M5b: `Loop` — единственная семантика).
- Перемотка `seek(Duration)` — синхронная (ждёт подтверждения декодер-потока);
  после неё очереди содержат устаревшие кадры/сэмплы — вызывающий код
  сбрасывает их (`clear_audio_queue`, кадры — по PTS).

## Известные упрощения среза

- Только YUV420P; другие форматы пикселей — чистая ошибка
  `UnsupportedPixelFormat` (swscale в сборке FFmpeg отключён — конвертация
  на CPU не предусмотрена дизайном; в шейдере решает `rst-render`).
- Пути файлов — UTF-8 (FFmpeg сам конвертирует в UTF-16 на Windows);
  не-UTF-8 путь → `VideoError::NonUtf8Path`.
- Потеря одного кадра при переполнении очереди (координатор медленнее
  реального времени) — это и есть корректное поведение пропуска кадров.
- При возобновлении после паузы таймлайн пере-якорится: до 3 закэшированных
  кадров показываются подряд (краткий «догоняющий» рывок).
- Множественные аудиодорожки: берётся первая, ассоциированная с видео.

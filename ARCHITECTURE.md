# resticker — техническая архитектура

Документ описывает **как** устроена программа. Что она делает — в [SPEC.md](SPEC.md).

---

## 1. Общая схема

```
                 ┌─────────────────────────────────────────────┐
                 │              Процесс resticker.exe          │
                 │                                             │
  ┌──────────┐   │  ┌───────────────┐      ┌────────────────┐  │
  │ Настройки│───┼──┤ Поток Tauri   │◄────►│  Ядро (Core)   │  │
  │ (WebView)│   │  │ (main thread) │ IPC  │  состояние,    │  │
  └──────────┘   │  └───────────────┘      │  конфиг, undo  │  │
                 │                          └───┬────────┬───┘  │
                 │                              │        │      │
                 │  ┌───────────────────────────▼──┐  ┌──▼────┐ │
                 │  │   Поток оверлея (Win32)      │  │Декодер│ │
                 │  │   • message pump             │  │ пул   │ │
                 │  │   • WinEvent hooks           │  │потоков│ │
                 │  │   • HWND на каждый монитор   │  └───┬───┘ │
                 │  │   • глобальные хоткеи        │      │     │
                 │  └───────────────┬──────────────┘      │     │
                 │                  │                     │     │
                 │  ┌───────────────▼─────────────────────▼───┐ │
                 │  │  Рендерер: D3D11 + DirectComposition    │ │
                 │  └─────────────────────────────────────────┘ │
                 └─────────────────────────────────────────────┘
```

Один процесс, чётко разделённые потоки.

**Поток Tauri (главный).** Владеет окном настроек и иконкой в трее. Не участвует в рендере оверлеев. Общается с ядром через каналы + Tauri commands/events.

**Поток оверлея.** Создаёт нативные Win32-окна, ставит `SetWinEventHook`, регистрирует хоткеи, крутит свой `GetMessage`-цикл. Хуки `WINEVENT_OUTOFCONTEXT` доставляют колбэки в тот поток, который их установил, и требуют работающей очереди сообщений — поэтому у оверлеев обязан быть собственный pump, отдельный от Tauri.

**Пул декодеров.** Rayon-подобный пул под FFmpeg. Один стикер-видео = одна задача. Отдаёт кадры в очередь на 2–3 элемента.

**Рендерер.** Один D3D11-девайс на процесс, по одной цепочке композиции на монитор.

### Структура репозитория

```
resticker/
├─ crates/
│  ├─ resticker/          — bin, точка входа, склейка
│  ├─ rst-core/           — модель данных, состояние, undo, конфиг
│  ├─ rst-win32/          — обёртки Win32: окна, хуки, хоткеи, перечисление, AOT
│  ├─ rst-render/         — D3D11 + DirectComposition, шейдеры, UI редактора
│  ├─ rst-media/          — загрузка изображений, GIF, ffmpeg, кэш, даунскейл

├─ ui/                    — фронтенд настроек (Tauri, TypeScript)
├─ assets/
└─ docs/
```

## 2. Модель окон: почему не Tauri для оверлеев

Инстинктивное решение — сделать каждый стикер отдельным окном Tauri. Это ошибка.

- Каждое окно Tauri — отдельный экземпляр WebView2. Это отдельный процесс браузерного движка, 40–80 МБ RAM, своя GPU-композиция.
- 25 стикеров = ~1,5 ГБ RAM и десятки процессов в диспетчере задач.
- Взаимный z-order 25 top-level окон практически неуправляем: Windows переупорядочивает их сама.
- Рамка выделения, растянутая на несколько стикеров, требует ещё одного окна поверх, и синхронизировать его с остальными — боль.
- Попиксельная маска перекрытия (см. раздел 3) внутри WebView недостижима.

**Принятая модель: одно нативное окно на монитор.** Все стикеры этого монитора рисуются внутри него как квады. 25 стикеров на трёх мониторах = 3 HWND.

Параметры окна:

```
CreateWindowExW(
    WS_EX_TOPMOST          // всегда физически сверху
  | WS_EX_TOOLWINDOW       // нет в Alt+Tab и на панели задач
  | WS_EX_NOACTIVATE       // не забирает фокус
  | WS_EX_TRANSPARENT      // клики проходят насквозь (снимается в режиме редактирования)
  | WS_EX_NOREDIRECTIONBITMAP,  // без redirection-поверхности DWM
    class, null, WS_POPUP, ...)
```

`WS_EX_NOREDIRECTIONBITMAP` говорит движку композиции не выделять окну redirection-поверхность. Содержимое подаётся напрямую через DirectComposition, что даёт аппаратно-ускоренную попиксельную альфу без `WS_EX_LAYERED` и без `UpdateLayeredWindow`.

Цепочка:

```
IDCompositionDevice → IDCompositionTarget (для HWND)
                    → IDCompositionVisual
                    → IDXGISwapChain1 (CreateSwapChainForComposition,
                                        DXGI_ALPHA_MODE_PREMULTIPLIED,
                                        FLIP_SEQUENTIAL,
                                        FRAME_LATENCY_WAITABLE_OBJECT)
```

Альфа — **premultiplied**. Все текстуры при загрузке приводятся к premultiplied RGBA, иначе на краях появится тёмная кайма.

### Почему D3D11 напрямую, а не wgpu

wgpu приятнее писать и открывает дорогу к кроссплатформенности. Но здесь решают два аргумента:

1. **Интероп с аппаратным декодом.** FFmpeg с `d3d11va` отдаёт кадр как `ID3D11Texture2D`, уже лежащий в видеопамяти. В D3D11 этот кадр рисуется напрямую — ноль копирований. В wgpu пришлось бы либо тащить кадр через системную память (это +5–15% CPU на каждое 1080p видео), либо городить unsafe-интероп через HAL, что сводит на нет всё удобство.
2. **DirectComposition.** Прозрачная композиционная swapchain — это Windows-специфичный путь, который в wgpu придётся всё равно настраивать через raw-handles.

Кроссплатформенность мы всё равно не планируем (см. SPEC). Поэтому D3D11 + `windows-rs`.

Запасной вариант: если D3D11 окажется слишком тяжёлым в разработке, можно на M1 сделать прототип на wgpu с software-декодом, а потом переехать. Абстракция `trait Renderer` в `rst-render` заложена именно на этот случай.

## 3. Проблема слоёв и её решение

Это центральная техническая проблема проекта. Разберём её честно.

### 3.1 Почему «в лоб» не работает

Windows не даёт произвольного z-order. Порядок окон делится на две полосы: topmost (`WS_EX_TOPMOST`) и обычные. Внутри полосы порядок определяется активацией пользователя. Сказать «будь выше Chrome, но ниже Photoshop» через API невозможно.

Что перебирали:

**Вариант А: динамическое переключение topmost.** Слушать `EVENT_SYSTEM_FOREGROUND` и на каждую смену активного окна вызывать `SetWindowPos` с `HWND_TOPMOST` или `HWND_NOTOPMOST`.
*Отвергнут.* Даёт видимое мерцание на смене окон, гонки при быстром Alt+Tab, и главное — решает задачу только для *активного* окна. Ситуация «стикер над Chrome, но Photoshop лежит поверх Chrome и не активен» не решается вообще.

**Вариант Б: вставка окна между конкретными окнами через `SetWindowPos(hwnd, hwndAfter, …)`.**
*Отвергнут.* Позиция теряется при любой активации любого окна. Пришлось бы восстанавливать её постоянно — это опрос и то же мерцание.

**Вариант В: рендер в слой обоев через `WorkerW`.**
Рабочий приём (так делает Wallpaper Engine): послать `Progman` недокументированное сообщение `0x052C`, найти второе окно класса `WorkerW` (то, у которого нет дочернего `SHELLDLL_DefView`) и сделать `SetParent` на него. Окно оказывается между обоями и иконками рабочего стола.
*Отвергнут как основной механизм*, но полезен как факт: он даёт только режим «строго под всеми окнами», и то нестабильно — на Windows 11 24H2 `WorkerW` появляется не сразу после старта и не всегда находится перечислением.

### 3.2 Принятое решение: маска перекрытия

Ключевая идея: **не бороться с z-order, а подделать его на уровне пикселей.**

Оверлей физически всегда `WS_EX_TOPMOST` — над всем. Но при отрисовке мы **вырезаем** из стикера те области, которые перекрыты окнами, которые по правилам должны быть выше него. Визуально результат неотличим от настоящего перекрытия.

Алгоритм на кадр (точнее, на пересчёт — см. 3.4):

```
1. Собрать список видимых top-level окон (см. 3.3), каждое с прямоугольником
   DWMWA_EXTENDED_FRAME_BOUNDS и порядком в z-order.
2. Исключить собственные окна resticker.
3. Для каждого стикера:
     occluders = { окно | окно ∉ allow_list(стикер) }
     если allow_list == ALL → occluders пуст → быстрый путь, маска не нужна
4. Отрендерить occluders в маску (R8, разрешение экрана) как белые прямоугольники
   со скруглением углов радиусом 8 px.
5. Отрисовать стикер с discard там, где маска ≠ 0.
```

Красота решения в том, что три пользовательских режима — это **один и тот же механизм**:

| Режим | `allow_list` | Что получается |
|---|---|---|
| Поверх всего | все окна | occluders пуст, ничего не вырезается |
| Выборочно | подмножество | вырезаются только «чужие» окна |
| Только рабочий стол | пусто | occluders = все окна, стикер виден только там, где голый десктоп |

Никаких спецкейсов, никакого `WorkerW`, никакого переключения topmost.

Заметим важный побочный эффект, который работает *правильно* сам собой: если окно A в allow-list, а окно B не в нём и лежит поверх A, — B всё равно попадает в occluders и вырезается. То есть стикер честно «уходит под» B, хотя над A он остаётся. Именно этого и ждёт пользователь.

### 3.3 Перечисление окон

Нужен список «настоящих» окон — тех же, что показывает Alt+Tab. `EnumWindows` возвращает много мусора: невидимые окна приостановленных UWP-приложений, тултипы, служебные окна.

Фильтр:

```rust
fn is_real_window(hwnd: HWND) -> bool {
    if !IsWindowVisible(hwnd) { return false; }

    // UWP-приложения оставляют "скрытые" окна — их отсекает DWM-флаг cloaked
    let mut cloaked: u32 = 0;
    DwmGetWindowAttribute(hwnd, DWMWA_CLOAKED, &mut cloaked, 4);
    if cloaked != 0 { return false; }

    if GetAncestor(hwnd, GA_ROOT) != hwnd { return false; }

    let ex = GetWindowLongPtrW(hwnd, GWL_EXSTYLE) as u32;
    if ex & WS_EX_NOACTIVATE != 0 { return false; }
    if ex & WS_EX_TOOLWINDOW != 0 && ex & WS_EX_APPWINDOW == 0 { return false; }
    if GetWindow(hwnd, GW_OWNER) != 0 && ex & WS_EX_APPWINDOW == 0 { return false; }

    true
}
```

Два подводных камня:

- **Границы.** `GetWindowRect` возвращает прямоугольник вместе с невидимыми полями изменения размера и тенью DWM — он на несколько пикселей больше видимой части. Для маски нужен `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`.
- **Свёрнутые окна.** `IsIconic` — исключать, у свёрнутого окна прямоугольник мусорный.

### 3.4 Когда пересчитывать

**Никакого опроса по таймеру.** Только события через `SetWinEventHook`:

| Событие | Зачем |
|---|---|
| `EVENT_SYSTEM_FOREGROUND` | смена активного окна → изменился z-order |
| `EVENT_OBJECT_LOCATIONCHANGE` | окно двигают или ресайзят |
| `EVENT_OBJECT_SHOW` / `EVENT_OBJECT_HIDE` | окно появилось или спрятано |
| `EVENT_OBJECT_DESTROY` | окно закрыто |
| `EVENT_SYSTEM_MINIMIZESTART` / `MINIMIZEEND` | сворачивание |
| `EVENT_SYSTEM_MOVESIZESTART` / `MOVESIZEEND` | начало и конец перетаскивания окна |

`EVENT_OBJECT_LOCATIONCHANGE` — самое частое, во время перетаскивания окна летит десятками в секунду. Обработка:
- фильтровать по `idObject == OBJID_WINDOW && idChild == CHILDID_SELF`;
- сразу отбрасывать HWND, которых нет в нашем кэше «реальных окон»;
- дебаунсить: не чаще одного пересчёта в 16 мс (один кадр при 60 Гц), с коалесцированием.

Кэш окон хранится как `Vec<WindowInfo>` и обновляется инкрементально. Полное `EnumWindows` — только на `FOREGROUND`, `SHOW`, `DESTROY`; на `LOCATIONCHANGE` обновляется только прямоугольник конкретного окна.

Дополнительные оптимизации:
- Если ни у одного стикера нет ограничений (`allow_list == ALL` у всех) — хуки на `LOCATIONCHANGE` **не ставятся вообще**. Типичный случай для многих пользователей.
- Если новый прямоугольник окна не пересекается ни с одним стикером и старый тоже не пересекался — перерисовка не запускается.

### 3.5 Известные ограничения решения

Честный список того, чего этот подход не может:

1. **Окна нестандартной формы** обрезаются по прямоугольнику. Практически не встречается.
2. **Тени окон.** Тень DWM рисуется вне extended frame bounds; стикер будет виден сквозь неё. Мелкий косметический артефакт.
3. **Эксклюзивный полноэкранный режим.** Overlay поверх такого приложения не появится в принципе — это ограничение самой Windows, не нашего подхода.
4. **Скруглённые углы.** Компенсируются в шейдере фиксированным радиусом 8 px. На нестандартно оформленных окнах может быть на пиксель мимо.

## 4. Как не убить процессор

Требование «чем оптимизированнее, тем лучше» переводится в конкретные правила.

### 4.1 Главный принцип: не рисовать, когда нечего рисовать

Большинство оверлей-программ крутят вечный цикл рендера на 60 FPS. Это неправильно. У нас:

- Рендер-поток спит на `MsgWaitForMultipleObjectsEx` и просыпается **только** от события: пришёл новый кадр видео, тикнул кадр GIF, изменилась геометрия окон, пользователь что-то делает в режиме редактирования, изменилась конфигурация.
- Если на экране только статичные PNG и ничего не происходит — **ноль кадров в секунду и ноль просыпаний**. DWM продолжает композитить последнюю поверхность сам, нам делать нечего.
- Целевой idle: приложение не потребляет измеримого CPU.

### 4.2 Частота кадров по требованию

Частота презента = максимум из частот активных анимаций, ограниченная сверху частотой обновления монитора.

- 1 GIF на 10 FPS → презентим 10 раз в секунду, а не 60
- Видео 30 FPS + GIF 10 FPS → 30
- Ничего не движется → 0

Каждый анимированный стикер имеет собственные часы. Общий планировщик собирает ближайший дедлайн и ставит waitable timer ровно на него.

`DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` даёт ожидание на объекте ядра вместо активного ожидания в `Present`. Latency = 1.

### 4.3 Отсечение невидимого

Мощнейшая оптимизация, вытекающая из маски перекрытия: мы и так вычисляем, какие области стикера видны.

- Стикер **полностью перекрыт** → его видео **не декодируется**, звук приглушается (или нет — конфигурируется), кадры GIF не тикают. Свёрнутая в фуллскрин игра поверх всего = 25 стикеров стоят колом и не стоят ничего.
- Стикер скрыт «глазом» → то же самое.
- Стикер на другом виртуальном рабочем столе → то же.
- Все мониторы, на которых нет активных анимаций, не презентят вообще.

Проверка перекрытия делается по площади: если объединение occluder-прямоугольников покрывает bbox стикера — он невидим.

### 4.4 Декодирование

**Видео:**
- Аппаратный декод через `d3d11va` там, где он доступен. Кадр остаётся в VRAM как `ID3D11Texture2D` — ни одного копирования в системную память.
- Fallback на программный декод: H.264/HEVC/AV1/VP9 при отсутствии поддержки, и **всегда** для видео с альфой (ни NVDEC, ни Quick Sync не декодируют альфа-канал — он лежит отдельным битстримом, который аппаратные декодеры игнорируют).
- Очередь кадров ограничена 3 элементами: больше не нужно, а память экономит.
- Один декодер = одна задача в пуле. При 25 видео пул не даёт им всем одновременно жечь все ядра: параллелизм ограничен `min(число_ядер - 2, 8)`.
- Seek не нужен нигде, кроме лупа — луп реализуется дешёвым `av_seek_frame` к началу без пересоздания контекста.

**Изображения:** декодируются один раз при загрузке в фоновом потоке, загружаются в текстуру с мипмапами и больше не трогаются.

**GIF / анимированный WebP:** все кадры распаковываются в текстурный атлас **один раз** при загрузке (типичная гифка — десятки кадров небольшого размера). Дальше анимация — это просто смена UV-координат, стоимость нулевая. Для очень длинных анимаций (> 300 кадров или > 256 МБ) переключаемся на потоковое декодирование.

### 4.5 Память

- Даунскейл при импорте до 4096 px по большей стороне (см. SPEC 2.4) — 8000×8000 PNG превращается из 256 МБ VRAM в 64 МБ.
- Мипмапы: стикер, отображаемый в четверть размера, сэмплируется с мип-уровня, а не с полного разрешения.
- Кэш даунскейла на диске, чтобы не пересчитывать при каждом старте.
- Промежуточные staging-текстуры переиспользуются из пула.

### 4.6 Прочее

- **Батарея.** Регистрируемся на `PowerSettingRegisterNotification` (`GUID_ACDC_POWER_SOURCE`, `GUID_POWER_SAVING_STATUS`). При переходе на батарею опционально ограничиваем FPS оверлеев (по умолчанию 30) — настраивается.
- **Блокировка экрана.** `WTSRegisterSessionNotification` → на `WTS_SESSION_LOCK` полностью останавливаем декодирование и звук.
- **Потеря устройства D3D.** `DXGI_ERROR_DEVICE_REMOVED` после выхода из сна или обновления драйвера — обязательна корректная пересборка девайса, swapchain и всех текстур.
- **Release-сборка:** `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, `opt-level = 3`.

## 5. Ввод и режим редактирования

### 5.1 Глобальный хоткей

Основной путь — `RegisterHotKey` на потоке оверлея. Дёшево, обрабатывается ядром, не требует хуков и не тормозит ввод в системе.

Ограничение: `RegisterHotKey` не умеет некоторые комбинации и конфликтует, если хоткей уже занят другой программой. Если регистрация не удалась — сообщаем пользователю и предлагаем другую комбинацию. Низкоуровневый хук `WH_KEYBOARD_LL` как fallback **не используется**: он проходит через весь ввод системы и при малейшем тормозе в обработчике вызывает лаги набора текста во всех приложениях. Цена не стоит выгоды.

### 5.2 Переключение в интерактивный режим

Оверлей-окна не имеют `WS_EX_TRANSPARENT` только в режиме редактирования:

```rust
// вход
SetWindowLongPtrW(hwnd, GWL_EXSTYLE, ex & !WS_EX_TRANSPARENT & !WS_EX_NOACTIVATE);
SetForegroundWindow(hwnd);
// выход — вернуть флаги
```

Затемнение на 50% — это полноэкранный квад с `rgba(0,0,0,0.5)`, отрисованный **под** стикерами в том же самом окне. Никакого дополнительного HWND.

### 5.3 UI редактора

Весь интерфейс режима редактирования (рамка выделения, 8 ручек, зона поворота, тулбар, панель у курсора, панель выбора окон) рисуется нами в D3D11 в режиме immediate mode.

Почему не WebView для тулбара: тулбар обязан быть точно спозиционирован относительно выделения, реагировать без задержки на перетаскивание и жить в том же композиционном слое, что и стикеры. Отдельное окно WebView даст рассинхрон на кадр и мерцание при перетаскивании.

Хит-тестинг: обратная аффинная трансформация точки курсора в локальные координаты стикера, проверка попадания в bbox. Порядок проверки — обратный порядку отрисовки (сверху вниз).

Зона поворота — кольцо от 6 до 24 логических пикселей наружу от угловой ручки.

### 5.4 Undo/Redo

Классический command stack. Каждая команда хранит обратимое изменение состояния (не снапшот всей модели). Одна операция перетаскивания коалесцируется в одну команду по `MOVESIZEEND`-аналогу — отпусканию кнопки мыши.

## 6. Стикеры-окна (порт Always On Top)

Логика взята по мотивам модуля Always On Top из PowerToys и переписана на Rust. Оригинал использует ровно тот же приём: расширенный стиль `WS_EX_TOPMOST`, выставляемый через `SetWindowPos`, плюс оконное свойство-маркер, чтобы помнить, что окно закреплено именно нами.

```rust
fn pin(hwnd: HWND) -> bool {
    SetPropW(hwnd, w!("RESTICKER_PINNED"), HANDLE(1));
    SetWindowPos(hwnd, HWND_TOPMOST, 0, 0, 0, 0,
                 SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE).is_ok()
}

fn unpin(hwnd: HWND) -> bool {
    RemovePropW(hwnd, w!("RESTICKER_PINNED"));
    SetWindowPos(hwnd, HWND_NOTOPMOST, 0, 0, 0, 0,
                 SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE).is_ok()
}
```

Детали, которые легко упустить:

- **Открепление при выходе.** Все закреплённые окна обязаны быть откреплены при завершении программы, включая аварийное. Ставим обработчик на `WM_QUERYENDSESSION` / `WM_ENDSESSION` и panic hook.
- **Права.** Если целевое окно принадлежит процессу с более высоким уровнем целостности, `SetWindowPos` тихо провалится из-за UIPI. Проверяем возврат и сообщаем пользователю.
- **Смерть окна.** `EVENT_OBJECT_DESTROY` для закреплённых HWND → убираем из активного списка.
- **Виртуальные рабочие столы.** `IVirtualDesktopManager::IsWindowOnCurrentVirtualDesktop` перед отрисовкой связанного состояния. API недокументированное и меняется между сборками Windows — оборачиваем в fallible-обёртку, при ошибке считаем, что окно на текущем столе.
- **Перемещение и ресайз** — обычный `SetWindowPos`, но ресайз ограничен тем, что позволяет само окно. Минимальные/максимальные размеры окно сообщает через `WM_GETMINMAXINFO`; мы их не видим напрямую, поэтому просто применяем `SetWindowPos` и читаем фактический результат `GetWindowRect` — если окно не приняло размер, ручка ресайза «упирается».
- **Восстановление из пресета** — по совокупности признаков: полный путь к исполняемому файлу процесса + класс окна + паттерн заголовка. Совпадений может быть несколько (три окна Chrome) — берём первое незанятое, остальные считаем недоступными.

## 7. Мультимонитор и DPI

**Единица хранения — логические (DIP) координаты относительно конкретного монитора.** Не физические пиксели глобального виртуального рабочего стола. Это единственный способ пережить смену масштаба монитора без «уползания» стикеров.

- Процесс объявляет `PROCESS_PER_MONITOR_DPI_AWARE_V2` в манифесте. Без этого Windows будет растягивать наши окна сама, и всё сломается на смешанном DPI.
- На каждый монитор — своё окно, свой DPI, свой обработчик `WM_DPICHANGED`.
- `EnumDisplayMonitors` + `GetMonitorInfoW` дают геометрию, `GetDpiForMonitor` — масштаб.
- Идентификация монитора для конфига: `EnumDisplayDevices` с флагом `EDD_GET_DEVICE_INTERFACE_NAME` даёт device interface path, стабильный при переподключении и не зависящий от номера монитора в системе.
- `WM_DISPLAYCHANGE` и `EVENT_SYSTEM_DESKTOPSWITCH` → пересборка набора оверлей-окон.

Реализация сценария из SPEC 6.1 (отключение монитора): состояние монитора и таймер на 20 секунд живут в ядре, окно уничтожается сразу, данные стикеров — нет.

## 8. Звук

Микшер через `cpal` (WASAPI shared mode). Один поток вывода на процесс, все аудиодорожки видео-стикеров микшируются в него.

- Ресемплинг к частоте устройства.
- Синхронизация: аудиочасы ведущие, видео подстраивается — стандартная схема, дающая отсутствие рассинхрона на длинных роликах.
- Стикеры, которые невидимы (перекрыты, скрыты, монитор отключён), по умолчанию **замолкают**. Это настраивается: некоторым нужен звук от невидимого стикера.
- Глобальный mute с хоткеем обязателен: 25 одновременных источников звука по умолчанию — потенциальный кошмар, у пользователя должна быть аварийная кнопка.

## 9. Персистентность

Подробная схема — в [CONFIG.md](CONFIG.md). Архитектурные требования:

- **Атомарная запись.** Пишем во временный файл в той же папке, `fsync`, затем `MoveFileExW` с `MOVEFILE_REPLACE_EXISTING`. Никогда не перезаписываем конфиг на месте — иначе выключение питания посреди записи оставит пользователя без всех настроек.
- **Версионирование схемы.** Поле `schema_version` с первого дня. Миграции — чистые функции `vN → vN+1`.
- **Дебаунс сохранения.** Не сохраняем на каждое движение мыши; сохраняем через 1 с после последнего изменения и обязательно при выходе из режима редактирования и при завершении программы.
- **Резервная копия.** Перед миграцией схемы и перед загрузкой пресета сохраняем `config.bak`.

## 10. Безопасность и приватность

- Программа не ходит в сеть. Совсем. Если когда-нибудь появится автообновление — только по явному согласию и с отдельным переключателем.
- Перечисление окон читает заголовки и пути процессов. Эти данные не покидают машину, но **попадают в конфиг пресетов**. При экспорте пресета пользователя надо предупредить, что внутри будут пути к его файлам и имена его программ.
- `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` — легитимная функция, но она же используется для обхода систем прокторинга. Мы применяем её только к собственным оверлеям и только по явному включению настройки. Никаких скрытых режимов.

## 11. Тестирование

Что действительно нужно проверять, потому что оно точно сломается:

| Область | Как тестировать |
|---|---|
| Маска перекрытия | Ручные сценарии + скриншот-тесты: сравнение отрендеренного кадра с эталоном |
| Мультимонитор | Виртуальные дисплеи (`usbmmidd`), смешанный DPI 100/150/200 |
| Hot-plug монитора | Физическое отключение кабеля, RDP-сессия, смена основного монитора |
| DPI | Смена масштаба на лету, перетаскивание стикера между 100% и 200% |
| Потеря D3D-устройства | `dxcap`, обновление драйвера, выход из сна |
| Утечки памяти | Прогон 24 часа с 25 видео, снимок рабочего набора каждый час |
| Idle CPU | Замер потребления за час при статичных стикерах — целевой ноль |
| Порядок стикеров | Property-based тесты на команды «выше»/«ниже» |
| Undo/Redo | Property-based: случайная последовательность операций, N раз undo, N раз redo → исходное состояние |
| Конфиг | Fuzz на парсер, тест атомарности записи через принудительное убийство процесса |

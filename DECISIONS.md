# resticker — архитектурные решения (ADR)

Каждая запись фиксирует принятое решение, рассмотренные альтернативы и причину выбора. Если решение впоследствии окажется неверным, запись не удаляется, а получает статус «Заменено».

---

## ADR-001. Язык: Rust

**Статус:** принято

**Контекст.** Нужен язык для десктопного приложения под Windows с интенсивной работой с Win32 API, GPU и декодированием видео в реальном времени.

**Решение.** Rust.

**Обоснование.**
- Tauri, выбранный для UI, требует Rust на бэкенде — альтернативы нет.
- Нет сборщика мусора, значит нет непредсказуемых пауз в рендер-петле.
- `windows-rs` — официальные, полные и актуальные биндинги ко всему Win32 от Microsoft.
- Безопасность памяти при интенсивной работе с сырыми указателями Win32 — реальная ценность, а не лозунг: половина классических багов оверлей-программ это use-after-free на HWND и текстурах.
- Хорошая многопоточность из коробки, что критично для 25 параллельных декодеров.

**Альтернативы.**
- **C++.** Идеально ложится на Win32 и D3D11, вся документация Microsoft на нём. Но несовместим с Tauri, и вся ручная работа с памятью ложится на разработчика.
- **C#.** Быстрее всего писать, WPF/WinUI под рукой. Но GC-паузы в рендер-петле, худший интероп с FFmpeg, больший расход памяти.

**Последствия.** Порог входа выше, компиляция дольше. Значительная часть кода будет в `unsafe`-блоках вокруг Win32 — их нужно аккуратно оборачивать в безопасные типы в `rst-win32`.

## ADR-002. Tauri только для окна настроек, не для оверлеев

**Статус:** принято

**Контекст.** Естественная мысль — реализовать каждый стикер как окно Tauri с прозрачным фоном.

**Решение.** Оверлеи — нативные Win32-окна с D3D11-рендером. Tauri владеет только окном настроек и треем.

**Обоснование.**
- Каждое окно Tauri — отдельный экземпляр WebView2 с расходом 40–80 МБ. 25 стикеров ≈ 1,5 ГБ.
- Управление взаимным z-order 25 top-level окон практически невозможно: Windows переупорядочивает их по своим правилам.
- Рамка выделения через несколько стикеров потребовала бы ещё одно окно поверх, с неизбежным рассинхроном на кадр.
- Маска перекрытия (ADR-004) внутри WebView недостижима в принципе.

**Последствия.** Весь UI режима редактирования пишется вручную в immediate mode на D3D11. Это заметная работа, но она даёт точную синхронизацию и нулевую задержку.

## ADR-003. Direct3D 11 + DirectComposition, а не wgpu

**Статус:** принято

**Контекст.** Нужен рендерер с попиксельной прозрачностью, аппаратным ускорением и интеропом с декодером видео.

**Решение.** D3D11 напрямую через `windows-rs`, презентация через DirectComposition с `CreateSwapChainForComposition` и premultiplied alpha.

**Обоснование.**
- FFmpeg с `d3d11va` отдаёт декодированный кадр как `ID3D11Texture2D`, уже в видеопамяти. В D3D11 он рисуется напрямую, без единого копирования. Это разница в 5–15% CPU на каждое 1080p-видео.
- `WS_EX_NOREDIRECTIONBITMAP` + DirectComposition — рекомендованный Microsoft путь к аппаратной прозрачности, в отличие от устаревшего `WS_EX_LAYERED` + `UpdateLayeredWindow`, который проходит через CPU.
- Полный контроль над моментом презента, что позволяет реализовать «ноль кадров в покое».

**Альтернативы.**
- **wgpu.** Гораздо приятнее в разработке, открывает путь к Linux/macOS. Но интероп с `d3d11va` требует unsafe-работы через HAL, что убивает всё удобство. Кроссплатформенность в требованиях явно отсутствует.
- **Direct2D.** Проще для 2D, но интероп с видео и произвольные шейдеры (маска перекрытия, шахматка) хуже.

**Последствия.** Проект жёстко привязан к Windows. В `rst-render` заложен трейт `Renderer`, чтобы теоретически можно было подменить бэкенд, но реальной кроссплатформенности это не даст.

## ADR-004. Слои видимости через маску перекрытия, а не через z-order

**Статус:** принято — **ключевое решение проекта**

**Контекст.** Требуется, чтобы стикер был виден поверх одних окон и скрывался под другими. Windows этого не позволяет: z-order делится всего на две полосы, topmost и обычную, и не даёт вставить окно «между» конкретными окнами устойчиво.

**Решение.** Оверлей всегда `WS_EX_TOPMOST`. Перекрытие имитируется: при отрисовке из стикера вырезаются области окон, которые по правилам должны быть выше. Реализуется маской в шейдере.

**Обоснование.**
- Даёт **произвольную** гранулярность: любое подмножество окон, а не три фиксированных режима.
- Три пользовательских пресета («поверх всего», «выборочно», «только рабочий стол») выражаются одним и тем же механизмом с разными списками — никаких спецкейсов в коде.
- Нет мерцания, нет гонок, нет постоянной борьбы с системой за позицию окна.
- Побочно даёт бесплатное отсечение: мы и так знаем, какие стикеры полностью невидимы, и можем не декодировать их видео.

**Альтернативы.**
- **Переключение topmost по `EVENT_SYSTEM_FOREGROUND`.** Мерцает, решает задачу только для активного окна, не работает для неактивных окон поверх разрешённых.
- **Вставка через `SetWindowPos(hwnd, hwndAfter, …)`.** Позиция сбрасывается при любой активации любого окна.
- **`SetParent` на `WorkerW`** (приём Wallpaper Engine). Даёт только режим «под всеми окнами», нестабилен на Windows 11 24H2, где `WorkerW` появляется не сразу и не всегда находится перечислением.

**Последствия и ограничения.**
- Окна нестандартной формы обрезаются по прямоугольнику.
- Тень DWM рисуется вне extended frame bounds — сквозь неё стикер будет виден. Косметика.
- Скруглённые углы Windows 11 компенсируются в шейдере фиксированным радиусом 8 px.
- Требуется точное и быстрое отслеживание геометрии всех окон (см. ADR-005).

## ADR-005. Отслеживание окон через WinEvent-хуки, без опроса

**Статус:** принято

**Контекст.** Маске перекрытия нужен актуальный список окон с их прямоугольниками. Наивное решение — опрашивать `EnumWindows` по таймеру.

**Решение.** Только события через `SetWinEventHook` с `WINEVENT_OUTOFCONTEXT`, с инкрементальным кэшем и дебаунсом 16 мс.

**Обоснование.**
- Опрос на 60 Гц с `EnumWindows` и `DwmGetWindowAttribute` для каждого окна — это несколько процентов CPU в вечном цикле, при том что 99% времени ничего не меняется.
- `WINEVENT_OUTOFCONTEXT` не внедряет DLL в чужие процессы: колбэк приходит в наш процесс. Никакого влияния на стабильность чужих программ.

**Последствия.**
- Поток, установивший хуки, обязан иметь работающую очередь сообщений — отсюда отдельный поток оверлея с собственным pump.
- `EVENT_OBJECT_LOCATIONCHANGE` летит очень часто при перетаскивании окна: нужна агрессивная фильтрация и коалесцирование.
- Если ни у одного стикера нет ограничений видимости, хуки на `LOCATIONCHANGE` не ставятся вовсе.

## ADR-006. Событийный рендер вместо постоянного цикла

**Статус:** принято

**Контекст.** Программа висит в автозапуске 24/7. Вечный цикл на 60 FPS — это постоянный расход батареи и тепла ради статичной картинки.

**Решение.** Рендер-поток спит на `MsgWaitForMultipleObjectsEx` и просыпается только по событию. Частота презента = максимум частот активных анимаций, ограниченный частотой обновления монитора. Ноль анимаций = ноль кадров.

**Обоснование.** Типичный сценарий использования — несколько статичных картинок, которые не меняются часами. Такой расклад обязан стоить ноль.

**Последствия.** Логика планировщика кадров сложнее наивного цикла. Любая забытая «просыпалка» будет заметна в замерах — нужен регулярный контроль idle-потребления в CI-подобном виде.

## ADR-007. Ссылка на оригинальный файл, а не копия

**Статус:** принято

**Контекст.** При добавлении стикера файл можно скопировать в папку приложения либо хранить путь.

**Решение.** Хранится путь. Копируется только содержимое, вставленное из буфера обмена (у него нет файла-источника).

**Обоснование.**
- Не дублируется гигабайт видео на диске.
- Изменение файла на диске автоматически отражается в стикере — это удобно.

**Последствия.**
- Перемещение или удаление файла ломает стикер. Требуется явная обработка: заглушка «файл не найден», кнопка переуказания пути, сохранение всех настроек стикера при потере источника.
- Пресет, экспортированный на другую машину, не заработает без тех же файлов по тем же путям. Пользователя нужно об этом предупреждать.

## ADR-008. FFmpeg, LGPL-сборка, только декодеры

**Статус:** принято

**Контекст.** Требование «видео в любых форматах» практически означает FFmpeg. У FFmpeg сложная лицензионная ситуация.

**Решение.** FFmpeg подключается **динамически** как shared-библиотека, собранная с `--disable-gpl --disable-nonfree` и без кодировщиков. Только декодирование.

**Обоснование.**
- GPL-компоненты FFmpeg (x264, x265, ряд фильтров) обязали бы весь проект стать GPL. Нам они не нужны: мы ничего не кодируем.
- Динамическая линковка с LGPL-библиотекой не накладывает требований на лицензию нашего кода при условии, что пользователь может подменить библиотеку.

**Последствия.**
- +30–60 МБ к дистрибутиву.
- В сборочной инструкции обязательно описываются точные флаги конфигурации FFmpeg.
- Файлы лицензии FFmpeg включаются в дистрибутив, бинарники не модифицируются.

## ADR-009. `RegisterHotKey` вместо низкоуровневого клавиатурного хука

**Статус:** принято

**Контекст.** Нужен глобальный хоткей для входа в режим редактирования.

**Решение.** `RegisterHotKey`. `WH_KEYBOARD_LL` не используется даже как fallback.

**Обоснование.**
- `RegisterHotKey` обрабатывается ядром, стоит ноль, не влияет на ввод в системе.
- `WH_KEYBOARD_LL` пропускает **весь** ввод пользователя через наш процесс. Любая задержка в обработчике превращается в лаги набора текста во всех программах. Также он часто ломается античитами и вызывает ложные срабатывания антивирусов.

**Последствия.** Некоторые комбинации выразить нельзя, возможен конфликт с уже занятым хоткеем. При неудачной регистрации показываем понятное сообщение и предлагаем другую комбинацию.

## ADR-010. Логические координаты относительно монитора

**Статус:** принято

**Контекст.** Позицию стикера можно хранить в физических пикселях глобального виртуального рабочего стола либо в логических координатах конкретного монитора.

**Решение.** Логические (DIP) координаты относительно монитора, идентифицированного стабильным device interface path.

**Обоснование.**
- Смена масштаба монитора со 100% на 150% не должна двигать стикер. При хранении в физических пикселях он уползёт.
- Смена номеров мониторов при переподключении не должна ничего ломать. Номер и координаты виртуального десктопа нестабильны, device interface path — стабилен.

**Последствия.**
- Обязателен `PROCESS_PER_MONITOR_DPI_AWARE_V2` в манифесте.
- Нужна полноценная обработка `WM_DPICHANGED` и тестирование на смешанном DPI, что легко забыть.
- Требуется явная логика для стикеров, чей монитор исчез (ADR-011).

## ADR-011. Стикеры пропавшего монитора мигрируют, но помнят дом

**Статус:** принято

**Контекст.** Монитор отключили. Куда девать его стикеры?

**Решение.**
1. Стикеры скрываются, данные сохраняются, запускается таймер 20 секунд.
2. Монитор вернулся вовремя — всё возвращается как было.
3. Не вернулся — стикеры переезжают на основной монитор с пропорциональным масштабированием позиции. Исходные монитор и координаты сохраняются в поле `origin`.
4. Монитор вернулся позже, хоть через неделю — стикеры автоматически возвращаются домой, если пользователь их с тех пор не двигал. Если двигал — остаются на месте, `origin` очищается.

**Обоснование.** Ни один из более простых вариантов не хорош: удалять стикеры — потеря данных; оставлять невидимыми — пользователь решит, что программа сломалась; безвозвратно мигрировать — при возврате монитора придётся всё расставлять заново. Предложенная схема не теряет данные ни в одном сценарии и не требует от пользователя действий.

**Последствия.** Дополнительное поле в схеме конфига и нетривиальная логика, требующая тестов на всех четырёх ветках.

## ADR-012. Инструменты рисования исключены из 1.0

**Статус:** принято

**Контекст.** Изначальная задумка включала слои с рисованием, текстом, фигурами, линиями, эффектами и ластиком.

**Решение.** Вынесено за пределы 1.0.

**Обоснование.**
- По объёму работ это сравнимо со всей остальной программой: только векторное представление, слои, ластик-как-маска и эффекты — это месяцы.
- Основной сценарий («приклеить картинку к монитору») полностью самодостаточен без этого.
- Есть реальный риск застрять на полпути и не выпустить вообще ничего.

**Последствия.** Модель данных проектируется с расчётом на будущее: у стикера есть поле `source`, которое сейчас всегда файл или окно, но спроектировано как перечисление, куда позже добавится вариант «слой рисования». Систему слоёв и порядок отрисовки закладываем сразу правильно.

## ADR-013. Один процесс, разделение по потокам

**Статус:** принято

**Контекст.** Tauri владеет главным потоком и его циклом сообщений. Оверлеям нужен собственный цикл сообщений для WinEvent-хуков.

**Решение.** Один процесс. Tauri на главном потоке, оверлеи и хуки на отдельном выделенном потоке со своим `GetMessage`-циклом, декодеры в пуле, связь через каналы и `PostThreadMessage` для пробуждения pump.

**Обоснование.**
- Отдельный процесс для оверлеев дал бы изоляцию от падений, но принёс бы IPC, удвоенный расход памяти и мучительную отладку.
- Разделение по потокам решает конфликт циклов сообщений и оставляет общее состояние в одном адресном пространстве.

**Последствия.** Общее состояние требует аккуратной синхронизации. Ядро проектируется как единственный владелец состояния, потоки общаются с ним сообщениями, а не разделяемыми мьютексами по всему коду.

## ADR-014. UI редактора — immediate-mode D3D11 в свапчейне оверлея

**Статус:** принято

**Контекст.** В режиме редактирования нужны тулбар стикера (SPEC 3.6) и панель у курсора (SPEC 3.8). Оба элемента существуют только в режиме редактирования, обязаны ехать за выделением в том же кадре и лежать в том же композиционном слое, что и стикеры. Подробное сравнение вариантов — в docs/M2_UI_NOTES.md.

**Решение.** Весь UI режима редактирования — тулбар, панель у курсора и (в M4) панель выбора окон (SPEC 4.2) — рисуется рендерером `rst-render` как геометрия (квады, скруглённые прямоугольники, иконки, текст) в конце списка отрисовки того же оверлей-окна. Хит-тест — теми же обратными аффинными преобразованиями, что и для выделения (ARCHITECTURE.md, раздел 5.3). Никаких дополнительных HWND.

**Обоснование.**
- Порядок отрисовки = z-order: UI гарантированно лежит над стикерами и затемнением, движение — в том же кадре, ноль `SetWindowPos` и мерцания.
- Один DPI-контекст на монитор: UI проектируется в DIP и масштабируется тем же `scale`, что и стикеры, — класса DPI-задач для UI не существует.
- Ввод через тот же оконно-широкий `WS_EX_TRANSPARENT`: промах хит-теста тулбара — это просто «клик ушёл дальше», а не переключение режима окна.
- Маска перекрытия (M4) режет только спрайты-стикеры; UI рисуется поверх неё безусловно — панели управления не «уходят» под чужие окна.
- Укладывается в событийный рендер (ADR-006): UI не анимируется сам, перерисовка только по событию.

**Альтернативы.**
- **Нативные дочерние окна Win32.** `SetWindowPos` на каждый кадр перетаскивания даёт рассинхрон и мерцание; дочернее или topmost-окно — борьба за z-order в полосе topmost и репарент при переносе стикера между мониторами (M3); каждому окну нужен свой `WS_EX_TRANSPARENT` и свой DPI-контекст. Выгода «нативный EDIT-контрол» не окупает.
- **Отдельные окна Tauri.** Каждое — процесс WebView2 на 40–80 МБ; позиционирование через IPC даёт задержку и мерцание; ещё одно topmost-окно в одной полосе с оверлеем; клик-сквозь остаётся оконно-широким. Та же мотивировка, что в ADR-002.

**Последствия.** В `rst-render` необходимо построить: (а) immediate-mode слой виджетов (панель, кнопка, ползунок, числовое поле, чекбокс) с хит-тестом в локальных координатах; (б) шрифты через DirectWrite — глифы в текстурный атлас с кэшем; (в) числовое поле как собственный виджет: фильтр «только цифры», `Backspace`, `Enter`, `Esc`, `Ctrl+V`, рисованная каретка, фокус внутри ядра редактора; (г) иконки кнопок тулбара из `assets/` как спрайты-текстуры. Порядок отрисовки кадра редактора: затемнение → стикеры → рамка/ручки выделения → тулбар → панель у курсора. Вне режима редактирования окно целиком клик-прозрачно (`WS_EX_TRANSPARENT`, UI не рисуется), в режиме — окно принимает ввод на всей площади. Разделение клавиатуры между числовым полем и хоткеями уточнить до реализации (docs/M2_UI_NOTES.md, раздел 9).

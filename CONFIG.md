# resticker — конфигурация и хранение данных

## Расположение

```
%APPDATA%\resticker\
├─ config.json            — глобальные настройки + активные стикеры
├─ config.bak             — копия перед миграцией схемы и загрузкой пресета
├─ presets\
│  ├─ work.json
│  └─ stream.json
└─ pasted\
   └─ <uuid>.png          — материализованные вставки из буфера обмена

%LOCALAPPDATA%\resticker\
├─ cache\
│  └─ <hash>.bin          — даунскейленные версии больших изображений
└─ logs\
   └─ resticker-YYYY-MM-DD.log
```

Разделение осознанное: `%APPDATA%` перемещается вместе с профилем пользователя, `%LOCALAPPDATA%` — нет. Кэш и логи привязаны к конкретной машине и роумиться не должны.

---

## Правила записи

**Атомарность обязательна.** Конфиг никогда не перезаписывается на месте:

```
1. Записать в config.json.tmp в той же папке
2. FlushFileBuffers
3. MoveFileExW(tmp, config.json, MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)
```

Выключение питания посреди обычной перезаписи оставило бы пользователя с обрезанным файлом и потерей всех настроек. Это не гипотетический риск, а типичный способ потерять доверие пользователя навсегда.

**Дебаунс.** Сохранение не происходит на каждое движение мыши. Пишем через 1 секунду после последнего изменения, а также принудительно при выходе из режима редактирования, при закрытии настроек и при завершении программы.

**Версионирование.** Поле `schema_version` присутствует с первой версии. Миграции — чистые функции `vN → vN+1`, применяемые последовательно. Перед миграцией создаётся `config.bak`.

**Битый конфиг.** Если файл не парсится: переименовать в `config.corrupt.<timestamp>.json`, попытаться загрузить `config.bak`, при неудаче — стартовать с дефолтов и сообщить пользователю в трее.

## Пояснения к полям

### `source.kind`

| Значение | Что хранится | Особенности |
|---|---|---|
| `file` | абсолютный путь | Файл не копируется. Пропал — стикер показывает заглушку, настройки сохраняются |
| `pasted` | путь внутри `%APPDATA%\resticker\pasted\` | Материализуется при вставке. Удаляется вместе со стикером |
| `window_crop` | приметы окна, прямоугольник crop и состояние сворачивания | HWND в конфиг не пишется; живой источник переподключается после перезапуска |

`window_crop` хранит вложенный объект `window` с полями `exe_path`, `title` и
`class`. Это устойчивые приметы источника, а не HWND: после закрытия источник
временно скрывает crop и ждёт, после запуска окна с теми же приметами
переподключается. Объект `crop` содержит `x`, `y`, `w`, `h` — доли (0..1)
клиентской области исходного окна, не физические пиксели. `minimized` —
состояние самого crop, по умолчанию `false`; сворачивание исходного окна
останавливает кадры до его восстановления и не меняет доли crop.
`always_on_top` — состояние кнопки-булавки: `false` оставляет кусок в обычном
порядке окон, `true` держит его поверх всех окон и сохраняется при
перезапуске.

### `visibility.mode`

- `all` — стикер поверх всего. Маска перекрытия не считается, это быстрый путь.
- `desktop_only` — эквивалентно `selective` с пустым списком: любое окно перекрывает стикер.
- `selective` — стикер виден над перечисленными целями и перекрывается всеми остальными окнами.
- `except` — зеркало `selective`: стикер перекрывается **только** перечисленными целями, всеми остальными окнами (в том числе теми, которых на момент выбора не существовало) — нет.

`all` и `except` описывают состояние, а не набор окон: они продолжают
действовать на приложения, запущенные позже, и переживают перезагрузку
компьютера. Выразить «все, кроме одного» через `selective`, перечислив
остальные запущенные процессы, — не то же самое: такой список стареет с
первым же новым окном.

`targets[].match`:
- `process` — все окна процесса, включая те, что появятся позже
- `window` — конкретное окно, опознаваемое по классу и паттерну заголовка

`title_pattern` поддерживает `*` как подстановку. При нескольких совпадениях (три окна Chrome) под правило подпадают все.

### `placement`

Координаты — логические пиксели относительно левого верхнего угла **своего** монитора, а не глобального виртуального рабочего стола. `cx`/`cy` — центр, а не левый верхний угол: так поворот и масштабирование от центра выражаются естественно и не накапливают ошибку при многократных операциях.

### `settings.cursor_panel_offset`

Смещение центра панели у курсора относительно позиции курсора, DIP (SPEC 3.8 «Панель перетаскиваемая, её позиция запоминается»). `null` — дефолтное смещение (12, 12). Записывается координатором, когда пользователь перетащил панель; панель и так едет за курсором, поэтому хранится именно смещение, а не абсолютная позиция (оно не зависит от монитора).

### `settings.snap_shrink_pct`

Отступ **закреплённого** окна внутри его снап-зоны Windows, проценты. `0` — функция выключена: окно занимает свою половину/четверть/треть целиком, как его и положила Windows. Иначе окно ужимается на этот процент по каждой стороне и встаёт по центру зоны, оставляя одинаковый зазор со всех четырёх сторон.

Потолок — **35%**: сильнее ужатая половина экрана перестаёт вмещать полезное содержимое. Значения выше срезаются при чтении, файл при этом не переписывается.

Значение выбирается в подменю трея «Snap gap» (пункты `Off`, `5%` … `35%`, текущий помечен точкой) либо вписывается числом в настройках, вкладка «Общие» → «Snap gap, %» — там шаг 1%, а не 5%. Текущее значение показано в заголовке подменю трея: произвольное число (17%) не совпадёт ни с одним пунктом списка, и без заголовка подменю выглядело бы так, будто отступ выключен. По умолчанию действует на все закреплённые окна сразу; галочку «на все окна» см. в `settings.snap_shrink_all_windows`. Пока оно не `0`, отступ восстанавливается при каждом новом снапе: перетащил окно к краю ещё раз — зазор снова на месте. Окно, уведённое из снап-зоны, отпускается и живёт по обычным правилам закрепления (магнит кромок, потолок 90% монитора).

Распознаются раскладки Windows 10/11: половины по обеим осям, четверти и колонки-трети, включая «две трети + треть». Развёрнутое окно снап-зоной не считается — им занимается отдельная ветка координатора.

### `groups`

Группы окон (SPEC.md, «Группы окон»). Массив; каждая группа:

```jsonc
{
  "id": "…uuid…",
  "number": 1,                 // цифра хоткея Ctrl+Alt+N, 1..9
  "name": "работа",            // подпись в менеджере, правится там же
  "gap_pct": 5,                // свой зазор группы, 0..=35
  "members": [
    {
      "exe_path": "C:\...\code.exe",  // главная примета окна
      "title": "main.rs — resticker",       // сравнение нестрогое
      "class": "Chrome_WidgetWin_1",        // меняется реже заголовка
      "place": {                            // null — место ещё не запоминалось
        "monitor_id": "\\?\DISPLAY#…",
        "x": 0.0, "y": 0.0, "w": 1280.0, "h": 1400.0
      }
    }
  ]
}
```

Хэндл окна (`HWND`) не хранится: после перезапуска он другой. Окно опознаётся по `exe_path` + `class` + похожести `title` — заголовки меняются на лету, когда в них пишут имя открытого документа. Одно живое окно достаётся ровно одному члену группы: пять окон одного браузера раздаются пятерым, а не все одному.

`place` — левый верхний угол и размер в **логических пикселях своего монитора**, как у `placement` стикеров и по той же причине: смена масштаба или перестановка мониторов не должна увозить окно неизвестно куда. Группа может занимать оба монитора — у каждого члена свой `monitor_id`.

`number` живёт отдельно от порядка в массиве: удаление группы 2 не переназначает хоткеи остальных.

`gap_pct` **не связан** с `settings.snap_shrink_pct`: тот отвечает за окна в снап-зонах Windows, и смена его в трее не перекладывает давно собранную группу.

### `settings.snap_shrink_all_windows`

Распространить отступ на **обычные, незакреплённые** окна. `false` (по умолчанию) — отступ действует только на окна, закреплённые в resticker; `true` — на любое окно, которое Windows положила в снап-зону.

Переключается галочкой «All windows, not just pinned» в том же подменю трея. Работает только вместе с ненулевым `snap_shrink_pct`: галочка задаёт **область действия** отступа, а не сам отступ.

Незакреплённым окнам достаётся ровно зазор — без потолка 90% монитора, без магнита кромок и без борьбы с разворачиванием: это правила закрепления, и к окну, попавшему под отступ лишь потому, что стоит в снапе, они не относятся.

Не трогаются: наши собственные окна, свёрнутые, нерастягиваемые (Windows такие и не снапит), развёрнутые и те, что пользователь прямо сейчас тащит мышью. Окно, которое три раза подряд не встало в зазор (права выше наших, собственный минимальный размер, приложение навязывает себе геометрию), оставляется в покое до тех пор, пока не покинет зону.

Снятая галочка ничего не возвращает на место — окна остаются там, где стоят: двигать чужие окна на **выключении** функции значило бы делать ровно то, чего этим выключением просят не делать.

### `settings.mitosis_max_memory_mb`

Потолок «веса» окна для режима резки — «митоза» ([SPEC.md](SPEC.md) раздел 14):
приватная память процесса в мегабайтах, сверх которой разрез отклоняется.
Дефолт `4096`.

Смысл порога — не производительность resticker, а честность обещания: митоз
**запускает второй экземпляр** приложения, то есть в худшем случае удваивает
его потребление памяти. Процесс тяжелее потолка не режется вовсе: ещё до
единого движения окна показывается баннер отказа `TooHeavy` («это приложение
держит N МБ, больше лимита M МБ — запуск второго экземпляра отменён»), окно
остаётся на месте.

Проверка веса — не единственная, что отказывает до движения окна: если
приватная память процесса больше свободной физической памяти системы, разрез
тоже отклоняется (`NotEnoughMemory`) — второй экземпляр утопил бы систему в
своп ещё до появления окна. Обе проверки выполняются до ужатия окна, поэтому
оригинал при них не двигается.

### `settings.mitosis_single_instance_apps`

Приложения, для которых митоз запрещён ([SPEC.md](SPEC.md) раздел 14.4):
имена файлов exe без пути, сравнение без учёта регистра. Дефолт —
`["discord.exe", "spotify.exe"]`.

Имя файла, а не полный путь: у самообновляющихся приложений (Discord ровно
такой) в пути стоит номер версии, и запрет по пути перестал бы действовать
молча на ближайшем обновлении.

Зачем список, если отказ и так приходит по таймауту: без него окно ужимается
СРАЗУ и стоит ужатым все секунды ожидания второго окна, которого не будет, —
со стороны это выглядит как «программа просто порезала окно и ничего не
открыла». Приложение из списка отсекается до единого движения окна.

Список **пополняется сам**: два подряд отказа «второго окна не появилось» по
одному и тому же exe заносят его сюда навсегда, и баннер об этом прямо
говорит. Два, а не один, — единичный отказ бывает и у нормального приложения
(холодный старт с диска не уложился в таймаут). Успешный митоз счётчик
обнуляет. Чтобы вернуть приложению митоз, уберите его из этого списка
вручную.

### `origin`

Заполняется только когда стикер был вынужденно мигрирован с пропавшего монитора:

```jsonc
"origin": {
  "monitor_id": "\\\\?\\DISPLAY#DEL4321#...",
  "cx": 960.0, "cy": 540.0, "w": 512.0, "h": 384.0,
  "rotation": 0.0,
  "migrated_at": "2026-07-31T18:00:00Z"
}
```

Логика описана в [SPEC.md](SPEC.md) раздел 6.1 и [DECISIONS.md](DECISIONS.md) ADR-011.

### `order`

Целое число, определяющее порядок отрисовки: больше значит выше. При добавлении нового стикера ему присваивается `max(order) + 1`. Для одиночного выделения кнопки «выше»/«ниже» меняют местами значения с соседом; для мультивыделения они перемещают выделенные стикеры на самый верх или в самый низ стека отрисовки, сохраняя их взаимный порядок (решение пользователя 2026-09-06). Периодическая нормализация к последовательности 0..N при сохранении.

### `playback.loop_mode`

Режим цикла для видео/анимации: `loop`, `once` или `hold_last_frame` (`loop` — значение по умолчанию). Поле сохраняется в `config.json`, но текущее воспроизведение пока всегда зациклено, поэтому `once` и `hold_last_frame` ещё не влияют на поведение.

### `playback.speed`

Множитель скорости воспроизведения (по умолчанию `1.0`). Соседняя с `loop_mode` половина того же долга: поле сохраняется в `config.json`, но ни декодер, ни часы анимации его не читают — скорость всегда обычная. В примере выше ключ показан ровно потому, что он реально сериализуется, а не потому, что уже работает.

### `playback.muted`

Флаг отключения звука видео-стикера (`true` / `false`, по умолчанию `false`). Добавлен по решению пользователя 2026-09-06 для кнопки-динамика в тулбаре («включить/выключить звук»). Вынесен в отдельное булево поле вместо сброса `volume` в 0, чтобы выключение звука было полностью обратимым в один клик с сохранением пользовательского уровня громкости.

## Формат пресета

Пресет — тот же формат, что и секция `stickers` в конфиге, плюс метаданные:

```jsonc
{
  "schema_version": 1,
  "name": "Стрим",
  "created_at": "2026-07-31T20:00:00Z",
  "app_version": "0.5.0",
  "stickers": [ /* ... тот же формат ... */ ]
}
```

Пресет **не содержит** глобальных настроек и хоткеев — только расстановку.

### Загрузка с недостающими элементами

```
1. Прочитать пресет, применить миграции схемы если нужно
2. Для каждого стикера проверить доступность источника:
     kind=file    → существует ли файл
     kind=window_crop → найдено ли подходящее окно среди запущенных
3. Если что-то недоступно — показать диалог со списком:
     • D:\refs\pose_01.png — файл не найден
     • OBS Studio — программа не запущена
   Кнопки: [Загрузить остальное] [Отмена]
4. При подтверждении применить пресет без недоступных элементов.
   Сам файл пресета НЕ изменяется.
5. Стикеры, чей монитор не найден, размещаются по правилам ADR-011.
```

### Экспорт и импорт

Пресет — обычный JSON, его можно передать другому человеку. При экспорте показывается предупреждение: внутри содержатся **абсолютные пути к файлам пользователя и имена запущенных программ**. На другой машине эти пути почти наверняка не совпадут.

## Ключ кэша даунскейла

```
hash = blake3(canonical_path || file_mtime || file_size || target_max_side)
```

Файл кэша содержит заголовок с исходными размерами, форматом и версией кодека даунскейла. Кэш можно удалить в любой момент — он пересоберётся. В настройках есть кнопка очистки и отображение занятого объёма.

## Миграции

```rust
fn migrate(mut value: Value) -> Result<Config> {
    let mut version = value["schema_version"].as_u64().unwrap_or(0);
    while version < CURRENT_SCHEMA_VERSION {
        value = match version {
            0 => migrate_v0_to_v1(value)?,
            1 => migrate_v1_to_v2(value)?,
            _ => bail!("неизвестная версия схемы: {version}"),
        };
        version += 1;
    }
    serde_json::from_value(value).context("не удалось разобрать конфиг после миграции")
}
```

Правила:
- Миграции только вперёд. Откат к старой версии программы не поддерживается.
- Перед первой миграцией сохраняется `config.bak`.
- Каждая миграция покрывается тестом на реальном файле конфига предыдущей версии, лежащем в `tests/fixtures/`.

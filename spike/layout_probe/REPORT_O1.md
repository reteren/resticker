# Отчёт по задаче O1: Налезание окон при раскладке групп

## 1. Измерения и воспроизведение (spike/layout_probe)

Тестовая конфигурация:
- Рабочая область: 2560x1400 (монитор 2560x1440 за вычетом панели задач).
- Раскладка: 3 окна, `stack_right` (1 большое слева 1228x1330, 2 справа стопкой 1227x648 и 1227x647), зазор 5% (35 px).

### Замеры на реальных окнах системы:
1. **Невидимые поля ресайза Win11 / DWM-рамки**:
   - Стандартные окна (`WS_OVERLAPPEDWINDOW`, Проводник, Qt/OBS, Tauri): рамки `[L: 7, T: 0, R: 7, B: 7]` px (`dx=7, dy=0, dw=-14, dh=-7`).
   - Custom-chrome окна (Discord, Spotify, Obsidian, Chrome, Electron): рамки `[0, 0, 0, 0]` px (`dx=0, dy=0, dw=0, dh=0`).
   - Развёрнутые окна (`WS_MAXIMIZE`): рамка вылезает за пределы монитора `[8, 8, 8, 8]` px (`dx=8, dy=8, dw=-16, dh=-16`).

2. **Минимальные габариты окон (`WM_GETMINMAXINFO` / `ptMinTrackSize`)**:
   - `OBS`: `1018 x 479 px`
   - `Discord`: `816 x 508 px`
   - `Spotify`: `800 x 600 px`
   - `Nemora` (Tauri): `700 x 500 px`
   - `Chrome/Opera`: `676 x 326 px`
   - `Orca`: `616 x 408 px`

## 2. Подтвердившиеся гипотезы

### Гипотеза 1 (Частично подтвердилась — баг в максимизированных окнах):
В `set_dwm_bounds` при попытке уложить развёрнутое окно (`WS_MAXIMIZE`) смещения `dx, dy, dw, dh` вычислялись *до* восстановления окна. В результате окно получало смещение максимизированного состояния (`dy=8, dh=-16`), а после `SetWindowPlacement` восстанавливалось со сдвигом на 8 px вверх и превышением высоты на 9 px.
**Исправлено:** `set_dwm_bounds` теперь сначала сбрасывает максимизацию в нормальное состояние, и только затем считывает реальные поля рамки и позиционирует окно через `SetWindowPos`. Для стандартных и custom-chrome окон погрешность стала ровно `dx=0, dy=0, dw=0, dh=0`.

### Гипотеза 2 (ПОЛНОСТЬЮ ПОДТВЕРДИЛАСЬ — коренная причина наезда на десятки процентов):
Windows на уровне Win32 API (`WM_GETMINMAXINFO`) аппаратно запрещает окну сжиматься меньше его `ptMinTrackSize`.
Когда пользователь раскладывает 3 окна на Full HD (высота слота 479 px) или 4–8 окон на 2K/4K:
- При попытке сжать Spotify (`min_h = 600 px`) в слот высотой `479 px`, Windows оставляет окно размером `600 px`.
- В результате верхнее окно вылезает вниз на `121 px`, перекрывая нижнее окно стопки более чем на 25% его высоты!
- При раскладке в 3 колонки (`w = 853 px`), окно OBS (`min_w = 1018 px`) перекрывает соседнюю колонку на `165 px`.

## 3. Что починено и что добавлено

1. **Исправлен `set_dwm_bounds`** (`crates/rst-win32/src/window_pin.rs`):
   - Корректная обработка развёрнутых окон перед расчётом DWM-метрик.
   - Защита от fallback-нулей DWM-буфера (предотвращение аномальных смещений при временной недоступности DWM).

2. **Добавлена функция и структура контроля расхождения геометрии**:
   - `rst_win32::window_pin::WindowLayoutDiscrepancy`: фиксирует `dx, dy, dw, dh` и флаг `exceeds_tolerance`.
   - `rst_win32::window_pin::check_layout_discrepancy(hwnd, target, tolerance_px)` и метод `WindowPins::check_layout_discrepancy`: сообщают координатору точное превышение габаритов после применения раскладки.
   - Написаны и проверены модульные тесты (`layout_discrepancy_exact_match...`, `layout_discrepancy_detects_min_track_size_overflow`, `layout_discrepancy_tolerates_subpixel_rounding`).

---

## 4. Что починить на уровне ОС нельзя
Сторонние процессы невозможно принудительно ужать ниже их `ptMinTrackSize` без инъекции DLL и перехвата оконных процедур (что нарушает стабильность и безопасность). Благодаря `check_layout_discrepancy` координатор теперь может обнаруживать такие окна и либо отображать предупреждение пользователю, либо адаптировать веса слотов.

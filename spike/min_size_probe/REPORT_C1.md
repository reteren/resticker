# C1: минимальный размер чужого окна — отчёт

Проба: `spike/min_size_probe` (свои окна на помп-потоках + живые приложения
пользователя ТОЛЬКО ЧТЕНИЕМ — ни одно окно не двигалось и не закрывалось).
Реализация: `crates/rst-win32/src/window_enum.rs` (добавлено, не переписано).

## Сигнатура

```rust
pub struct WindowMinSize { pub w: i32, pub h: i32 }   // DWM-границы, физические px

pub const MIN_SIZE_FETCH_TIMEOUT_MS: u32;             // = 25

pub fn min_window_size(hwnd: usize) -> Option<WindowMinSize>
```

Что делает: `IsWindow` → `SendMessageTimeoutW(WM_GETMINMAXINFO, SMTO_ABORTIFHUNG,
25 мс)` → `ptMinTrackSize` переводится из GetWindowRect-пространства в
DWM-пространство прибавлением рамки `dw`/`dh` (та же математика, что в
`WindowPins::set_dwm_bounds`; `(0,0,0,0)` при недоступности DWM-границ —
свёрнутое окно). Доставка от таймаута различается через `GetLastError`
(для `WM_GETMINMAXINFO` результат сообщения всегда 0, см. пункт «подвох»).
`None` — окна нет или оно не ответило за таймаут; не ошибка, раскладка
обходится без минимума.

## Таймаут 25 мс — обоснование замером (пункт 1)

| Окно | отклик (min/avg/max, 5 повторов) |
|---|---|
| своё, Default | 473 мкс / 1.34 мс / 1.75 мс |
| своё, CustomMin | 186 мкс / 0.91 мс / 1.49 мс |
| своё, FixedSize | 508 мкс / 1.41 мс / 2.13 мс |
| Chrome-семейство (Orca, Claude, Upscayl, GitHub Desktop, Opera) | 33–58 мкс |
| Проводник | 91 мкс |
| Spotify Free | 144 мкс |
| Discord | 76 мкс |
| Steam | 24 мкс |
| Nemora | 42 мкс |
| Настройки (ApplicationFrameWindow) | 34 мкс |

Худший живой ответ — 2.13 мс (собственное окно с гранулярным помпом; у
реальных приложений ≤ 250 мкс). Зависшее окно (поток без помпа):
`SMTO_ABORTIFHUNG` НЕ обрывает сразу — вызов ждёт ровно таймаут + ~5–14 мс
накладных (замеры: таймауты 10/50/200/500/2000 мс → ожидание 14.9/62/202/513/2009 мс,
`ERROR_TIMEOUT`). Итог: 25 мс = 15-кратный запас над худшим живым ответом при
цене зависшего окна ~30–40 мс.

## Пункт 2: точность — запрос совпадает с реальным ужатием (главный замер)

На своём окне с обработчиком `WM_GETMINMAXINFO` (минимум 400x300):

- запрос = `ptMinTrackSize` (400, 300) — живёт в **GetWindowRect**-пространстве;
- `SetWindowPos(60x60)` → фактическое GWR = **400x300 ровно**;
- фактическое DWM = **386x293** = 400+(-14) x 300+(-7) — перевод рамкой точен.

Смещение GWR→DWM на стандартной рамке Win11: dx=+7, dy=0, dw=-14, dh=-7.
Окно Default (без своего минимума): запрос (0,0), но системный пол
`SM_CXMINTRACK/SM_CYMINTRACK` (136x39) всё равно действует — измеренный
фактический минимум 136x60. «Ноль в ответе» ≠ «можно ужать до нуля»; пол
маленький и раскладку не ломает, но ноль трактуется как «приложение минимум
не объявляет».

## Пункт 3: окна без WS_THICKFRAME

Возвращают (0,0) за ~30 мкс — «минимума нет» (не системное умолчание!).
Ресайзить их всё равно нельзя (`is_resizable`), раскладка их и так не трогает.

## Пункт 4: врут ли приложения

Да, могут. Своё «врущее» окно: в `WM_GETMINMAXINFO` обещает (100,100), реально
не ужимается ниже (500,400) — ограничение задано в `WM_WINDOWPOSCHANGING`.
Запрос дал 100x100, факт 500x400: расхождение +400/+300. На живых приложениях
(после исключения свёрнутых — у них DWM-границы мусорные) ни одно окно не
оказалось меньше заявленного минимума: Discord 816x508, Spotify 800x600,
Steam 1010x600, Nemora 700x500, GitHub Desktop 960x660, Upscayl 600x500 — все
честны. Значит: число достоверно для честных приложений (их большинство);
ложь ловится по факту существующей `check_layout_discrepancy` (окно не влезло
в слот → Oversized).

## Подвох, найденный пробой

`SendMessageTimeoutW` возвращает результат СООБЩЕНИЯ, а для
`WM_GETMINMAXINFO` это всегда 0 (данные в структуре) — по одному возврату
«доставлено» от «таймаута» не отличить. Решение: `SetLastError(ERROR_SUCCESS)`
перед вызовом и `GetLastError() == ERROR_SUCCESS` после; зависшее окно даёт
1460 (ERROR_TIMEOUT). Проверено на живых окнах (err=0 у всех ответивших,
1460 у зависшего).

## Честная оценка доверия к числу

1. Для приложений, реализующих `WM_GETMINMAXINFO` (все крупные: Chrome-семейство,
   Electron/Tauri-оболочки, Steam, Проводник), число ТОЧНОЕ: доказано точным
   совпадением запроса и фактического предела ужатия (400x300 = 400x300).
2. Перевод в DWM-пространство точен для окон со стандартной рамкой
   (измерено: 386x293 = 400+(-14) x 300+(-7)); для custom-chrome окон
   (Discord/Spotify — рамка 0, смещение (0,0,0,0)) перевод — тождество,
   тоже точен.
3. Ограничения: (а) ноль в ответе не означает «ужимается до нуля» — остаётся
   системный пол ~136x60; (б) приложение может солгать (предел в другом
   обработчике) — ловится discrepancy-проверкой; (в) свёрнутые окна —
   минимум возвращается без перевода (DWM не отдаёт границы).
4. Время: один запрос ≤ 2.2 мс у живых окон; таймаут 25 мс гарантирует
   верхнюю границу для зависших.

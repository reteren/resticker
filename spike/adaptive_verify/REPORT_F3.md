# F3: независимая проверка раскладки «adaptive» на живых окнах

Проба: `spike/adaptive_verify` (локальный workspace: rst-core и rst-win32 как
path-зависимости — проверяется ПРОДУКЦИОННЫЙ код). Окна пользователя только
читаются (`min_window_size`, геометрия), ничего не двигалось, не закрывалось
и не сворачивалось. Зазор — из конфига пользователя: gap_pct = 4.

## 1. Живые минимумы (замер в момент прогона)

Монитор 2560x1440; рабочая область (SPI_GETWORKAREA) = 2560x1392.

| окно | минимум (DWM) |
|---|---|
| Orca [Chrome] | 602x401 |
| Discord [Chrome] | 800x492 |
| Steam [SDL_app] | 1010x600 |
| Opera [Chrome] | 660x310 |
| Obsidian (reschedule) | 184x134 |
| Claude [Chrome] | 602x401 |
| Проводник [CabinetWClass] | 147x243 |
| Nemora [Tauri] | 686x493 |

Всего 12 окон с ненулевым минимумом; группы 2..8 набирались из первых N в
порядке z-order перечисления.

## 2. Главный вопрос: насколько «adaptive» сильнее семейств

| N | семейства: вернули | семейства: ВЫПОЛНИМО | adaptive нашла |
|---|---|---|---|
| 2 | 7 | 7 | ДА |
| 3 | 5 | 5 | ДА |
| 4 | 6 | 6 | ДА |
| 5 | 6 | 6 | ДА |
| 6 | 7 | 1 | ДА |
| 7 | 8 | 2 | ДА |
| 8 | 7 | **0** | ДА |

Выполнимость семейств и «adaptive» проверена одним и тем же независимым
кодом пробы (apply → fit_slots → каждый слот ≥ минимума). Разница в пользу
«adaptive»: **6 окон — семейства 1 из 7, adaptive нашла; 7 окон — 2 из 8,
нашла; 8 окон — НОЛЬ из семи выполнимых семейств, а adaptive сочинила
раскладку**. Для 8 окон это и есть её оправдание: ни одно семейство не
может, а она может.

## 3. Инварианты (свой код, генератору не доверялось)

Для КАЖДОЙ из семи найденных раскладок (n = 2..8) проверено своим кодом:
число слотов == числу окон; слоты не пересекаются (в долях и в пикселях
после `apply`); все лежат внутри 2560x1392; после `fit_slots` каждый слот
≥ своего минимума. **Нарушений нет ни в одном случае.** Силуэты «adaptive»
— guillotine-разрезания с границами по суммам минимумов, перекрытий не
возникает по построению, и это подтверждено попарной проверкой всех слотов.

## 4. Формы словами (что увидит пользователь в миниатюре)

- **4 окна** (Orca 602x401, Discord 800x492, Steam 1010x600, Opera 660x310):
  «два ряда по два окна: сверху два окна в ряд, снизу два окна в ряд,
  граница между окнами в рядах НЕ совпадает — окна верхнего и нижнего ряда
  стоят со сдвигом друг относительно друга».
- **5 окон** (+ Obsidian 184x134): «слева два окна друг под другом (чуть
  уже половины экрана); справа сверху одно окно на всю ширину правой части;
  справа снизу ещё два окна в ряд — широкое и узкое».
- **7 окон** (+ Claude 602x401, Проводник 147x243): «слева четыре окна:
  два сверху в ряд и два снизу в ряд (границы колонок не совпадают);
  справа узкая колонка с тремя окнами друг под другом».
- 8 окон: «верхний ряд — два окна; ниже слева одно высокое окно, правее
  него два друг под другом; справа узкая колонка с тремя окнами друг под
  другом».

## 5. Устойчивость (детерминизм)

`adaptive_layout` вызвана ДВАЖДЫ на каждом входе (n = 2..8): ответы
побитово одинаковые во всех семи случаях (сравнение `Vec<UnitRect>` через
`==`, без допусков). Лента не будет прыгать между перерисовками.

## Вывод

«adaptive» решает задачу, с которой семейства не справляются: при 6..8
окнах на этой машине семейства дают 1..0 выполнимых вариантов, а она —
ровно одну выполнимую раскладку во всех 7 случаях, без нарушений
инвариантов и детерминированно. Для наборов, где семейства и так богаты
(2..5 окон), «adaptive» тоже находит решение (обычно одно из «регулярных»
со смещёнными границами).
